## THE THESIS OF THIS TOPIC

**The same feature defined at several levels resolves by one of three rules, additive, override-by-name or merge, and you must know which rule applies before you debug a conflict.**

**Prove-it, in one sentence:** predict the outcome of a same-name conflict for a skill, a subagent, an MCP server and a hook, then confirm each in a real session.

**The single most important discipline: before debugging a 'wrong version' problem, name the feature's layering rule.**

**The counterintuitive claim you will learn to defend:** hooks do not override: all registered hooks fire for matching events regardless of source, so a project hook cannot cancel a user hook [Claude Code docs, Extend Claude Code, 2026].

## 5.1.7.1 — FOUR RULES

**Framing.** The docs describe layering for features defined at user, project, plugin or managed levels [Claude Code docs, Extend Claude Code, 2026].

| Feature | Rule | Detail |
|---|---|---|
| CLAUDE.md files | Additive | All levels contribute at once; conflicts are reconciled by Claude's judgement |
| Skills | Override by name | Managed > user > project; plugin skills are namespaced |
| Subagents | Override by name | Managed > CLI flag > project > user > plugin |
| MCP servers | Override by name | Local > project > user |
| Hooks | Merge | All registered hooks fire |

[Claude Code docs, Extend Claude Code, 2026]

The failure mode: **Rule-swap.** You assume subagents rank like MCP servers (local over project over user) and debug a shadowed agent for an hour.

The fix: Look up the rule for that feature specifically; the orders differ.

Cross-references: scopes in settings are Module 4.1; MCP scopes are sub-topic 5.5.3.

**If you remember one thing:** each feature has its own rule; look it up.

## 5.1.7.2 — SKILL PRIORITY IN DETAIL

**Framing.** The skills reference gives a fuller table: enterprise, personal, project, nested, additional-directory and plugin levels, with enterprise overriding personal and personal overriding project; your skill replaces a bundled skill or built-in command of the same name but not its aliases; added-directory clashes get a prefix such as `/cli:verify` (v2.1.309+) [Claude Code docs, Skills, 2026]. The overview's shorter statement is 'managed > user > project'; the two are consistent, with the skills page adding the nested and added-directory cases.

| Clash | Winner |
|---|---|
| Personal `deploy` vs project `deploy` | Personal |
| Your `review` vs bundled skill of same name | Yours |
| Skill vs `.claude/commands/` file, same name | The skill |
| Two plugins both ship `review` | No clash: `/a:review`, `/b:review` |

The failure mode: **Silent shadowing.** A personal skill with the same name as a project skill quietly replaces it for you, so you and your teammates run different procedures under one name.

The fix: Give team skills distinctive names or ship them in a plugin, and check with `/skills`.

Cross-references: skills are Module 5.2 (sub-topic 5.2.2 covers locations).

**If you remember one thing:** same name means one wins; know which.

## 5.1.7.3 — MCP AND HOOK CONFLICTS

**Framing.** Same-name MCP servers resolve local over project over user [Claude Code docs, Extend Claude Code, 2026]. Hooks differ: they all fire. If two hooks both match, both run, so a blocking one still blocks even when another allows.

```text
settings.json (user)     PreToolUse: Bash -> audit.sh        # runs
.claude/settings.json    PreToolUse: Bash -> block-rm.sh     # runs too
```
Both run; if `block-rm.sh` exits 2, the call is blocked regardless of `audit.sh`.

The failure mode: **Cancel-by-override.** You expect a project hook to replace a user hook on the same event and are surprised when both fire.

The fix: Remove or edit the unwanted hook at its own level; overriding does not apply to hooks.

Cross-references: hook configuration is sub-topic 5.4.2.

**If you remember one thing:** hooks add up; they never cancel each other.
