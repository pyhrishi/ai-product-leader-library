# MODULE 9.2.1 — RED, GREEN, REFACTOR WITH AN AGENT: THE COMPLETE CRAFT

## THE THESIS OF THIS TOPIC

**Test-driven development maps cleanly onto the agent loop: the failing test is the check Claude can run, so write it first, confirm it fails for the stated reason, implement until it passes, then refactor with the test as a guard.**

**Prove-it, in one sentence:** show a test that failed for the right reason, the minimal change that turned it green, and a refactor that kept it green.

**The single most important discipline: never accept a green run that you did not see red first.**

**The counterintuitive claim you will learn to defend:** a test that was never red proves nothing, because it may pass for reasons unrelated to the feature [judgement, general practice].

**THE TIME BUDGET.** Reading time: ~16 minutes. Prove-it time: ~2 hours (120 minutes, 7.5 times the reading time).

## 9.2.1.1 — RED: A FAILING TEST FOR THE RIGHT REASON

**Framing.** Claude stops when the work looks done, so it needs something that returns pass or fail; a test file is the first example of a check the docs list [Claude Code docs, Best practices, 2026]. Their sample bug prompt asks Claude to write a failing test that reproduces the problem, then fix it [Claude Code docs, Best practices, 2026].

```text
users report login fails after the session times out. look at token refresh in src/auth/,
write a failing test that reproduces it, then fix it
```

| Red-phase check | How to confirm |
|---|---|
| The test fails | Run it; capture the output |
| It fails for the stated reason | The assertion message names the missing behaviour, not an import error |
| It fails alone | Run only this test file |

The failure mode: **Wrong-reason red.** The test fails on a typo or missing import, so it turns green after a trivial fix that does not implement the feature.

The fix: Read the failure message; require it to cite the missing behaviour before any implementation starts.

Cross-references: specs name the cases to test: Module 9.1.2; the check concept is Module 2.3.

**If you remember one thing:** red must mean what you think it means.

## 9.2.1.2 — GREEN: SMALLEST CHANGE, EVIDENCE SHOWN

**Framing.** Once the test is red for the right reason, tell Claude to implement only enough to pass and to show the output. The docs advise asking for evidence rather than a bare 'all tests pass' [Claude Code docs, Best practices, 2026].

| Phase | Prompt | Evidence you require |
|---|---|---|
| Red | "Write the failing test; run it; show the failure" | Failure output |
| Green | "Implement the smallest change that passes; run the test and the neighbouring suite" | Pass output, suite totals |
| Refactor | "Simplify without changing behaviour; rerun" | Same pass output |

Run one file while iterating: `pnpm vitest run path/to/file.test.ts` is the docs' sample single-test command [Claude Code docs, Best practices, 2026].

The failure mode: **Test-editing fix.** Claude makes the test pass by changing the assertion, not the code.

The fix: Say 'do not modify the test' during green, and review the test file diff separately.

Cross-references: separate writers fix this structurally: Module 9.2.2.

**If you remember one thing:** green means the unchanged test passes.

## 9.2.1.3 — REFACTOR WITH THE TEST AS A GUARD

**Framing.** Refactoring is safe only while the checks stay green. The docs advise small, testable increments when refactoring and running tests for the refactored code [Claude Code docs, Common workflows, 2026].

| Refactor step | Guard |
|---|---|
| Rename, extract | Test file still green |
| Remove duplication | Neighbouring suite green |
| Simplify | `/simplify` pass, then rerun (Module 9.4.6) |

`/simplify` reviews changed code for reuse, simplification, efficiency and abstraction level; it does not look for correctness bugs [Claude Code docs, Commands, 2026].

The failure mode: **Refactor with no guard.** You refactor at the end of a long session without rerunning the red-green test, and a behaviour change slips in.

The fix: Make 'rerun the test after each refactor step' part of the prompt and the Stop hook (Module 9.2.5).

Cross-references: refactoring at scale is Module 9.4.

**If you remember one thing:** refactor only while green.

## CLOSING REFRAME

This is the craft of TDD with an agent: **a red you understand, a green you watched, a refactor under guard.** The engineer who understands this does not ask "do the tests pass?" — they ask "did they fail first, and for the right reason?"
