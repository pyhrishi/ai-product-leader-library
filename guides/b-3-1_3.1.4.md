# MODULE 3.1.4 — COST OF FEATURES: THE COMPLETE CRAFT

## THE THESIS OF THIS TOPIC

**Every extension has a loading strategy, and the context cost is determined by when it loads and what loads: always-on, on demand, isolated or free.**

**Prove-it, in one sentence:** fill a cost-by-feature table for your own setup and verify two rows with /context.

**The single most important discipline: put always-on content only where it is needed on every request, and everything else on demand.**

**The counterintuitive claim you will learn to defend:** a hook costs nothing until it returns output, while a long CLAUDE.md costs something on every request [Claude Code docs, Extend Claude Code, 2026].

## 3.1.4.1 — THE COST TABLE

**Framing.** Each feature has a different loading strategy and context cost [Claude Code docs, Extend Claude Code, 2026].

| Feature | When it loads | What loads | Cost |
|---|---|---|---|
| CLAUDE.md | Session start | Full content | Every request |
| Output styles | Start, and when you switch | Active style's instructions; nothing for Default | Every request |
| Skills | Start, then when used | Descriptions, then full body | Low; descriptions every request |
| MCP servers | Start | Tool names; schemas on demand | Low until a tool is used |
| Code intelligence | After edits, on demand | Diagnostics; symbol locations | Low; can reduce reads |
| Subagents | When spawned | Fresh isolated context | Isolated from main session |
| Hooks | On trigger | Nothing by default | Zero unless output returned |

The failure mode: **Always-on bloat.** You put reference material, such as API docs, in CLAUDE.md, so it is paid for on every request of every session.

The fix: Move reference content to a skill or path-scoped rule so it loads only when relevant.

Cross-references: CLAUDE.md design is Module 3.2; skills are Module 5.1.

**If you remember one thing:** if it is needed sometimes, load it sometimes.

## 3.1.4.2 — ON-DEMAND MECHANISMS AND THEIR CONTROLS

**Framing.** Claude sees skill names and descriptions in every request and loads the full body only on use; `disable-model-invocation: true` keeps a manual-only skill out of context until you invoke it, and `skillOverrides` in settings does the same for skills you did not write [Claude Code docs, How Claude Code works, 2026]. Many skills can crowd the list: names always load, but when there are many, some skills lose their descriptions entirely [Claude Code docs, Large codebases, 2026].

```yaml
---
name: deploy
description: Run the release checklist
disable-model-invocation: true   # invisible to Claude until you type /deploy
---
```

The failure mode: **Description sprawl.** You install dozens of skills with long overlapping descriptions, and Claude loads the wrong one or the list loses descriptions entirely.

The fix: Keep descriptions short, lead with words a request would contain, and hide manual-only skills.

Cross-references: skill authoring is Module 5.1; per-directory skills are Module 3.5.

**If you remember one thing:** the description is the always-on part.

## 3.1.4.3 — MCP, SUBAGENTS AND HOOKS

**Framing.** MCP tool search is on by default, so idle MCP tools consume minimal context: only tool names and server instructions load, and `/context all` shows per-tool token use [Claude Code docs, Extend Claude Code, 2026]. Connected servers add names and instructions even when unused, so disable the ones you do not need [Claude Code docs, Best practices, 2026]. A subagent gets an isolated window containing its own system prompt, preloaded skills, CLAUDE.md and git status (the built-in Explore and Plan agents omit both), and whatever the lead passes in [Claude Code docs, Extend Claude Code, 2026].

| Mechanism | Where its tokens go | Lever |
|---|---|---|
| MCP server | Names and instructions in main context | Disconnect unused servers in `/mcp` |
| Subagent | Its own window; summary returns | Ask for short summaries |
| Hook | Nowhere, unless output returns | Return nothing for pure side effects |

The failure mode: **Free-hook assumption.** You build a PostToolUse hook that prints full linter output on every edit and call hooks free, but the returned text lands in context each time.

The fix: Have the hook return only a one-line result or nothing, and log details to a file.

Cross-references: hooks are Module 5.4; subagent design is Module 5.3.

**If you remember one thing:** free means no output.

## 3.1.4.4 — CHOOSING THE HOME FOR CONTENT

**Framing.** The docs give a rule: put it in CLAUDE.md if Claude should always know it; in a skill if it is reference material needed sometimes or a workflow you trigger; in a rule with `paths` to load only when matching files are opened; in a hook if it must happen every time [Claude Code docs, Extend Claude Code, 2026]. Keep CLAUDE.md under 200 lines.

| Content | Best home | Why |
|---|---|---|
| Build and test commands | CLAUDE.md | Needed every session |
| Language-specific style | Path-scoped rule | Only when those files are touched |
| Release checklist | Skill | Triggered, needed rarely |
| Never edit `.env` | Hook or deny rule | Cannot have exceptions |

The failure mode: **Wrong-home placement.** You put a must-happen rule in CLAUDE.md, where it is only a request that works most of the time.

The fix: Use a hook or deny rule for anything that cannot have exceptions.

Cross-references: rules files are Module 3.3; permissions are Module 4.2.

**If you remember one thing:** match the load strategy to the need.

## CLOSING REFRAME

This is the craft of cost: **every feature has a load strategy, and placement is the lever.** The engineer who understands this does not ask "should I add this?" — they ask "when does it need to be in the window?"
