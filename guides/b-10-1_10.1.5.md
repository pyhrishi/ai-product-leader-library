# MODULE 10.1.5 — TRAINING: THE COMPLETE CRAFT

## THE THESIS OF THIS TOPIC

**Training works when it is short, task-shaped and backed by shared prompts and office hours rather than one long workshop.**

**Prove-it, in one sentence:** design a four-week training plan with one format per week and a success check for each.

**The single most important discipline: teach the loop and the controls together, never the prompts alone.**

**The counterintuitive claim you will learn to defend:** the module brief lists in-product lessons (/powerup), but I could not verify that command in the retrieved docs, so a training plan should not depend on it [Claude Code docs index, 2026].

## 10.1.5.2 — FOUR FORMATS, FOUR WEEKS

**Framing.** [Practitioner structure.] Mix a workshop, shared prompts, office hours and paired sessions so people with different styles all have a route. Anchor week one on the docs' own advice to start with codebase Q&A and small fixes, and to ask for a plan first [Claude Code docs, Enterprise deployment overview, 2026].

| Week | Format | Check |
|---|---|---|
| 1 | 60-minute workshop on the loop and `/status` | Everyone runs a plan-first task |
| 2 | Shared prompt library | Each team adds 3 prompts |
| 3 | Office hours | Questions logged |
| 4 | Pair on a real ticket | Ticket merged |

The failure mode: **Marathon workshop.** One four-hour session covers everything and nothing is retained.

The fix: Keep sessions to an hour and attach a hands-on check to each.

Cross-references: the loop itself is Module 1.2; prompting is Module 2.2.

**If you remember one thing:** short sessions with a task each.

---

## 10.1.5.3 — SHARED PROMPT LIBRARIES

**Framing.** Prompts should live with the code. The docs recommend repository-level CLAUDE.md files holding architecture, build commands and contribution guidelines, checked into source control so all users benefit [Claude Code docs, Enterprise deployment overview, 2026]. Reusable procedures can become skills [see Module 5.2].

```text
repo/
  CLAUDE.md            architecture, build, conventions
  .claude/skills/...   reusable procedures
  docs/prompts.md      team prompt examples with outcomes
```

The failure mode: **Wiki-rot prompts.** Prompts live on a wiki, drift from the code, and nobody trusts them.

The fix: Store prompts in the repository and review them in pull requests.

Cross-references: CLAUDE.md is Module 3.2; skills are Module 5.2.

**If you remember one thing:** prompts belong in version control.

---

## 10.1.5.4 — TEACHING THE CONTROLS

**Framing.** Training must include what Claude Code is not allowed to do. Teach `/permissions` to inspect effective rules, `/status` to see which settings sources apply, and Esc plus `/rewind` for recovery [Claude Code docs, Server-managed settings, 2026; Claude Code docs, Manage costs effectively, 2026].

| Command | Teach it as |
|---|---|
| `/permissions` | See your effective rules |
| `/status` | See which managed source applies |
| `Esc`, `/rewind` | Stop and undo |
| `/usage` | See your session spend and plan usage |

The failure mode: **Prompt-only training.** People learn prompts but not the controls, then blame the tool when a policy blocks them.

The fix: Spend a third of every session on controls and diagnostics.

Cross-references: diagnostics are Module 12.1.

**If you remember one thing:** teach the controls with the craft.

## CLOSING REFRAME

This is the craft of training: **short sessions, committed prompts, and the controls taught beside the craft.** The administrator who understands this does not ask "how much training?" — they ask "what can each person do and check by Friday?"
