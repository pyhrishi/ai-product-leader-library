## 1.2.2.1 — THE TOOL GROUPS

**Framing.** Claude Code has built-in tools to understand and modify your codebase. The tool names are the exact strings you use in permission rules, subagent tool lists and hook matchers [Claude Code docs, Tools reference, 2026]. The Permission-required column shows whether each tool prompts in Manual mode for paths inside the working directory; Bash prompts but runs a built-in set of read-only commands without asking; file-access tools marked No still prompt for paths outside the working directory [Claude Code docs, Tools reference, 2026].

| Group | Tools | Prompts in Manual mode |
|---|---|---|
| Read and search | Read, Grep, Glob, LSP | No (inside the working directory) |
| Edit | Edit, Write, NotebookEdit | Yes |
| Execute | Bash, PowerShell (Windows), Monitor | Yes; read-only built-ins excepted |
| Web | WebFetch, WebSearch | Yes |
| Orchestrate | Agent, task and ask-user tools | Varies |
| MCP | `mcp__server__tool`, ToolSearch, ListMcpResourcesTool | Follow the permission system |

[Claude Code docs, Tools reference, 2026; the table is a summary of search excerpts, verify rows against the page]

The failure mode: **Tool-name guessing.** You write a rule or matcher with a plausible name that is not a real tool, and it silently matches nothing.

The fix: Copy names from the Tools reference and trigger the action once to confirm the rule fires.

Cross-references: the full control surface is Module 1.2.3; settings are Module 4.1; MCP tools are Module 5.5.

**If you remember one thing:** tool names are the keys to every control.

## 1.2.2.2 — RULE SYNTAX: NAME PLUS SPECIFIER

**Framing.** Permission rules, subagent lists and hooks all take a `ToolName(specifier)` format, and the specifier depends on the tool [Claude Code docs, Tools reference, 2026].

| Rule | Applies to | Matching |
|---|---|---|
| `Bash(npm run *)` | Bash, Monitor | Command pattern |
| `PowerShell(Get-ChildItem *)` | PowerShell | Command pattern |
| `Read(~/secrets/**)` | Read, Grep, Glob, LSP | Path pattern |
| `Edit(/src/**)` | Edit, Write, NotebookEdit | Path pattern |
| `Skill(deploy *)` | Skill | Skill name |
| `Agent(Explore)` | Agent | Subagent type |
| `WebFetch(domain:example.com)` | WebFetch | Domain |
| `WebSearch` | WebSearch | No specifier; allow or deny the whole tool |

Hook matchers use bare tool names, not the parenthesised rule format [Claude Code docs, Tools reference, 2026]. Tools not listed (such as ExitPlanMode) accept only bare names.

Two interactions to remember: a `Read(...)` deny also blocks Edit and Write on that path, including creating a new file there [Claude Code docs, Tools, 2026]; an `Edit(...)` allow also grants read access to that path [Claude Code docs, Tools reference, 2026].

The failure mode: **Deny-rule gap.** You deny one command spelling and assume the secret is protected, while another tool or spelling reaches the same file.

The fix: Write path-level `Read(...)` denies (which also block Edit and Write) and add sandboxing for Bash.

Cross-references: rule design is Module 4.2; sandboxing is Module 4.4; subagent tool lists are Module 5.3.

**If you remember one thing:** path rules protect paths; command rules protect only the commands they name.

## 1.2.2.3 — BASH BEHAVIOUR YOU MUST KNOW

**Framing.** Each Bash command runs in a separate process. A `cd` carries into later commands only while Claude stays inside the project directory or an added directory; if it lands outside, Claude Code resets to the project directory and appends a note to the result. Subagent sessions never carry directory changes [Claude Code docs, Tools reference, 2026]. Suspicious commands need manual approval even if allowlisted (command injection detection) [Claude Code docs, Security, 2026].

```bash
# What persists between Bash calls: the working directory (inside the project) and
# files on disk. What does not: shell variables and functions from earlier calls.
cd src && export X=1      # the cd may carry over; X does not
```

| Behaviour | Consequence |
|---|---|
| Separate process per command | Do not rely on exported variables across calls |
| cd outside the project resets | Use absolute paths for outside work |
| Read-only built-ins run without a prompt | `ls`, `cat`, `git status` are cheap to approve |
| Injection detection overrides allowlists | A broad allow rule is not a blank cheque |

The failure mode: **Shell-state assumption.** You expect an exported variable or an environment change from one Bash call to exist in the next, and a later step fails mysteriously.

The fix: Put state in files or repeat it in each command, and use absolute paths when leaving the project directory.

Cross-references: sandboxing is Module 4.4; permissions are Module 4.2.

**If you remember one thing:** each Bash call is a fresh process; state lives in files.

## 1.2.2.4 — CODE INTELLIGENCE AND EXTENSIONS

**Framing.** The code-intelligence category (type errors, go to definition, find references) exists through the LSP tool when a code-intelligence plugin is installed; without it Claude falls back to Grep and Read. Extensions such as skills, MCP, hooks and subagents layer on top of the built-ins [Claude Code docs, How Claude Code works, 2026].

```bash
/context   # live breakdown of what is in context, including tool definitions
/mcp       # connected MCP servers and their tools
```

| Need | Without a plugin | With a plugin |
|---|---|---|
| Find all uses of a symbol | Grep text matches | LSP references |
| Check types after an edit | Run the compiler | LSP diagnostics after each edit |
| Jump to a definition | Grep then Read | LSP go to definition |

MCP tool definitions are deferred: only names and server instructions load at startup, full schemas load on demand [Claude Code docs, Glossary, 2026].

The failure mode: **Missing-category blindness.** You expect symbol-aware navigation and Claude uses text search because no code-intelligence plugin is installed.

The fix: Check `/context` and `/mcp`, install the plugin for your language and verify with a find-references test.

Cross-references: code-intelligence plugins are Module 5.8; MCP is Module 5.5.

**If you remember one thing:** the fifth tool category needs a plugin before it exists.
