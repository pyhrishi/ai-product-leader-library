# MODULE 2.1.1 — EXPLORE: READ BEFORE YOU CHANGE: THE COMPLETE CRAFT

---

## THE THESIS OF THIS TOPIC

**Exploration is the cheapest phase of any change: you ask questions, Claude reads code, and nothing on disk moves, so every wrong assumption is caught for the price of a few messages instead of a bad diff.**

**Prove-it, in one sentence:** run a read-only exploration of a repo you did not write and produce a one-page map whose every claim cites a file you opened yourself.

**The single most important discipline: make exploration read-only by construction (plan mode), not by promise.**

**The counterintuitive claim you will learn to defend:** exploration is not free in a subagent: delegated reads cost tokens and can finish slower than asking in place [Claude Code docs, Best practices, 2026].

**THE TIME BUDGET.** Reading time: ~20 minutes. Prove-it time: ~2 hours (120 minutes, 6.0 times the reading time).

|---|---|
| L3 | Ask orientation questions and enter plan mode |

| L5 | Route broad searches to the right context and verify the summary |

## 2.1.1.1 — QUESTIONS A SENIOR ENGINEER WOULD ASK

**Framing.** The docs' own recipes for a new codebase start broad and narrow down: an overview, then architecture patterns, data models, and how a concern such as authentication is handled [Claude Code docs, Common workflows, 2026]. The prompt library carries the same shapes as copy-paste prompts, including a change-impact question and a history question [Claude Code docs, Prompt library, 2026].

| Goal | Prompt shape (from the docs) |
|---|---|
| Orient | `give me an overview of this codebase` |
| Locate | `find the files that handle user authentication` |
| Trace | `trace the login process from front-end to database` |
| Impact | `what would break if I deleted {target}?` |
| History | `look through the commit history of {path} and summarize how it evolved and why` |
| Scope | `which files would I need to touch to {change}?` |

The page's tips: start with broad questions then narrow, use the project's domain language, and request a glossary of project terms [Claude Code docs, Common workflows, 2026].

The failure mode: **Question-sprawl.** You fire ten unrelated orientation questions in a row, the answers pile up in one context, and none of them converges on the change you actually need.

The fix: Pick the one change you intend to make, then ask the locate, trace and impact questions for that change only.

Cross-references: prompting detail is Module 2.2; context cost is Module 3.1.

**If you remember one thing:** ask about the change you are about to make, not about the whole repo.

## 2.1.1.2 — READ-ONLY BY CONSTRUCTION: PLAN MODE

**Framing.** Plan mode tells Claude to research and propose changes without making them: it reads files, runs shell commands to explore and writes a plan, but does not edit source [Claude Code docs, Permission modes, 2026]. Enter it with `Shift+Tab`, prefix one prompt with `/plan`, or start with `claude --permission-mode plan` [Claude Code docs, Permission modes, 2026].

What a shell command may do during planning depends on the session, and the first matching case applies [Claude Code docs, Permission modes, 2026]:

| Session | Planning shell commands |
|---|---|
| Interactive terminal, bypass permissions available | Neither classifier nor prompt applies |
| Auto mode available and `useAutoModeDuringPlan` on (the default) | Classifier reviews commands other than critical-path removals |
| Auto mode unavailable, or setting off | Commands outside the built-in read-only set prompt you |

```bash
claude --permission-mode plan      # start read-only
# or inside a session: Shift+Tab until the bar shows  ⏸ plan mode on
```

The failure mode: **Plan-mode-as-sandbox.** You assume plan mode blocks every side effect, but shell commands still run under the classifier or a prompt, so an exploratory command with a side effect can execute.

The fix: Read the three cases above for your session, and keep deny rules and the sandbox for anything that must never run.

Cross-references: mode cycling is Module 4.3; sandboxing is Module 4.4.

**If you remember one thing:** plan mode blocks source edits, not every command.

## 2.1.1.3 — KEEPING EXPLORATION OUT OF THE MAIN WINDOW

**Framing.** Broad codebase searches go to the built-in Explore agent, and the subagent keeps long output out of your main conversation. The docs are plain about the price: every subagent sends its own requests against the same usage, and a fresh subagent must gather context your conversation already had, so it can be slower [Claude Code docs, Best practices, 2026].

| Choose | When |
|---|---|
| Ask in place | The answer needs two or three file reads you will keep using |
| Subagent / Explore | A wide search whose raw output you will not reuse |
| Code intelligence plugin | A typed language where go-to-definition beats text search [Claude Code docs, Common workflows, 2026] |

```text
use a subagent to investigate how our auth system handles token refresh
```
That prompt is the docs' example of delegating research so only the findings return [Claude Code docs, Common workflows, 2026].

The failure mode: **Explore-tax blindness.** You delegate every question to a subagent assuming it is free, and usage rises while your main window gains nothing you will reuse.

The fix: Delegate only wide, read-heavy searches and check `/usage` to see which subagent types earn their cost.

Cross-references: subagent mechanics are Module 5.3; usage is Module 1.4.

**If you remember one thing:** delegate the search you will not re-read.

## 2.1.1.4 — TURNING EXPLORATION INTO SOMETHING YOU CAN TRUST

**Framing.** An exploration summary is a claim about files, and the docs' test for what is worth writing down applies in reverse: if Claude could find it by reading the code, check it there [Claude Code docs, Best practices, 2026]. The useful output of this phase is a short list of facts with paths, because the plan phase consumes exactly that.

| Artifact | Contents | Checked by |
|---|---|---|
| Map | Entry points, data flow, the files a change would touch | You open three of them |
| Unknowns | What exploration could not answer | Becomes interview questions (guide 2.1.6) |
| Constraints | Conventions, tests, the check command | Goes into the plan |

The failure mode: **Unchecked-summary.** You accept a fluent overview whose file names you never opened, and the plan inherits a hallucinated entry point.

The fix: Open at least three cited files before planning and ask Claude to correct any path that does not exist.

Cross-references: verification habits are Module 2.3; planning is the next guide.

**If you remember one thing:** a map you did not spot-check is a guess.

## THE PROVE-IT SECTION

**Deliverable.** A one-page codebase map from a read-only session, with each claim linked to a file you spot-checked.

**Close this topic. Build the artifact below from memory. Return to the text only after your first attempt is complete.**

| Step | Action | Output |
|---|---|---|
| 1 | Pick a repo you did not write and a change you could plausibly make | One-line change statement |
| 2 | Start with `claude --permission-mode plan` and ask the overview question | Overview transcript |
| 3 | Ask locate, trace and impact questions for that change only | Three answers |
| 4 | Record which mode and rule cases applied to the shell commands Claude ran | A case label per command |
| 5 | Open three cited files and mark each claim true or false | Verification column |
| 6 | Write the one-page map with unknowns listed | `map.md` |

**A passing artifact looks like this:**

| Claim | File | Opened by me | True |
|---|---|---|---|
| Login is handled in the auth middleware | `src/auth/middleware.ts` | Yes | Yes |
| Tokens refresh in a shared helper | `src/auth/refresh.ts` | Yes | Partly: also in a hook |
| Unknown: who owns session expiry | none | n/a | Listed as unknown |

**A failing artifact (a realistic near-miss):**

| Element | What is wrong |
|---|---|
| Overview pasted as the map | **Unchecked-summary** |
| No mode noted for shell commands | **Plan-mode-as-sandbox** risk |

**The verdict.** The artifact passes only if every claim names a file, at least three files were opened by you, and unknowns are listed rather than guessed.

## CLOSING REFRAME

This is the craft of exploring: **ask about the change you intend, keep it read-only, and trust only what you opened.** The engineer who understands this does not ask "what does this repo do?" — they ask "which files does this change touch, and have I seen them?"
