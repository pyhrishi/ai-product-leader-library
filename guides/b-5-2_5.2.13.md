## THE THESIS OF THIS TOPIC

**Good skills fall into recognisable shapes, reference or task at the top level, with checklists, runbooks and rubrics as the common bodies, and choosing the shape first makes the file easy to write.**

**Prove-it, in one sentence:** write two skills of different shapes for the same domain and show how invocation and body style differ.

**The single most important discipline: decide whether the skill is reference or task before writing a line.**

**The counterintuitive claim you will learn to defend:** the docs themselves name only two content types, reference and task; the longer list of patterns is a working taxonomy, not an official catalogue.

## 5.2.13.1 — REFERENCE VERSUS TASK

**Framing.** The skills page states two content types. Reference content adds knowledge Claude applies to current work (conventions, patterns, style guides, domain knowledge) and runs inline. Task content gives step-by-step instructions for a specific action such as deployments, commits or code generation, and is often best invoked directly with `/skill-name` [Claude Code docs, Skills, 2026].

| Type | Invocation | Frontmatter hint | Body style |
|---|---|---|---|
| Reference | Claude loads when relevant | Default, descriptive `description` | Facts and conventions |
| Task | You type `/name` | `disable-model-invocation: true` if side effects | Numbered steps |

The failure mode: **Mixed-type skill.** One skill holds both the style guide and the deploy steps, so loading it for style also loads and risks the deploy procedure.

The fix: Split into a reference skill and a task skill.

Cross-references: frontmatter is sub-topic 5.2.3; skill-vs-subagent is sub-topic 5.1.3.

**If you remember one thing:** decide reference or task before writing.

## 5.2.13.2 — BODY PATTERNS

**Framing.** Within those types the same bodies recur. These names are a working taxonomy [judgement, not an official list].

| Pattern | Suits | Shape |
|---|---|---|
| Checklist | Pre-merge, pre-release | Tick list with pass/fail |
| Decision tree | Choosing among options | If/then branches |
| Template | Repeated outputs (ADR, PR description) | Fill-in skeleton |
| Review rubric | Consistent critique | Criteria with scoring |
| Runbook | Operations, incident response | Ordered commands and checks |
| Domain glossary | Terms Claude keeps misusing | Term, meaning, not-to-confuse |
| API conventions | Team code style | Rules plus examples |
| Release procedure | Shipping | Steps with side effects: manual invocation |
| Data-analysis recipe | Repeatable analysis | Query, transform, chart steps |

The failure mode: **Pattern-by-fashion.** You write a decision tree for a job that is really a template, and Claude branches where it should have filled in.

The fix: Name the job's output first (a list, a choice, a document) and match the pattern to it.

Cross-references: descriptions are sub-topic 5.2.4; disclosure is sub-topic 5.2.7.

**If you remember one thing:** the output shape picks the pattern.

---

## 5.2.13.3 — WHERE SIDE EFFECTS BELONG

**Framing.** Skills with side effects such as release procedures should set `disable-model-invocation: true`; the docs recommend it for workflows like `/deploy` and the overview tip says to use it for skills with side effects, which saves context and ensures they run only when named [Claude Code docs, Skills and Extend Claude Code, 2026]. A rule that must hold every time belongs in a hook instead.

| Pattern | Auto-load OK? |
|---|---|
| Glossary, conventions, rubric | Yes |
| Template | Usually yes |
| Release procedure, runbook with actions | No: manual |
| Checklist | Depends on whether it runs commands |

The failure mode: **Auto-run runbook.** A runbook that restarts services is left auto-invocable and a loosely matched request triggers it.

The fix: Mark it manual-only.

Cross-references: hooks for guarantees are Module 5.4.

**If you remember one thing:** side effects mean manual invocation.

## CLOSING REFRAME

This is the craft of skill shape: **reference or task, then the body that fits the output.** The engineer who understands this does not ask "what should the skill say?" — they ask "what shape is this job?"
