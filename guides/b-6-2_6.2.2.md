## THE THESIS OF THIS TOPIC

**There are four ways into a worktree, the --worktree flag, asking Claude, subagent isolation and desktop sessions, and they differ in where the directory lives, who cleans it up and which exits prompt you.**

**Prove-it, in one sentence:** create a worktree four ways and record, for each, where it lands, its branch name and what happens on exit.

**The single most important discipline: name the worktree yourself when you will come back to it.**

## 6.2.2.1 — THE --WORKTREE FLAG

**Framing.** Pass `--worktree` or `-w` with a name to create a worktree and start Claude in it. By default it lands under `.claude/worktrees/<name>/` at the repository root, on a new branch named `worktree-<name>`. Omit the name and Claude generates one such as `bright-running-fox`. Interactive runs require workspace trust; non-interactive `-p` runs skip the trust check [Claude Code docs, Worktrees, 2026].

```bash
claude --worktree feature-auth      # .claude/worktrees/feature-auth/, branch worktree-feature-auth
claude -w                          # generated name, e.g. bright-running-fox
claude --worktree "#1234"          # from a pull request (quote the #)
```

The docs advise adding `.claude/worktrees/` to `.gitignore` so worktree contents do not show as untracked in your main checkout [Claude Code docs, Worktrees, 2026].

The failure mode: **Unquoted-hash prompt.** You type `claude --worktree #1234` and your shell treats `#1234` as a comment, so you get a generated worktree with no pull request.

The fix: Quote the argument: `claude --worktree "#1234"`.

Cross-references: the base branch for new worktrees is sub-topic 6.2.4.

**If you remember one thing:** name it, ignore the directory, quote the hash.

## 6.2.2.2 — SUBAGENT ISOLATION

**Framing.** Subagents can run in their own worktrees so parallel edits do not conflict. Ask Claude to use worktrees for its agents, or make isolation permanent with `isolation: worktree` in a custom subagent's frontmatter. Each subagent gets a temporary worktree removed automatically if it finishes without changes; with changes, the worktree stays until a periodic sweep can remove it safely [Claude Code docs, Worktrees, 2026].

```markdown
---
name: refactorer
description: Applies mechanical refactors across many files
isolation: worktree
---

Apply the requested refactor across every affected file, then run the tests
and report the results.
```
[quoted from Claude Code docs, Worktrees, 2026]

A subagent in its own worktree takes its starting instructions from your main conversation, and when that worktree is in the default location it does not load that worktree's own `CLAUDE.md` or `.claude/rules/` as it reads files there [Claude Code docs, Worktrees, 2026].

The failure mode: **Branch-local rules assumption.** You change `CLAUDE.md` on the worktree's branch and expect an isolated subagent to obey it, but it takes instructions from the main conversation.

The fix: Put binding instructions in the prompt or the agent definition, not only in a branch-local file.

Cross-references: subagent definitions are Module 5.3; cleanup is sub-topic 6.2.4.

**If you remember one thing:** `isolation: worktree` makes safety a property of the agent.

## 6.2.2.3 — DESKTOP AND ASKING CLAUDE

**Framing.** In the desktop app you select the worktree option when you start a session, and the same `.worktreeinclude` and sharing rules apply [Claude Code docs, Worktrees, 2026]. Inside any session you can ask Claude to work in a worktree and it uses the EnterWorktree tool; once in one it can switch to another under `.claude/worktrees/` by path [Claude Code docs, Worktrees, 2026].

| Method | Where it lands | Approval behaviour |
|---|---|---|
| `--worktree name` | `.claude/worktrees/name/` | Workspace trust required interactively |
| Ask Claude | `.claude/worktrees/` (EnterWorktree) | A path outside that directory prompts first; a permission rule or don't-ask-again does not suppress it |
| Subagent `isolation: worktree` | Temporary worktree | Removed if no changes |
| Desktop worktree option | Worktree-backed session | Same sharing rules |

Before v2.1.206, Claude could enter any existing worktree path without asking; since then a path outside `.claude/worktrees/` needs your approval, and only `bypassPermissions` mode skips it [Claude Code docs, Worktrees, 2026].

The failure mode: **Outside-path surprise.** You point Claude at a worktree outside `.claude/worktrees/` and keep getting an approval prompt that no rule will silence.

The fix: Keep worktrees under `.claude/worktrees/`, or accept that entering other paths always asks.

Cross-references: permission modes are Module 4.3; desktop sessions are Module 7.2.

**If you remember one thing:** the entry method decides the location and the prompts.

## 6.2.2.4 — WHAT HAPPENS ON EXIT

**Framing.** On exit of an interactive worktree session Claude checks for work removal would delete. Clean and unnamed: removed with its branch. Clean and named: prompts you. With work in it: prompts to keep or remove. Unverifiable: prompts. `-p` runs have no exit prompt, so Claude does not clean them up and leaves the creation lock in place [Claude Code docs, Worktrees, 2026].

| State at exit | What Claude does |
|---|---|
| Clean, unnamed session | Removes worktree and branch automatically |
| Clean, named session | Prompts so you can keep it |
| Has changed or untracked files, or new commits | Prompts to keep or remove; removal deletes the work |
| State cannot be verified | Prompts and names what it could not check |
| `claude -p --worktree` | No cleanup; run `git worktree remove` (and `git worktree unlock` if locked) |

The failure mode: **Orphaned -p worktree.** A scripted `claude -p --worktree` loop leaves one locked worktree per run until the disk fills.

The fix: Add `git worktree remove` to the script, with `git worktree unlock` first if git refuses.

Cross-references: the periodic sweep is sub-topic 6.2.4.

**If you remember one thing:** interactive exits ask; scripts leave litter.

## CLOSING REFRAME

This is the craft of entering worktrees: **four doors, one default location, exits that depend on state.** The engineer who understands this does not ask "did it clean up?" — they ask "was it named, was it dirty, and was it -p?"
