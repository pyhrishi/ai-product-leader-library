## THE THESIS OF THIS TOPIC

**Different failures need different checks: integration and contract tests for boundaries, snapshot and visual tests for output, load tests for capacity and accessibility checks for users, and each can be a pass-or-fail check Claude runs.**

**Prove-it, in one sentence:** choose the right check for five failure types and run one non-unit check end to end.

**The single most important discipline: match each risk to the cheapest check that can detect it.**

**The counterintuitive claim you will learn to defend:** a unit suite can be fully green while the product is unusable, because units never exercise the seams.

## 9.2.4.1 — MATCH RISK TO CHECK

**Framing.** The docs' list of checks is broad: a test file, a build exit code, a linter, a script that diffs output against a fixture, or a browser screenshot next to the mockup [Claude Code docs, Best practices, 2026]. The table maps common risks to those and to other test types.

| Risk | Check | Runs as |
|---|---|---|
| Logic bug | Unit test | `pnpm vitest run file` |
| Two components disagree | Integration test | Test with real DB or fake |
| API shape drifts | Contract test (consumer expectations vs provider) | Pact-style tool (not verified here) |
| Output formatting changes | Snapshot test | Diff vs stored snapshot |
| Capacity | Load test | Tool of your choice (not verified here) |
| UI regression | Screenshot compared with design | Browser integration (Module 7.6) |
| Accessibility | Automated audit plus manual check | See Module 9.6.4 |

The failure mode: **One-check-fits-all.** The team has hundreds of unit tests and no integration test, so a broken wiring ships.

The fix: For each module, name the cheapest check per risk and add the missing type.

Cross-references: verifying UI is Module 9.6; browser integration is Module 7.6.

**If you remember one thing:** different risks need different instruments.

## 9.2.4.2 — SNAPSHOT AND VISUAL TESTS NEED REVIEW DISCIPLINE

**Framing.** A snapshot test passes when output equals the stored snapshot, so updating the snapshot to make it pass erases the signal. Ask Claude to explain every snapshot diff before accepting it.

| Action | Rule |
|---|---|
| Snapshot fails | Read the diff; classify intended or regression |
| Intended | Update snapshot in its own commit with the reason |
| Regression | Fix the code, leave the snapshot |

```text
The snapshot test failed. Show the diff, say whether each hunk is intended per SPEC.md,
and do not update the snapshot until I agree.
```

The failure mode: **Blind snapshot update.** Claude runs the update flag and the test turns green with the regression baked in.

The fix: Forbid snapshot updates in the prompt and review snapshot diffs as code.

Cross-references: reviewing AI diffs is Module 9.12.3.

**If you remember one thing:** a snapshot update is a code change.

## 9.2.4.3 — SLOW CHECKS AND WHEN TO RUN THEM

**Framing.** Heavier checks should run where they cost little: in CI or on demand, not in every loop. The docs say hooks give deterministic control and warn to keep the enforced set small [Claude Code docs, Best practices, 2026].

| Check | Where |
|---|---|
| Unit, single file | Every iteration |
| Integration | Before commit, via Stop hook or CI |
| Load, long visual suites | CI or scheduled |

Stop hook example from the docs: `pnpm tsc --noEmit 1>&2 || exit 2`; exit 2 blocks the stop, and after eight blocked stops in a row with no tool call between them Claude Code overrides the next block [Claude Code docs, Best practices, 2026].

The failure mode: **Slow-loop stall.** A 20-minute suite runs in the Stop hook on every turn and the session crawls.

The fix: Keep the Stop hook to fast checks and push heavy suites to CI.

Cross-references: Stop hooks are Module 9.2.5; CI is Module 9.9.2.

**If you remember one thing:** put each check where its cost is lowest.
