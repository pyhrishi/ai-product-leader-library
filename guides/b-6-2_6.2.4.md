## 6.2.4.1 — CHOOSING THE BASE BRANCH

**Framing.** `worktree.baseRef` accepts two values. `"fresh"` (default) branches from the repository's default branch on the remote, usually `main`, giving a clean tree matching the remote. `"head"` branches from your current local `HEAD`, carrying unpushed commits and feature-branch state; inside a worktree it resolves to that worktree's HEAD. It cannot be set to a branch name; to start from a specific branch, use `git worktree add` [Claude Code docs, Worktrees, 2026].

```json
{ "worktree": { "baseRef": "head" } }
```
[quoted from Claude Code docs, Worktrees, 2026]

For fresh, Claude Code keeps `origin/HEAD` current: if the repository has not been fetched in 24 hours it fetches the default branch, capped at five seconds, and uses the cached ref if the fetch fails; with no remote or no cached `origin/HEAD` it falls back to local HEAD. Before v2.1.208 it used whatever `origin/HEAD` was cached [Claude Code docs, Worktrees, 2026].

The failure mode: **Missing-unpushed-work.** You start a worktree to continue your feature branch and your three local commits are not there because baseRef is fresh.

The fix: Set `worktree.baseRef` to `head` for in-progress work, or create the worktree with `git worktree add` from the branch you want.

Cross-references: settings files are Module 4.1.

**If you remember one thing:** fresh means the remote, head means your tip.

## 6.2.4.2 — BRANCHING FROM A PULL REQUEST

**Framing.** Pass `--worktree` a `#number`, a GitHub pull request URL, or a GitLab merge request URL. Claude Code fetches that change's head commit from `origin` and creates `.claude/worktrees/pr-<number>`. Only the number is read from the URL; the fetch path depends on origin's host: `pull/<n>/head` for github.com, `merge-requests/<n>/head` for gitlab.com, and both tried in order for other hosts [Claude Code docs, Worktrees, 2026].

| Origin host | Fetch path |
|---|---|
| github.com | `pull/<number>/head` |
| gitlab.com | `merge-requests/<number>/head` |
| GitHub Enterprise, self-managed GitLab, other | `pull/<number>/head` first, then `merge-requests/<number>/head` |

The fetch never waits for terminal input; if git or ssh would prompt for a password, passphrase or new-host confirmation, it fails with `Error creating worktree: Failed to fetch PR/MR #<number>`. Load your key in `ssh-agent` and run `git fetch` once by hand [Claude Code docs, Worktrees, 2026].

The failure mode: **Prompted-fetch failure.** The PR fetch fails because ssh wanted a passphrase or host confirmation and the tool cannot ask.

The fix: Add the key to ssh-agent and run `git fetch` once by hand to record the host.

Cross-references: pull request review workflows are Module 9.12.

**If you remember one thing:** the fetch is non-interactive; prepare credentials.

## 6.2.4.3 — REUSING A NAME

**Framing.** Passing `--worktree` a name whose directory exists opens that worktree. With fresh, a reopened worktree resets to the default branch when it has no uncommitted changes or untracked files, is still on its Claude-created branch, and has no commits of its own or its PR was merged and remote branch deleted. Otherwise it reopens at its old tip, as it does with baseRef `head` or a PR reference [Claude Code docs, Worktrees, 2026].

| Condition | Reopened at |
|---|---|
| Clean, on its branch, no own commits (fresh) | Default branch (reset) |
| Clean, PR merged, remote branch deleted (fresh) | Default branch (reset) |
| Uncommitted changes or untracked files | Old tip |
| baseRef `head`, or a PR/MR reference name | Old tip |
| State cannot be verified | Old tip |

The failure mode: **Reset-on-reuse surprise.** You reuse a name expecting last week's branch and find it reset to main because it was clean and merged.

The fix: Commit or push work you want to keep, or pick distinct names for long-lived worktrees.

Cross-references: resuming worktree sessions is Module 2.4.

**If you remember one thing:** reuse can reset; commit what you care about.

## 6.2.4.4 — THE PERIODIC SWEEP

**Framing.** A sweep removes worktrees Claude created for subagents and background sessions once older than `cleanupPeriodDays`. It keeps a worktree that holds work (changed or untracked files, unpushed commits), one with dirty submodules (v2.1.274 or later check), one blocked by filter-driver cases, a `--worktree` session you have not backgrounded, and any worktree you created yourself with `git worktree add`. While an agent runs Claude Code holds a `git worktree lock`; the sweep releases a lock for a dead session (v2.1.210+) but never one you set [Claude Code docs, Worktrees, 2026].

| Sweep keeps | Sweep removes |
|---|---|
| Worktrees with changes or unpushed commits | Older-than-`cleanupPeriodDays` clean subagent and background worktrees |
| Your own `git worktree add` worktrees | Locks left by killed Claude-owned sessions |
| Foreground `--worktree` sessions you have not backgrounded |  |

To remove one the sweep keeps: `git worktree remove` (add `--force` with uncommitted changes); `git worktree unlock` first if locked [Claude Code docs, Worktrees, 2026].

The failure mode: **Sweep-will-handle-it.** You leave dozens of `--worktree` sessions and hand-made worktrees and assume the sweep clears them, but it only removes Claude-created subagent and background worktrees that hold no work.

The fix: Remove your own worktrees with `git worktree remove` and check `git worktree list` weekly.

Cross-references: disk and retention settings are Module 4.1.

**If you remember one thing:** the sweep is a safety net with a short list.

## CLOSING REFRAME

This is the craft of worktree lifecycle: **start from the right commit, name for reuse, and remove what the sweep will not.** The engineer who understands this does not ask "why is my work missing?" — they ask "which ref did that worktree start from?"
