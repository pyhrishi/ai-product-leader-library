## THE THESIS OF THIS TOPIC

**The strangler pattern wraps old behaviour behind a new interface, routes a small share of traffic to the new implementation and grows that share while the old path stays available to roll back.**

**Prove-it, in one sentence:** build a routing seam, move one route's traffic to a new implementation behind a flag and show the rollback.

**The single most important discipline: build the seam before the new implementation, and keep rollback a single switch.**

**The counterintuitive claim you will learn to defend:** the new code is the easy part; the seam, the traffic switch and the comparison are the migration.

## 9.4.5.1 — SEAM, FLAG, COMPARE

**Framing.** The pattern is general architecture practice, not from the Claude Code docs. Claude's role is to write the facade, flag and comparison harness from a spec and to run the checks the docs recommend.

| Element | Purpose |
|---|---|
| Facade | One entry point both paths sit behind |
| Flag or percentage | Chooses old or new |
| Shadow compare | Run both, return old, log differences |
| Rollback | Flip the flag |

```text
Create a facade for pricing.calculate() that calls legacy or new based on flag PRICING_NEW (0 to 100).
In shadow mode call both, return legacy, and log any difference with inputs. Do not change legacy.
```

The failure mode: **Unreachable rollback.** The old path is deleted or diverges, so a bad rollout cannot be undone.

The fix: Keep the old path untouched until the new one has run clean for your agreed period.

Cross-references: characterisation tests are Module 9.4.1; gradual modernisation is Module 9.5.4.

**If you remember one thing:** keep the exit open.

## 9.4.5.2 — MOVING TRAFFIC GRADUALLY

**Framing.** Increase the share in steps and watch comparison logs and error rates between steps; use read-only observability access (Module 9.3.4).

| Stage | Share | Gate |
|---|---|---|
| Shadow | 0% served by new | Differences understood |
| Canary | small share (your choice) | Error rate flat |
| Majority | increasing | No new differences |
| Full | 100% | Old path removable after soak |

The failure mode: **Blind ramp.** Share increases on a schedule with nobody reading comparison logs.

The fix: Make each step conditional on a reviewed comparison report.

Cross-references: observability is Module 9.3.4.

**If you remember one thing:** ramp on evidence.

---

## 9.4.5.3 — DELETING THE OLD PATH

**Framing.** Remove old code only after a soak period and with a deletion PR that stands alone. Cleanup passes (Module 9.4.6) apply after.

| Check before delete | Evidence |
|---|---|
| No traffic to old | Metrics show 0 |
| No references | `grep` shows none |
| Tests | New path covered |
| Rollback plan | Documented or consciously retired |

The failure mode: **Zombie legacy.** The old path stays forever because deletion was never scheduled.

The fix: Put the deletion ticket in the plan at the start.

Cross-references: cleanup is Module 9.4.6.

**If you remember one thing:** plan the ending at the start.

**A passing artifact looks like this:**

| Stage | Evidence |
|---|---|

| Element | What is wrong |
|---|---|
| No flag | **Unreachable rollback** |
| No review of diffs | **Blind ramp** |

**The verdict.** The artifact passes only if the rollback was exercised and shadow differences were reviewed before any traffic moved.

## CLOSING REFRAME

This is the craft of strangling: **seam first, ramp on evidence, plan the deletion.** The engineer who understands this does not ask "is the new code done?" — they ask "how do I undo this in one switch?"
