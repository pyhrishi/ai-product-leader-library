# MODULE 9.3.5 — ROOT CAUSE DISCIPLINE: THE COMPLETE CRAFT

## THE THESIS OF THIS TOPIC

**Ask Claude for the cause, not a suppression, and require an explanation and a regression test, because the cheapest-looking fix to an error is often to hide it.**

**Prove-it, in one sentence:** show a diff where the fix addresses the cause, with an explanation, a regression test and no suppression.

**The single most important discipline: no fix merges without a stated cause and a test that fails without it.**

**The counterintuitive claim you will learn to defend:** an error that disappears is not a bug that is fixed; suppression looks identical to success until the next incident.

## 9.3.5.1 — CAUSE VERSUS SUPPRESSION

**Framing.** The docs' bug example compares a vague prompt with one that names the symptom and asks for a reproduction and fix; it also suggests asking Claude for a few ways to fix a `@ts-ignore` [Claude Code docs, Common workflows, 2026]. A `@ts-ignore` is itself a suppression.

| Suppression | Cause fix |
|---|---|
| `try/catch` that swallows | Handle or prevent the error condition |
| `@ts-ignore` | Correct the type |
| Retry or sleep | Fix the race (Module 9.2.6) |
| Default value hiding null | Make the null impossible or handled explicitly |
| Disable the failing test | Fix the code |

The failure mode: **Symptom suppression.** The error stops appearing because it is caught and ignored, and the underlying fault persists.

The fix: Prompt: 'explain the root cause before changing anything; do not catch-and-ignore, skip tests or add ts-ignore'.

Cross-references: TDD is Module 9.2.1.

**If you remember one thing:** ask why before how.

## 9.3.5.2 — THE EXPLANATION REQUIREMENT

**Framing.** Require a short causal chain: trigger, mechanism, why it escaped earlier checks. The docs advise asking for evidence rather than bare claims [Claude Code docs, Best practices, 2026].

| Field | Example |
|---|---|
| Trigger | Session expires between request and refresh |
| Mechanism | Refresh uses stale token after rotation |
| Escape | No test covered timeout during rotation |
| Fix | Rotate-then-refresh ordering |
| Guard | Test `refreshes_after_timeout` |

The failure mode: **Plausible story.** The explanation is fluent but not tied to evidence, and the fix is not the cause.

The fix: Ask which log line, line of code or test output supports each step and verify one by experiment.

Cross-references: evidence is Module 9.3.2.

**If you remember one thing:** each causal step cites evidence.

---

## 9.3.5.3 — REGRESSION TEST AND THE FIVE-WHYS LIMIT

**Framing.** A regression test fails before the fix and passes after. Asking 'why' repeatedly finds the process cause too, but stop when the next answer is outside your control.

| Question | Output |
|---|---|
| Why did it fail? | Mechanism |
| Why was it not caught? | Missing test or check |
| What prevents recurrence? | Test, hook or CLAUDE.md line (Module 9.12.9) |

Confirm with: revert the fix, rerun the test, see red.

The failure mode: **Unverified regression test.** The new test passes with or without the fix.

The fix: Revert the fix on a scratch branch and confirm the test fails.

Cross-references: learning loop is Module 9.12.9.

**If you remember one thing:** prove the guard guards.

## CLOSING REFRAME

This is the craft of root cause: **cause first, evidence per step, a guard that bites.** The engineer who understands this does not ask "did the error stop?" — they ask "what was true that should not have been, and what prevents it now?"
