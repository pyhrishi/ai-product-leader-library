## 3.2.3.1 — /INIT AND WHAT IT DOES

**Framing.** `/init` generates a starting file from your codebase; if one exists it suggests improvements rather than overwriting it, and it also incorporates existing `AGENTS.md`, `.cursorrules` and `.windsurfrules` [Claude Code docs, Memory, 2026]. The How Claude Code works page lists `/init` as generating a starter CLAUDE.md and `/doctor` as a setup checkup [Claude Code docs, How Claude Code works, 2026].

| Command | Does |
|---|---|
| `/init` | Generate or suggest improvements to CLAUDE.md |
| `/memory` | List loaded CLAUDE.md, local and rules files; toggle auto memory; open the memory folder |
| `/doctor` | Setup checkup; can propose cuts to a checked-in CLAUDE.md |

The failure mode: **Ship-the-draft.** You commit the /init output unreviewed, so it carries lines Claude could derive from the code.

The fix: Review every line and cut anything Claude can already work out.

Cross-references: pruning is sub-topic 3.2.6 of Module 3.2.

**If you remember one thing:** the draft is a start.

## 3.2.3.2 — THE INTERACTIVE FLOW

**Framing.** Setting `CLAUDE_CODE_NEW_INIT=1` gives an interactive multi-phase flow that asks which artifacts to set up (CLAUDE.md, skills, hooks) and presents a reviewable proposal before writing files [Claude Code docs, Memory, 2026]. It is an environment-variable opt-in in the page read, so confirm that it still applies to your version.

```bash
CLAUDE_CODE_NEW_INIT=1 claude
/init
```

[from the Memory page; verify the variable on the current page before relying on it]

The failure mode: **Unreviewed-proposal.** You accept the proposal for hooks and skills as a bundle without reading each, and install automation you did not mean to.

The fix: Review each proposed artifact separately and decline what you cannot explain.

Cross-references: hooks are Module 5.4; skills are Module 5.1.

**If you remember one thing:** review before it writes.

## 3.2.3.3 — EDITING WITH /MEMORY

**Framing.** `/memory` lists the CLAUDE.md, CLAUDE.local.md and rules files loaded in the session, toggles auto memory and opens the auto memory folder; selecting a file opens it in your editor [Claude Code docs, Memory, 2026]. Run `/context` to confirm Claude loaded the file [Claude Code docs, Best practices, 2026].

| Check | How |
|---|---|
| File loaded? | `/memory` list or `/context` |
| Edit applies now? | Not mid-session; see sub-topic 3.2.11 of Module 3.2 |
| Auto memory contents? | `/memory` then open the folder |

The failure mode: **Edit-and-assume.** You edit CLAUDE.md in `/memory` mid-session and assume Claude now follows it.

The fix: Start a new session or `/clear` or `/compact` to load it, then verify behaviour.

Cross-references: the caching reason is Module 3.4.

**If you remember one thing:** editing is not loading.

## THE PROVE-IT SECTION

**Deliverable.** A before-and-after of an /init draft with a cut log, plus the final file under 200 lines.

**Close this topic. Build the artifact below from memory. Return to the text only after your first attempt is complete.**

| Step | Action | Output |
|---|---|---|
| 1 | Run `/init` in a real repo | Draft |
| 2 | Count its lines and categorise each | Category count |
| 3 | Cut every derivable line | Cut log |
| 4 | Confirm with `/context` that the file loads | Load proof |
| 5 | Run `/doctor` and compare its suggestions | Comparison |
| 6 | Commit only the pruned file | Final file |

**A passing artifact looks like this:**

| Metric | Draft | Final |
|---|---|---|
| Lines | Over 200 | Under 200 |
| Derivable lines | Several | None |
| Gotchas kept | Some | All |

**A failing artifact (a realistic near-miss):**

| Element | What is wrong |
|---|---|
| Final equals draft | **Ship-the-draft** |
| No load proof | Unverified |

**The verdict.** The artifact passes only if the final file is shorter than the draft, every cut is justified and the file was confirmed loaded.
