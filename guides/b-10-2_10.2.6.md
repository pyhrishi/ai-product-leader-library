## THE THESIS OF THIS TOPIC

**The GitHub Action calls the Claude API by default; to use your own cloud it takes one provider input plus an OIDC trust you configure on the cloud side, so no long-lived cloud key lives in the repository.**

**Prove-it, in one sentence:** write a workflow with the correct provider input, permissions and OIDC step, and name the cloud-side trust it needs.

**The single most important discipline: scope the cloud trust to one repository and verify the commenter before any credential step.**

**The counterintuitive claim you will learn to defend:** on public repositories a comment containing the trigger phrase from any user starts the workflow, and credential steps run before the action checks the commenter's write access [Claude Code docs, Use Claude Code GitHub Actions with cloud providers, 2026].

## 10.2.6.1 — PROVIDER INPUT AND OIDC

**Framing.** Set one input in the `anthropics/claude-code-action` step: `use_bedrock: "true"`, `use_vertex: "true"` or `use_foundry: "true"`. The workflow needs the `id-token: write` permission so GitHub issues the OIDC token your cloud exchanges for short-lived credentials [Claude Code docs, Use Claude Code GitHub Actions with cloud providers, 2026].

```yaml
permissions: { contents: write, pull-requests: write, issues: write, id-token: write }
...
- uses: aws-actions/configure-aws-credentials@v4
  with: { role-to-assume: ${{ secrets.AWS_ROLE_TO_ASSUME }}, aws-region: us-west-2 }
- uses: anthropics/claude-code-action@v1
  with: { github_token: ${{ steps.app-token.outputs.token }}, use_bedrock: "true",
          claude_args: '--model us.anthropic.claude-sonnet-4-6' }
```

The failure mode: **Missing id-token.** The workflow omits `id-token: write`, no OIDC token is issued, and authentication fails.

The fix: Add the permission; check trust repository conditions and secret names match.

Cross-references: cloud setup is Module 10.2.2; CI is Module 7.8.

**If you remember one thing:** no id-token permission, no federation.

## 10.2.6.2 — CLOUD-SIDE TRUST

**Framing.** On AWS, add a GitHub OIDC provider (URL `https://token.actions.githubusercontent.com`, audience `sts.amazonaws.com`), create a role with the Bedrock invocation policy and limit trust to your repository, for example `repo:your-org/your-repo:*`. On Google Cloud, enable IAM Credentials, STS and the Agent Platform API, create a Workload Identity Pool with an attribute condition for your repository, and a service account with only `roles/aiplatform.user`. On Azure, register an Entra application with a federated credential and assign `Foundry User` on the resource [Claude Code docs, Use Claude Code GitHub Actions with cloud providers, 2026].

| Cloud | Secrets | Least-privilege role |
|---|---|---|
| AWS | `AWS_ROLE_TO_ASSUME` | Bedrock invoke policy |
| Google | `GCP_WORKLOAD_IDENTITY_PROVIDER`, `GCP_SERVICE_ACCOUNT` | `roles/aiplatform.user` |
| Azure | `AZURE_CLIENT_ID`, `AZURE_TENANT_ID`, `AZURE_SUBSCRIPTION_ID` | `Foundry User` |

The failure mode: **Org-wide trust.** The trust policy allows `repo:your-org/*`, so any repository in the organisation can assume the Claude role.

The fix: Pin the subject or attribute condition to the one repository.

Cross-references: least privilege is Module 11.3.

**If you remember one thing:** scope the trust to one repository.

## 10.2.6.3 — THE PUBLIC-REPOSITORY TRAP

**Framing.** The docs warn that credential steps run before the action checks the commenter's write access, so an unauthorised commenter can trigger an App token and a cloud sign-in, leaving audit-log entries and consuming Actions minutes. Add a step that verifies the commenter's write access before the credential steps. Bound cost with `--max-turns` in `claude_args` [Claude Code docs, Use Claude Code GitHub Actions with cloud providers, 2026].

```text
trigger comment
  -> [verify commenter has write access]   <- add this first
  -> generate App token
  -> cloud OIDC sign-in
  -> claude-code-action (--max-turns N)
```

The failure mode: **Credentials-before-check.** Anyone can comment and force a cloud sign-in on a public repository.

The fix: Verify write access before the credential steps and cap turns.

Cross-references: prompt injection through comments is Module 11.2.

**If you remember one thing:** authorise the commenter before spending credentials.

## 10.2.6.4 — GITHUB IDENTITY CHOICES

**Framing.** Choose the GitHub identity: the official Claude GitHub App, a custom app with only Contents, Issues and Pull requests read and write permissions, or the automatic `GITHUB_TOKEN`, which does not trigger your CI workflows on commits it makes [Claude Code docs, Use Claude Code GitHub Actions with cloud providers, 2026]. Bedrock cross-region model IDs need access granted in every region of the region group. The feature table marks GitHub Actions available on Bedrock, Agent Platform and Foundry but not Claude Platform on AWS [Claude Code docs, Feature availability, 2026].

| Identity | Trade-off |
|---|---|
| Official Claude GitHub App | Full official permission set |
| Custom GitHub App | Only three permissions; you maintain it |
| `GITHUB_TOKEN` | No app; does not trigger CI on its commits |

The failure mode: **Silent CI skip.** You use `GITHUB_TOKEN`, Claude pushes fixes, and your CI never runs on them.

The fix: Use an App token when downstream workflows must run.

Cross-references: CI patterns are Module 7.8.

**If you remember one thing:** choose the identity by what must trigger next.

| Element | What is wrong |

**The verdict.** The workflow passes only if a non-writer comment is rejected before any cloud sign-in and the trust names one repository.

## CLOSING REFRAME

This is the craft of CI on your cloud: **federation instead of keys, trust scoped to one repo, and authorise before you authenticate.** The administrator who understands this does not ask "does it run?" — they ask "who can make it run?"
