# MODULE 1.1.2 — CHATBOT VERSUS AGENT: THE OPERATIONAL DIFFERENCE: THE COMPLETE CRAFT

---

## THE THESIS OF THIS TOPIC

**A chatbot answers and waits; an agent plans, acts, observes the result and loops until it is done or blocked. The difference is not intelligence, it is who closes the loop.**

**Prove-it, in one sentence:** run one bug through a chat window and through Claude Code, count the copy-paste handoffs in each, and point to the transcript line where the agent verified its own work.

**The single most important discipline: count handoffs. Every time you copy something from the model to your machine or back, you are the loop, and you are the slowest part of it.**

**The counterintuitive claim you will learn to defend:** a chatbot can be smarter than an agent on any single answer and still lose, because the agent's advantage is the verified result, not the quality of one reply [Claude Code docs, How Claude Code works, 2026].

**THE TIME BUDGET.** Reading time: ~25 minutes. Prove-it time: ~2 hours (120 minutes, 4.8 times the reading time).

## 1.1.2.1 — THREE MODES, ONE TABLE

**Framing.** Tools that touch code fall into three modes. **Autocomplete** predicts the next tokens at your cursor. A **chatbot** answers questions about text you give it, then waits. An **agent** acts on your project through tools, reads what happened and decides the next action. The glossary defines agentic coding the same way: the AI reads files, runs commands and makes changes while you watch, redirect or step away, as opposed to chat assistants that only respond with text you must apply yourself [Claude Code docs, Glossary, 2026].

| Mode | Sees | Does | Who runs the code | Who closes the loop |
|---|---|---|---|---|
| Autocomplete | The cursor neighbourhood | Predicts next tokens | You | You, line by line |
| Chatbot | What you paste | One answer, then waits | You, by copy and paste | You, by relaying results |
| Agent | Your project through tools | Acts, observes, repeats | The agent, through tools | The agent, if it has a check |

```
 AUTOCOMPLETE          CHATBOT                      AGENT
 type ► suggestion     paste ► answer ► (wait)      goal ► act ► observe ► decide ► act ...
   ▲        │             ▲                  │                    ▲                    │
   └ accept ┘             └── you run it ◄───┘                    └──── check passes? ─┘
```

The same bug shows the gap. In a chat window you paste the stack trace, read the answer, apply it, run the tests, paste the next error. In Claude Code you state the failing command and the goal; it runs the command, reads the output, edits, and runs again.

The failure mode: **Mode confusion.** You use an agent like autocomplete (asking for snippets) or a chatbot like an agent (expecting it to know what your tests did), so you get neither the speed of one nor the verification of the other.

The fix: Decide the mode before you start: snippet at the cursor is autocomplete, advice about pasted text is chat, a task with a check is an agent run.

Cross-references: the loop is Module 1.2; the surfaces you run it on are Module 7.1.

**If you remember one thing:** the question that separates the modes is who runs the code and reads the result.

## 1.1.2.2 — THE LOOP, AND WHERE YOU SIT IN IT

**Framing.** Claude Code works through every task in three blended phases: gather context, take action, verify results. The phases blend into each other, and you can interrupt at any point [Claude Code docs, How Claude Code works, 2026]. A turn is one complete response from your message until Claude finishes, with any number of tool calls in between [Claude Code docs, Glossary, 2026].

| Phase | What happens | Example tool calls | What you can do |
|---|---|---|---|
| Gather context | Search, read files, inspect git state | Grep, Read, `git status` | Point it at the right directory |
| Take action | Edit files, run commands | Edit, Write, Bash | Approve or deny a permission prompt |
| Verify results | Run tests, read output, compare | Bash, Read | Provide the check; interrupt if wrong |

The docs' own example for "fix the failing tests" chains six moves: run the suite, read the errors, find the relevant files, read them, edit, run the tests again [Claude Code docs, How Claude Code works, 2026]. A chatbot can reason through the middle four but cannot do the first and last, so you do them.

You steer in two ways: `Esc` stops immediately, and typing a correction then pressing `Enter` redirects without stopping [Claude Code docs, How Claude Code works, 2026].

The failure mode: **Loop-abandonment.** You start an agent run and then do nothing while it goes down a wrong path for ten minutes, because you treated it as fire-and-forget.

The fix: Watch the first few tool calls of any new kind of task, interrupt with Esc at the first sign of a wrong direction, and only walk away once the check is in place.

Cross-references: the loop with its hook points is Module 1.2; session steering is Module 2.4.

**If you remember one thing:** you are inside the loop, so interrupt early rather than review late.

## 1.1.2.3 — COUNTING HANDOFFS: THE METRIC THAT MAKES THIS CONCRETE

**Framing.** The most useful single measure of whether you are really using an agent is the number of handoffs: times you move information between the model and your machine by hand. Chat workflows pay a handoff on every iteration. An agent run, with a check, pays only at the start and at the review.

```text
Task: make `npm test` pass in a small repo (3 failing tests).

CHAT RUN                                     AGENT RUN
1 paste failing output   -> handoff 1         1 "run npm test, fix failures,
2 apply patch by hand    -> handoff 2             re-run until green. Do not
3 run tests              -> handoff 3             add dependencies."
4 paste new output       -> handoff 4         2 review `git diff` and test output
5 apply patch            -> handoff 5
6 run tests              -> handoff 6         handoffs: 2   (start, review)
handoffs: 6+ (grows per iteration)
```

The counts are illustrative; yours will vary. The point is the shape: chat cost grows with iterations, agent cost stays flat.

| What the handoff count tells you | Reading |
|---|---|
| High and growing | You are the messenger; give Claude the command and the check |
| Low but the result is wrong | The agent had no real check; add one |
| Low and correct | The loop is closed; you only review |

The failure mode: **Human-as-messenger loop.** You copy errors into the tool and patches back into the editor, so the model is an agent in capability and a chatbot in practice.

The fix: Give Claude the command that reproduces the problem and the check that proves it fixed, so it can run and read results itself.

Cross-references: verification design is Module 2.3; prompting for outcomes is Module 2.2.

**If you remember one thing:** count your handoffs; the number is your loop-closing score.

## 1.1.2.4 — WHAT AN AGENT COSTS YOU: THE NEW RISKS

**Framing.** Handing the loop to an agent removes handoffs and adds three risks that a chatbot does not have. The agent can take actions with side effects, it can stop when the work only looks done, and it can spend a large amount of context and plan usage on one task. The docs name the verify gap directly: Claude stops when the work looks done, so a check it can run is what makes the difference between a session you watch and one you walk away from [Claude Code docs, Best practices, 2026].

| Risk | Why a chatbot does not have it | Control |
|---|---|---|
| Side effects | It cannot touch your machine | Permission modes and rules, sandboxing, git |
| Looks-done stop | It never claims a result it did not see | A check Claude can run; `/goal` or a Stop hook for unattended runs |
| Context and usage spend | One answer is cheap | `/clear` between tasks, scoped prompts, `/usage` |

In Manual mode Claude Code starts with read-only permissions and asks before edits and commands; it runs a built-in set of read-only commands such as `ls`, `cat` and `git status` without asking [Claude Code docs, Security, 2026]. That posture is the price of agency: more power, more gates.

The failure mode: **Autonomy-without-gate.** You give an agent a broad task in a permissive mode with no check and no branch, and find out after the fact what it changed.

The fix: Work on a branch, keep the tree clean at the start, give a check, and review the diff before you commit.

Cross-references: permissions are Modules 4.2 and 4.3; cost control is Module 1.4; checkpoints and undo are Module 2.5.

**If you remember one thing:** an agent removes the handoffs and adds the review, so keep the check and the gate.

## THE PROVE-IT SECTION

**Deliverable.** A side-by-side run log of one task done both ways, with a handoff count, a loop diagram of the agent run and a one-paragraph verdict.

**Close this topic. Build the artifact below from memory. Return to the text only after your first attempt is complete.**

| Step | Action | Output |
|---|---|---|
| 1 | Pick a small repo with a failing test and a clean tree | `task.md` with the test command |
| 2 | Chat run: paste output, apply patches by hand until green; log each handoff | Handoff log A |
| 3 | Reset the repo to the same state | Clean tree |
| 4 | Agent run: state the command, the goal and a constraint; let Claude loop | Session transcript |
| 5 | Count handoffs, tool calls, iterations and wall-clock time for both | A two-column table |
| 6 | Mark the transcript lines for gather, act, verify | Three line references |
| 7 | Write the verdict: which mode fits this task and why, and what risk the agent run added | One paragraph |

**A passing artifact looks like this:**

| Metric | Chat run | Agent run |
|---|---|---|
| Handoffs by hand | 6 | 2 |
| Iterations to green | 3 | 2 (internal) |
| Check passed | Yes, because you ran it | Yes, output visible in the transcript |
| Risk noted | Typos when copying | Edits made without per-step review; reviewed `git diff` |

The numbers above are illustrative. A passing log names the phase lines, the handoff count and one risk.

**A failing artifact (a realistic near-miss):**

| Element | What is wrong |
|---|---|
| "The agent was faster" with no count | No evidence; counting handoffs was the point |
| The agent run had no test command | **Autonomy-without-gate** and no verify phase |
| The verdict says "agents are always better" | **Mode confusion**: a snippet at the cursor is autocomplete territory |

**The verdict.** The artifact passes only if both runs started from the same repo state, the handoff counts come from your own logs, and the transcript shows the line where the agent ran the check and read the result.

## CLOSING REFRAME

This is the craft of telling a chatbot from an agent: **who runs the code and who reads the result.** The engineer who understands this does not ask "is this model smart?" — they ask "how many handoffs does my task need, and what check lets the agent close the loop?"
