## 1.4.2.1 — THREE STRUCTURES

**Framing.** Claude Code charges by API token consumption on API or provider billing; subscription pricing is separate [Claude Code docs, Costs, 2026]. Plan prices and window lengths change often; read claude.com/pricing and your Console for current figures.

| Path | You pay | Guardrails |
|---|---|---|
| Claude Console (API) | Per token | Workspaces with spend limits; Console reports |
| Cloud provider (Bedrock, Google Cloud, Foundry) | Per token on your cloud bill | Provider quotas, budgets, alerts |
| Subscription plus usage credits | Plan, then pay-as-you-go overflow | A monthly credit limit you set |

[Claude Code docs, Costs, 2026]

The failure mode: **Uncapped key.** An API key with no workspace spend limit runs in a loop or CI job and the first signal is the invoice.

The fix: Create a workspace per use case, set a spend limit before issuing the key, and alert on the Usage page.

Cross-references: sign-in paths are Module 1.3.2; enterprise governance is Part 11.

**If you remember one thing:** ceiling first, key second.

## 1.4.2.2 — WORKSPACE LIMITS AND REPORTS

**Framing.** For API organisations, spend is managed through workspaces with limits on total Claude Code spend, and admins can view cost and usage reports in the Console [Claude Code docs, Costs, 2026].

| Control | Where |
|---|---|
| Workspace spend limit | Console |
| Cost and usage reports | Console |
| Per-key attribution | One key per use case |
| Alerts | Console Usage page or provider budgets |

The failure mode: **Shared-workspace blur.** All projects share one workspace and key, so you cannot tell which one spent what or cap one without capping all.

The fix: One workspace and key per use case.

Cross-references: team spend is in Part 11.

**If you remember one thing:** one use case, one workspace.

---

## 1.4.2.3 — USAGE CREDITS ON A SUBSCRIPTION

**Framing.** Credits let you continue after plan limits by switching to pay-as-you-go. Set a monthly limit with `/usage-credits`; if you hit it with credits remaining, Claude Code prompts you to raise or remove it, and changing the limit needs billing access [Claude Code docs, Costs, 2026].

```text
/usage-credits    # set or review the monthly credit limit
```

A third-party mirror lists `/extra-usage` and `/cost`; command names shift across versions, so run `/help` in your install and confirm on the Costs page.

The failure mode: **Credits-on-autopilot.** You enable usage credits to get past a limit and forget, so every later limit hit becomes spend.

The fix: Set a monthly cap the day you enable credits and review month-to-date spend.

Cross-references: fast mode billing is Module 1.4.3.

**If you remember one thing:** enable credits and cap them in the same minute.

## 1.4.2.4 — ESTIMATING SPEND

**Framing.** Cost per task is roughly input plus output tokens times the per-token price, with context re-reads dominating long sessions. The docs advise starting with a small pilot group and using tracking tools to build a baseline before wider rollout [Claude Code docs, Costs, 2026].

| Step | Output |
|---|---|
| Pilot 3 to 5 users for two weeks | Per-user spend range |
| Break out by task type | Spend per feature, per fix |
| Multiply for rollout, add headroom | Forecast |
| Set workspace limit above forecast | Ceiling |

The failure mode: **Guess-budget.** You set a team budget from intuition and either starve the team or blow through it.

The fix: Run a pilot, measure, then set the ceiling above the measured range.

Cross-references: rollout is in Part 11.

**If you remember one thing:** measure a pilot, then forecast.

## CLOSING REFRAME

This is the craft of billing paths: **ceiling before key, cap before credit, pilot before forecast.** The engineer who understands this does not ask "what will this cost?" — they ask "what is the most this can cost, and who is alerted?"
