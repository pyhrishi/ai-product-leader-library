## THE THESIS OF THIS TOPIC

**Upgrades go best as staged changes driven by the changelog: read the release notes, update one version step at a time, run tests, fix deprecations, and repeat.**

**Prove-it, in one sentence:** upgrade one dependency across a major version in stages with a green suite after each.

**The single most important discipline: upgrade one major boundary at a time and never in the same change as a feature.**

**The counterintuitive claim you will learn to defend:** skipping straight to the latest version feels fast and makes every failure ambiguous.

**THE TIME BUDGET.** Reading time: ~13 minutes. Prove-it time: ~1.5 hours (90 minutes, 6.9 times the reading time).

## 9.4.3.1 — CHANGELOG-DRIVEN PLAN

**Framing.** Have Claude read the changelogs or migration guide for each version between yours and the target, then produce an ordered plan. The docs' refactor workflow starts by finding deprecated API usage in the codebase [Claude Code docs, Common workflows, 2026].

| Step | Prompt |
|---|---|
| Inventory | "find deprecated API usage in our codebase" |
| Read | "read the migration guide for v4 to v5 at <url>; list breaking changes that affect us" |
| Plan | "propose an ordered list of staged upgrades, each green on its own" |
| Execute | One stage per commit |

Give Claude the changelog text or URL; WebFetch is a built-in tool that prompts for permission by default [Claude Code docs, Tools reference, 2026].

The failure mode: **Memory-based upgrade.** Claude applies breaking-change fixes from training memory, not the actual release notes, and misses a change.

The fix: Provide the changelog or migration guide as input and ask it to cite the entry for each fix.

Cross-references: web tools are Module 1.2; plans are Module 9.1.4.

**If you remember one thing:** work from the document.

## 9.4.3.2 — STAGE AND VERIFY

**Framing.** Each stage ends with install, typecheck, tests and a smoke run. Use `/verify` for the running app when tests are not enough (Module 9.2.5).

| Stage | Checks |
|---|---|
| Bump version | install succeeds, lockfile diff reviewed |
| Fix compile errors | typecheck 0 errors |
| Fix tests | suite green |
| Remove deprecation warnings | warnings count 0 |
| Smoke run | `/verify` observes the app |

The failure mode: **Big-bang bump.** Three majors are bumped together and a failure could be any of them.

The fix: Upgrade one major at a time with a green suite between.

Cross-references: small steps are Module 9.4.2.

**If you remember one thing:** stage the upgrade.

## 9.4.3.3 — LOCKFILES, TRANSITIVE AND SECURITY

**Framing.** Review lockfile diffs for unexpected transitive changes. Run your package manager's audit command as a check; this guide verified no specific command.

| Review item | Action |
|---|---|
| New transitive packages | Confirm each is expected |
| Licence changes | Check policy |
| Peer-dependency warnings | Resolve before merge |
| Audit output | Triage, do not blanket-ignore |

The failure mode: **Blind lockfile accept.** A huge lockfile diff is accepted without review and pulls in an unwanted package.

The fix: Ask Claude to summarise lockfile changes and flag additions.

Cross-references: dependency audits are Module 9.10.3.

**If you remember one thing:** the lockfile is code.

## THE PROVE-IT SECTION

**Deliverable.** A staged upgrade log: version path, per-stage checks and a lockfile summary.

**Close this topic. Build the artifact below from memory. Return to the text only after your first attempt is complete.**

| Step | Action | Output |
|---|---|---|
| 1 | Inventory deprecations | List |
| 2 | Read the guide, list breaking changes | Notes |
| 3 | Stage 1 bump and check | Commit |
| 4 | Stage 2 fix and check | Commit |

**A passing artifact looks like this:**

| Stage | Check |
|---|---|
| bump 4.2 to 5.0 | tests green |

**A failing artifact (a realistic near-miss):**

| Element | What is wrong |
|---|---|
| Jump 3 majors | **Big-bang bump** |

**The verdict.** The artifact passes only if each stage is a separate green commit and each fix cites a changelog entry.

## CLOSING REFRAME

This is the craft of upgrades: **document-driven, staged, lockfile-reviewed.** The engineer who understands this does not ask "what version should we be on?" — they ask "which single step is next, and what proves it?"
