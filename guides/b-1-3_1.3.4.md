## 1.3.4.1 — WHAT TRUST IS

**Framing.** In an interactive session Claude Code shows the workspace trust dialog when you start in a folder you have not trusted. Until you accept, some content the repository supplies, such as project allow rules and marketplaces from `.claude/settings.json`, is held back [Claude Code docs, Security and Glossary, 2026].

| Fact | Detail |
|---|---|
| Scope | Acceptance saved per project directory |
| Home directory | Trust held for the current session only, not written to disk; prompt returns each launch |
| MCP servers | Servers in `.mcp.json` have their own approval prompt |
| Non-interactive `-p` | Shows neither prompt |

[Claude Code docs, Security, 2026]

The failure mode: **Reflexive trust.** You accept every folder without reading, including a fresh clone whose `.claude/settings.json` registers a hook.

The fix: Inspect `.claude/` and CLAUDE.md in unfamiliar repos before trusting, or use a disposable environment.

Cross-references: permissions are Module 1.2.3; the security model is Module 11.1.

**If you remember one thing:** trust means honouring someone else's configuration.

## 1.3.4.2 — INSPECTING A REPO BEFORE YOU TRUST IT

**Framing.** Treat the repo as data until you vouch for it. The files that matter are the ones Claude Code reads.

```bash
git clone <url> /tmp/inspect && cd /tmp/inspect
ls -la .claude CLAUDE.md AGENTS.md .mcp.json 2>/dev/null
cat .claude/settings.json 2>/dev/null          # hooks, permissions, marketplaces
cat .mcp.json 2>/dev/null                      # servers it would start
```

| Look for | Why |
|---|---|
| `hooks` in settings | They run shell commands |
| `permissions.allow` entries | Pre-approved actions |
| Marketplaces and plugins | Third-party code |
| `.mcp.json` servers | Processes and network access |

The failure mode: **Unread-config trust.** You trust a repo whose settings define hooks or broad allow rules you never read.

The fix: Read `.claude/settings.json` and `.mcp.json` before accepting, and decline if anything is unexplained.

Cross-references: hooks are Module 1.2.6; MCP is Module 5.5; plugins are Module 5.6.

**If you remember one thing:** read the config before you vouch for it.

## 1.3.4.3 — HOME DIRECTORY AND THE BOUNDARY

**Framing.** Starting in your home directory means trust is not persisted, there is no setting to persist it, and the working-directory boundary covers all of home. Start from a project subdirectory instead [Claude Code docs, Security, 2026].

| Start in | Trust | Boundary |
|---|---|---|
| `~/projects/app` | Saved per directory | Project only |
| `~` | Session only | Everything in home |

The failure mode: **Home-directory launch.** You start in home out of habit, the prompt reappears every time, and the boundary is far wider than the task needs.

The fix: cd into the project before running `claude`.

Cross-references: boundaries are Module 1.2.3.

**If you remember one thing:** cd first, then claude.

## 1.3.4.4 — SCRIPTED RUNS: NO DIALOG

**Framing.** Non-interactive `-p` sessions show neither the trust nor the MCP prompt, and the docs list what a repository's files can run there [Claude Code docs, Security, 2026]. In CI the protection must come from flags, managed settings and isolation, not a dialog.

| Control | Use |
|---|---|
| `--bare` | Start without hooks, skills, plugins, MCP, auto memory or CLAUDE.md; consistent CI runs [Claude Code docs, Glossary, 2026] |
| Explicit allowed tools | Limit what `-p` may use |
| Disposable environment | Containers for untrusted checkouts |
| No broad permissions | Never combine `-p` with bypass on unknown code |

The failure mode: **Headless blind spot.** You assume the dialog protects scripted runs and run `-p` against an untrusted checkout with broad permissions.

The fix: Control scripted runs with explicit flags, managed settings, `--bare` and isolated environments.

Cross-references: headless mode is Module 6.8; CI is Module 7.8; sandboxing is Module 4.4.

**If you remember one thing:** scripts get no dialog; add your own guard.

## CLOSING REFRAME

This is the craft of trust: **vouch for configuration you have read, and add your own guards where there is no dialog.** The engineer who understands this does not ask "can I click accept?" — they ask "what would this repo run if I did?"
