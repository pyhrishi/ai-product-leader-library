# MODULE 1.2 — HOW CLAUDE CODE WORKS: THE AGENTIC LOOP: THE COMPLETE CRAFT

## THE THESIS OF THIS MODULE

**Claude Code is one loop with a fixed set of places where outside code and rules can intervene, and every feature you will learn later is a plug that fits one of those places.**

**Prove-it, in one sentence:** draw the loop from memory and mark exactly where permissions, hooks and compaction act.

**The single most important discipline: when something misbehaves, locate it in the loop first, then pick the tool.** A permission prompt, a hook, a stale context and a wrong model are four different problems that look identical from the outside ("Claude did the wrong thing").

**The counterintuitive claim you will learn to defend:** the model is the least controllable part of the system. Everything you can control sits in the harness: what enters the context, which tools are allowed, which hooks fire. A deterministic hook beats a sentence in CLAUDE.md for anything that must happen every time [Claude Code docs, 2026].

**THE TIME BUDGET.** Reading time: ~30 minutes. Prove-it time: ~3 hours. 3 hours is 180 minutes, six times the reading time.

## 1.2.1 — THE LOOP

**Framing.** Every task runs through the same cycle: **gather context, take action, verify results, repeat until done or interrupted** [Claude Code docs, Glossary, 2026]. Each tool use returns information that feeds the next step. A *turn* is one complete response, from your message to Claude finishing, with any number of tool calls between; a session is many turns [Claude Code docs, Glossary, 2026].

```
 you ──prompt──► ┌─────────────────────────── ONE TURN ───────────────────────────┐
                 │ UserPromptSubmit hook                                          │
                 │        │                                                       │
                 │        ▼                                                       │
                 │  MODEL decides ──► tool call ──► PreToolUse hook               │
                 │        ▲                              │                        │
                 │        │                    permission check (mode + rules)    │
                 │        │                              │                        │
                 │        │                         tool executes                 │
                 │        │                              │                        │
                 │        └── result enters context ◄── PostToolUse hook          │
                 │                                                                │
                 │  (context near limit ──► PreCompact ► summarise ► PostCompact) │
                 │                                                                │
                 │  model stops talking ──► Stop hook ──► turn ends               │
                 └────────────────────────────────────────────────────────────────┘
```

Memorise this picture. It is the prove-it, and it is also the debugging map.

**Three phases blend.** A question may need only context gathering. A bug fix cycles through gather, act and verify several times. You can interrupt at any point: `Esc` stops, typing and pressing `Enter` steers [Claude Code docs, How Claude Code works, 2026].

**Why the loop matters more than the model.** The Agent SDK and `claude -p` run this same loop with no human; the glossary names the verification loop as the prerequisite for `/goal`, unattended runs and dynamic workflows, because "without one, the only thing deciding the agent is finished is the agent itself" [Claude Code docs, Glossary, 2026].

The failure mode: **Loop-blind debugging.** You blame "the model" for a behaviour that was a permission denial, a hook, or stale context, and you rewrite the prompt for a problem the prompt did not cause.

The fix: place the symptom on the diagram. Did a tool call get blocked (permission or PreToolUse hook)? Did it run and return something unexpected (tool result)? Did Claude stop early (no check, Stop hook)? Then fix that layer.

Cross-references: the explore, plan, implement, commit pattern is Module 2.1; verification is Module 2.3.

**If you remember one thing:** every misbehaviour has an address in the loop, so find the address before you change anything.

## 1.2.2 — BUILT-IN TOOLS

**Framing.** Tools are how the loop touches the world. The tool names are **the exact strings you use in permission rules, subagent tool lists and hook matchers** [Claude Code docs, Tools reference, 2026], so knowing them is not trivia, it is the vocabulary of every control surface later in the book.

| Group | Tools (examples) | Prompts in Manual mode? |
|---|---|---|
| Read and search | Read, Grep, Glob, LSP | No, for paths inside the working directory |
| Edit | Edit, Write, NotebookEdit | Yes |
| Execute | Bash (PowerShell on Windows), Monitor | Yes; a built-in set of read-only commands runs without prompting |
| Web | WebFetch, WebSearch | Yes |
| Orchestrate | Agent (subagents), task tools, ask-user | Varies |
| MCP | mcp__server__tool, ToolSearch, ListMcpResourcesTool | Follow the permission system |

[Claude Code docs, Tools reference, 2026; per-tool rows beyond those quoted in the page excerpts are summarised from the page's table and should be re-checked against it]

**Rule syntax ties tools to controls.** The docs list formats such as `Bash(npm run *)` (command pattern), `Read(~/secrets/**)` (path pattern, applies to Read, Grep, Glob and LSP), `Edit(/src/**)` (applies to Edit, Write and NotebookEdit), `Agent(Explore)` (subagent type) and `WebFetch(domain:example.com)` [Claude Code docs, Tools reference, 2026].

Two interactions surprise people:

1. **A Read deny also blocks Edit and Write on that path**, including creating a new file there, because both change content Claude must be able to read back [Claude Code docs, Tools, 2026].
2. **An Edit allow rule also grants read access to the same path**, so you do not need a matching Read rule [Claude Code docs, Tools reference, 2026].

**Bash behaviour.** Each Bash command runs in a separate process. A `cd` carries into later commands only while Claude stays inside the project or an added directory; outside, Claude Code resets to the project directory and appends "Shell cwd was reset" to the result. Subagent sessions never carry directory changes [Claude Code docs, Tools reference, 2026].

**Code intelligence is optional.** The LSP tool (go to definition, find references, type errors) appears when a code-intelligence plugin is installed [Claude Code docs, 2026]. Without it, Claude falls back to Grep and Read.

```bash
# See what is actually available in YOUR session, not what you assume:
/context        # live breakdown by category, including tool definitions
/mcp            # connected MCP servers and their tools
```

The failure mode: **Tool-name guessing.** You write a permission rule or hook matcher with a plausible but wrong tool name (`Shell(...)`, `FileEdit(...)`), the rule silently matches nothing, and you believe a control exists that does not.

The fix: copy tool names from the Tools reference, then test the rule by triggering the action once and watching whether the prompt or block appears.

The failure mode: **Deny-rule gap.** You deny `Bash(cat .env)` and assume the secret is protected, while Read, Grep or a different shell command can reach the same file.

The fix: write the deny at the path level with `Read(...)` (which also blocks Edit and Write on it) and add sandboxing for Bash; do not rely on blocking one command spelling.

Cross-references: permission rule design is Module 4.2; sandboxing is Module 4.4; subagent tool lists are Module 5.3; code intelligence plugins are Module 5.8.

**If you remember one thing:** tool names are the keys to permissions, hooks and subagents, so use the exact strings and test every rule once.

## 1.2.3 — TOOL PERMISSIONS

**Framing.** **Every tool call passes through the permission system before it runs** [syllabus Module 1.2.3; mechanism detail in Part 4]. Two layers act together: the *permission mode* sets the baseline, and *permission rules* refine it.

| Layer | What it is | Set by |
|---|---|---|
| Permission mode | Baseline approval behaviour for the session: `default` (labelled Manual), `acceptEdits`, `plan`, `auto`, `dontAsk`, `bypassPermissions` | Shift+Tab, `/plan`, settings, flags |
| Permission rule | Allow, ask or deny entry matched on tool name and argument pattern | Settings files |
| Sandbox | OS-level filesystem and network isolation for Bash, separate from rules | Sandbox settings |

[Claude Code docs, Glossary, 2026]

**Evaluation order.** Rules are evaluated **deny, then ask, then allow, with first match winning** [Claude Code docs, Glossary, 2026]. A deny always beats an allow written elsewhere.

**Auto mode** uses a separate classifier model that reviews actions instead of you; it blocks scope escalation, untrusted infrastructure and prompt injection, and tool results are stripped from what the classifier sees so hostile content in a file cannot manipulate it directly. It still asks before actions your explicit ask rules match [Claude Code docs, Glossary, 2026]. On Pro, Max and Team it is the built-in starting mode for interactive terminal and VS Code sessions [Claude Code docs, Glossary, 2026].

**Where permissions sit relative to hooks.** The order inside one tool call is: PreToolUse hook, then permission check, then execution, then PostToolUse. A PreToolUse hook can block. A hook that exits with code 2 blocks even if its JSON said "allow" [Claude Code docs, Hooks, 2026]. That makes hooks the right place for policy that must hold under every mode.

The failure mode: **Mode-as-policy confusion.** You treat Accept edits or Auto as a security boundary, then a Bash command touches something you assumed was protected.

The fix: use modes for convenience and rules plus sandboxing for boundaries; if a thing must never happen, make it a deny rule or a blocking hook.

Cross-references: permission modes are Module 4.3; rules are Module 4.2; security posture is Part 11, starting at Module 11.1.

**If you remember one thing:** the mode sets the mood, the rules set the law, and the sandbox is the wall.

## 1.2.4 — THE SYSTEM PROMPT AND TOOL RESULTS

**Framing.** The model has no memory between turns except what is in its context window. **The context window holds everything Claude knows about your session: your instructions, the files it reads, its own responses, and content that never appears in your terminal** [Claude Code docs, Context window, 2026].

```
 CONTEXT WINDOW  (200,000 tokens on most models; 1,000,000 on Sonnet 5, Opus 4.6+, Sonnet 4.6, Fable 5 [secondary: dev.to, 2026; confirm in /context])
 ┌─ loads before you type ──────────────────────────────────────────┐
 │ system prompt (~4,200 tokens in the docs' simulation)            │
 │ tool definitions (MCP schemas deferred by default)               │
 │ skill descriptions (names + descriptions only)                   │
 │ ~/.claude/CLAUDE.md, ./CLAUDE.md, auto memory (first 200 lines / 25 KB of MEMORY.md) │
 ├─ grows as you work ──────────────────────────────────────────────┤
 │ your prompts · file reads · command output · Claude's replies    │
 │ hook output (additionalContext) · path-scoped rules on first match │
 └──────────────────────────────────────────────────────────────────┘
```

[Claude Code docs, Context window and Glossary, 2026; the ~4,200 figure is from the docs' interactive simulation, which states it uses representative numbers; run `/context` for yours]

**Why long outputs matter.** Every tool result stays in context for the rest of the session unless compaction clears it. A command that prints 5,000 lines costs the same tokens as reading a large file, and it displaces earlier instructions. Hook output enters context without truncation, so the docs advise keeping it concise [Claude Code docs, Context window, 2026].

**MCP tool definitions are deferred.** Only tool names and server instructions load at startup; full schemas load on demand through tool search. `ENABLE_TOOL_SEARCH=auto` loads schemas upfront when they fit within 10% of the context window [Claude Code docs, Context window, 2026].

**What survives compaction.** When the window nears its limit Claude Code compacts: older tool outputs are cleared first, then the conversation is summarised [Claude Code docs, Glossary, 2026]. Afterward:

| Mechanism | After compaction |
|---|---|
| Project-root CLAUDE.md and auto memory | Re-read fresh from disk |
| Instructions given only in conversation | May be lost |
| Path-scoped rules and nested CLAUDE.md | Summarised with the history; reload when a matching file is read again |
| Skill listing | Not re-injected; only skills you actually invoked are preserved |
| Recently touched files | Up to five of the most recently modified are re-read |

[Claude Code docs, Context window, 2026]

You can steer it: `/compact focus on the auth bug fix` tells the summary what to keep [Claude Code docs, Context window, 2026].

The failure mode: **Chat-only rule.** You state an important rule in conversation ("never touch the migrations folder"), compaction summarises it away, and Claude later edits migrations.

The fix: put durable rules in project-root CLAUDE.md, or enforce them with a hook or deny rule, and verify with `/memory` that the file loaded.

The failure mode: **Output flood.** A test run or log dump pours thousands of lines into context, pushing out earlier instructions and degrading later answers.

The fix: pipe to a file and read the tail (`npm test 2>&1 | tail -50`), run the noisy work in a subagent, or add a preprocessing hook that trims output.

Cross-references: the context window in depth is Module 3.1; CLAUDE.md is Module 3.2; rules and auto memory are Module 3.3; prompt caching is Module 3.4.

**If you remember one thing:** if an instruction lives only in the conversation, assume compaction will eventually lose it.

## 1.2.5 — SUBAGENTS AND BACKGROUND WORK

**Framing.** A subagent is **a specialised assistant that runs in its own context window with a custom system prompt, specific tool access and independent permissions, does a delegated task and returns a summary** [Claude Code docs, Subagents, 2026]. The point is context hygiene: verbose search results, logs and file contents stay out of your main window.

| Fact | Detail |
|---|---|
| Starts fresh | It does not see your conversation or files Claude already read; Claude writes a delegation message |
| Initial context | System prompt, the task message, CLAUDE.md files and a git status snapshot (both skipped for Explore and Plan) |
| Exception | A *fork* inherits the parent conversation |
| Built-ins | Explore (read-only search), Plan (read-only research in plan mode), general-purpose, plus helpers such as statusline-setup |
| Background | Subagents Claude spawns run in the background by default; permission prompts surface in your main session |
| Limits | Nesting up to 3 layers by default; 20 concurrent by default; a startup warning when non-built-in descriptions exceed 15,000 tokens |
| Cost | Subagent requests count toward the same usage limits as the main conversation |

[Claude Code docs, Subagents, 2026]

```markdown
---
name: code-improver
description: Scans files and suggests improvements. Use after writing or modifying code.
tools: Read, Grep, Glob
model: sonnet
---
You are a code improvement specialist. Explain each problem, show the current code, give a fix.
```

**Subagent versus agent team.** A subagent stays inside one session and reports only to its parent. Agent teams are separate sessions with their own context, a shared task list and peer messaging; they are experimental and disabled by default [Claude Code docs, Glossary, 2026].

**Trade-off.** A subagent saves your main context but not your usage budget. Five subagents each reading 20 files can spend more total tokens than one session reading 20 files once.

The failure mode: **Subagent sprawl.** You spawn many subagents for small tasks, each rebuilding context from scratch, and usage climbs while the results are no better than one focused read.

The fix: delegate only work that is large, read-heavy and summarisable (broad searches, log analysis), and keep small edits in the main session.

The failure mode: **Context-blind delegation.** You expect a subagent to know what you discussed earlier, but it starts fresh and returns a plausible answer to a question that was missing the key constraint.

The fix: put every constraint, file path and success criterion in the delegation message, or use a fork when the full conversation is needed.

Cross-references: subagent design is Module 5.3; parallel approaches are Module 6.1; agent teams are Module 6.4; background sessions are Module 6.3.

**If you remember one thing:** a subagent is a clean desk, so give it everything it needs on the first page.

## 1.2.6 — HOOKS IN THE LOOP

**Framing.** A hook is **a user-defined handler that runs automatically at a specific lifecycle point, and hooks are deterministic: they fire at fixed points rather than at the model's discretion** [Claude Code docs, Glossary, 2026]. CLAUDE.md is advisory; a hook is a guarantee.

A hook has three levels: the *event*, a *matcher* that filters when it fires, and a *handler* that runs [Claude Code docs, Glossary, 2026].

| Where in the loop | Events (selection from the docs' list of 33 events) |
|---|---|
| Session | SessionStart, SessionEnd, Setup |
| Prompt | UserPromptSubmit, UserPromptExpansion |
| Tool call | PreToolUse (can block), PermissionRequest, PermissionDenied, PostToolUse, PostToolUseFailure, PostToolBatch |
| Subagents and tasks | SubagentStart, SubagentStop, TaskCreated, TaskCompleted |
| Turn end | Stop, StopFailure |
| Context | PreCompact, PostCompact, InstructionsLoaded |
| Environment | ConfigChange, CwdChanged, FileChanged, WorktreeCreate, WorktreeRemove |

[Claude Code docs, Hooks, 2026; the page was truncated at 100,000 of 282,608 characters, so per-event input schemas are not reproduced]

**Handler types:** `command` (shell, input on stdin), `http` (POST JSON), `mcp_tool`, `prompt` (single-turn model decision) and `agent` (a subagent that can use tools; experimental) [Claude Code docs, Hooks, 2026].

**Exit codes decide enforcement:**

| Exit code | Meaning |
|---|---|
| 0 | Success; JSON on stdout is applied |
| 2 | Blocking error; on events that can block, the action stops and stderr is the reason |
| Any other | Non-blocking: the action proceeds and a notice appears |

[Claude Code docs, Hooks, 2026]

**The trap:** exit 1 is not a block. Only `exit 2` enforces. Exit 2 also has no effect on some events such as PostToolUse, where the tool already ran; use the JSON `decision` there instead [Claude Code docs, Hooks, 2026]. `onFailure: "block"` (v2.1.295+) makes a failed, timed-out or invalid hook block the action [Claude Code docs, Hooks, 2026].

**Numbers to know:** default timeouts are 600 s for command, http and mcp_tool, 30 s for prompt and 60 s for agent; SessionEnd shares a 1.5 s budget by default; more than 12 prompt or agent hooks on one event run 12 at a time; injected text such as `additionalContext` is capped at 10,000 characters [Claude Code docs, Hooks, 2026].

```bash
#!/usr/bin/env bash
# PreToolUse hook: block edits to migrations. Input JSON arrives on stdin.
path=$(jq -r '.tool_input.file_path // empty')
if [[ "$path" == *"/migrations/"* ]]; then
  echo "Migrations are frozen. Create a new migration instead." >&2
  exit 2          # exit 2 = block; exit 1 would only warn
fi
exit 0
```

The failure mode: **Exit-1 illusion.** Your policy hook exits 1 on violation, the action proceeds anyway, and you believe the rule is enforced.

The fix: use `exit 2` (or a JSON block decision) for enforcement, add `onFailure: "block"` where supported, and test by deliberately violating the rule once.

The failure mode: **Advisory-for-mandatory.** A rule that must hold every time lives only in CLAUDE.md, so it holds most of the time.

The fix: convert any rule you cannot tolerate breaking into a hook or deny rule, and keep CLAUDE.md for guidance.

Cross-references: hooks in depth are Module 5.4; settings that register hooks are Module 4.1; choosing between extension types is Module 5.1.

**If you remember one thing:** if it must happen every time, it belongs in a hook, and the hook must exit 2.

## 1.2.7 — SESSIONS AS TRANSCRIPTS

**Framing.** **A session is a conversation tied to your current directory with its own independent context window** and its transcript is stored under `~/.claude/projects/` [Claude Code docs, Glossary, 2026]. That makes conversations durable objects you can resume, branch and audit.

| Action | Command | Effect |
|---|---|---|
| Resume latest | `claude -c` | Continue the most recent session |
| Resume by pick | `/resume` | Choose a stored session |
| Fork | `--fork-session` or `/branch` | New session ID, history preserved |
| Fresh start | `/clear` | New session; the old one stays stored and resumable |
| Rewind | `Esc Esc` or `/rewind` | Restore code, conversation or both to a checkpoint |
| One-shot | `claude -p` | Non-interactive; still saved unless `--no-session-persistence` |

[Claude Code docs, Glossary, 2026]

**Checkpoints** snapshot files before every edit and are saved with the conversation, so a resumed session can still rewind. They are separate from git and do not track changes made through Bash [Claude Code docs, Glossary, 2026].

**Privacy consequence.** Transcripts are plaintext JSONL on disk (from earlier research on the sessions page [Claude Code docs, 2026]). A secret that was pasted or printed in a session sits in that file.

The failure mode: **Transcript leak.** A token or customer record appears in a prompt or tool output and persists in plaintext under `~/.claude/projects/`, then gets swept up in a backup or shared machine image.

The fix: keep secrets out of prompts and commands, use deny rules on secret paths, and delete or exclude transcripts for sensitive work.

The failure mode: **Zombie session.** You resume a three-day-old session with a cluttered context and wonder why quality dropped.

The fix: for a new task, `/clear` or start fresh and re-supply only what matters; resume only when the prior context is the asset.

Cross-references: session management is Module 2.4; checkpoints are Module 2.5; headless mode is Module 6.8.

**If you remember one thing:** a session is a file, so treat it like one: resumable, branchable and sensitive.

## 1.2.8 — THE MODEL LAYER

**Framing.** The model is a setting, not an identity. **Different models and effort levels trade speed, cost and depth** (see Module 4.6). Effort is an adaptive-reasoning control: higher effort means more thinking tokens and deeper reasoning, lower is faster and cheaper; it is supported on Fable models, Opus 4.6 and later, and Sonnet 4.6 and later [Claude Code docs, Glossary, 2026].

| Lever | Raises | Costs |
|---|---|---|
| Stronger model | Depth on hard reasoning | Usage, latency |
| Higher effort | Thoroughness | Thinking tokens |
| Longer context | Capacity | Dilution as it fills; compaction risk |
| More subagents | Parallel search | Total tokens |

Switch with `/model` or `claude --model <name>`. Subagents can use a different model through their `model:` field, and `CLAUDE_CODE_SUBAGENT_MODEL` sets the default for general-purpose subagents [Claude Code docs, Subagents, 2026].

The failure mode: **Max-everything default.** You run the strongest model at the highest effort for every task, hit plan limits early, and the extra depth buys nothing on routine edits.

The fix: default to a mid-tier model and moderate effort, escalate for architecture and hard debugging, and de-escalate for mechanical changes.

Cross-references: model, effort and speed settings are Module 4.6; usage limits are Module 1.4.

**If you remember one thing:** match model and effort to the difficulty of the step, not the importance of the project.

## CLOSING REFRAME

This is the craft of the agentic loop: **one cycle of gather, act and verify, with fixed places where rules, hooks and compaction can intervene, and every control you will ever add fits one of those places.** The engineer who understands this does not ask "why did Claude do that?" — they ask "where in the loop did that happen, and which layer owns the fix?"
