## 9.3.8.1 — TIMELINE FROM EVIDENCE

**Framing.** Feed Claude the raw sources: alerts, logs, chat export and the git history. Piping command output into `claude -p` is a documented pattern, for example summarising recent commits [Claude Code docs, Common workflows, 2026].

```bash
git log --since="2026-11-10 13:00" --until="2026-11-10 18:00" --oneline \
  | claude -p "list these as timeline entries with timestamps"
```

| Timeline field | Source |
|---|---|
| Detected | Alert timestamp |
| Mitigated | Deploy or rollback record |
| Resolved | Error rate back to baseline |
| Actions | Chat export lines |

The failure mode: **Invented timeline.** Claude fills gaps with plausible times and events that are not in the sources.

The fix: Require a source for each timeline row and 'unknown' where there is none.

Cross-references: evidence is Module 9.3.2.

**If you remember one thing:** no source, no row.

---

## 9.3.8.2 — POST-MORTEM DRAFT

**Framing.** Ask for a blameless structure: impact, timeline, root cause, contributing factors, what went well, what did not, action items. Judge each against evidence; the causal chain from Module 9.3.5 is the core.

| Section | Check |
|---|---|
| Impact | Numbers match monitoring |
| Root cause | Has a regression test or guard |
| Contributing factors | Process, tooling, alerts |
| Action items | Owner, due date, ticket |

The failure mode: **Blame drift.** The draft names individuals as the cause and hides systemic factors.

The fix: Prompt for blameless wording and review for people-as-cause language before sharing.

Cross-references: root cause is Module 9.3.5.

**If you remember one thing:** systems fail, not people.

---

## 9.3.8.3 — FOLLOW-UP TICKETS

**Framing.** Turn action items into tickets through a connected tracker only with human approval. Without a tracker, produce the text and file it yourself. Connected servers carry trust risks [Claude Code docs, MCP, 2026].

| Ticket field | Rule |
|---|---|
| Title | Verb plus object |
| Acceptance | A check that can pass or fail |
| Owner | A named human |
| Link | Post-mortem section |

The failure mode: **Orphan action item.** Actions have no owner or check, so nothing happens.

The fix: Reject any item lacking an owner and a pass-or-fail acceptance line.

Cross-references: learning loop is Module 9.12.9.

**If you remember one thing:** an action without an owner is a wish.

## THE PROVE-IT SECTION

**Deliverable.** An incident bundle: timeline with sources, post-mortem draft and three tickets with owners and checks.

**Close this topic. Build the artifact below from memory. Return to the text only after your first attempt is complete.**

| Step | Action | Output |
|---|---|---|
| 1 | Collect sources | Folder |
| 2 | Generate timeline with citations | Timeline |
| 3 | Draft post-mortem | Draft |
| 4 | Review for blame and invention | Review notes |
| 5 | Write tickets | 3 tickets |

**A passing artifact looks like this:**

| Item | Evidence |
|---|---|
| Timeline rows | 12, all sourced |
| Tickets | 3, each with owner |

**A failing artifact (a realistic near-miss):**

| Element | What is wrong |
|---|---|
| Unsourced rows | **Invented timeline** |
| No owners | **Orphan action item** |

**The verdict.** The artifact passes only if every timeline row has a source and every ticket has an owner and an acceptance check.
