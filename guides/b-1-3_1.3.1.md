## THE THESIS OF THIS TOPIC

**A good install is one binary, one install path, a known version and a diagnostic that passes.**

**Prove-it, in one sentence:** install on a clean account, run the version and doctor checks, and show that exactly one copy of claude is on the PATH.

**The single most important discipline: pick one install method and prove it with the version and doctor commands.**

**The counterintuitive claim you will learn to defend:** more install options is not more flexibility; mixed methods produce two binaries at different versions and behaviour that depends on which shell you opened.

## 1.3.1.1 — THE INSTALL PATHS

**Framing.** The recommended route is the native installer. Alternatives exist for Homebrew, WinGet and Linux package managers (apt, dnf, apk); native installs auto-update in the background while Homebrew and WinGet do not [Claude Code docs, Overview and Setup, 2026]. Most surfaces need a Claude subscription or Console account; the terminal CLI, VS Code and JetBrains also support third-party providers [Claude Code docs, Overview, 2026].

| Platform | Documented route | Updates |
|---|---|---|
| macOS, Linux, WSL | `curl -fsSL https://claude.ai/install.sh \| bash` | Auto |
| Windows (PowerShell) | `irm https://claude.ai/install.ps1 \| iex` | Auto |
| macOS | `brew install --cask claude-code` | Manual |
| Windows | `winget install Anthropic.ClaudeCode` | Manual |
| Debian, Fedora, RHEL, Alpine | apt, dnf or apk | Per package manager |

[Claude Code docs, Overview and Setup, 2026; read the exact current line on the Setup page before running]

The native installer places the binary at `~/.local/bin/claude` on macOS and Linux and `%USERPROFILE%\.local\bin\claude.exe` on Windows [Claude Code docs, Troubleshoot install, 2026].

The failure mode: **Copy-pasted installer.** You paste an install one-liner from a blog post or old note and run a script you did not read.

The fix: Take the command only from the official Setup page, read what it does, and verify the version afterward.

Cross-references: sign-in is Module 1.3.2; fleet rollout is in Part 11.

**If you remember one thing:** official page, one method, verified.

## 1.3.1.2 — PLATFORM SPECIFICS

**Framing.** Windows has two routes: native (needs Git Bash, with a PowerShell tool) or WSL, where you install and launch `claude` inside the WSL terminal rather than PowerShell or CMD [Claude Code docs, Setup, 2026]. Alpine and other musl distributions need `bash` and `curl` installed first, and Claude Code requires `bash` or `zsh`; set `USE_BUILTIN_RIPGREP=0` there [Claude Code docs, Setup, 2026].

| Platform | Gotcha | Fix |
|---|---|---|
| Native Windows | Git Bash not found | Set `CLAUDE_CODE_GIT_BASH_PATH` in settings `env` |
| WSL | Installing from PowerShell | Install inside the WSL terminal |
| Alpine | No bash or curl by default | Install them, set `USE_BUILTIN_RIPGREP=0` |
| IDE extension only | No `claude` on PATH | Run the standalone installer |

```json
{ "env": { "CLAUDE_CODE_GIT_BASH_PATH": "C:\\Program Files\\Git\\bin\\bash.exe" } }
```

ripgrep is usually bundled; if search fails see the search troubleshooting section [Claude Code docs, Setup, 2026]. The VS Code extension carries a private CLI copy and does not add `claude` to PATH [Claude Code docs, Troubleshoot install, 2026].

The failure mode: **Wrong-environment install.** You install in PowerShell and then launch from WSL (or the reverse) and cannot find the binary.

The fix: Install and launch in the same environment, and verify with `claude --version` there.

Cross-references: IDE integrations are Module 7.3; troubleshooting is Module 1.3.7.

**If you remember one thing:** install where you will run it.

## 1.3.1.3 — VERIFY, ALWAYS

**Framing.** A working installation prints a version number such as 2.1.211 (Claude Code); for a deeper check run `claude doctor` [Claude Code docs, Setup, 2026].

```bash
claude --version     # e.g. 2.1.211 (Claude Code)
claude doctor        # detailed installation and configuration check
which -a claude      # list EVERY claude on PATH (Windows: where claude)
```

| Output | Meaning |
|---|---|
| Version prints | Binary and PATH fine |
| `command not found` | PATH problem, see 1.3.7 |
| Two paths from `which -a` | Install-path drift |

The failure mode: **Install-path drift.** You install by one method, later by another, and end up with two binaries at different versions.

The fix: Pick one method, list all copies with `which -a claude`, remove extras and confirm the version.

Cross-references: updating is Module 1.3.5; troubleshooting is Module 1.3.7.

**If you remember one thing:** `which -a claude` should list exactly one.

## 1.3.1.4 — REMOVING AND PINNING

**Framing.** Version management is part of install: the native installer accepts a version number or a release channel (latest or stable); `DISABLE_UPDATES` blocks all update paths including manual ones [Claude Code docs, Setup, 2026].

| Goal | Mechanism |
|---|---|
| Stay on a stable cadence | `stable` channel |
| Freeze a version | Install a specific version number |
| Block updates entirely | `DISABLE_UPDATES` |
| Uninstall | Per-method (remove native binary, `brew uninstall`, winget uninstall); see Setup |

The failure mode: **Unpinned fleet.** Every developer auto-updates on their own schedule and behaviour differs across the team.

The fix: Pin a version or use the stable channel for fleets and record the version in bug reports.

Cross-references: enterprise rollout is in Part 11; settings are Module 4.1.

**If you remember one thing:** a team needs a version policy.

| Check | Result |
