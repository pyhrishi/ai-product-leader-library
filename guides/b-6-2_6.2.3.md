# MODULE 6.2.3 — WHAT WORKTREES SHARE AND DO NOT SHARE WITH THE MAIN CHECKOUT: THE COMPLETE CRAFT

## THE THESIS OF THIS TOPIC

**A worktree gets its own files and branch but shares the .git directory, project-scope plugins, permission approvals and untracked project skills with the main checkout, and anything gitignored must be brought in on purpose.**

**Prove-it, in one sentence:** create a worktree, list what is present and missing, then use a .worktreeinclude to bring the missing files in.

**The single most important discipline: list the gitignored files a project needs and put them in .worktreeinclude before the first worktree.**

**The counterintuitive claim you will learn to defend:** approving a Bash command with don't-ask-again inside a worktree saves the rule to the main checkout's settings, so it applies in every other worktree and survives the worktree's removal [Claude Code docs, Worktrees, 2026].

## 6.2.3.1 — WHAT IS SHARED

**Framing.** The docs list four shared things. The repository's `.git` directory: git commands in a worktree write to the shared directory, and sandboxing allows those writes so `git commit` works with the sandbox on. Project-scope plugins: they load in worktrees of the same repository (v2.1.200 or later). Permission approvals: a don't-ask-again for a Bash command saves to the main checkout's `.claude/settings.local.json`. Untracked skills, agents and commands: read through from the main checkout when the worktree has no `.claude/skills` of its own [Claude Code docs, Worktrees, 2026].

| Shared | Detail | Version noted |
|---|---|---|
| `.git` directory | Commits and refs written to the shared repo | none |
| Project-scope plugins | No reinstall per worktree | v2.1.200+ |
| Permission approvals | Saved to main checkout's `.claude/settings.local.json` | v2.1.211+ (earlier saved inside the worktree) |
| Untracked skills | Main checkout's project skills load if the worktree has no `.claude/skills` | v2.1.277+ for skills |

The failure mode: **Approval-leak surprise.** You grant a broad Bash approval for a quick experiment in a throwaway worktree and later find it active in your main checkout and every other worktree.

The fix: Approve narrowly, review `.claude/settings.local.json` after experiments, and use a one-time yes instead of don't-ask-again for risky commands.

Cross-references: permission rules are Module 4.2; skills are Module 5.2.

**If you remember one thing:** a worktree isolates files, not settings approvals.

## 6.2.3.2 — WHAT IS NOT SHARED

**Framing.** A worktree is a fresh checkout, so gitignored files such as `.env` and `.env.local` are absent, dependencies are not installed, and the working directory contents are its own. Git LFS content set up with `git lfs install --local` arrives as pointer files because Claude Code skips the repository's own filter drivers when creating a worktree; run `git lfs pull` inside it [Claude Code docs, Worktrees, 2026].

| Missing in a new worktree | Remedy |
|---|---|
| `.env` and other gitignored files | `.worktreeinclude` |
| Installed dependencies | Ask Claude to install, or keep the install command in `CLAUDE.md` |
| LFS content (with `--local` install) | `git lfs pull` in the worktree |
| Large untracked directories | `worktree.symlinkDirectories` setting (per the best-practices page) |

The failure mode: **Empty-checkout run.** A fresh worktree lacks `.env` and `node_modules`, tests fail on missing config, and you debug code that is fine.

The fix: Bring needed files via `.worktreeinclude` and install dependencies as the first step in every new worktree.

Cross-references: environment setup is Module 4.5; context setup is Module 3.2.

**If you remember one thing:** assume nothing gitignored arrived.

## 6.2.3.3 — .WORKTREEINCLUDE

**Framing.** Add a `.worktreeinclude` file to the project root, using `.gitignore` syntax. Only files that match a pattern and are also gitignored are copied, so tracked files are never duplicated. It applies to `--worktree`, subagent worktrees and desktop parallel sessions [Claude Code docs, Worktrees, 2026].

```text .worktreeinclude
.env
.env.local
config/secrets.json
```
[quoted from Claude Code docs, Worktrees, 2026]

For `**/` patterns inside a wholly ignored directory the rule is narrow: Claude Code copies matches only when that directory matches the pattern or when the first name after `**/` is one of the names in the directory's path. `**/.claude/skills/*.md` works; use `vendor/**/config.json` rather than `**/config.json` [Claude Code docs, Worktrees, 2026]. Keep it to small files: the best-practices page notes it copies rather than links, so `node_modules` in there means a full copy per worktree.

The failure mode: **Pattern-that-matches-nothing.** You write `**/config.json` and the file inside an ignored `vendor/` directory is never copied, with no error.

The fix: Name the directory in the pattern (`vendor/**/config.json`) and verify by listing the new worktree.

Cross-references: settings are Module 4.1; secrets handling is Module 11.4.

**If you remember one thing:** list the files, check they landed.

## 6.2.3.4 — SECRETS AND HOOKS

**Framing.** Copying `.env` into every worktree spreads secrets onto more disk locations, so keep the list short and the worktrees disposable. Hooks need care too: after Claude enters a worktree, `${CLAUDE_PROJECT_DIR}` still points at the project root where the session started, while the hook input's `cwd` field is the worktree root [Claude Code docs, Worktrees, 2026].

| Variable or field | Points at | Use it for |
|---|---|---|
| `${CLAUDE_PROJECT_DIR}` | Original project root (does not follow) | Locating hook scripts |
| `cwd` in hook input JSON | Worktree root; moves on `cd` | Operating on the session's files |

The failure mode: **Hook-path mixup.** A hook formats files under `${CLAUDE_PROJECT_DIR}` and silently reformats the main checkout instead of the worktree.

The fix: Read `cwd` from the hook's input JSON when the hook acts on session files.

Cross-references: hook design is Module 5.4; this variable is revisited in sub-topic 6.2.6.

**If you remember one thing:** scripts live at the root; work happens at cwd.

## CLOSING REFRAME

This is the craft of the worktree boundary: **files are yours, .git and approvals are shared, gitignored files are invited in.** The engineer who understands this does not ask "why is my config missing?" — they ask "what crossed the boundary, and what should not have?"
