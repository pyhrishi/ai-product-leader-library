# MODULE 1.2.6 — HOOKS IN THE LOOP: DETERMINISTIC CONTROL: THE COMPLETE CRAFT

## THE THESIS OF THIS TOPIC

**A hook is a user-defined handler that runs at a fixed lifecycle point, so it fires every time regardless of what the model decides, which makes it the right tool for rules that must hold.**

**Prove-it, in one sentence:** write a blocking hook, show it blocks with exit 2, and show that exit 1 does not.

**The single most important discipline: if it must happen every time, it belongs in a hook, and the hook must exit 2.**

**The counterintuitive claim you will learn to defend:** a hook that exits 1 on violation does not enforce anything; only exit 2 blocks [Claude Code docs, Hooks, 2026].

## 1.2.6.1 — EVENTS, MATCHERS, HANDLERS

**Framing.** A hook has three levels: the event (the lifecycle point), a matcher that filters when it fires, and a handler that runs. Hooks are deterministic: they fire at fixed lifecycle points rather than at the model's discretion [Claude Code docs, Glossary, 2026].

| Group | Events (of 33 listed) |
|---|---|
| Session | SessionStart, SessionEnd, Setup |
| Prompt | UserPromptSubmit, UserPromptExpansion |
| Tool call | PreToolUse (can block), PermissionRequest, PermissionDenied, PostToolUse, PostToolUseFailure, PostToolBatch |
| Subagents, tasks | SubagentStart, SubagentStop, TaskCreated, TaskCompleted, TeammateIdle |
| Turn end | Stop, StopFailure |
| Context | PreCompact, PostCompact, InstructionsLoaded |
| Environment | ConfigChange, CwdChanged, DirectoryAdded, FileChanged, WorktreeCreate, WorktreeRemove |
| Model | PreModelSwitch, PostModelSwitch |
| MCP | Elicitation, ElicitationResult |

[Claude Code docs, Hooks, 2026; the page was truncated at 100,000 of 282,608 characters, so per-event input schemas are not reproduced]

The failure mode: **Event-guessing.** You register a hook on an event that does not fire at the point you assumed, and the policy never runs.

The fix: Check the event table for exactly when it fires and test by triggering the situation once.

Cross-references: hooks in depth are Module 5.4; settings that register hooks are Module 4.1.

**If you remember one thing:** pick the event by when it fires, then test it.

## 1.2.6.2 — HANDLER TYPES AND EXIT CODES

**Framing.** Handlers can be a shell command (input on stdin), an HTTP POST, an MCP tool call, a prompt to a Claude model for a single-turn decision, or an agent that spawns a subagent to verify conditions (experimental) [Claude Code docs, Hooks, 2026].

| Exit code (command hook) | Meaning |
|---|---|
| 0 | Success; JSON on stdout is applied |
| 2 | Blocking error; action stops and stderr is the reason, even if JSON said allow |
| Any other | Non-blocking; action proceeds with a notice |

Exit 2 has no effect on some events such as PermissionRequest, PostToolUse and Notification; use the JSON `decision` object there. `onFailure: "block"` (v2.1.295+) makes a failed, timed-out or invalid hook block the action [Claude Code docs, Hooks, 2026].

```bash
#!/usr/bin/env bash
path=$(jq -r '.tool_input.file_path // empty')
if [[ "$path" == *"/migrations/"* ]]; then
  echo "Migrations are frozen. Create a new migration instead." >&2
  exit 2          # exit 2 blocks; exit 1 would only warn
fi
exit 0
```

The failure mode: **Exit-1 illusion.** Your policy hook exits 1 on violation, the action proceeds, and you believe the rule is enforced.

The fix: Use exit 2 or a JSON block decision, add onFailure block where supported, and test by violating the rule once.

Cross-references: permissions interplay is Module 1.2.3; debugging configuration is Part 12.

**If you remember one thing:** exit 2 blocks; exit 1 only warns.

## 1.2.6.3 — NUMBERS TO KNOW

**Framing.** Defaults and caps shape reliable hooks [Claude Code docs, Hooks, 2026].

| Item | Value |
|---|---|
| Default timeout, command, http, mcp_tool | 600 s |
| Default timeout, prompt | 30 s |
| Default timeout, agent | 60 s |
| UserPromptSubmit, PreModelSwitch, PostModelSwitch | 30 s for command, http, mcp_tool |
| MessageDisplay | 10 s |
| SessionEnd shared budget | 1.5 s, raisable to 60 s per hook |
| Concurrency | More than 12 prompt or agent hooks on one event run 12 at a time |
| Output cap | `additionalContext`, `systemMessage`, plain stdout: 10,000 characters each; larger output saved to a file with a 2,000-character preview |
| Skill hooks | At most 1,024 per skill source per session (v2.1.304+) |
| Duplicates | An identical handler in several settings files runs once |

The failure mode: **Slow-hook stall.** A hook with a long default timeout blocks every tool call or prompt for many seconds, and the session feels frozen.

The fix: Set a short explicit timeout, keep hooks fast and move heavy work to async or a subagent.

Cross-references: performance and costs are Module 1.4; hook design is Module 5.4.

**If you remember one thing:** short timeouts, short output.

## 1.2.6.4 — HOOKS VERSUS CLAUDE.MD AND PERMISSIONS

**Framing.** CLAUDE.md is advisory; hooks are deterministic. Permission rules are also deterministic but only decide allow, ask or deny. A PreToolUse hook runs before the permission check and can block, and an exit 2 blocks even if the JSON said allow [Claude Code docs, Hooks and Best practices, 2026].

| Need | Use |
|---|---|
| Guidance and conventions | CLAUDE.md |
| Never allow X | Deny rule |
| Run a formatter after every edit | PostToolUse hook |
| Block edits to a path with a custom message | PreToolUse hook, exit 2 |
| Stop Claude ending the turn early | Stop hook |

The failure mode: **Advisory-for-mandatory.** A rule that must hold lives only in CLAUDE.md, so it holds most of the time.

The fix: Convert must-hold rules into hooks or deny rules and keep CLAUDE.md for guidance.

Cross-references: CLAUDE.md is Module 3.2; extension choice is Module 5.1.

**If you remember one thing:** advice goes in CLAUDE.md; guarantees go in hooks.

## CLOSING REFRAME

This is the craft of hooks: **fixed points in the loop where your code decides, enforced by exit 2.** The engineer who understands this does not ask "can I tell Claude to always do X?" — they ask "which event guarantees X, and have I seen it block?"
