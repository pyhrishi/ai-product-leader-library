## THE THESIS OF THIS TOPIC

**Settings files are layered by scope, and which file you edit decides who is affected.**

**Prove-it, in one sentence:** change one key at each scope and show which wins.

## 14.4.2.1 — FILES AND AUDIENCE

**Framing.** User `~/.claude/settings.json` affects you everywhere; shared project `.claude/settings.json` affects everyone in the folder and should be committed; project local `.claude/settings.local.json` is yours in one project; managed settings from managed sources apply org-wide. `~/.claude.json` is a fifth file Claude Code writes for itself [Claude Code docs, Settings, 2026].

| File | Who | Commit |
|---|---|---|
| `~/.claude/settings.json` | You, every project | n/a |
| `.claude/settings.json` | Everyone in project | Yes |
| `.claude/settings.local.json` | You, one project | No |
| `managed-settings.json` etc. | Organisation | Deployed |
| `~/.claude.json` | App state, MCP personal | Do not edit |

The failure mode: **Wrong-audience.** You commit a personal preference in the shared file and change behaviour for the whole team.

The fix: Put personal settings in `settings.local.json`.

Cross-references: settings are Module 4.1.

**If you remember one thing:** pick the file by audience.

---

## 14.4.2.2 — PRECEDENCE

**Framing.** Highest first: managed, command line (`--settings`), project local, shared project, user. Lists such as `permissions.allow` merge across files; environment variables are not a level and are decided per key pair, for example `ANTHROPIC_MODEL` over the `model` key [Claude Code docs, Settings, 2026].

| Level | Wins over |
|---|---|
| 1 Managed | Everything (narrow exceptions) |
| 2 `--settings` | Files below |
| 3 Local | Shared and user |
| 4 Shared project | User |
| 5 User | n/a |

The failure mode: **Env-is-a-level.** You treat an environment variable as another layer in the stack and mis-predict a model choice.

The fix: Check the key's entry for its paired variable.

Cross-references: env vars are Module 14.6.

**If you remember one thing:** env vars are per-key, not a level.

---

## 14.4.2.3 — KEYS THAT DO NOT APPLY

**Framing.** `permissions.defaultMode` values `auto` and `bypassPermissions` do not take effect from project or local settings; `allow` rules and most `env` values from a committed file wait until the folder is trusted, while `deny` and `ask` apply at once [Claude Code docs, Settings, 2026].

| Key | From shared file |
|---|---|
| `permissions.deny`, `ask` | Applies at once |
| `permissions.allow` | After workspace trust |
| `defaultMode: auto` | Ignored in project/local |

The failure mode: **Untrusted-allow.** You commit an allow rule and a teammate still gets prompts because trust is not yet accepted.

The fix: Tell teammates to trust the folder, and use deny rules where enforcement is immediate.

Cross-references: workspace trust is Module 1.3.

**If you remember one thing:** allow waits for trust.

---

## 14.4.2.4 — VERIFY AND RECOVER

**Framing.** Settings files are strict JSON: a comment or trailing comma is an error. Run `/status` for Setting sources and `claude doctor` for rejected entries; a broken user, project or local file raises a Settings Error dialog, while a bad single entry raises a Settings Warning and is skipped [Claude Code docs, Settings, 2026].

```bash
claude doctor        # lists rejected entries
```

The failure mode: **Comment-in-JSON.** You add a `//` comment to settings.json and the file fails to load.

The fix: Remove comments; use `/status` and `claude doctor` to confirm.

Cross-references: debugging is Part 12.

**If you remember one thing:** settings files are strict JSON.

## CLOSING REFRAME

This is the craft of settings files: **audience decides the file and precedence decides the winner.** The engineer who understands this does not ask "why didn't my setting apply?" — they ask "which file, which level and is trust pending?"
