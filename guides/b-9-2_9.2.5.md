## THE THESIS OF THIS TOPIC

**Tests and type checks miss problems that appear only in the running app, so `/run` and `/verify` drive the real application, and a Stop hook turns a fast check into a gate that Claude Code, not Claude, enforces.**

**Prove-it, in one sentence:** run /verify on a change, record the recipe it writes, and add a Stop hook that blocks completion on a failing check.

**The single most important discipline: close the loop with a command the harness enforces, then add the running app as a second check.**

**The counterintuitive claim you will learn to defend:** a passing test suite is evidence about code, not about the product, and the docs ship a separate skill for the second kind of evidence.

## 9.2.5.1 — /RUN, /VERIFY AND /RUN-SKILL-GENERATOR

**Framing.** Three bundled skills launch your app and confirm a change against the running app. `/run` launches and drives the app, `/verify` builds and runs it to confirm a change does what it should without falling back to tests or type checks, and `/run-skill-generator` teaches both how to build and launch your project [Claude Code docs, Skills, 2026].

| Skill | Does | Writes |
|---|---|---|
| `/run` | Launch and drive the app | Nothing by default |
| `/verify` | Build, run, observe the result | May record `.claude/skills/verify/SKILL.md` |
| `/run-skill-generator` | Capture install commands, env vars and launch script | `.claude/skills/run-<name>/` |

`/run` and `/verify` work without setup by inferring the launch from the project type and from README, `package.json` or `Makefile`; that is unreliable when a project needs a database, env file, graphical session or multi-step build. `/verify` runs only when you invoke it [Claude Code docs, Skills, 2026].

The failure mode: **Inferred launch.** You rely on /verify's inference for an app needing a database and env file, and it verifies a broken or empty app.

The fix: Run `/run-skill-generator` once per project, commit the generated skill, and rerun it when the build changes.

Cross-references: skills are Module 5.2; real-app verification in UI work is Module 9.6.3.

**If you remember one thing:** teach the launch once, commit it.

## 9.2.5.2 — THE RECORDED RECIPE

**Framing.** When `/verify` has to build and drive the app without a recipe, it can record one. At the repo root the recorded skill replaces the bundled `/verify`; Claude edits the file only when it steered a run wrong, so it can be committed without per-session diffs [Claude Code docs, Skills, 2026].

| Fact | Detail |
|---|---|
| Path | `.claude/skills/verify/SKILL.md` at repo root; touched package dir in a monorepo |
| Effect at root | Replaces the bundled `/verify` |
| Edit rule | Only when a run was steered wrong |
| Commit it? | Yes; no per-session diffs expected |

The failure mode: **Shadowed bundled skill.** A recorded verify skill at the repo root silently replaces the bundled one and nobody reviews it.

The fix: Review the recorded file in a PR like any code and keep it current.

Cross-references: plugins and shared skills are Module 9.12.7.

**If you remember one thing:** a recorded recipe is code under review.

## 9.2.5.3 — STOP HOOKS AS GATES

**Framing.** A Stop hook runs your script whenever Claude tries to end its turn, and sends Claude back to work if it exits with code 2, so the turn does not end until the check passes or the block limit is reached [Claude Code docs, Best practices, 2026].

```json
{
  "hooks": {
    "Stop": [
      { "hooks": [ { "type": "command", "command": "pnpm tsc --noEmit 1>&2 || exit 2" } ] }
    ]
  }
}
```

| Fact | Detail |
|---|---|
| Block signal | Exit code 2; stderr goes back to Claude |
| Cap | Override after eight blocked stops in a row with no tool call between |
| Env var to raise | `CLAUDE_CODE_STOP_HOOK_BLOCK_CAP` |
| Alternative | `/goal <condition>`, checked by a separate model each turn |

The failure mode: **Exit-1 gate.** The Stop hook exits 1 on failure; only exit 2 blocks, so Claude finishes with a failing check.

The fix: End the command with `|| exit 2` and test it by breaking a type on purpose.

Cross-references: hooks are Module 5.4; goals are Module 6.7.

**If you remember one thing:** gates need exit 2.

## CLOSING REFRAME

This is the craft of verification skills and hooks: **a running-app check plus a harness-enforced gate.** The engineer who understands this does not ask "did the tests pass?" — they ask "did the app work, and could the turn have ended if it hadn't?"
