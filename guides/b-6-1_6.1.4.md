## THE THESIS OF THIS TOPIC

**Every parallel worker is a separate context sending its own requests, so parallelism multiplies token use, and your plan limits are the real ceiling on how wide you can go.**

**Prove-it, in one sentence:** estimate and then measure, with `/usage`, the usage of one task run serially and then in parallel, and state the multiple you observed.

**The single most important discipline: decide the width before launching, and pilot on a small slice.**

**The counterintuitive claim you will learn to defend:** the docs' own figure for agent teams is roughly seven times a standard session when teammates run in plan mode, so more workers can cost far more than they save [Claude Code docs, Costs, 2026].

## 6.1.4.1 — WHERE THE TOKENS GO

**Framing.** The module's anchor is that parallelism multiplies token use. The parallel-work page puts it as a note: running several sessions or subagents at once multiplies token usage [Claude Code docs, Run agents in parallel, 2026]. The costs page lists the mechanisms: subagents and workflow agents each send their own requests on top of the main conversation's, and each active teammate keeps consuming tokens until it exits [Claude Code docs, Costs, 2026].

| Source | Why it multiplies |
|---|---|
| Subagent | Own context window and requests on top of yours |
| Workflow agent | Every agent spawned sends its own requests |
| Agent teammate | Separate Claude instance; keeps consuming until it exits |
| Background session | Uses subscription quota independently [Claude Code docs, Agent view, 2026] |

The failure mode: **Hidden-multiplier blindness.** You judge cost by the transcript you see and miss that five background sessions each consumed quota independently.

The fix: Open `/usage` and read the attribution breakdown for subagents and skills, and check agent view for every session that is still alive.

Cross-references: plan limits are Module 1.4; cost governance is Module 10.6.

**If you remember one thing:** count workers, not turns.

## 6.1.4.2 — KNOWN FIGURES

**Framing.** The costs page gives some numbers. Agent teams use approximately 7x more tokens than standard sessions when teammates run in plan mode [Claude Code docs, Costs, 2026]. The page also reports an enterprise average of around $13 per developer per active day, below $30 for 90 percent of users, as a single-session baseline before multiplication [Claude Code docs, Costs, 2026]. A dynamic workflow shows a Large workflow warning when it schedules more than 25 agents or projects over 1.5 million tokens [Claude Code docs, Dynamic workflows, 2026].

| Figure | Value | Where stated |
|---|---|---|
| Agent team tokens vs standard session (plan mode) | ~7x | Costs |
| Workflow Large-workflow warning, agent count | More than 25 | Dynamic workflows |
| Workflow Large-workflow warning, projected tokens | Above 1.5 million | Dynamic workflows |
| Workflow agents total per run | 1,000 | Dynamic workflows |
| Enterprise average per developer per active day | About $13 | Costs |

*These are the docs' figures, not your measured ones; your multiple depends on model, context size and task.*

The failure mode: **Borrowed-multiple trust.** You budget a fan-out as exactly 7x because you read it once, though that figure is for plan-mode teammates, not workflows or subagents.

The fix: Treat quoted multiples as warnings, and measure your own run on a small slice with `/usage` before scaling.

Cross-references: workflow size is sub-topic 6.5.3; the team's own costs are Module 6.4.

**If you remember one thing:** quoted multiples describe cases, not your job.

## 6.1.4.3 — LEVERS TO CONTROL COST

**Framing.** The docs give concrete levers. For agent teams: use Sonnet for teammates, keep teams small, keep spawn prompts focused and shut teammates down when done [Claude Code docs, Costs, 2026]. For workflows: run a small slice first, pick a smaller model for stages that do not need the strongest, and set a size guideline of small, medium or large [Claude Code docs, Dynamic workflows, 2026].

| Lever | Where | Effect |
|---|---|---|
| `workflowSizeGuideline`: small / medium / large | Settings or `/config` | Aim for fewer than 5 / 10 / 50 agents; advice, not a cap |
| `CLAUDE_CODE_WORKFLOW_MAX_CONCURRENT_AGENTS` (1 to 256) | Environment | Bounds concurrent agents; default up to 16 |
| `--max-budget-usd` | Print mode | Stops the run at an estimated spend; spend can pass the cap |
| Model per subagent | Agent frontmatter | Smaller model for simple stages |

The failure mode: **Cap-as-guarantee.** You set a size guideline or a budget cap and assume spend cannot exceed it, but the docs say the guideline is advice and spend can pass the budget cap.

The fix: Leave headroom under a budget, and treat guidelines as steering plus a stop button, not a limit.

Cross-references: model choice is Module 4.6; print-mode flags are sub-topic 6.8.4.

**If you remember one thing:** levers steer; only measurement confirms.
