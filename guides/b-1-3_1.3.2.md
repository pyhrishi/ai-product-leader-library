## 1.3.2.1 — THE ACCOUNT FAMILIES

**Framing.** Claude Code supports individual Claude.ai accounts, Claude for Teams or Enterprise, the Claude Console, and cloud providers such as Amazon Bedrock, Google Vertex AI (now named Google Cloud's Agent Platform in some pages) and Microsoft Foundry [Claude Code docs, Authentication, 2026].

| Path | How you sign in | Billing |
|---|---|---|
| Claude.ai subscription | Browser login | Included in plan, rolling limits |
| Teams or Enterprise | Org account | Org plan |
| Claude Console | Console credentials; admin invites first | Per-token API billing |
| Cloud provider | Set environment variables before running `claude`; no browser login | Your cloud bill |
| Claude apps gateway | `/login` with enterprise SSO | Gateway to your provider |

Use `/login` inside Claude Code to log in again or switch accounts, and `/logout` to log out and re-authenticate [Claude Code docs, Authentication, 2026].

The failure mode: **Wrong-billing-path surprise.** You sign in with a Console key out of habit and a long session bills per token, or you run CI on a subscription.

The fix: Choose the path deliberately and check the active account and `/usage`.

Cross-references: plans and limits are Module 1.4; provider setup is in Part 11.

**If you remember one thing:** the login is the billing decision.

## 1.3.2.2 — CREDENTIAL PRECEDENCE

**Framing.** When several credentials exist, Claude Code selects one in a fixed order. Cloud-provider credentials win when `CLAUDE_CODE_USE_BEDROCK`, `CLAUDE_CODE_USE_VERTEX` or `CLAUDE_CODE_USE_FOUNDRY` is set. A signed Claude apps gateway session sits outside the list and takes precedence over them: when a gateway session exists, the CLI authenticates with the gateway token even if those variables are set [Claude Code docs, Authentication, 2026]. The rest of the order (bearer token, API key, `apiKeyHelper`, subscription) is on the Authentication page; this guide does not reproduce it because it was read via search excerpts.

| Mechanism | Purpose |
|---|---|
| `.credentials.json` | Managed by `/login` and `/logout` |
| `ANTHROPIC_BASE_URL` | Route requests through a custom API endpoint |
| `apiKeyHelper` setting | A script that returns an API key |
| Cloud provider env vars | Select Bedrock, Vertex or Foundry |

[Claude Code docs, Authentication and Team, 2026]

The failure mode: **Env-var override.** A leftover provider or API-key environment variable silently overrides your subscription login, and the bill or limits are not what you expected.

The fix: Check the environment (`env | grep -i -E 'anthropic|claude_code_use'`) and `/login` status, and remove stale variables.

Cross-references: settings and environment variables are Modules 4.1 and 4.8.

**If you remember one thing:** the environment can outrank your login.

## 1.3.2.3 — TEAMS: WHO HOLDS THE KEY

**Framing.** For teams, per-user accounts or per-workspace keys keep usage attributable and revocable. Shared personal credentials make both impossible.

| Pattern | Attribution | Revocation |
|---|---|---|
| Per-user Teams or Enterprise account | Per user | Per user |
| Per-workspace Console key with spend limit | Per workspace | Per key |
| One shared personal login | None | All or nothing |
| Key in repo or shell history | Leaked | Rotate everything |

Store keys in a secrets manager, never in repositories or shell history.

The failure mode: **Shared-credential shortcut.** A team shares one personal login for convenience, so usage cannot be attributed and revoking one person revokes all.

The fix: Use per-user accounts or per-workspace keys with spend limits stored in a secrets manager.

Cross-references: cost governance is in Part 11; spend limits are Module 1.4.

**If you remember one thing:** one identity per person or per workspace.

## 1.3.2.4 — CREDENTIAL EXPIRY AND LONG-RUNNING WORK

**Framing.** Persistent Remote Control sessions stop making progress when credentials expire and cannot recover until you log in again [Claude Code docs, Authentication, 2026; from the translated page, verify in English].

| Situation | What to do |
|---|---|
| Login loop or wrong account | `/logout`, then `/login`, and confirm the account shown |
| Long-running remote session | Check that credentials are valid before leaving |
| Scheduled or CI runs | Use a Console key or provider credentials, not a personal login |

The failure mode: **Expired-credential stall.** A long remote or scheduled session loses credentials and silently stops.

The fix: Refresh login before leaving and use service credentials for unattended runs.

Cross-references: remote control is Module 7.5; CI is Module 7.8.

**If you remember one thing:** unattended work needs durable credentials.
