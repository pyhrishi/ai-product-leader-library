# MODULE 9.1.1 — THE SPEC-DRIVEN WORKFLOW: THE COMPLETE CRAFT

---

## THE THESIS OF THIS TOPIC

**Spec-driven development splits a feature into two sessions: one that interviews you and writes down what to build, and a fresh one that builds from the written file, so the build starts with clean context and a defined finish line.**

**Prove-it, in one sentence:** run the seven steps on a small feature and show the SPEC.md, the fresh-session build, the review against the spec and the commit.

**The single most important discipline: never start building in the same context that did the interviewing.**

**The counterintuitive claim you will learn to defend:** writing a spec first is not slower for fuzzy ideas: the interview is how you discover what you wanted, and the file is what makes the later review checkable [Claude Code docs, Best practices, 2026].

**THE TIME BUDGET.** Reading time: ~18 minutes. Prove-it time: ~2 hours (120 minutes, 6.7 times the reading time).

## 9.1.1.1 — INTERVIEW, THEN WRITE THE SPEC

**Framing.** When you do not know exactly what you want, you do not have to work it out before prompting. The docs suggest asking Claude to interview you and write SPEC.md; Claude returns multiple-choice questions about the parts you have not pinned down, such as per-user versus per-key limits, behaviour over the limit and what is out of scope [Claude Code docs, Best practices, 2026].

```text
I want to add rate limiting to the public API but haven't thought it through yet.
Interview me until you could write the spec, then write it to SPEC.md.
```

| Step | Who acts | Output |
|---|---|---|
| 1 Interview | Claude asks, you answer | Decisions on the unpinned parts |
| 2 Write SPEC.md | Claude | A file in the repo |
| 3 Review the spec | You (judgement, not from the docs) | Corrections before any code |
| 4 Fresh session | You | Clean context |
| 5 Implement against the spec | Claude | A diff |
| 6 Verify against the spec | A reviewer prompt or subagent | Gap list |
| 7 Commit | You or Claude | A reviewable change |

The failure mode: **Spec-by-vibes.** You accept the first SPEC.md without reading it, so Claude's guesses about scope become requirements.

The fix: Read the spec as you would a diff, and strike or correct every line you did not decide before opening the build session.

Cross-references: plan mode is Module 2.1; the interview wording is Module 9.1.3.

**If you remember one thing:** the interview turns your unknowns into decisions before code exists.

## 9.1.1.2 — WHY THE BUILD STARTS IN A FRESH SESSION

**Framing.** The docs say that once SPEC.md exists you should start a fresh session to build from it, so the build begins with a clean context and a written definition of done. The same file is what you point the reviewer at later [Claude Code docs, Best practices, 2026].

| Property | Same session as interview | Fresh session from SPEC.md |
|---|---|---|
| Context at start | Full of interview turns and rejected options | Only the spec and the repo |
| Definition of done | Remembered, may drift | Written in a file |
| Restart cost | Re-explain | `claude`, then point at SPEC.md |

```bash
claude            # new session
> Implement SPEC.md. Run the checks it lists and show the output.
```

The failure mode: **Context carry-over.** You build in the interview session, and discarded options and half-decisions steer the code.

The fix: End the interview at the written file, then open a new session and start the build prompt from the file.

Cross-references: context and sessions are Module 2.4; the structure of the file is Module 9.1.2.

**If you remember one thing:** the file, not the chat history, is the contract.

## 9.1.1.3 — REVIEW AGAINST THE SPEC, THEN COMMIT

**Framing.** The docs give a review prompt that checks the work against your plan rather than hunting for bugs in general: a subagent reviews the diff against SPEC.md, checks every requirement is implemented and the listed edge cases have tests, and skips style [Claude Code docs, Best practices, 2026].

```text
use a subagent to review the rate limiter diff against SPEC.md, check every requirement
is implemented and the listed edge cases have tests, report gaps that affect correctness
and skip style
```

| Review prompt part | Why |
|---|---|
| "against SPEC.md" | Gives the reviewer a fixed standard |
| "every requirement is implemented" | Catches omissions |
| "edge cases have tests" | Links spec to tests |
| "skip style" | A reviewer asked to find problems will always find something [Claude Code docs, Best practices, 2026] |

The failure mode: **Reviewer-invented work.** You drop the skip-style clause, the reviewer finds something to report, and fixing it adds abstraction layers and tests for impossible cases.

The fix: Keep the 'report gaps that affect correctness and skip style' clause in every spec review.

Cross-references: verification gates are Module 9.13; review of AI code is Module 9.12.

**If you remember one thing:** review for gaps against the spec, not for taste.

## THE PROVE-IT SECTION

**Deliverable.** A SPEC.md, a transcript of a fresh build session, a spec-review output and a commit for one small feature.

**Close this topic. Build the artifact below from memory. Return to the text only after your first attempt is complete.**

| Step | Action | Output |
|---|---|---|
| 1 | Pick a feature you have not designed; start an interview prompt | Interview transcript |
| 2 | Have Claude write SPEC.md | SPEC.md |
| 3 | Edit the spec by hand and record what you changed | Edit list |
| 4 | Open a fresh session; implement from SPEC.md | Diff |
| 5 | Run the spec-review prompt with skip style | Gap list |
| 6 | Fix gaps and commit referencing SPEC.md | Commit |

**A passing artifact looks like this:**

| Element | Evidence |
|---|---|
| SPEC.md edited by hand | Edit list with 3 changes |
| Build ran in a new session | Session ids differ |
| Review output | Lists gaps by requirement number |

**A failing artifact (a realistic near-miss):**

| Element | What is wrong |
|---|---|
| Spec identical to Claude's first draft | **Spec-by-vibes** |
| Build in the interview chat | **Context carry-over** |

**The verdict.** The artifact passes only if the build session id differs from the interview session id and the review maps each gap to a requirement in SPEC.md.

## CLOSING REFRAME

This is the craft of spec-driven work: **interview, write down, rebuild from the file.** The engineer who understands this does not ask "what should I tell Claude?" — they ask "what must the file say so a stranger could build and check it?"
