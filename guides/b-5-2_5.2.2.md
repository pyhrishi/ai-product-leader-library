## THE THESIS OF THIS TOPIC

**A skill's location decides who gets it and which copy wins when names clash, so placement is a sharing and priority decision.**

**Prove-it, in one sentence:** place the same skill name at two levels, predict the winner from the priority rules, and confirm it.

**The single most important discipline: choose the location by audience first (you, this repo, everyone) and name by uniqueness second.**

**The counterintuitive claim you will learn to defend:** project skills do not override personal ones: the order is enterprise over personal over project [Claude Code docs, Skills, 2026].

## 5.2.2.1 — THE LEVELS

**Framing.** The skills page lists six filesystem levels, and also notes skills synced from a claude.ai account [Claude Code docs, Skills, 2026].

| Level | Path | Scope |
|---|---|---|
| Enterprise | `.claude/skills/<name>/SKILL.md` in the managed settings directory | All users in the organisation |
| Personal | `~/.claude/skills/<name>/SKILL.md` | All your projects |
| Project | `.claude/skills/<name>/SKILL.md` | This repository |
| Nested | `<subdir>/.claude/skills/<name>/SKILL.md` | Sessions started in or below `<subdir>` |
| Additional directory | `.claude/skills/` in a `--add-dir` directory | That session |
| Plugin | `<plugin>/skills/<name>/SKILL.md` | Where the plugin is enabled, as `/plugin-name:skill-name` |

Project skills load from the start directory and every parent up to the repository root; nested skills load when Claude first touches a file in that subdirectory [Claude Code docs, Skills, 2026].

The failure mode: **Wrong-scope placement.** A team procedure is saved in `~/.claude/skills/`, so only you have it and teammates run something else.

The fix: Put team procedures in the project's `.claude/skills/` and commit them.

Cross-references: sharing is sub-topic 5.2.11; layering across features is sub-topic 5.1.7.

**If you remember one thing:** audience decides the level.

## 5.2.2.2 — CLASH RESOLUTION

**Framing.** When names match, enterprise overrides personal and personal overrides project; your skill replaces a bundled skill or built-in command of the same name but not its aliases; plugin skills are namespaced and never conflict; added-directory clashes get a prefix like `/cli:verify` (v2.1.309+) [Claude Code docs, Skills, 2026].

| Clash | Winner |
|---|---|
| Personal `deploy` vs project `deploy` | Personal |
| Enterprise `deploy` vs personal `deploy` | Enterprise |
| Your `debug` vs bundled `/debug` | Yours |
| Skill vs `.claude/commands/` same name | Skill |

The failure mode: **Shadow-by-name.** You name a personal skill `review` and it silently replaces the bundled review behaviour you wanted for the rest of the team's habits.

The fix: Pick a distinctive name, and check `/skills` after adding one.

Cross-references: bundled skills are sub-topic 5.2.8.

**If you remember one thing:** overrides are silent; names are the guard.

## 5.2.2.3 — MONOREPOS AND NESTED SKILLS

**Framing.** Because nested skills load only when Claude first touches a file in that subdirectory, a monorepo package can carry its own skills without crowding every session [Claude Code docs, Skills, 2026]. The `paths` field further limits automatic loading to files matching its globs, relative to the working directory; files outside it do not match [Claude Code docs, Skills, 2026].

```text
repo/
  .claude/skills/release/SKILL.md          # whole repo
  packages/api/.claude/skills/migrate/     # loads when Claude touches packages/api files
```

The failure mode: **Out-of-tree paths.** A skill with `paths` never activates for files in a sibling git worktree added with `/add-dir`, because they are outside the working directory.

The fix: Start Claude Code in that worktree, or move the session there with `/cd`.

Cross-references: large codebases are Module 3.5.

**If you remember one thing:** nested placement keeps skills local to the code they serve.
