# MODULE 9.4.1 — CHARACTERISATION TESTS FIRST: THE COMPLETE CRAFT

---

## THE THESIS OF THIS TOPIC

**Before changing structure, lock the current behaviour with tests that record what the code does today, so any change in behaviour during a refactor turns a test red.**

**Prove-it, in one sentence:** write characterisation tests for an untested function, show they pass on the current code and fail on a deliberate behaviour change.

**The single most important discipline: pin what the code does, not what it should do, before touching it.**

**The counterintuitive claim you will learn to defend:** a characterisation test may enshrine a bug, and that is acceptable: it separates 'preserve' decisions from 'fix' decisions.

**THE TIME BUDGET.** Reading time: ~14 minutes. Prove-it time: ~1.5 hours (90 minutes, 6.4 times the reading time).

## 9.4.1.1 — WHAT A CHARACTERISATION TEST IS

**Framing.** A characterisation test records current behaviour, correct or not, as the safety net for restructuring. The docs' test workflow begins by finding functions not covered by tests, then generating scaffolding, then adding edge cases, then running and verifying [Claude Code docs, Common workflows, 2026].

| Step | Prompt |
|---|---|
| Find gaps | "find functions in NotificationsService.swift that are not covered by tests" |
| Pin behaviour | "write tests that assert exactly what each function returns today for these inputs; do not fix anything" |
| Edge cases | "add cases for boundary values and error conditions" |
| Verify | "run the new tests and fix any failures" (failures here mean the test is wrong, not the code) |

The failure mode: **Fixing while pinning.** Claude 'corrects' a bug while writing the test, so the test no longer records current behaviour.

The fix: Say 'do not change source files in this task' and check the diff touches only test files.

Cross-references: test quality is Module 9.2.3; legacy work is Module 9.5.4.

**If you remember one thing:** pin first, judge later.

## 9.4.1.2 — CHOOSING INPUTS

**Framing.** Characterisation depends on input coverage. Ask Claude to read the code paths and propose inputs that hit each branch, then confirm each branch with the test run. Branch coverage numbers come from your own coverage tool; this guide verified no specific tool.

| Input class | Examples |
|---|---|
| Typical | Real values from logs |
| Boundary | Empty, zero, max length |
| Error | Invalid type, missing field |
| Historical | Inputs from past bug reports |

The failure mode: **Happy-path pin.** Only typical inputs are pinned, so a refactor that changes error handling passes.

The fix: Require at least one input per branch and per error path.

Cross-references: reproduction is Module 9.3.1.

**If you remember one thing:** pin the branches you will touch.

---

## 9.4.1.3 — PROVE THE NET HOLDS

**Framing.** Introduce a deliberate behaviour change and confirm the pinned tests catch it. This is the same break-the-code check as in Module 9.2.3, applied before the refactor rather than after.

| Probe | Expected |
|---|---|
| Change a return value | A pinned test fails |
| Reorder output | A pinned test fails |
| Rename internals only | All tests stay green |

The failure mode: **Hole in the net.** A probe change stays green, so a refactor could break that behaviour unseen.

The fix: Add a test for the missed behaviour before starting the refactor.

Cross-references: small steps are Module 9.4.2.

**If you remember one thing:** probe the net before relying on it.

## CLOSING REFRAME

This is the craft of pinning: **record, probe, then refactor.** The engineer who understands this does not ask "is the code right?" — they ask "what must not change?"
