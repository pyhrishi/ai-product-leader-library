## 9.3.3.1 — BISECT WITH A TEST AS ORACLE

**Framing.** `git bisect run <command>` automates the search: the command exits 0 for good, 1 to 127 except 125 for bad, and 125 to skip [secondary: git documentation, git-bisect, not fetched for this guide]. Claude Code runs shell commands through its Bash tool and can drive the sequence [Claude Code docs, Tools reference, 2026].

```bash
git bisect start
git bisect bad HEAD
git bisect good v2.3.0
git bisect run pnpm vitest run path/to/regression.test.ts
git bisect reset
```

| Input | Meaning |
|---|---|
| good commit | Known-working revision |
| bad commit | Known-failing revision |
| run command | Oracle; exit 0 good, non-zero bad, 125 skip |

The failure mode: **Flaky oracle.** The reproduction passes and fails at random, so bisect lands on an unrelated commit.

The fix: Stabilise the reproduction (Module 9.2.6) or run it several times per step before trusting a verdict.

Cross-references: reproduction is Module 9.3.1.

**If you remember one thing:** bisect is only as good as its oracle.

## 9.3.3.2 — BLAME AND HISTORY QUESTIONS

**Framing.** When a bisect is unnecessary, ask Claude to explain when and why a line changed, using git log and blame. Piping command output is a documented pattern, for example `git log --oneline -20 | claude -p "summarize these recent commits"` [Claude Code docs, Common workflows, 2026].

| Question | Prompt |
|---|---|
| Who changed this and why | "Use git blame on lines 40-60 of limiter.ts and the commit messages; explain intent" |
| What changed between releases | "Summarise `git log v2.3.0..HEAD` for changes touching auth" |
| Did this ever work | "Find the earliest commit where this test passes" |

The failure mode: **Blame as verdict.** You treat the last editor of a line as the cause, though the real change was elsewhere.

The fix: Use blame for questions and bisect for evidence; the committer of a line is not necessarily the origin of the regression.

Cross-references: legacy investigations are Module 9.5.2.

**If you remember one thing:** blame points; bisect proves.

## 9.3.3.3 — RUN IT SAFELY

**Framing.** Bisect checks out many revisions, so run it where a dirty tree cannot be lost. `claude --worktree <name>` creates an isolated checkout on its own branch [Claude Code docs, Worktrees, 2026].

| Safety step | Why |
|---|---|
| Clean tree before starting | Bisect checks out revisions |
| Work in a worktree | Main checkout untouched |
| `git bisect reset` after | Return to the original branch |
| Dependencies per revision | Install step may be needed in the oracle |

The failure mode: **Dirty-tree bisect.** You bisect with uncommitted work in the tree and lose or conflict with it.

The fix: Commit or stash first, or bisect in a worktree.

Cross-references: worktrees are Module 6.2.

**If you remember one thing:** isolate the search.

## CLOSING REFRAME

This is the craft of bisecting: **a reliable oracle, an isolated tree, proof over blame.** The engineer who understands this does not ask "who broke it?" — they ask "which commit flips the oracle?"
