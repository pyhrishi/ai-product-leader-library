# MODULE 10.1.4 — COMMUNICATIONS: THE COMPLETE CRAFT

## THE THESIS OF THIS TOPIC

**Rollout communication fails when it says what is available but not what is enforced; the message set must match the actual policy.**

**Prove-it, in one sentence:** write a three-message sequence and an FAQ whose every answer matches a setting you can show.

**The single most important discipline: write each message from the live policy, never from memory.**

**The counterintuitive claim you will learn to defend:** several of the most common user complaints are policy outcomes the user cannot see, so the FAQ must name them before the user hits them [Claude Code docs, Control MCP server access for your organization, 2026].

## 10.1.4.1 — WHAT THE USER CANNOT SEE

**Framing.** The module brief mentions a communications kit with announcements, drip messages and FAQ answers. I did not find a page of that name in the docs index, so this guide builds the message set from behaviours the docs describe. Several admin controls remove or block things silently: when MCP policy blocks a previously configured server, it disappears from `/mcp` and `claude mcp list` with no signal that policy is the reason, so the docs advise telling affected users which servers are blocked when you roll out a new restriction [Claude Code docs, Control MCP server access, 2026].

| Control | What the user sees | Message needed |
|---|---|---|
| MCP restriction | Server vanishes from `/mcp` | Which servers, why |
| Plugin allowlist | `Marketplace ... is not in the allowed marketplace list` | Which marketplaces are approved |
| Login restriction | Claude Code exits at startup on wrong org | Use your work account |

The failure mode: **Silent restriction.** You tighten a policy and say nothing, so users file bugs for behaviour that is working as configured.

The fix: Publish a change note before each restriction ships.

Cross-references: policy contents are Module 10.4; troubleshooting is Module 12.5.

**If you remember one thing:** every restriction needs a message before it needs a ticket.

## 10.1.4.2 — THE THREE-MESSAGE SEQUENCE

**Framing.** [Practitioner structure, not from the docs.] A launch message, a week-one drip and a week-four drip cover the arc. Use the docs' own recommended first tasks in the drip: codebase Q&A, small bug fixes, plan first [Claude Code docs, Enterprise deployment overview, 2026].

```text
Day 0   Announce: what, who, how to install, where to ask
Day 7   Drip: first safe tasks (Q&A, small fixes, plan first)
Day 28  Drip: what we changed after the pilot, what is blocked and why
```

The failure mode: **Feature-list announcement.** The announcement lists features but not limits, so users assume everything works everywhere.

The fix: Include one 'what is not available here' line per message.

Cross-references: training schedule is Module 10.1.5 topic.

**If you remember one thing:** announce limits as well as features.

## 10.1.4.3 — FAQ BUILT FROM REAL MESSAGES

**Framing.** Anchor FAQ answers to exact messages the docs document. 'You haven't been added to your organization yet' means the seat lacks Claude Code access [Claude Code docs, Set up Claude Code for your organization, 2026]. A spend-limit message means a usage-credit cap was reached and an admin can raise it under Organization settings > Usage [Claude Code docs, Manage costs effectively, 2026].

| User sees | Meaning | Who acts |
|---|---|---|
| 'You haven't been added to your organization yet' | Seat has no Claude Code access | Admin updates seat |
| 'You've hit your session limit' | Seat usage window | User waits, or `/usage-credits` |
| Spend limit message | Usage-credit cap reached | Admin raises limit |

The failure mode: **Paraphrased FAQ.** The FAQ paraphrases error messages, so users cannot search for the wording they actually see.

The fix: Quote the exact message text.

Cross-references: limits and errors are Module 12.6; plans are Module 1.4.

**If you remember one thing:** quote the message, then explain it.

## 10.1.4.4 — KEEPING IT CURRENT

**Framing.** [Practitioner heuristic.] Treat communications as versioned documentation: each policy change updates the FAQ in the same change request.

| Trigger | Update |
|---|---|
| New managed key | FAQ entry + change note |
| New provider | Install page |
| Version floor raised | Update instructions |

The failure mode: **Stale FAQ.** Policy changes ship but the FAQ still describes last quarter's setup.

The fix: Make FAQ updates a required checklist item on every policy change.

Cross-references: version floors are Module 10.4.

**If you remember one thing:** docs and policy ship together.
