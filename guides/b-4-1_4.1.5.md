## 4.1.5.1 — /STATUS: WHICH SOURCES LOADED

**Framing.** Run /status; the Status tab's `Setting sources` line lists each settings file loaded this session, such as `User settings` or `Project local settings`. With managed settings active, the managed entry shows in parentheses how they reached the machine [Claude Code docs, Settings files and precedence, 2026].

| You see | It means |
|---|---|
| `User settings`, `Project local settings` | Those files loaded |
| Managed entry with delivery in parentheses | Which managed source won |
| Different managed source than admin changed | A higher-priority source applies |
| `Organization policy` line (v2.1.261+, in `claude doctor`; in /status only when policy did not load) | Where policy loaded from or why not |

By default the highest-ranked managed source wins and others are skipped silently; /status names the source used and those skipped [Claude Code docs, Deploy managed settings, 2026].

The failure mode: **Source-for-key confusion.** You read Setting sources and conclude which file set a key, but the line only says files loaded.

The fix: Check each loaded file's contents and the precedence order to find the winner.

Cross-references: precedence is sub-topic 4.1.2; managed combining is 4.1.6.

**If you remember one thing:** /status lists files, not winners.

## 4.1.5.2 — CLAUDE DOCTOR: WHAT WAS DROPPED

**Framing.** `claude doctor` prints read-only diagnostics without starting a session: install health, settings validation errors and Remote Control eligibility. After a `-p` run that ignores a setting, run it to see what was dropped [Claude Code docs, CLI reference, 2026].

| Symptom | Likely `claude doctor` finding |
|---|---|
| `mcp__` rule with parentheses in settings | Skipped rule listed |
| Bad permission rule | Settings Warning: entry skipped, file kept |
| Invalid JSON | Settings Error: file skipped |
| IPv6 entry unbracketed | `Sandbox network domain entries have unreliable spellings` |
| Managed entry invalid | Dropped; some keys fall back to stricter values |

`/doctor` (in-session skill) additionally proposes fixes that Claude applies after you confirm.

The failure mode: **Print-mode blindness.** A `-p` run shows no dialog, so you never see the broken entry that was silently skipped.

The fix: Run `claude doctor` after any headless run that ignored a setting.

Cross-references: headless flags are Module 4.8.

**If you remember one thing:** no dialog does not mean no problem.

## 4.1.5.3 — --SAFE-MODE AND THE CLEAN TEST

**Framing.** `--safe-mode` starts with all customizations disabled: CLAUDE.md, skills, plugins, hooks, MCP servers, custom commands and agents, output styles, workflows, custom themes, custom keybindings, status line and file-suggestion commands, LSP servers and auto memory. Authentication, model selection, built-in tools and permissions still work [Claude Code docs, CLI reference, 2026].

| Test | Reading |
|---|---|
| Symptom gone in --safe-mode | A customization causes it; bisect |
| Symptom remains | Core, auth, permission or managed policy |
| Compare with `--bare` | `--bare` skips discovery for speed; safe mode is for debugging |

Permissions keep working in safe mode, so an over-restrictive rule will still reproduce.

The failure mode: **Bisect by hunch.** You disable hooks, then plugins, then MCP one at a time by memory instead of using --safe-mode first.

The fix: Run --safe-mode first; if the symptom disappears, re-enable one category at a time.

Cross-references: plugins are Module 7; hooks are Module 5.4.

**If you remember one thing:** prove whether customization is the cause first.
