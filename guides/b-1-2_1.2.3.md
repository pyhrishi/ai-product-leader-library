## 1.2.3.1 — MODES: THE BASELINE

**Framing.** A permission mode sets which actions Claude can take without asking. The modes are `default` (shown as Manual in the CLI, IDE extensions and desktop app), `acceptEdits`, `plan`, `auto`, `dontAsk` and `bypassPermissions`; `Shift+Tab` cycles them in the CLI [Claude Code docs, Glossary, 2026].

| Mode | Behaviour |
|---|---|
| Manual (`default`) | Asks before edits and commands; read-only built-ins run freely |
| `acceptEdits` | Auto-approves file edits |
| `plan` | Reads and explores, does not edit source |
| `auto` | A classifier model reviews actions instead of you |
| `dontAsk`, `bypassPermissions` | Progressively fewer prompts; bypass for disposable environments |

Auto mode still asks before actions your explicit ask rules match, blocks scope escalation and prompt injection, and strips tool results from what its classifier sees [Claude Code docs, Glossary, 2026].

The failure mode: **Mode-as-policy confusion.** You treat Accept edits or Auto as a security boundary and a command touches something you assumed was protected.

The fix: Use modes for convenience and rules, sandboxing or blocking hooks for boundaries.

Cross-references: permission modes are Module 4.3; auto mode in depth is Module 4.3 too.

**If you remember one thing:** the mode sets the mood, not the law.

## 1.2.3.2 — RULES: ALLOW, ASK, DENY

**Framing.** Permission rules allow, ask about or deny a tool invocation by tool name and argument pattern. Rules are evaluated deny, then ask, then allow, with the first match winning [Claude Code docs, Glossary, 2026]. `/permissions` lists all rules and the settings file each comes from [Claude Code docs, Permissions, 2026]. A rule you add mid-turn applies from Claude's next tool call (from v2.1.234; earlier versions queued it until the turn ended) [Claude Code docs, Permissions, 2026].

```json
{
  "permissions": {
    "allow": ["Bash(npm run test)", "Edit(/src/**)"],
    "ask":   ["Bash(git push *)"],
    "deny":  ["Read(./.env)", "Bash(rm -rf *)"]
  }
}
```

| Question | Answer |
|---|---|
| Does a deny beat an allow? | Yes: deny is evaluated first |
| Where can rules live? | Managed policy, CLI args, local, project, user settings |
| Can a user re-allow a managed deny? | No; managed deny is absolute [secondary: UVM KB article, 2026] |

The failure mode: **Rule-order guess.** You add an allow rule expecting it to override a deny somewhere else, and the action stays blocked.

The fix: Remember deny, ask, allow with first match winning, and use `/permissions` to see which file each rule comes from.

Cross-references: rules in depth are Module 4.2; settings are Module 4.1.

**If you remember one thing:** deny always wins, and `/permissions` shows who set it.

## 1.2.3.3 — SANDBOX: WHAT AN ALLOWED COMMAND CAN REACH

**Framing.** Sandboxing is OS-level filesystem and network isolation for the Bash tool: commands run inside a boundary you define, so Claude can work freely within it without per-command prompts. It is a separate layer from permission rules [Claude Code docs, Glossary, 2026]. Permission modes decide whether Claude asks; the sandbox and outer isolation decide what an action can reach once it runs [Claude Code docs, Permission modes, 2026].

| Layer | Decides | Enforced by |
|---|---|---|
| Mode | Whether Claude asks | The harness |
| Rule | Whether this exact call is allowed | The harness |
| Sandbox | What a running Bash command can touch | The OS boundary |

A third-party university guide warns that the most common mistake is assuming the built-in sandbox restricts everything Claude reads; it applies to Bash, not to the file tools [secondary: UVM IT knowledge base, 2026; confirm in Sandboxing docs].

The failure mode: **Sandbox-coverage assumption.** You enable the sandbox and assume file reads through the Read tool are also confined.

The fix: Use `Read(...)` deny rules for file tools and the sandbox for Bash; they are separate layers.

Cross-references: sandboxing is Module 4.4; security posture is Module 11.1.

**If you remember one thing:** rules gate the call, the sandbox bounds the command.

## 1.2.3.4 — WORKSPACE BOUNDARY AND TRUST

**Framing.** In Manual mode Claude Code can write only to the folder where it started and its subfolders, and asks before reading outside that boundary with Read, Grep and Glob [Claude Code docs, Security, 2026]. A workspace trust dialog appears for folders you have not trusted [Claude Code docs, Security, 2026].

| Situation | Behaviour |
|---|---|
| Edit inside the project | Allowed per mode |
| Write in a parent directory | Needs explicit permission |
| Read outside the boundary | Prompt in Manual mode |
| Start in your home directory | Trust held for the session only; prompt returns each launch |
| `-p` non-interactive run | No trust prompt and no MCP-server prompt |

[Claude Code docs, Security, 2026]

The failure mode: **Home-directory launch.** You start Claude Code in your home directory out of habit, so trust is not saved and the working-directory boundary covers far more than you intend.

The fix: Start Claude Code from a project subdirectory so trust is saved per directory and the boundary is narrow.

Cross-references: trust is Module 1.3; sandbox and isolation are Module 4.4.

**If you remember one thing:** start in the project, not in home.

## CLOSING REFRAME

This is the craft of permissions: **a mode for convenience, rules for decisions, a sandbox for reach.** The engineer who understands this does not ask "should I approve this?" — they ask "which layer should have decided this, and is it configured?"
