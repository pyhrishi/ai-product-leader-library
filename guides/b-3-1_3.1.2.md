## THE THESIS OF THIS TOPIC

**You cannot manage a window you cannot see, so Claude Code offers three views of it: `/context` for a live breakdown, an interactive explainer for the concepts, and a status line for continuous readout.**

**Prove-it, in one sentence:** build a status line that shows context percentage and verify its number against `/context`.

**The single most important discipline: measure with `/context` before changing configuration, and measure again after.**

**The counterintuitive claim you will learn to defend:** the status line's percentage counts input tokens only, so it will not match a figure that includes output tokens [Claude Code docs, Status line, 2026].

**THE TIME BUDGET.** Reading time: ~20 minutes. Prove-it time: ~2 hours (120 minutes, 6.0 times the reading time).

## 3.1.2.1 — `/CONTEXT` AND ITS EXPANDED FORM

**Framing.** `/context` gives a live breakdown by category with optimization suggestions, including which CLAUDE.md and auto memory files loaded; `/memory` opens and edits those files [Claude Code docs, Context window, 2026]. `/context all` shows how many tokens each loaded MCP tool uses [Claude Code docs, Extend Claude Code, 2026]. The large-codebases guide says to check the list under **Memory files** to confirm which instruction files loaded [Claude Code docs, Large codebases, 2026].

| You want to know | Run | Reads |
|---|---|---|
| Total and per-category usage | `/context` | Live breakdown and suggestions |
| Which instruction files loaded | `/context` then Memory files; or `/memory` | File list |
| Per-tool MCP token cost | `/context all` | Per-tool counts |
| Server connection state | `/mcp` | Status per server |
| Cache hit state | `/usage` | `Prompt cache (main)` line |

The failure mode: **One-reading conclusion.** You take a single `/context` reading mid-task and conclude a feature is expensive, without a baseline to compare it with.

The fix: Take a baseline at session start and a second reading after the change; compare the two, not one number.

Cross-references: what fills the window is Module 3.1; MCP tool cost is Module 5.5.

**If you remember one thing:** measure twice and compare.

## 3.1.2.2 — THE INTERACTIVE EXPLAINER

**Framing.** The docs include an interactive simulation of a session from startup to compaction, using representative token counts, that shows what loads before you type, what each read costs, when rules and hooks fire and how a subagent keeps reads out of your context [Claude Code docs, Context window, 2026]. It teaches the shape of the window; it does not measure yours.

```text
Explainer timeline (as documented)
 startup  -> CLAUDE.md, memory, MCP names, skill descriptions load
 work     -> reads add context; path rules load; PostToolUse hook fires
 follow-up-> subagent researches in its own window; summary returns
 /compact -> history replaced by a structured summary; most startup content reloads
```

The failure mode: **Explainer-as-meter.** You quote the explainer's token numbers as if they described your project, then size a budget on them.

The fix: Use the explainer to learn the shape and `/context` to get your own numbers.

Cross-references: compaction behaviour is sub-topic 3.1.7 in Module 3.1.

**If you remember one thing:** the explainer teaches; `/context` measures.

## 3.1.2.3 — A STATUS LINE THAT SHOWS CONTEXT

**Framing.** The status line is a bar at the bottom of Claude Code that runs a shell script you configure and receives JSON session data on stdin [Claude Code docs, Status line, 2026]. `/statusline` accepts natural language and writes a script into `~/.claude/` and updates settings; manually you set `statusLine` with a `command` and optional `padding` [Claude Code docs, Status line, 2026].

```json
{ "statusLine": { "type": "command", "command": "~/.claude/statusline.sh", "padding": 2 } }
```

```bash
#!/bin/bash
input=$(cat)
PCT=$(echo "$input" | jq -r '.context_window.used_percentage // 0' | cut -d. -f1)
echo "[$(echo "$input" | jq -r '.model.display_name')] ${PCT}% context"
```

[pattern adapted from the documented quickstart; verify field names on the Status line page before relying on them]

The failure mode: **Null-field crash.** Your script assumes `used_percentage` is always a number, but it can be null early in a session, and `current_usage` is null before the first API call and again after `/compact` until the next call, so the line breaks or shows garbage.

The fix: Default every field with `// 0` or `// empty` in `jq` and test the first-prompt and post-compact states.

Cross-references: settings layering is Module 4.1; status line design for awareness is Module 3.6.

**If you remember one thing:** default every field; the early states are null.

## 3.1.2.4 — HOW THE READOUT IS COMPUTED AND REFRESHED

**Framing.** `used_percentage` is calculated from input tokens only: `input_tokens + cache_creation_input_tokens + cache_read_input_tokens`; it excludes `output_tokens` [Claude Code docs, Status line, 2026]. The script runs at session start and again on a new assistant message, `/compact` finishing, a permission-mode change, a Vim-mode toggle, a changed `command`, or an optional `refreshInterval` (minimum 1 second); updates are debounced at 300ms, and an in-flight script is cancelled when a new update triggers [Claude Code docs, Status line, 2026].

| Fact | Value |
|---|---|
| Debounce | 300ms |
| `refreshInterval` minimum | 1 second |
| Percentage formula | input + cache creation + cache read tokens |
| `current_usage` null | Before first API call, and after `/compact` until next call |

The failure mode: **Output-token mismatch.** You compute context from output tokens too, get a number higher than the status line shows and conclude the status line is wrong.

The fix: Use the same input-only formula when you recompute `used_percentage` by hand.

Cross-references: cache fields in the same JSON are covered in Module 3.4.

**If you remember one thing:** match the formula before you doubt the number.

**A passing artifact looks like this:**

| Test | Expected | Observed |
|---|---|---|
| Before first prompt | No error | Prints 0% |
| After `/compact` | No error | Falls back to default |
| Mid-task | Within a few points of `/context` | Matches |

**A failing artifact (a realistic near-miss):**

| Element | What is wrong |
|---|---|
| Script uses `.used_percentage` with no fallback | **Null-field crash** waiting to happen |
| No comparison with `/context` | The number is untested |

**The verdict.** The artifact passes only if the script was exercised in the null states and its output was compared with `/context`.
