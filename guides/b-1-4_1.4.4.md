# MODULE 1.4.4 — FEATURE AVAILABILITY BY PLAN, PROVIDER AND VERSION: THE COMPLETE CRAFT

---

## THE THESIS OF THIS TOPIC

**A documented feature is not an entitled feature until you have checked plan, provider and version.**

**Prove-it, in one sentence:** pick five features your runbook uses and record plan, provider and minimum version for each.

**The single most important discipline: put the three-way check in the runbook.**

**The counterintuitive claim you will learn to defend:** the docs describe the product, not your account; the same page can be right and not apply to you.

**THE TIME BUDGET.** Reading time: ~15 minutes. Prove-it time: ~2 hours (120 minutes, 8.0 times the reading time).

## 1.4.4.1 — THREE AXES

**Framing.** Some features, for example auto mode, cloud sessions and Code Review, differ by plan or backend; the docs maintain a feature-availability page for this [syllabus Module 1.4.4]. That page was not fetched in full for this guide; read it before standardising a workflow.

| Axis | Question |
|---|---|
| Plan | Pro, Max, Team or Enterprise? |
| Provider | Anthropic, Bedrock, Vertex, Foundry? |
| Version | Does `claude --version` meet the minimum? |

The failure mode: **Doc-as-entitlement.** You read a feature in the docs, build a workflow on it, and a teammate on another plan or provider cannot run it.

The fix: Check plan, provider and version for each team member and put the check in the runbook.

Cross-references: surfaces are Module 7.1; versions are Module 1.3.5.

**If you remember one thing:** three axes, every feature.

## 1.4.4.2 — EXAMPLES FROM THE DOCS

**Framing.** Examples show how much varies.

| Example | What the docs say |
|---|---|
| Auto mode | Built-in starting mode on Pro, Max and Team for interactive terminal and VS Code; from v2.1.283 more broadly |
| Computer use, Dispatch | Desktop, on Pro and Max |
| Third-party providers | CLI and IDE extensions support them |
| Artifact sharing | Public link on Pro and Max; organisation sharing on Team and Enterprise |
| Agent teams | Experimental, off by default |

[Claude Code docs, 2026; verify each row on its own page]

The failure mode: **Default-mode mismatch.** Your session starts in a different permission mode than a colleague's and you debug a difference that is only the starting mode.

The fix: Compare `/permissions` and starting mode before debugging behaviour.

Cross-references: permission modes are Module 4.3.

**If you remember one thing:** starting state differs by plan and version.

## 1.4.4.3 — THE WORKING METHOD

**Framing.** Before writing a team runbook, list the features it uses, then check plan, provider and version for each and record `claude --version`.

| (fill in) | | | | |

The failure mode: **Matrix-drift.** The availability matrix is written once and never updated, so it slowly becomes wrong.

The fix: Date each row and review after each release with `/release-notes`.

Cross-references: release notes are Module 1.3.5.

**If you remember one thing:** a dated matrix beats a remembered one.

## 1.4.4.4 — PROVIDER-ROUTE LIMITS

**Framing.** Third-party provider users are limited to the CLI and IDE extensions in several docs examples, so surfaces such as the desktop app or web may not be available on that route [Claude Code docs, Overview, 2026].

| Route | Surfaces |
|---|---|
| Anthropic subscription or Console | All surfaces per plan |
| Bedrock, Vertex, Foundry | Terminal CLI, VS Code, JetBrains |

The failure mode: **Provider-blind plan.** You plan a desktop or web workflow for a team that runs Bedrock and discover the surface is not offered.

The fix: List surfaces per provider before choosing a workflow.

Cross-references: surfaces are Module 7.1; providers are in Part 11.

**If you remember one thing:** the provider constrains the surface.

## CLOSING REFRAME
