# MODULE 1.3.3 — THE FIRST SESSION: A SMALL, REVIEWED CHANGE: THE COMPLETE CRAFT

## THE THESIS OF THIS TOPIC

**The first session has one job: let you see the whole loop once at low stakes, from question to reviewed diff.**

**Prove-it, in one sentence:** complete the five-step first session on a small repo and identify one tool call of each kind in the transcript.

**The single most important discipline: start clean, keep it small, and read the diff before widening the task.**

**The counterintuitive claim you will learn to defend:** the best first task is boring. A showpiece failure teaches you nothing about whether setup, prompt or model was at fault.

## 1.3.3.1 — START CLEAN

**Framing.** Claude Code reads your project files as needed; you do not add context manually [Claude Code docs, Quickstart, 2026]. Start from a project directory with a clean tree so the diff afterwards is only Claude's.

```bash
cd ~/projects/small-repo
git status        # clean? if not, commit or stash
git switch -c first-session
claude
```

Starting in a project subdirectory (not your home directory) means workspace trust is saved per directory [Claude Code docs, Security, 2026].

The failure mode: **Dirty-tree start.** You begin with uncommitted work, Claude edits files, and the two sets of changes blur together.

The fix: Commit or stash first, work on a branch and treat `git diff` as the review surface.

Cross-references: git workflows are Module 2.6; trust is Module 1.3.4.

**If you remember one thing:** a clean tree makes the diff the whole story.

## 1.3.3.2 — THE FIVE STEPS

**Framing.** The quickstart sequence: install, start a session, ask a first question, make a first change, use git [Claude Code docs, Quickstart, 2026].

| Step | Prompt (examples from the quickstart) | What to watch |
|---|---|---|
| Orient | `give me an overview of this codebase` | Which files it reads |
| Ask | `how is authentication handled?` | Search before guessing |
| Change | `add a hello world function to the main file` | A permission prompt, then an edit |
| Git | `what files have I changed?` then `commit my changes with a descriptive message` | `git` via Bash |
| Review | `git diff` | Scope and surprises |

Press `Shift+Tab` at any time to switch permission mode [Claude Code docs, Quickstart, 2026]. If a change misbehaves, your git history is untouched until you commit, so `git checkout` undoes it [Claude Help Center, Your first day, 2026].

The failure mode: **Showpiece first session.** You open your most important repo and ask for a large refactor on day one, then cannot tell whether a bad result was setup, prompt or model.

The fix: Use a small repo or throwaway branch, one scoped change, and read the diff before widening the task.

Cross-references: the explore, plan, implement, commit loop is Module 2.1; prompting is Module 2.2.

**If you remember one thing:** boring first tasks teach the most.

## 1.3.3.3 — READING THE PERMISSION PROMPT

**Framing.** In Manual mode Claude asks before edits and commands. The prompt offers approve once, approve and do not ask again for edits for the rest of the session, or reject with an explanation [Claude Help Center, Your first day, 2026].

| Choice | Effect |
|---|---|
| Yes | Run this action once |
| Yes, don't ask again for edits | Auto-approve edits for the session |
| No (with a comment) | The comment becomes the reason; Claude continues |

If you select No without a comment on a main-conversation prompt, Claude Code stops the turn [Claude Code docs, Permissions, 2026].

The failure mode: **Approve-all-early.** You pick 'don't ask again' on the first prompt and later approve edits you would have rejected.

The fix: Approve once while learning, and widen only when you trust the pattern.

Cross-references: permission modes are Module 4.3; rules are Module 4.2.

**If you remember one thing:** approve once until you know the pattern.

---

## 1.3.3.4 — ENDING WELL: INIT, COMMIT OR REVERT

**Framing.** End the session by either committing or reverting. The first-day guide suggests running `/init` once per project to generate a CLAUDE.md capturing codebase conventions [Claude Help Center, Your first day, 2026].

```text
/init                     # generate CLAUDE.md from the codebase (once per project)
commit with a descriptive message     # or: git restore .  to revert
```

| Outcome | Action |
|---|---|
| Diff is right | Commit |
| Diff is wrong | `git restore .` and rewrite the prompt |
| Learned a convention | Add it to CLAUDE.md |

The failure mode: **Unreviewed commit.** You let Claude commit without reading the diff, and a stray change lands in history.

The fix: Read `git diff` first and ask for a commit message only after you have reviewed.

Cross-references: CLAUDE.md is Module 3.2; checkpoints are Module 2.5.

**If you remember one thing:** review, then commit; or revert.
