# MODULE 8.3.6 — TOOL DESIGN PRINCIPLES FOR AGENTS: THE COMPLETE CRAFT

---

## THE THESIS OF THIS TOPIC

**A tool is a prompt the model reads at the moment of decision, so a clear name, a description written for the model, actionable errors and bounded output matter more than the implementation.**

**Prove-it, in one sentence:** rewrite a poor tool (vague name, generic error, unbounded output) into a good one and show the behaviour change on a fixed task set.

**The single most important discipline: design the result Claude will read, not only the function you will run.**

**The counterintuitive claim you will learn to defend:** the description is the interface: Claude reads it to decide when to call the tool, so a correct implementation behind a vague description is a tool that is not used [Agent SDK docs, Give Claude custom tools, 2026].

**THE TIME BUDGET.** Reading time: ~19 minutes. Prove-it time: ~2 hours (120 minutes, 6.3 times the reading time).

## 8.3.6.1 — NAMES AND DESCRIPTIONS

**Framing.** The docs state that the description tells Claude what the tool does so it can decide when to call it, that `.describe()` on a Zod field or Annotated in Python gives a field description Claude sees, and that names and descriptions are what tool search matches [Agent SDK docs, Give Claude custom tools, 2026; Agent SDK docs, Scale to many tools with tool search, 2026].

| Element | Weak | Strong |
|---|---|---|
| Name | query_slack | search_slack_messages |
| Tool description | 'Query Slack' | 'Search Slack messages by keyword, channel, or date range' |
| Field description | none | 'Latitude coordinate' via .describe() or Annotated |
| Enum | free string | constrained with z.enum or JSON Schema enum |

[Agent SDK docs, Give Claude custom tools and tool search pages, 2026]. Constraining with enums turns invalid inputs into schema errors before they reach your handler.

The failure mode: **Implementation-first description.** You describe how the tool works internally, not when to use it, and Claude never picks it.

The fix: Write the description as 'when and for what', with the key inputs named.

Cross-references: tool search naming is Module 8.3.4; custom tools are Module 8.3.2.

**If you remember one thing:** name and describe for the decision, not the code.

## 8.3.6.2 — ACTIONABLE ERRORS

**Framing.** A failing handler should compose the message Claude reads. The docs' example returns the status, a reason and isError, and notes that an uncaught exception reaches Claude as the raw string with no context [Agent SDK docs, Give Claude custom tools, 2026].

| Error style | What Claude can do |
|---|---|
| Raw exception 'Unexpected token <' | Guess |
| 'API error: 404 Not Found' with isError | Retry with a different endpoint or report |
| 'Unsupported conversion: furlongs to miles' with isError | Tell the user, pick a supported unit |

Pattern from [Agent SDK docs, Give Claude custom tools, 2026]. Add what to try next when you know it, such as the list of valid values.

The failure mode: **Dead-end error.** The error says 'failed' with no cause, so Claude retries the identical call until max turns.

The fix: Include the cause and one next step in every error result.

Cross-references: turn limits are Module 8.2.1.

**If you remember one thing:** an error is the next prompt.

## 8.3.6.3 — TOKEN-EFFICIENT OUTPUT

**Framing.** Tool output consumes context every turn. MCP results over 25,000 tokens are saved to a file and the result replaced by an error naming the path; a text result over 50,000 characters is saved regardless, unless the tool declares anthropic/maxResultSizeChars [Agent SDK docs, Connect to external tools with MCP, 2026]. structuredContent returns exact fields, and when set, text blocks in content are not forwarded [Agent SDK docs, Give Claude custom tools, 2026].

| Technique | Effect |
|---|---|
| Paginate and summarize | Smaller results per call |
| Return fields, not prose, via structuredContent | Claude reads exact values |
| Return an image plus its data points | Visual and exact |
| Raise MAX_MCP_OUTPUT_TOKENS | Last resort; costs context |

The failure mode: **Dump-everything result.** A search tool returns every row and the output exceeds the limit, so the agent reads a file path instead of the data.

The fix: Return a page with a count and a cursor, and let Claude ask for more.

Cross-references: context window is Module 8.2.1.

**If you remember one thing:** return what the next decision needs.

## 8.3.6.4 — SCOPE: ONE BROAD TOOL OR SEVERAL NARROW ONES

**Framing.** Tool count has a cost: 50 tools can use 10-20K tokens and accuracy degrades past 30-50 loaded tools [Agent SDK docs, Scale to many tools with tool search, 2026]. Annotations help too: readOnlyHint lets the loop run read-only tools in parallel [Agent SDK docs, Give Claude custom tools, 2026].

| Choice | Benefit | Cost |
|---|---|---|
| Few broad tools | Fewer definitions | Complex schemas; harder to annotate |
| Many narrow tools | Clear names; precise annotations | Context cost; use tool search |
| Split read and write | Parallel reads; clear approvals | More tools |

Rule from the docs' annotations: split so the read-only hint is truthful.

The failure mode: **Swiss-army tool.** One tool does read, write and delete by a mode argument, so it cannot be marked read-only and every call needs approval.

The fix: Split by side effect.

Cross-references: subagent tool scoping is Module 8.3.5.

**If you remember one thing:** scope tools by side effect.

## THE PROVE-IT SECTION

**Deliverable.** A before/after tool pair with a task-set comparison (selection rate, error recovery, tokens per result).

**Close this topic. Build the artifact below from memory. Return to the text only after your first attempt is complete.**

| Step | Action | Output |
|---|---|---|
| 1 | Pick a weak tool and write its flaws | A critique |
| 2 | Rewrite name, description, schema | A new definition |
| 3 | Make errors actionable | Three error cases |
| 4 | Bound the output | A paginated result |
| 5 | Run 10 tasks before and after; record selection, recovery, tokens | A comparison table |
| 6 | Split any mixed read/write tool | Two tools |

**A passing artifact looks like this:**

| Metric | Before | After |
|---|---|---|
| Selected when needed | recorded | recorded |
| Recovered from error | recorded | recorded |
| Tokens per result | recorded | recorded |

**A failing artifact (a realistic near-miss):**

| Element | What is wrong |
|---|---|
| Only the name changed | **Implementation-first description** remains |
| No numbers | Cannot show improvement |

**The verdict.** The artifact passes only if the comparison table is measured on the same task set before and after.
