## THE THESIS OF THIS TOPIC

**For SVN, Perforce, Mercurial and other systems, a WorktreeCreate hook replaces Claude Code's git logic entirely and a WorktreeRemove hook cleans up, so isolation is whatever your hook script makes it.**

**Prove-it, in one sentence:** write a WorktreeCreate hook that prints a directory path, show Claude starting in it, and show why .worktreeinclude no longer applies.

**The single most important discipline: make the hook print only the directory, and create that directory outside any git repository.**

**The counterintuitive claim you will learn to defend:** a hook that works can still be refused: a hook-created directory inside a git repository resolves to that repository's checkout, and Claude Code declines it as an isolation worktree [Claude Code docs, Worktrees, 2026].

## 6.2.5.1 — WHAT THE HOOK REPLACES

**Framing.** Worktree isolation uses git by default. For other systems you configure `WorktreeCreate` and `WorktreeRemove` hooks to provide creation and cleanup. Because the hook replaces the default git behaviour, `.worktreeinclude` is not processed with `--worktree`; copy local configuration inside the script [Claude Code docs, Worktrees, 2026].

| Concern | Git default | With WorktreeCreate |
|---|---|---|
| Creating the directory | `git worktree add` under `.claude/worktrees/` | Your script, anywhere you choose |
| Copying `.env` | `.worktreeinclude` | Your script |
| Cleanup | Exit prompts and the sweep | Your WorktreeRemove hook |
| Sweep marker | Written into git metadata | None; the sweep keeps hook-created worktrees |

The failure mode: **Lost-include surprise.** You keep a `.worktreeinclude` and a hook, and the `.env` never arrives because the file is not processed when a hook creates the worktree.

The fix: Copy needed local files inside the hook script.

Cross-references: hooks in general are Module 5.4; sharing is sub-topic 6.2.3.

**If you remember one thing:** a hook replaces the whole creation path.

## 6.2.5.2 — A CREATE HOOK

**Framing.** The docs' example reads the worktree name from the JSON on stdin with `jq`, checks out a fresh SVN working copy and prints the directory so Claude Code can use it as the session's working directory. It prints the path to stdout and sends other output to stderr (`>&2`) [Claude Code docs, Worktrees, 2026].

```json
{ "hooks": { "WorktreeCreate": [ { "hooks": [ {
  "type": "command",
  "command": "bash -c 'NAME=$(jq -r .name); DIR=\"$HOME/.claude/worktrees/$NAME\"; svn checkout https://svn.example.com/repo/trunk \"$DIR\" >&2 && echo \"$DIR\"'"
} ] } ] } }
```
[quoted from Claude Code docs, Worktrees, 2026]

If the hook prints anything other than the directory it created, or the directory is deleted later, Claude Code prints an error naming the path and exits with code 1 at startup [Claude Code docs, Worktrees, 2026].

The failure mode: **Chatty-hook stdout.** Your checkout command prints progress to stdout, the hook's output is no longer a bare path, and startup fails with the can't-enter error.

The fix: Send everything but the final path to stderr, as the docs' example does with `>&2`.

Cross-references: stdin payload details are in the hooks reference (Module 5.4).

**If you remember one thing:** stdout is the path and nothing else.

## 6.2.5.3 — PAIRING A REMOVE HOOK

**Framing.** The docs say to pair it with a `WorktreeRemove` hook to clean up when the session ends and point to the hooks reference for the input schema and a removal example. A worktree your hook created has no git metadata; the resume check can still pass it [Claude Code docs, Worktrees, 2026].

| Hook | Runs | Output contract |
|---|---|---|
| WorktreeCreate | When a worktree is requested | Print the directory path to stdout |
| WorktreeRemove | When the session ends | Per the hooks reference; not fetched here |

*The remove hook's exact input schema was not retrieved; read the hooks reference before relying on it.*

The failure mode: **Leaked-checkout buildup.** You ship a create hook without a remove hook and every session leaves a full working copy in `~/.claude/worktrees/`.

The fix: Add a WorktreeRemove hook, and check the directory after test sessions.

Cross-references: retention is Module 4.1.

**If you remember one thing:** every create needs a remove.

## 6.2.5.4 — ISOLATION REFUSALS

**Framing.** Claude Code checks a directory's git identity before adopting it as an isolation worktree. A directory with no git metadata passes only when no git repository contains it. If the hook creates the directory inside a repository, git resolves it to that repository's checkout and Claude Code refuses with a `git resolves its working tree to` message. The refused directory is left in place because it may hold work [Claude Code docs, Worktrees, 2026].

| Message fragment | Meaning | Action |
|---|---|---|
| `git resolves its working tree to` | Hook directory sits inside a repository | Create hook directories outside any repository |
| `it contains the protected checkout` | Path is a parent of the main checkout, such as your home directory | Change the returned path; do not delete it |
| `its recorded path has a network spelling` | Network path | Recreate at a local path |

The failure mode: **Inside-the-repo directory.** Your hook creates worktrees under the project directory, so every session is refused as an isolation worktree.

The fix: Return a path outside any git repository, such as under your home's own worktree folder.

Cross-references: resume rules are Module 2.4; refusal handling continues in sub-topic 6.2.6.

**If you remember one thing:** outside any repository, or it is refused.
