## THE THESIS OF THIS TOPIC

**The iOS Simulator pane streams a per-session simulator next to the chat so Claude can build, install, tap and read your app while you watch, without taking over your screen.**

**Prove-it, in one sentence:** state the requirements, how the pane opens, the consent model, and the device lifecycle, and run a build-and-verify loop in a simulator.

**The single most important discipline: name the device and the goal in the prompt ('run it on the iPhone SE simulator and check onboarding') so the pane opens on the right target.**

**The counterintuitive claim you will learn to defend:** the pane does not use computer use and needs no Accessibility or Screen Recording permission, because it drives the simulator directly [Claude Code docs, iOS Simulator, 2026].

## 7.2.5.1 — REQUIREMENTS AND WHEN IT OPENS

**Framing.** The pane is in public beta on macOS, available on Pro, Max, Team and Enterprise plans, except Enterprise organizations with a HIPAA configuration. It needs Claude Desktop v1.24012.0 or later and Xcode with the iOS platform installed [Claude Code docs, iOS Simulator, 2026].

| Requirement | Detail |
|---|---|
| Desktop version | v1.24012.0 or later |
| OS | macOS only |
| Xcode | Use Xcode 26.x; the pane does not yet work with Xcode 27 (Device Hub) |
| Session type | Local sessions only; not cloud or SSH |
| Opens when | Claude builds, installs, launches or checks the app in a simulator |
| Manual open | Views menu, iOS Simulator entry, once a session has a simulator or edited Swift files |

If `xcode-select` points at Xcode 27, select a 26.x install with `sudo xcode-select -s /Applications/Xcode-26.4.app` and confirm with `xcode-select -p` [Claude Code docs, iOS Simulator, 2026].

The failure mode: **Xcode-27 mismatch.** The pane reports no simulators although devices exist, because `xcode-select` points at Xcode 27.

The fix: Install Xcode 26.x alongside and point `xcode-select` at it, then restart the session.

Cross-references: desktop basics are Module 7.2; the CLI route to the simulator is Module 7.6.

**If you remember one thing:** match the Xcode, then ask in terms of running the app.

## 7.2.5.2 — CONSENT AND WHO DRIVES THE DEVICE

**Framing.** The first time Claude uses a simulator, Desktop asks you to allow it. Consent is once per device, not per session, and covers controlling the device and taking screenshots [Claude Code docs, iOS Simulator, 2026].

| Action | Governed by |
|---|---|
| Tap, type, launch, screenshot on an allowed device | One-time device consent |
| Opening a URL on the device | Your session permission mode |
| Building the app (`xcodebuild`) | Your session permission mode |
| Turn off Claude's access | Desktop settings, or managed `disableMobileSimulatorTools` |
| Disable the pane entirely | `requireCoworkFullVmSandbox` policy key |

Claude's screenshots of the device are sent to Anthropic and kept under your normal retention settings, so do not sign in to real accounts on a device Claude uses. While Claude drives, a **Claude is using this device** badge shows; wait for it to clear before tapping [Claude Code docs, iOS Simulator, 2026].

The failure mode: **Real-account leak.** You sign in to a personal Apple or app account on a simulator Claude controls, and screenshots of it are sent to Anthropic.

The fix: Use test accounts and seeded data on any device Claude uses.

Cross-references: data handling is Module 10.7; secrets are Module 11.4.

**If you remember one thing:** treat the device as a shared screen.

## 7.2.5.3 — DEVICE LIFECYCLE AND THE VERIFY LOOP

**Framing.** Each device belongs to the session that launched it, so parallel sessions do not share a device. Up to 4 devices can open per session. Desktop shuts down simulators it booted when you quit, archive the session, or 10 minutes after you detach a device; devices you booted yourself are never shut down automatically [Claude Code docs, iOS Simulator, 2026].

```text
Prompt: Build the app, run it on the iPhone SE simulator, tap through
onboarding, and tell me if any screen takes longer than one second to load.
Then screenshot the failing screen. After you fix it, relaunch and verify.
```

| Control | Shortcut |
|---|---|
| Home | `Cmd+Shift+H` |
| Lock | `Cmd+L` |
| Rotate | `Cmd+Right Arrow` |
| Screenshot / recording | `Cmd+S` / `Cmd+R`, saved to Desktop |

Claude drives simulated devices only; it cannot control a physical iPhone [Claude Code docs, iOS Simulator, 2026].

The failure mode: **Tap-collision.** You tap through the app while Claude is mid-test, so the app state Claude reads is not the state its steps produced.

The fix: Wait for the badge to clear, or tap to a state first and then ask Claude to check it.

Cross-references: verification loops are Module 7.6 and Module 2.3.

**If you remember one thing:** one driver at a time.

| Check | Evidence |
|---|---|
| Xcode 26.x selected | `xcode-select -p` path |
| Named device | iPhone SE in prompt |
| Verify after fix | Before and after screenshots |

**A failing artifact (a realistic near-miss):**

| Element | What is wrong |
|---|---|
| Real Apple ID signed in | **Real-account leak** |
| Verified once, before fix | No post-fix check |

**The verdict.** The artifact passes only if before and after screenshots come from the same named device and no real account appears.
