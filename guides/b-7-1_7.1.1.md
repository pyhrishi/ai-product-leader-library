## THE THESIS OF THIS TOPIC

**Claude Code is one engine with many front ends, so choosing a surface is choosing where the work runs, who can see it and what you review it with, not choosing a different product.**

**Prove-it, in one sentence:** name each of the six platforms and six integrations from memory and say, for each, where Claude actually executes.

## 7.1.1.1 — SIX PLATFORMS, ONE ENGINE

**Framing.** The platforms page says Claude Code runs the same underlying engine everywhere, but each surface is tuned for a different way of working [Claude Code docs, Platforms and integrations, 2026]. The six platforms are the CLI, Desktop, VS Code, JetBrains, Web and Mobile.

| Platform | Best for (per the docs) | Where Claude runs |
|---|---|---|
| CLI | Terminal workflows, scripting, remote servers | Your machine |
| Desktop | Visual review, parallel sessions, managed setup | Your machine (local), or cloud and SSH from the same app |
| VS Code | Working inside VS Code without a terminal | Your machine |
| JetBrains | IntelliJ, PyCharm, WebStorm and other JetBrains IDEs | Your machine, in the IDE's terminal |
| Web | Long-running tasks that need little steering | Cloud, Anthropic-managed by default |
| Mobile | Starting and monitoring tasks while away | Cloud sessions, or your machine through Remote Control |

The docs call the CLI the most complete surface for terminal-native work: scripting and the Agent SDK are CLI-only, and Desktop and the IDE extensions trade some CLI-only features for visual review and tighter editor integration [Claude Code docs, Platforms and integrations, 2026]. Mobile is described as a thin client into cloud sessions or into a local session through Remote Control.

The failure mode: **Surface-as-product.** You treat Desktop, the IDE extension and the CLI as separate tools, so you configure each from scratch and conclude 'it behaves differently' when the real difference is a missing CLI-only feature.

The fix: Start from the engine: check the docs' feature comparison for the specific feature before assuming a bug, and keep shared configuration in the files all local surfaces read.

Cross-references: the module overview is Module 7.1; the extension layer that every surface shares is Module 5.1; cloud sessions in depth are Module 7.4.

**If you remember one thing:** same engine, different trade-offs; the CLI has the most.

## 7.1.1.2 — SIX INTEGRATIONS AND WHAT THEY CONNECT

**Framing.** Integrations let Claude work with services outside your codebase. The platforms page lists Chrome, GitHub Actions, GitLab CI/CD, Code Review, Slack and Claude Tag, and says MCP servers and connectors cover almost anything else, such as Linear, Notion or Google Drive [Claude Code docs, Platforms and integrations, 2026].

| Integration | What it does | Use it for |
|---|---|---|
| Chrome | Controls your browser with your logged-in sessions | Testing web apps, filling forms, sites with no API |
| GitHub Actions | Runs Claude in your CI pipeline | PR reviews, issue triage, scheduled maintenance |
| GitLab CI/CD | Same as GitHub Actions for GitLab | CI-driven automation on GitLab |
| Code Review | Reviews every PR automatically | Catching bugs before human review |
| Slack | Responds to `@Claude` mentions | Turning bug reports into pull requests |
| Claude Tag | `@Claude` as the organization's shared identity, admin-configured access | Shared team access on Team and Enterprise plans |

Notice that only Chrome acts on your own machine and browser; the rest run in CI runners or Anthropic's cloud. That difference decides what they can see and what credentials they hold.

The failure mode: **Integration-sprawl.** You switch on Chrome, Slack, Actions and Code Review at once for a small team and nobody can say which one posted a given comment or spent a given token.

The fix: Add one integration per workflow, name its owner, and record the trigger and the identity it acts as before adding the next.

Cross-references: Chrome is Module 7.6; Slack and Claude Tag are Module 7.7; Actions, GitLab and Code Review are Module 7.8.

**If you remember one thing:** each integration is a trigger plus an identity; know both.

## 7.1.1.3 — WHAT IS SHARED AND WHAT IS NOT

**Framing.** You can mix surfaces on the same project: configuration, project memory and MCP servers are shared across the local surfaces [Claude Code docs, Platforms and integrations, 2026]. Cloud and Mobile are different: cloud sessions work from a fresh clone and do not read your local user settings (Module 7.4).

| Thing | Local surfaces (CLI, Desktop local, IDE) | Cloud session |
|---|---|---|
| CLAUDE.md in the repo | Read | Read from the clone |
| Your user settings | Read | Not read; set environment variables or commit project settings |
| MCP servers added with `claude mcp add` | Read | Not carried; use connectors or a committed `.mcp.json` |
| Local files not committed | Visible | Absent unless bundled by `--cloud` |

Source for the cloud column: [Claude Code docs, Cloud sessions and Scheduled tasks, 2026]. Where a cloud session differs, the docs tell you to commit the setting to the repository or use an environment variable.

The failure mode: **Phantom-config.** You tune permissions and MCP servers in your user settings, then start a cloud session and are surprised that none of it applies.

The fix: List what the session needs, and move each item into the repository or the cloud environment before you start it.

Cross-references: settings precedence is Module 4.1; the environment layer is Module 4.5.

**If you remember one thing:** local surfaces share config; cloud sessions need it in the repo or environment.

## CLOSING REFRAME

This is the craft of choosing a surface: **one engine, many front ends, and a clear answer to where it runs.** The engineer who understands this does not ask "which app is best?" — they ask "where should this session execute, and what does it need to see?"
