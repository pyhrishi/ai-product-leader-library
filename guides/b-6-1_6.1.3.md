# MODULE 6.1.3 — QUALITY WORKFLOWS: FRESH CONTEXT IMPROVES REVIEW: THE COMPLETE CRAFT

## THE THESIS OF THIS TOPIC

**A reviewer that did not write the code finds different problems than the author, so a fresh session or subagent is the cheapest independent check, provided you scope what it is allowed to complain about.**

**Prove-it, in one sentence:** run one change through an author session and a fresh reviewer, and show a finding the reviewer made that the author did not, plus the scope sentence that kept it on correctness.

**The single most important discipline: give every reviewer a spec to check against and an explicit list of what to skip.**

**The counterintuitive claim you will learn to defend:** a fresh reviewer is a different view, not a smarter one: by default it is the same model or a smaller one, so you get independence, not extra intelligence [Claude Code docs, Best practices, 2026].

**THE TIME BUDGET.** Reading time: ~22 minutes. Prove-it time: ~2.5 hours (150 minutes, 6.8 times the reading time).

## 6.1.3.1 — WHY FRESH CONTEXT HELPS

**Framing.** The best-practices page says a second session is the easiest independent reviewer you can get: one session writes the code, another reviews it without having watched it being written, and you paste the findings back [Claude Code docs, Best practices, 2026]. The module overview gives the reason: the reviewer is not biased toward code it just wrote.

| Reviewer | Has seen | Bias risk |
|---|---|---|
| Author, same context | Its own reasoning and dead ends | Defends decisions it already made |
| Fresh session | The diff and the spec only | None from this session's history |
| Subagent with limited tools | What you hand it | None; and it cannot edit if tools are read-only |

The docs are explicit about what fresh review is not: handing the same task to a subagent does not make the answer better, and subagents by default run the same model or a smaller one [Claude Code docs, Best practices, 2026].

The failure mode: **Self-review blindness.** You ask the author session to double-check its own work and it confirms it, because it is judging its own reasoning from inside that reasoning.

The fix: Move the review to a fresh session or a subagent that sees only the diff and the written requirements.

Cross-references: verification in general is Module 2.3; subagents are Module 5.3.

**If you remember one thing:** independence comes from what the reviewer has not seen.

## 6.1.3.2 — SCOPE THE REVIEWER

**Framing.** The best-practices page shows a review prompt that checks a diff against `SPEC.md` and ends with `report gaps that affect correctness and skip style`. It warns not to drop the skip-style clause: a reviewer asked to find problems will always find something, and fixing every finding produces extra abstraction layers and tests for cases that cannot happen [Claude Code docs, Best practices, 2026].

```text
use a subagent to review the rate limiter diff against SPEC.md, check every
requirement is implemented and the listed edge cases have tests, report gaps
that affect correctness and skip style
```
[quoted from Claude Code docs, Best practices, 2026]

The failure mode: **Reviewer overreach.** An unscoped reviewer returns twelve style and architecture nits, you apply them all, and the diff grows three layers of abstraction nobody asked for.

The fix: Scope the prompt to correctness and stated requirements, and name what to skip; apply only findings tied to a requirement or a bug.

Cross-references: writing the spec is Module 9.1; over-engineering patterns are in sub-topic 6.10.7.

**If you remember one thing:** tell the reviewer what counts as a finding.

## 6.1.3.3 — A READ-ONLY REVIEWER

**Framing.** A reviewer subagent can be limited by its tool list. The docs describe a `reviewer` subagent in `.claude/agents/` given only `tools: Read, Grep, Glob`: a reviewer that cannot edit anything, with the limit enforced by Claude Code rather than requested in a prompt [Claude Code docs, Best practices, 2026].

| Property | Prompt-only reviewer | Read-only subagent reviewer |
|---|---|---|
| Can it edit files? | Only if you asked it not to | No; tools are Read, Grep, Glob |
| Where the limit lives | In the prompt | In the agent definition, enforced by Claude Code |
| Fresh context? | If a new session | Yes, its own context window |

You invoke it in plain language, such as `have the reviewer compare the rate limiter against SPEC.md`, and the gaps come back into your session where Claude can fix them [Claude Code docs, Best practices, 2026].

The failure mode: **Reviewer with edit rights.** Your reviewer has the full tool set and quietly 'fixes' what it flags, so the review and the change are no longer separable.

The fix: Define the reviewer with read-only tools in its frontmatter so it can report but not modify.

Cross-references: writing subagent files is Module 5.3; tool names are Module 1.2.

**If you remember one thing:** make the limit structural, not a polite request.

## 6.1.3.4 — WHAT IT COSTS

**Framing.** Independent review is not free. The best-practices page says subagents are great for parallel work, noisy output and independent review, but each of those costs extra tokens [Claude Code docs, Best practices, 2026]; the costs page adds that a subagent's requests draw on your usage [Claude Code docs, Costs, 2026].

| Choice | Extra cost | Use when |
|---|---|---|
| Same session self-check | None | Never as your only check |
| Fresh session you paste findings from | A second context plus your time | Risky or large changes |
| Read-only subagent | A subagent's tokens | Every change worth a second view |

To spend less on the reviewer, the costs page says to choose a smaller model for a subagent [Claude Code docs, Costs, 2026].

The failure mode: **Review-everything tax.** You send every one-line change through a full reviewer and the reviews cost more than the edits.

The fix: Reserve independent review for changes whose failure is expensive, and use a smaller model for routine reviews.

Cross-references: cost controls are Module 10.6; model choice is Module 4.6.

**If you remember one thing:** independence is worth paying for when mistakes are expensive.

## THE PROVE-IT SECTION

**Deliverable.** One real change reviewed twice (author and fresh reviewer) with both outputs, the scoped prompt and a note of which findings you acted on.

**Close this topic. Build the artifact below from memory. Return to the text only after your first attempt is complete.**

| Step | Action | Output |
|---|---|---|
| 1 | Implement one change in session A | A diff |
| 2 | Write a SPEC.md of requirements and edge cases | `SPEC.md` |
| 3 | Open session B (or a read-only subagent) and review against the spec | Findings |
| 4 | Add the scope clause: correctness only, skip style | Scoped prompt |
| 5 | Compare findings with session A's own self-review | Diff of findings |
| 6 | Apply only findings tied to a requirement | Applied list |

**A passing artifact looks like this:**

| Finding | Tied to | Action |
|---|---|---|
| Missing test for expired token | SPEC edge case 3 | Added test |
| Off-by-one in window reset | SPEC requirement 2 | Fixed |
| Rename helper for taste | None | Skipped by scope |

**A failing artifact (a realistic near-miss):**

| Element | What is wrong |
|---|---|
| Review prompt: 'find problems' | **Reviewer overreach** |
| Author reviewed its own diff | **Self-review blindness** |
| Reviewer had Edit and Write | **Reviewer with edit rights** |

**The verdict.** The artifact passes only if the reviewer was fresh, the prompt was scoped to a written spec, and at least one finding differs from the author's self-review.

## CLOSING REFRAME

This is the craft of independent review: **a fresh context, a written spec, a scope that excludes taste.** The engineer who understands this does not ask "did it look at the code?" — they ask "what has the reviewer not seen, and what is it allowed to flag?"
