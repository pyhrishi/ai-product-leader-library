# MODULE 1.3 — INSTALLATION, AUTHENTICATION AND FIRST RUN: THE COMPLETE CRAFT

---

## THE THESIS OF THIS MODULE

**A correct setup is not "it launches"; it is a known version, on a known account and billing path, in a trusted folder, with a diagnostic you can run when it breaks.**

**Prove-it, in one sentence:** install from scratch on a clean machine or account, sign in, complete one reviewed change, and fix one deliberately induced failure, with a log of each step.

**The single most important discipline: verify each layer before you stack the next.** Version, then login, then trust, then first task. A failure at layer four is usually a layer-one problem wearing a disguise.

**The counterintuitive claim you will learn to defend:** the first session should be a small, reviewed change, not a showpiece. The point is to see the loop, the diff and the permission prompts once, with nothing at stake.

**THE TIME BUDGET.** Reading time: ~20 minutes. Prove-it time: ~2 hours. 2 hours is 120 minutes, six times the reading time.

| Depth | What you can do after this module |
|---|---|
| L3 | Install, sign in, run a first session, and name what each setup step guards against |
| L4 | Choose the install path, account type and update policy for a team |
| L5 | Own a fleet rollout with pinned versions and managed settings |

Written at L3. Commands change with versions; the docs, not this page, are authoritative for the exact installer line.

## 1.3.1 — REQUIREMENTS AND INSTALL

**Framing.** Install paths multiply, and each has a different update behaviour. The recommended route is the **native installer**; alternatives exist for package managers and for npm [Claude Code docs, Setup, 2026]. Most surfaces need a Claude subscription or Console account; the CLI and the IDE extensions also support third-party providers [Claude Code docs, Overview, 2026].

| Platform | Documented path | Updates |
|---|---|---|
| macOS, Linux, WSL | `curl -fsSL https://claude.ai/install.sh \| bash` | Native installs auto-update |
| Windows (native) | `irm https://claude.ai/install.ps1 \| iex` in PowerShell | Auto-update |
| macOS | `brew install --cask claude-code` | Homebrew does not auto-update |
| Windows | `winget install Anthropic.ClaudeCode` | WinGet does not auto-update |
| Debian, Fedora, RHEL, Alpine | apt, dnf or apk packages | Per package manager |

[Claude Code docs, Overview and Setup, 2026; verify the current exact command on the Setup page before running]

**Where it lands.** The native installer puts the binary at `~/.local/bin/claude` on macOS and Linux, and `%USERPROFILE%\.local\bin\claude.exe` on Windows [Claude Code docs, Troubleshoot install, 2026].

**Platform notes that bite:**

- **Windows:** two routes. Native Windows needs Git Bash (set `CLAUDE_CODE_GIT_BASH_PATH` in settings if it is not found) and offers a PowerShell tool; WSL means you install and launch `claude` inside the WSL terminal, not from PowerShell or CMD [Claude Code docs, Setup, 2026].
- **Alpine and musl distributions:** the install command needs `bash` and `curl`, and Claude Code requires `bash` or `zsh`; Alpine ships neither by default, so install them and set `USE_BUILTIN_RIPGREP=0` [Claude Code docs, Setup, 2026].
- **ripgrep** is usually bundled; if search fails, see the search troubleshooting section [Claude Code docs, Setup, 2026].
- **IDE extensions** do not put `claude` on your PATH. The VS Code extension carries a private CLI copy for its own panel; run the standalone installer to use `claude` in a terminal [Claude Code docs, Troubleshoot install, 2026].

**Verify, always:**

```bash
claude --version     # prints e.g. "2.1.211 (Claude Code)"
claude doctor        # deeper check of installation and configuration
```

**Disagreement named:** older guidance listed Node.js 18 or newer as a prerequisite and installation by `npm install -g`; the current docs recommend the native installer and list npm as an advanced option [Claude Code docs, Setup, 2026]. **The current Setup page wins.** Do not install via npm unless you have a reason such as a locked-down environment.

The failure mode: **Install-path drift.** You install by one method, later by another, and end up with two binaries on PATH at different versions, so behaviour changes depending on which shell you opened.

The fix: pick one method, run `which -a claude` (or `where claude` on Windows) to list every copy, remove the extras, and confirm with `claude --version`.

The failure mode: **Copy-pasted installer.** You paste an install one-liner from a blog post or an old note rather than the current docs and run a script you did not read.

The fix: take the command only from the official Setup page, read what it does, and verify the version afterward.

Cross-references: choosing a surface is Module 7.1; enterprise rollout and version pinning are in Part 11.

**If you remember one thing:** one install path, one binary, and `claude --version` to prove it.

## 1.3.2 — SIGN-IN OPTIONS

**Framing.** How you sign in decides who pays, which limits apply and which features exist. The syllabus lists three families: a **Claude subscription** (Pro, Max, Team, Enterprise), the **Anthropic Console** with API billing, or a **cloud provider** (Amazon Bedrock, Google Cloud's Agent Platform, Microsoft Foundry, Claude Platform on AWS) [syllabus Module 1.3.2; Claude Code docs, Authentication, 2026].

| Path | Billing | Where limits come from | Typical user |
|---|---|---|---|
| Subscription (Pro, Max) | Included in plan; rolling usage windows | Plan limits; optional usage credits | Individual developer |
| Team or Enterprise plan | Org plan | Org policy and plan | Company |
| Console (API) | Per-token | Workspace spend limits | Heavy or automated use, CI |
| Cloud provider | Your cloud bill | Provider quotas | Orgs with cloud commitments and data-residency needs |

[Claude Code docs, Costs, 2026; Claude Help Center, 2026]

**Switching accounts.** If you are logged in through Console pay-as-you-go and want your subscription, run `/login` from within Claude Code to switch [Claude Help Center, 2026].

**Trade-off.** A subscription gives predictable cost and rate-limited usage. API billing gives uncapped throughput and exact per-token cost. The wrong choice shows up as either surprise throttling or a surprise invoice.

The failure mode: **Wrong-billing-path surprise.** You sign in with a Console key out of habit and a long session bills per token, or you rely on a subscription for a CI job that exceeds its windows.

The fix: choose the path deliberately, check which account `/login` shows, and use `/usage` to see what is being counted.

The failure mode: **Shared-credential shortcut.** A team shares one personal login or API key for convenience, so usage cannot be attributed and revoking one person's access means revoking everyone's.

The fix: use per-user accounts on a Team or Enterprise plan, or per-workspace Console keys with spend limits, and store keys in a secrets manager, not in repos or shell history.

Cross-references: plans and limits are Module 1.4; enterprise authentication is in Part 11, starting at Module 11.1.

**If you remember one thing:** the login you pick is your billing decision, so make it on purpose.

## 1.3.3 — FIRST SESSION

**Framing.** The first session has one job: let you see the whole loop once at low stakes. The syllabus sequence is: open a project folder, run `claude`, ask it to explain the codebase, make one small change, review the diff.

```bash
cd ~/projects/some-small-repo
git status                  # start clean so the diff is only Claude's
claude                      # starts an interactive session
```

| Step | Prompt (example) | What you are watching |
|---|---|---|
| 1. Orient | `give me an overview of this codebase` | Which files it reads: the gather phase |
| 2. Ask precisely | `how is authentication handled?` | Whether it searches rather than guesses |
| 3. Small change | `add a --verbose flag to the CLI and run the tests` | Permission prompts, edit, test run: all three phases |
| 4. Review | read the diff (`git diff`) | Whether the change matches the intent |
| 5. Commit or revert | `commit with a descriptive message` or `git restore .` | That you remain the gate |

Start with a clean working tree. If the repo is dirty, you cannot tell Claude's changes from yours, and `git restore` becomes dangerous.

**What good looks like.** By the end you should be able to point to one tool call of each kind (a read, a search, an edit, a shell command) in the transcript, and to the single permission prompt (if any) that appeared.

The failure mode: **Showpiece first session.** You open your most important repo and ask for a large refactor on day one, then cannot tell whether a bad result was setup, prompt or model.

The fix: use a small repo or a throwaway branch, make one scoped change, and read the diff before widening the task.

The failure mode: **Dirty-tree start.** You begin with uncommitted work, Claude edits files, and the two sets of changes blur together.

The fix: commit or stash first, work on a branch, and treat `git diff` as the review surface.

Cross-references: the explore, plan, implement, commit loop is Module 2.1; prompting is Module 2.2; checkpoints and undo are Module 2.5.

**If you remember one thing:** the first session is for seeing the loop, so keep the task small and the tree clean.

## 1.3.4 — TRUST DIALOG

**Framing.** A repository can carry configuration that Claude Code would act on. **Project trust is a dialog that accepts a directory before Claude Code loads its configuration** [Claude Code docs, Glossary, 2026]. Until you trust a directory, Claude Code holds back some of what the repository supplies, such as project allow rules and marketplaces from `.claude/settings.json` [Claude Code docs, Glossary, 2026].

| Fact | Detail |
|---|---|
| Scope | Acceptance is saved per project directory |
| Exception | Your home directory: trust is held for the current session only and the prompt reappears each launch |
| Before trust | Some repository-supplied content is held back; the docs list each kind in "What runs before you trust a folder" |
| Non-interactive | A `-p` session runs without a dialog; the docs state what it runs |

[Claude Code docs, Glossary, 2026]

**Why it exists.** A cloned repo is untrusted input. Its settings could define hooks or rules; the trust dialog is the moment you decide whether to honour them. This is the same reasoning as prompt-injection defence: content in a repo is data until you vouch for it.

**Practical rule.** Read the dialog. Trust folders you wrote or have reviewed. For an unfamiliar repository, read `.claude/settings.json` and `.claude/` contents first, or open it in a sandbox or cloud session.

The failure mode: **Reflexive trust.** You press accept on every folder without reading, including a freshly cloned repo from an unknown source whose `.claude/settings.json` registers a hook.

The fix: inspect `.claude/` and any `CLAUDE.md` in an unfamiliar repo before trusting it, and use a disposable environment for code you do not control.

The failure mode: **Headless blind spot.** You assume the dialog protects scripted runs, but `-p` sessions run without one.

The fix: in CI and scripts, control behaviour through explicit flags, managed settings and `--bare` where appropriate, and never run `-p` against untrusted checkouts with broad permissions.

Cross-references: sandboxing is Module 4.4; prompt injection and the security model are Module 11.1; headless mode is Module 6.8.

**If you remember one thing:** trust is a decision about someone else's configuration, so make it knowingly.

## 1.3.5 — UPDATING

**Framing.** Updates change behaviour. The docs' policy: **native installations auto-update in the background; Homebrew and WinGet do not** [Claude Code docs, Overview and Setup, 2026].

| Task | Command or setting |
|---|---|
| Check version | `claude --version` |
| Update now | `claude update` |
| Already latest | Native reports "Claude Code is up to date (<version>)"; Homebrew, WinGet and apk report "Claude is up to date!" |
| Release channels | `latest` or `stable`, selectable by the native installer |
| Pin a version | The native installer accepts a specific version number |
| Block all updates | `DISABLE_UPDATES` (blocks manual updates too) |
| Read what changed | `/release-notes` |

[Claude Code docs, Setup / Installation, 2026]

**When to pin.** Pin when you distribute through your own channels and need everyone on the same version, or when a workflow depends on a specific behaviour. Otherwise take updates, because feature availability is version-gated: for example, reading `AGENTS.md` directly needs v2.1.277 or later, and `onFailure: "block"` for hooks needs v2.1.295 or later [Claude Code docs, Glossary and Hooks, 2026].

The failure mode: **Silent-update regression.** An auto-update changes a behaviour your team's workflow relied on, and no one can say which version it started on.

The fix: record `claude --version` in bug reports and runbooks, read `/release-notes` after updates, and pin via the `stable` channel or a version number for fleets.

The failure mode: **Stale package-manager install.** You installed with Homebrew or WinGet, assume it self-updates, and months later cannot use a feature whose docs assume a newer version.

The fix: run `claude update` or the package manager's upgrade on a schedule, and compare `claude --version` to what the docs require.

Cross-references: settings and update-related environment variables are Modules 4.1 and 4.8; enterprise version control is in Part 11.

**If you remember one thing:** your version is part of every bug report, so know it and control it.

## 1.3.6 — LEARNING IN-PRODUCT

**Framing.** The product teaches itself, which is faster than searching docs. The syllabus names three entry points: `/powerup` interactive lessons, `/help`, and `/doctor` (or `claude doctor` from the shell) for a setup checkup [syllabus Module 1.3.6; Claude Code docs, Setup, 2026].

| Tool | Use it when | Failure it prevents |
|---|---|---|

| `/powerup` | You want a guided lesson inside the product | Cold-start confusion; the exact lesson list changes, check in-product |

| `/memory` | You want to confirm which CLAUDE.md and memory files loaded | Assuming instructions were read |

[`/powerup` details not verified against the docs this session; run it to see the current lessons]

The failure mode: **Docs-first debugging.** You spend 30 minutes searching the web for a symptom that `claude doctor` would have diagnosed in seconds.

The fix: run `claude doctor` first, then search the Troubleshoot install page with the exact error string.

Cross-references: the vocabulary behind these commands is Module 1.5; context inspection is Module 3.1; memory inspection is Module 3.2.

## 1.3.7 — TROUBLESHOOTING INSTALL AND LOGIN

**Framing.** Most install and login failures fall into five buckets. The Troubleshoot install page is organised by error string; the discipline is to match your exact message, not your guess [Claude Code docs, Troubleshoot install, 2026].

| Symptom | Likely cause | First action |
|---|---|---|
| `command not found: claude` or `'claude' is not recognized` | Install directory not on PATH | Verify PATH includes `~/.local/bin` (Windows: `%USERPROFILE%\.local\bin`); open a new terminal or `source ~/.zshrc` |
| PowerShell installer finishes but `claude` missing or old | Terminal not restarted; PATH not refreshed | Close and reopen PowerShell, verify PATH |
| `A parameter cannot be found that matches parameter name 'fsSL'` | Used the macOS/Linux `curl` command in PowerShell | Use the PowerShell installer line |
| Installer cannot download | Network, proxy or firewall | Check connectivity; set the proxy variables for the installer |
| Crash or hang though `--version` prints | Corrupt binary or conflicting installs | Run `claude doctor`; list every `claude` on PATH |
| Version unexpectedly old | Multiple installs; legacy `~/.claude/local` from older npm installs | Remove duplicates, keep one |
| Login loops or wrong account | Credential for another account cached | `/login` to switch; check which account is active |

[Claude Code docs, Troubleshoot install and Claude Help Center, 2026]

**The PATH sequence, in order:**

```bash
# 1. Does the binary exist?
ls -l ~/.local/bin/claude
# 2. Is its folder on PATH?
echo "$PATH" | tr ':' '\n' | grep -n 'local/bin'
# 3. Fix for this shell, then persist in ~/.zshrc or ~/.bashrc
export PATH="$HOME/.local/bin:$PATH"
# 4. Confirm, and list ALL copies
claude --version && which -a claude
```

Three places a `claude` binary can come from: `~/.local/bin/claude` (native installer), `~/.claude/local/` (a legacy local npm install from older versions) and the global npm list [Claude Code docs, Troubleshoot install, 2026].

If the page says "try again in a few minutes", believe it: the docs note that network failures are often temporary [Claude Code docs, Troubleshoot install, 2026].

The failure mode: **Guess-and-reinstall loop.** You reinstall repeatedly when the binary was fine and PATH was the problem, adding a second copy each time.

The fix: check `ls ~/.local/bin/claude`, then PATH, then `which -a claude`, before you reinstall anything.

The failure mode: **Wrong-shell fix.** You fix PATH in one shell's profile (`~/.bashrc`) while using another (zsh), so the fix never applies.

The fix: identify the shell with `echo $SHELL`, edit the matching profile, then open a new terminal.

Cross-references: runtime troubleshooting is Part 12; permission issues are Module 4.2.

**If you remember one thing:** match your exact error string to the table, then check PATH before you reinstall.

## THE PROVE-IT SECTION

**Deliverable.** A setup log for a clean install, one reviewed change, and one induced-and-fixed failure.

**Close this module. Build the artifact below from memory. Return to the text only after your first attempt is complete.**

| Step | Action | Output |
|---|---|---|
| 1 | On a clean machine, user account or container, install by the recommended path | `claude --version` output |
| 2 | Run `claude doctor` and save the result | `doctor.txt` |
| 3 | Sign in; record which account type and billing path is active | One line |
| 4 | In a small repo with a clean tree, run the five-step first session: orient, ask, small change, review diff, commit or revert | Transcript and `git diff` |
| 5 | Open an untrusted-looking folder with a `.claude/settings.json` and read the trust dialog without accepting; list what it says is held back | Three bullets |
| 6 | Induce a PATH failure: remove `~/.local/bin` from PATH in one shell, reproduce `command not found`, fix it | Before and after output |
| 7 | Run `claude update` (or the package manager equivalent) and read `/release-notes` | Version before and after |

**A passing artifact looks like this:**

| Element | Evidence |
|---|---|
| Version | A version string and the install method named |
| Doctor | A saved output with no unresolved warnings, or each warning explained |
| Billing | "Subscription (Pro), `/login` confirmed" |
| First session | A diff of under ~30 lines on a branch, with the tests run |
| PATH failure | The exact error string, the three checks in order, and the fixed `which -a claude` showing one copy |

**A failing artifact (a realistic near-miss):**

| Element | What is wrong |
|---|---|
| "Reinstalled three times, now works" | **Guess-and-reinstall loop**; two binaries may be on PATH |
| First change was a 400-line refactor on the main repo | **Showpiece first session** and **Dirty-tree start** if uncommitted work existed |
| Trust dialog accepted on a cloned repo without reading | **Reflexive trust** |

**The verdict.** The artifact passes only if the PATH failure is reproduced and fixed with the three ordered checks, and `which -a claude` shows exactly one copy at the end.
