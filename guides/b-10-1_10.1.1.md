## 10.1.1.1 — FIVE DECISIONS, ONE ORDER

**Framing.** The admin-setup page is explicitly a decision map that walks deployment decisions in order. Each row names what you are choosing and links to the reference page for that area [Claude Code docs, Set up Claude Code for your organization, 2026].

| # | Decision | What you are choosing | Where the answer lives |
|---|---|---|---|
| 1 | Choose your API provider | Where Claude Code authenticates and how it is billed | Authentication, Amazon Bedrock, Google Cloud's Agent Platform, Microsoft Foundry |
| 2 | Decide how settings reach devices | How managed policy reaches developer machines | Server-managed settings, delivery mechanisms |
| 3 | Decide what to enforce | Which tools, commands and integrations are allowed | Permissions, Sandboxing |
| 4 | Set up usage visibility | How you track spend and adoption | Analytics, Monitoring, Costs |
| 5 | Review data handling | Retention and compliance posture | Data usage, Security |

The failure mode: **Policy-first drafting.** You draft a long list of permission rules before you know which provider and delivery channel you will use, then discover the channel cannot carry some of the keys.

The fix: Do decisions 1 and 2 first; only then write the keys for decision 3.

Cross-references: the module that holds each decision is Module 10.2 for the provider, Module 10.4 for delivery and policy, Module 10.6 for cost and Module 10.7 for data.

**If you remember one thing:** decision order matters because the early answers limit the later ones.

## 10.1.1.2 — PROVIDER CHOICE GATES FEATURES

**Framing.** The recommended default is Claude for Teams or Enterprise: one per-seat subscription for Claude Code and claude.ai with no infrastructure to run. Console suits API-first or pay-as-you-go; Bedrock, Google Cloud's Agent Platform and Foundry suit organisations that want to inherit existing cloud compliance controls and billing [Claude Code docs, Set up Claude Code for your organization, 2026]. Some features need a claude.ai account: cloud sessions, Routines, Code Review, Remote Control and the Chrome extension are not available through Console API keys or cloud-provider credentials alone [Claude Code docs, Set up Claude Code for your organization, 2026].

| Provider | Choose this when |
|---|---|
| Claude for Teams / Enterprise | You want one per-seat subscription and no infrastructure (the default recommendation) |
| Claude Console | You are API-first or want pay-as-you-go billing |
| Amazon Bedrock | You want to inherit existing AWS compliance controls and billing |
| Google Cloud's Agent Platform | You want to inherit existing GCP compliance controls and billing |
| Microsoft Foundry | You want to inherit existing Azure compliance controls and billing |

The failure mode: **Seatless cloud rollout.** You deploy through a cloud provider and promise developers cloud sessions or Code Review, but nobody holds a claude.ai seat, so the features are simply absent.

The fix: Before rollout, list the claude.ai-only features you promised and decide who also needs a Teams or Enterprise seat.

Cross-references: the full backend comparison is Module 10.2; plan limits are Module 1.4.

**If you remember one thing:** pick the provider by the features you need, not only by the bill you want.

## 10.1.1.3 — FOUR SOURCES, ONE WINNER

**Framing.** Managed settings define organisation policy and take precedence over local developer configuration. Claude Code checks four sources in priority order: server-managed first, then plist or registry policy, then file-based managed settings, then the Windows user registry [Claude Code docs, Set up Claude Code for your organization, 2026]. By default the first source that delivers a policy key wins and the rest are ignored rather than merged [Claude Code docs, Deploy managed settings, 2026].

| Priority | Mechanism | Delivery |
|---|---|---|
| Highest | Server-managed | claude.ai admin console, or a self-hosted Claude apps gateway |
| High | plist / registry policy | macOS `com.anthropic.claudecode`; Windows `HKLM\SOFTWARE\Policies\ClaudeCode` |
| Medium | File-based managed | `/Library/Application Support/ClaudeCode/managed-settings.json`, `/etc/claude-code/managed-settings.json`, `C:\Program Files\ClaudeCode\managed-settings.json` |
| Lowest | Windows user registry | `HKCU\SOFTWARE\Policies\ClaudeCode`, writable without elevation, so a convenience default, not enforcement |

Server-managed settings are fetched at startup and refreshed hourly during the session; delivery through the admin console needs a Teams or Enterprise plan [Claude Code docs, Set up Claude Code for your organization, 2026].

The failure mode: **Mixed-provider gap.** Part of the fleet uses Bedrock or Vertex, you configure only server-managed settings, and those developers silently receive no policy.

The fix: Deliver server-managed settings for claude.ai users plus a file-based or plist/registry fallback for everyone else.

Cross-references: delivery detail is Module 10.4; the gateway option is Module 10.5.

**If you remember one thing:** the highest source with a policy key wins, so one stray source can hide the rest.

## 10.1.1.4 — VERIFY, THEN ONBOARD

**Framing.** After configuring managed settings, have a developer run `/status`. On the Status tab the `Setting sources` line shows `Enterprise managed settings` followed by the winning source in parentheses [Claude Code docs, Set up Claude Code for your organization, 2026]. For login problems the page lists three common fixes: `/logout` then `/login` to switch accounts, `claude update` if the enterprise auth option is missing, and a terminal restart after updating. A seat without Claude Code access produces the message 'You haven't been added to your organization yet' [Claude Code docs, Set up Claude Code for your organization, 2026].

```text
/status  ->  Setting sources: Enterprise managed settings (file)
                 label tells you which of the four sources won
```

The failure mode: **Unverified go-live.** You announce the rollout after editing the console, and nobody checks a real machine, so a typo in the policy file means no policy at all.

The fix: Run `/status` on one machine per OS and provider before announcing.

Cross-references: the verification procedure is Module 10.4; first-run login is Module 1.3.

**If you remember one thing:** a rollout is not done until `/status` on a real machine names the source you intended.
