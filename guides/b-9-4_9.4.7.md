## THE THESIS OF THIS TOPIC

**Keep diffs reviewable: one concern per pull request, bounded size, and explicit limits in the prompt, because an agent will happily touch every file that looks related.**

**Prove-it, in one sentence:** set a diff-size policy, apply it to one task and show that scope stayed within it.

**The single most important discipline: state the scope boundary in the prompt and check the diff against it before review.**

**The counterintuitive claim you will learn to defend:** cheap code makes big diffs easy, which moves the cost to reviewers; the limit protects them.

## 9.4.7.1 — CAUSE OF CHURN

**Framing.** Claude tends to read a request conservatively, but the docs also note that when you want the fuller version you should say so; the reverse holds: when you want less, bound it [Claude Code docs, Best practices, 2026]. Unscoped prompts and broad `/simplify` runs create churn.

| Cause | Control |
|---|---|
| Vague prompt | Name files and out-of-scope |
| Reformat on save | Formatter hook runs only on touched files (docs example: PostToolUse on Edit or Write) |
| Broad refactor | One module per task |
| Generated code | Exclude from edits via deny rule |

The failure mode: **Scope creep diff.** The diff touches 40 files for a 3-file task because the prompt did not set limits.

The fix: Add 'touch only these files; list anything else you think should change instead of changing it'.

Cross-references: quality discipline is Module 9.13.2.

**If you remember one thing:** ask for suggestions, not edits, outside scope.

## 9.4.7.2 — MEASURING AND LIMITING

**Framing.** Check `git diff --stat` before asking for review. Define a limit for your team; the number is a policy choice and the docs give none.

```bash
git diff --stat main...HEAD | tail -1
```

| Policy | Example (illustrative) |
|---|---|
| Max changed files | 15 |
| Max changed lines | 400 |
| Split rule | Separate refactor from behaviour change |
| Exempt | Generated files, lockfiles (reviewed by summary) |

The failure mode: **Unmeasured diff.** Nobody looks at the stat, and a 3,000-line diff goes to review.

The fix: Add the stat to the PR template and the Stop hook for large diffs.

Cross-references: PR conventions are Module 9.12.2.

**If you remember one thing:** measure before asking for review.

---

## 9.4.7.3 — SPLITTING AFTER THE FACT

**Framing.** When a diff is too big, ask Claude to propose a split into commits or PRs by concern, then apply it with interactive-free commands. Keep each piece green.

| Split by | Result |
|---|---|
| Mechanical (renames) | One PR, reviewed by summary |
| Behaviour | One PR with tests |
| Cleanup | One PR |
| Docs | One PR |

The failure mode: **Mixed-concern PR.** Renames, features and docs sit in one PR, so reviewers miss the behaviour change.

The fix: Split by concern and keep each branch green.

Cross-references: pairing patterns are Module 9.12.5.

**If you remember one thing:** one concern, one PR.
