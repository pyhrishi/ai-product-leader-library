# MODULE 1.1.4 — SAME ENGINE, MANY SURFACES: WHAT CARRIES OVER: THE COMPLETE CRAFT

## THE THESIS OF THIS TOPIC

**Because every surface runs the same engine, your configuration travels with you; because features differ by surface, plan and provider, availability does not.**

**Prove-it, in one sentence:** list five things that carry across surfaces and five that do not, each with a source you verified.

**The single most important discipline: put shared rules in files the engine reads, and verify a feature exists on every surface and plan before you depend on it.**

**The counterintuitive claim you will learn to defend:** more surfaces do not mean more consistency. A convenience feature on one surface can be the exact thing a teammate on another plan cannot use.

## 1.1.4.1 — WHAT IS SHARED

**Framing.** Each surface connects to the same underlying engine, so the files that configure Claude Code work across all of them: the docs say your CLAUDE.md files, settings and MCP servers carry over between local surfaces [Claude Code docs, Overview and Platforms, 2026].

| Shared across local surfaces | Where it lives | Why it carries |
|---|---|---|
| Project instructions | `./CLAUDE.md` or `./.claude/CLAUDE.md` | Read from disk by the engine |
| Settings | `~/.claude/settings.json`, `.claude/settings.json` | Same layered hierarchy everywhere |
| MCP servers | `.mcp.json`, user config | Same server connection layer |
| Skills, hooks, subagents | `.claude/` | Same extension loader |
| Auto memory | `~/.claude/projects/` | Keyed by repository |

The settings hierarchy, highest to lowest, is managed policy, command-line arguments, local settings, project settings, then user settings; arrays merge across layers and scalars at a higher layer override lower ones [Claude Code docs, Glossary, 2026].

The failure mode: **Habit-over-file.** A rule lives in your terminal habits ('I always run X first') rather than in a file, so a teammate on another surface never gets it.

The fix: Move the rule into CLAUDE.md, settings or a hook, and commit it.

Cross-references: settings are Module 4.1; CLAUDE.md is Module 3.2; the `.claude` directory is Module 3.3.

**If you remember one thing:** if a rule must apply on every surface, put it in a file the engine reads.

## 1.1.4.2 — WHAT IS NOT SHARED

**Framing.** Availability differs by surface and by account. Cloud sessions are the sharpest case: the glossary says cloud sessions start from a fresh clone of your repository and do not read `~/.claude/` on your machine [Claude Code docs, Glossary, 2026].

| Differs | Example | Source |
|---|---|---|
| Scripting and the Agent SDK | CLI only | Platforms |
| Visual diff viewer, app preview, parallel sessions | Desktop | Platforms |
| Computer use and Dispatch | Desktop, Pro and Max | Platforms, Glossary |
| Third-party providers | CLI, VS Code, JetBrains (Desktop has its own provider path) | Overview, Platforms |
| User-level config in cloud sessions | Cloud starts from a fresh clone, no `~/.claude/` | Glossary |
| Artifacts sharing | Pro and Max: public link; Team and Enterprise: organisation sharing | Glossary |

[Claude Code docs, Overview, Platforms and Glossary, 2026]

The practical consequence: anything in your user-level `~/.claude/` (personal CLAUDE.md, personal skills) will not exist in a cloud session. Project-level files, committed to the repository, will.

The failure mode: **Assumed parity.** You write a runbook around a command or feature seen on one surface, and a teammate on another surface or plan cannot do it.

The fix: Check the platforms and feature-availability pages for every surface, plan and provider your team uses, and keep the check in the runbook.

Cross-references: surfaces compared in depth are Module 7.1; cloud environments are Module 4.5; plans and availability are Module 1.4.

**If you remember one thing:** user-level config does not travel to the cloud; project files do.

## 1.1.4.3 — DESIGNING FOR PORTABILITY

**Framing.** Treat your repository as the portable unit. Anything that must work for every teammate and every surface goes in committed project files; anything personal stays in `~/.claude/`.

```
 repo/
 ├─ CLAUDE.md                    # conventions, commands, architecture notes (committed)
 ├─ .mcp.json                    # project MCP servers (committed; has its own approval prompt)
 └─ .claude/
    ├─ settings.json             # team permissions and hooks (committed)
    ├─ settings.local.json       # personal overrides (gitignored)
    ├─ skills/  agents/  rules/  # extensions (committed)
 ~/.claude/                      # personal: CLAUDE.md, skills, settings (NOT in cloud sessions)
```

A short portability checklist: list the features your workflow uses, tag each with the surfaces, plans and providers it needs, record `claude --version`, and put the list at the top of the runbook.

Servers in a project's `.mcp.json` have their own approval prompt, so a committed server is not silently trusted [Claude Code docs, Security, 2026].

The failure mode: **Personal-config dependency.** Your workflow depends on a personal skill or setting in `~/.claude/`, and it breaks in a cloud session or for a new teammate.

The fix: Move shared skills and settings into the repository's `.claude/` and commit them.

Cross-references: skills are Module 5.2; plugins and marketplaces for sharing are Module 5.6; managed settings for orgs are in Part 11.

**If you remember one thing:** the repo is the portable unit; `~/.claude/` is yours alone.

**A failing artifact (a realistic near-miss):**

| Element | What is wrong |

| No version recorded | The availability claim cannot be re-checked |

**The verdict.** The artifact passes only if you proved one item loads from a fresh clone and every surface-specific claim has a doc citation.
