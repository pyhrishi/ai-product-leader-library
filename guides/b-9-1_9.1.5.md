# MODULE 9.1.5 — SPECS AS THE REVIEW ARTEFACT: THE COMPLETE CRAFT

## THE THESIS OF THIS TOPIC

**When a spec exists, a reviewer checks the diff against stated requirements instead of guessing intent, which makes review faster and makes gaps reportable.**

**Prove-it, in one sentence:** review one diff against one spec and produce a gap list that cites requirement ids.

**The single most important discipline: review the diff against the spec first, then for style only if asked.**

**The counterintuitive claim you will learn to defend:** a reviewer who is told to find problems will always find something, so the spec must bound what counts as a problem [Claude Code docs, Best practices, 2026].

## 9.1.5.1 — TWO REVIEWERS, TWO QUESTIONS

**Framing.** The docs describe two review routes. In the terminal, `/code-review` reviews the diff in a fresh subagent that never saw your conversation, so it is not swayed by the reasoning that produced the code [Claude Code docs, Best practices, 2026]. The spec review is a prompt you write yourself to check the work against your plan [Claude Code docs, Best practices, 2026].

| Reviewer | Question | Standard |
|---|---|---|
| `/code-review` | Are there correctness bugs? | General correctness |
| Spec-review prompt | Is every requirement built and every edge case tested? | SPEC.md |
| Human | Is this the right thing and is it maintainable? | Judgement |

`/code-review [low|medium|high|xhigh|max|ultra] [--fix] [--comment] [pr#|branch|path]` reviews the current diff, a PR number, a branch or a path; `--comment` posts findings to the PR [Claude Code docs, Commands, 2026].

The failure mode: **Wrong-standard review.** You run a general bug review and conclude the feature is complete, but a requirement was never built.

The fix: Run the spec-review prompt as well; a bug hunt cannot find an omission.

Cross-references: AI-code review norms are Module 9.12.3; fresh-context review is Module 9.13.3.

**If you remember one thing:** bugs and omissions need different reviewers.

## 9.1.5.2 — WRITING THE SPEC-REVIEW PROMPT

**Framing.** Use the docs' form: a subagent reviews the diff against SPEC.md, checks every requirement is implemented and the listed edge cases have tests, reports gaps that affect correctness and skips style [Claude Code docs, Best practices, 2026].

| Output column | Meaning |
|---|---|
| Requirement id | R1, E2, V1 from SPEC.md |
| Status | Built, partial, missing |
| Evidence | File:line or test name |
| Severity | Affects correctness or not |

```text
Review the diff against SPEC.md. Table: id, status, evidence. Report only gaps that
affect correctness. Skip style.
```

The failure mode: **Style-noise review.** Style comments drown the two real gaps and the author fixes the wrong things.

The fix: Keep 'skip style' in the prompt and ask for severity so triage is mechanical.

Cross-references: refactor guard is Module 9.4.7.

**If you remember one thing:** a table keyed to ids makes the review auditable.

## 9.1.5.3 — WHAT REVIEWERS DO WITH THE RESULT

**Framing.** The finding list is input to a decision, not a to-do list. The docs warn that fixing every finding from a reviewer told to find problems yields extra abstraction layers and tests for cases that cannot happen [Claude Code docs, Best practices, 2026].

| Gap type | Action |
|---|---|
| Requirement missing | Build it, add a test |
| Edge case untested | Add a test (Module 9.2.3) |
| Spec wrong | Edit the spec first (Module 9.1.6), then the code |
| Style only | Ignore unless the team rule says otherwise |

The failure mode: **Fix-everything reflex.** You fix every finding and the diff grows with defensive code the spec never asked for.

The fix: Triage each finding against the spec; reject any that does not map to a requirement or a real edge case.

Cross-references: diff size limits are Module 9.13.3.

**If you remember one thing:** findings are proposals, not orders.

**Deliverable.** A spec-review table for one real diff, with each gap mapped to a requirement id and an action.

| Step | Action | Output |
|---|---|---|
| 1 | Pick a diff with a SPEC.md | Inputs |

**A passing artifact looks like this:**

| Id | Status | Action |
|---|---|---|
| R2 | missing | Build |
| E1 | untested | Add test |

**A failing artifact (a realistic near-miss):**

| Element | What is wrong |
|---|---|
| Only a bug review | **Wrong-standard review** |
| Every finding fixed | **Fix-everything reflex** |

**The verdict.** The artifact passes only if at least one finding came from the spec review that the bug review did not report, and each action cites an id.

## CLOSING REFRAME

This is the craft of spec review: **a fixed standard, a table of ids, triage before fixing.** The engineer who understands this does not ask "did the reviewer find anything?" — they ask "which requirement is unmet?"
