# MODULE 1.1.1 — DEFINITION: WHAT CLAUDE CODE IS, IN ONE SENTENCE YOU CAN DEFEND: THE COMPLETE CRAFT

## THE THESIS OF THIS TOPIC

**Claude Code is defined by four verbs, not by a product category: it reads your codebase, edits files, runs commands and integrates with your tools. Remove any one verb and you have a different, weaker thing.**

**Prove-it, in one sentence:** write the definition from memory, then show one transcript line for each verb that proves it.

**The single most important discipline: test any definition of Claude Code by asking which verb it drops.** "An AI that suggests code" drops run. "An AI that edits files" drops observe. Definitions that drop a verb produce the wrong workflows.

**The counterintuitive claim you will learn to defend:** the model is not the product. The docs call Claude Code the agentic harness around the model: the model reasons, the harness supplies tools, context management and the execution environment [Claude Code docs, Glossary, 2026]. Most things people call "Claude being dumb" or "Claude being clever" are properties of the harness.

## 1.1.1.1 — THE SENTENCE, VERB BY VERB

**Framing.** The official definition is one sentence: **Claude Code is an agentic coding tool that reads your codebase, edits files, runs commands, and integrates with your development tools**, available in the terminal, IDE, desktop app and browser [Claude Code docs, Overview, 2026]. Every clause earns its place. Read it as four capabilities, each of which removes a specific limit of earlier tools.

| Verb | What it adds | Without it you are back to | Evidence you can see |
|---|---|---|---|
| **Reads** the codebase | Claude finds what it needs itself | Pasting files into a chat by hand | Read and search tool calls in the transcript |
| **Edits** files | Changes land in your working tree | Copying code out of a chat window | A diff in `git diff` |
| **Runs** commands | Tests, builds, servers, git | You running everything and reporting back | A shell tool call and its output |
| **Integrates** with tools | Git, MCP servers, CI, chat, browser | A tool that cannot reach where work actually lives | MCP tools, `gh`, a GitHub Actions run |

The word that connects the verbs is **agentic**: Claude acts, observes the result and decides the next action, rather than answering once and stopping [Claude Code docs, Glossary, 2026]. The glossary defines agentic coding as a workflow where the AI reads files, runs commands and makes changes autonomously while you watch, redirect or step away, as opposed to chat-based assistants that respond with text you must apply yourself [Claude Code docs, Glossary, 2026].

```
  REAL TASK:  "write tests for the auth module, run them, and fix any failures"
              (an example prompt from the docs [Claude Code docs, Overview, 2026])

  reads  ──► finds the auth module and existing test style
  edits  ──► writes the test file
  runs   ──► executes the test suite
  reads  ──► reads the failure output
  edits  ──► fixes the code or the test
  runs   ──► executes again until green
```

Notice the order: **runs** is what makes the second **edits** possible. A tool that only reads and edits writes code blind. The run-and-observe step is the whole difference between suggestion and agency.

**The "dev tools" clause.** Integration is where the definition stops being about one machine. The overview lists git, command-line tools, MCP servers and CI systems as places Claude Code connects, and the docs say it can pipe in the Unix style, for example feeding the last 200 lines of a log to a non-interactive run [Claude Code docs, Overview, 2026].

```bash
# The docs' own pattern: Claude Code as a Unix tool
tail -200 app.log | claude -p "Slack me if you see any anomalies"
# (the pipe-and-prompt shape is from the docs; the specific prompt wording here is illustrative)
```

The failure mode: **Verb-skipping.** You grant Claude the ability to read and edit but never give it a command to run, so it writes plausible code, stops, and you become the one who runs the tests.

The fix: every task you hand over includes the command that proves it worked (a test, a build, a script), so the run-and-observe verbs are part of the task.

Cross-references: the loop that links the verbs is Module 1.2; verification design is Module 2.3; the vocabulary of "harness" and "agentic" is Module 1.5.

**If you remember one thing:** reads, edits, runs, integrates — and the run is what turns an editor into an agent.

## 1.1.1.2 — THE HARNESS IS THE PRODUCT

**Framing.** The docs split the system in two: **Claude is the model, Claude Code is the harness**. The glossary defines the agentic harness as the tools, context management and execution environment that turn a language model into a capable coding agent; it supplies file access, shell execution, permission gating, memory loading and the loop that chains actions together [Claude Code docs, Glossary, 2026]. The How Claude Code works page puts it as: the model reasons, the tools act [Claude Code docs, How Claude Code works, 2026].

```
  ┌───────────────────────── HARNESS (Claude Code) ─────────────────────────┐
  │                                                                         │
  │   MODEL                          the harness provides:                  │
  │   ┌──────────┐                   ● tools (read/edit/run/search/web)     │
  │   │ reasons, │ ◄──── context ──── ● context management + compaction     │
  │   │ decides  │                    ● permission gating (modes, rules)    │
  │   │ next step│ ───── tool call ──►● memory loading (CLAUDE.md, memory)  │
  │   └──────────┘                    ● hooks, extensions, the loop itself  │
  └─────────────────────────────────────────────────────────────────────────┘
```

This matters because the two layers fail differently, and the fix lives in a different place:

| Symptom | Layer | Typical cause | Where you fix it |
|---|---|---|---|
| "It asked permission 20 times" | Harness | Permission mode and rules | Settings, modes (Part 4) |
| "It forgot my rule mid-session" | Harness | Compaction summarised a chat-only instruction | CLAUDE.md or a hook |
| "It can't jump to definitions" | Harness | No code-intelligence plugin installed | Install the plugin |
| "It misjudged an architectural trade-off" | Model | Reasoning depth | Stronger model or higher effort, a better prompt |
| "It stopped when the work looked done" | Harness plus prompt | No check Claude could run | Add a verifiable check |

The docs also tie model choice to the harness: Sonnet handles most coding tasks well, Opus gives stronger reasoning for complex architectural decisions, and you switch with `/model` or `claude --model <name>` [Claude Code docs, How Claude Code works, 2026]. The same harness drives whichever model you pick.

**An L4 consequence.** Because the harness is separable from the model, the same harness can run on different providers. The CLI, VS Code and JetBrains support third-party providers; most other surfaces need a Claude subscription or Console account [Claude Code docs, Overview, 2026]. Capability then depends on both the model you route to and the features the harness exposes for that route.

The failure mode: **Model-attribution error.** You blame or credit "the model" for something the harness controls (a permission prompt, a lost instruction, a missing tool), and spend an hour rewriting prompts for a problem a setting would fix.

The fix: before changing the prompt, ask which layer owns the symptom using the table above; change the prompt only if the layer is the model.

Cross-references: the loop and its intervention points are Module 1.2; models, effort and speed are Module 4.6; permissions are Module 4.2.

**If you remember one thing:** when something goes wrong, ask "model or harness?" before you touch the prompt.

## 1.1.1.3 — THE FIVE TOOL CATEGORIES

**Framing.** "Reads, edits, runs" are not abstractions; they are tools with names. The docs group the built-in tools into **five categories**: file operations, search, execution, web and code intelligence [Claude Code docs, How Claude Code works, 2026]. Knowing the categories is how you predict what Claude can do without being told.

| Category | What it lets Claude do | Example tools | Permission behaviour in Manual mode |
|---|---|---|---|
| **File operations** | Read files, edit code, create new files, rename and reorganise | Read, Edit, Write, NotebookEdit | Reads inside the working directory run without prompting; edits prompt |
| **Search** | Find files by pattern, search content by regex, explore a codebase | Glob, Grep | Run without prompting inside the working directory |
| **Execution** | Run shell commands, start servers, run tests, use git | Bash (PowerShell on Windows), Monitor | Prompt, except a built-in set of read-only commands |
| **Web** | Search the web, fetch documentation, look up error messages | WebSearch, WebFetch | Prompt |
| **Code intelligence** | See type errors and warnings, jump to definitions, find references | LSP, via code-intelligence plugins | Run without prompting |

[Claude Code docs, How Claude Code works and Tools reference, 2026. The tools-reference page was read through search excerpts only, so verify the permission column against the page for your version.]

Beyond the five: tools for spawning subagents, asking you questions and tracking tasks, plus any tools your MCP servers expose [Claude Code docs, How Claude Code works, 2026]. Claude Code also layers extensions on top of the built-ins: skills, MCP, hooks and subagents.

**The tool names are an API.** The exact tool name strings are the same ones you use in permission rules, subagent tool lists and hook matchers [Claude Code docs, Tools reference, 2026]. That makes this table a map of your future control surface: `Bash(npm run *)` and `Read(~/secrets/**)` only work if you know that `Bash` and `Read` are the names.

**Choosing between categories in practice.**

```
 Claude needs to know something about the code
 ├─ where is X?                    ► Search (Glob by name, Grep by content)
 ├─ what does this file say?       ► File ops (Read)
 ├─ what does this symbol mean?    ► Code intelligence (if plugin installed), else Grep + Read
 ├─ does this actually work?       ► Execution (run the test or script)
 └─ what does the library do?      ► Web (fetch the docs)
```

The failure mode: **Missing-category blindness.** You expect symbol-aware navigation (go to definition, find references) and Claude falls back to text search, because the code-intelligence category is empty until you install a plugin.

The fix: check what is loaded with `/context` and `/mcp`, install the relevant code-intelligence plugin for your language, and confirm by asking Claude to find all references to one function.

The failure mode: **Tool-name guessing.** You write a permission rule or hook matcher with a plausible name that is not a real tool, so it silently matches nothing.

The fix: copy names from the Tools reference, and test every rule by triggering the action once.

Cross-references: the full tool list and rule syntax are Module 1.2; code-intelligence plugins are Module 5.8; MCP-provided tools are Module 5.5.

**If you remember one thing:** five categories, and one of them (code intelligence) needs a plugin before it exists.

## 1.1.1.4 — WHAT CLAUDE CODE CAN SEE

**Framing.** "Reads your codebase" is broader and narrower than it sounds. The docs list what Claude has access to when you run it: **your project** (files in your directory and subdirectories, and files elsewhere with your permission), **your terminal** (anything you can run: build tools, git, package managers, scripts), **your git state** (current branch, uncommitted changes, recent history), **your CLAUDE.md** (a markdown file for project instructions), **auto memory** (learnings Claude saves automatically) and **your extensions** (MCP servers, hooks, skills, custom subagents) [Claude Code docs, How Claude Code works, 2026].

| Source of context | Written by | Loaded when | Limit worth knowing |
|---|---|---|---|
| Files it reads | Your repo | When Claude reads them | Each read costs tokens in the context window |
| CLAUDE.md (project, user, managed) | You | Session start, concatenated broadest to most specific | Project-root file survives compaction |
| AGENTS.md | You | If no CLAUDE.md exists, or per the Project instructions setting | Direct reading needs v2.1.277 or later; unavailable in some sessions |
| Auto memory (`MEMORY.md`) | Claude | Session start | Only the first 200 lines or 25 KB load |
| Git state | Your repo | When Claude runs git | Only what git reports |
| Your conversation | You | Continuously | Compaction can summarise it away |

[Claude Code docs, How Claude Code works and Glossary, 2026]

The practical consequence: **Claude sees only what is in its context window**, which the docs describe as holding your instructions, the files it reads, its own responses and content that never appears in your terminal [Claude Code docs, Context window, 2026]. If a fact is not in a file Claude reads, a loaded instruction file or the conversation, it is not in Claude's context. The model does not know your team's unwritten conventions.

```
  What YOU believe Claude knows          What Claude ACTUALLY has in context
  ─────────────────────────────          ─────────────────────────────────────
  "our conventions"                  ►   only those written in CLAUDE.md / rules
  "what we discussed Tuesday"        ►   nothing, unless resumed or in memory
  "the repo's history"               ►   only what git commands return
  "my other terminal's output"       ►   nothing
```

**Sessions start fresh.** Each new session begins with a fresh context window; continuity comes from CLAUDE.md and auto memory, not from the previous conversation [Claude Code docs, How Claude Code works, 2026].

The failure mode: **Invisible-context assumption.** You rely on a convention that exists only in your head or a past chat, Claude produces code that violates it, and you correct the same mistake every session.

The fix: write the convention into project-root CLAUDE.md (or a rule file), keep it short, and confirm it loaded with `/memory`.

The failure mode: **AGENTS.md assumption.** Your repo has an `AGENTS.md` for other tools and you assume Claude reads it; in some sessions it cannot, and on versions before v2.1.277 it does not read it directly.

The fix: import it from CLAUDE.md (a one-line include) so the content loads whichever way Claude starts, and check the version with `claude --version`.

The failure mode: **Memory overflow.** `MEMORY.md` grows past 200 lines or 25 KB and the tail silently stops loading, so a correction you gave last week no longer applies.

The fix: prune and consolidate the index, move detail into topic files, and check what loaded with `/memory`.

Cross-references: the context window is Module 3.1; CLAUDE.md is Module 3.2; rules and auto memory are Module 3.3.

**If you remember one thing:** if it is not written where Claude reads it, Claude does not know it.

## 1.1.1.5 — BEYOND CODE: ANYTHING YOU CAN DO FROM THE COMMAND LINE

**Framing.** The word "coding" in the name undersells the tool. The docs state that Claude Code can help with anything you can do from the command line: writing docs, running builds, searching files, researching topics and more [Claude Code docs, How Claude Code works, 2026]. The reason is mechanical: the execution tools run shell commands, so the ceiling is the command line, not code editing.

| Work | Command-line shape | Example prompt | Check Claude can run |
|---|---|---|---|
| Documentation | Read code, write markdown | "Document the public API in `docs/api.md`" | A docs build or a link checker |
| Log analysis | Pipe and filter | `tail -200 app.log \| claude -p "..."` | The summary cites line numbers you can grep |
| Data cleanup | Scripts over CSV | "Normalise dates in `data/`" | A row-count and schema assertion |
| Research | Web tools plus files | "Summarise how library X handles retries" | Sources fetched and quoted |
| Migrations | Search and edit at scale | "Move from library A to B across `src/`" | The test suite and a type check |
| Git work | git via Bash | "Write the commit message and push the branch" | `git log` shows it |

[Categories derived from the docs' statement above; the table rows are illustrative workflows, not an official list.]

**Where the boundary really is.** The edge is set by permissions and environment, not capability: anything your shell can reach, Claude can attempt, subject to your permission mode and rules. That is the same fact that makes the tool powerful and makes the permission system necessary.

**Non-interactive use.** `claude -p` runs a single prompt and exits, which lets Claude Code run in scripts, CI and pipes. It is the same engine, and the run is still saved as a resumable session unless you pass `--no-session-persistence` [Claude Code docs, Glossary, 2026].

The failure mode: **Code-only framing.** You use Claude Code only to write functions, and never for the docs, log analysis, migrations or research that sit in the same terminal and often have the clearest checks.

The fix: list your five most repetitive command-line chores this week and try one as a delegated task with a check; log, doc and migration work are the usual quick wins.

The failure mode: **Boundary blindness.** Because "anything on the command line" includes destructive commands, you treat a broad permission mode as harmless and a task touches data you did not intend.

The fix: scope the task and the directory, keep the work in git, and use permission rules and sandboxing for anything that reaches beyond the project.

Cross-references: permission modes are Module 4.3; sandboxing is Module 4.4; headless and programmatic use are Module 6.8 and Part 8; everyday workflows are Module 2.6.

**If you remember one thing:** the real boundary of Claude Code is your shell and your permissions, not the word "code".

## 1.1.1.6 — WHERE THE DEFINITION APPLIES: SURFACES AND ACCOUNTS

**Framing.** The sentence in 1.1.1.1 ends with "available in your terminal, IDE, desktop app, and browser" [Claude Code docs, Overview, 2026]. The definition is the same on each surface, but access depends on how you sign in. Two checks decide what you can use: **the surface** and **the account or provider**.

| Surface | Account route | Notes |
|---|---|---|
| Terminal CLI | Claude subscription, Console, or a third-party provider | The most complete; scripting and the Agent SDK are CLI-only |
| VS Code | Same as CLI, including third-party providers | Inline diffs |
| JetBrains | Same, with the CLI installed separately | Runs in the IDE |
| Desktop app | Claude subscription or Console; Bedrock/Foundry users use CLI or an IDE extension | Visual review, parallel sessions |
| Web and mobile | Claude subscription | Cloud sessions; mobile is a thin client |

[Claude Code docs, Overview and Platforms, 2026]

The install paths for the CLI are the native installer, Homebrew, WinGet and Linux package managers; native installs auto-update while Homebrew and WinGet do not [Claude Code docs, Overview, 2026]. The module-level guide and Module 1.3 cover installation in full.

**Why this belongs in the definition.** "Claude Code can do X" is incomplete without "on which surface, on which account, on which version". The glossary's own AGENTS.md entry shows how version-specific the details can be: reading AGENTS.md directly requires v2.1.277 or later [Claude Code docs, Glossary, 2026].

The failure mode: **Surface-account mismatch.** You plan a workflow around the web or mobile surface while your organisation routes Claude Code through Bedrock or Foundry, and those surfaces do not apply to that route.

The fix: before designing a workflow, write down the surface, the account route and the version, and check them against the platforms page and the feature-availability page.

Cross-references: choosing where to run is Module 7.1; installation and sign-in are Module 1.3; plans and feature availability are Module 1.4.

**If you remember one thing:** a capability claim needs three qualifiers: which surface, which account, which version.

## 1.1.1.7 — THE DEFINITION TEST

**Framing.** A definition is only useful if it lets you reject wrong claims. This section turns the sentence into a test you can apply to any description of Claude Code, including your own.

**The four-verb test.** For any statement, ask which of the four verbs it relies on and whether it drops one.

| Claim | Verbs used | Verdict |
|---|---|---|
| "It suggests the next line as you type" | None of the four | That is autocomplete, not Claude Code |
| "It answers questions about code you paste in" | Reads (only what you paste) | A chatbot; Claude Code reads the repo itself |
| "It reads your repo and proposes a patch" | Reads, edits (maybe) | An assistant; it lacks the run-and-observe verb |
| "It reads the repo, edits files, runs the tests and iterates until they pass" | Reads, edits, runs | Claude Code |
| "It also opens a PR and posts to Slack" | All four, including integrates | Claude Code with integrations |

**Common wrong definitions, and why they fail:**

| Wrong definition | Why it fails | Better |
|---|---|---|
| "A chatbot in your terminal" | Drops the harness and the tools | "An agent that acts on your project with tools" |
| "Autocomplete but smarter" | Drops runs and the loop | "It plans, acts, observes and repeats" |
| "A replacement for engineers" | Overclaims; it needs checks and review | "It does delegated work against a check you define" |
| "An IDE plugin" | The CLI is the most complete surface; the engine is shared | "One engine across terminal, IDE, desktop and web" |

**The two-minute version.** If you had to explain it to a colleague: it is an agent, not a chatbot; it reads your code itself, edits files, runs your commands and sees the output; you give it an outcome and a check, and it loops until the check passes or it is blocked; and it is only as trustworthy as that check.

The failure mode: **Marketing-definition drift.** You describe Claude Code as "an AI pair programmer that writes code", which drops the run-and-observe verb, and your team then expects diffs it has to verify by hand.

The fix: use the four-verb sentence in docs, onboarding and prompts; if a description does not contain reads, edits, runs and integrates, rewrite it.

Cross-references: the chatbot-versus-agent contrast is Module 1.1.2; delegation is Module 1.1.5; limits of the tool are Module 1.1.6.

**If you remember one thing:** if a definition drops a verb, it describes a different tool.
