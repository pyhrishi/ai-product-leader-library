# MODULE 10.1.2 — PILOT DESIGN: THE COMPLETE CRAFT

---

## THE THESIS OF THIS TOPIC

**A pilot is a measurement exercise first: a small, deliberately mixed group, a baseline taken before anyone starts, and exit criteria written down in advance.**

**Prove-it, in one sentence:** write a one-page pilot charter with a roster, a baseline table and three exit criteria.

**The single most important discipline: capture the baseline before the first developer opens a session.**

**The counterintuitive claim you will learn to defend:** cost per developer varies so widely that you cannot estimate your own spend from an average, which is why the pilot exists [Claude Code docs, Manage costs effectively, 2026].

**THE TIME BUDGET.** Reading time: ~14 minutes. Prove-it time: ~2 hours (120 minutes, 8.6 times the reading time).

## 10.1.2.1 — WHY PILOT AT ALL

**Framing.** The costs page says per-developer cost varies widely with model selection, codebase size and usage patterns such as running multiple instances or automation. Across enterprise deployments the average is about $13 per developer per active day and $150-250 per developer per month, with costs below $30 per active day for 90 percent of users. To estimate your own spend, start with a small pilot group and establish a baseline with the tracking tools before wider rollout [Claude Code docs, Manage costs effectively, 2026].

| Figure | Value | Source status |
|---|---|---|
| Average per developer per active day | about $13 | Anthropic docs, enterprise average |
| Average per developer per month | $150-250 | Anthropic docs, enterprise average |
| Users below $30 per active day | 90% | Anthropic docs |

These are Anthropic's published averages, not a forecast for your team [Claude Code docs, Manage costs effectively, 2026].

The failure mode: **Average-as-budget.** You multiply the published $150-250 per month by headcount and present it as the budget, then the real distribution surprises finance.

The fix: Use the pilot's own per-developer distribution, and plan for the tail, not the mean.

Cross-references: cost tracking tools are Module 10.6; measurement is Module 10.8.

**If you remember one thing:** the published average is a starting point; your pilot produces your number.

## 10.1.2.2 — WHO GOES IN THE PILOT

**Framing.** The module brief asks for a small group across seniority levels and stacks. The docs advise starting guided: encourage new users to try codebase Q&A or smaller bug fixes, ask Claude Code to make a plan, check its suggestions, and over time let it run more agentically [Claude Code docs, Enterprise deployment overview, 2026]. [Practitioner heuristic, not in the docs: include at least one sceptic and one team with a hard legacy stack.]

| Slot | Why | Example |
|---|---|---|
| Senior engineer | Judges output quality | Staff backend |
| Junior engineer | Tests onboarding path | New hire |
| Different stacks | Finds tool and MCP gaps | Web, data, mobile |
| One sceptic | Surfaces objections early | Chosen by manager |

The failure mode: **Volunteer-only pilot.** Only enthusiasts join, results look great, and the rollout stalls on the first sceptical team.

The fix: Fill at least one slot with a sceptic and one with a stack nobody expects to work.

Cross-references: champion selection is Module 10.1.3 in this module's later topic; training is Module 10.1.5 topic.

**If you remember one thing:** mix seniority and stack on purpose.

## 10.1.2.3 — BASELINE BEFORE DAY ONE

**Framing.** Baselines are only meaningful if taken before the tool is used. The analytics dashboard reports adoption and contribution metrics, and the docs say to use contribution metrics alongside DORA metrics, sprint velocity or other engineering KPIs [Claude Code docs, Track team usage with analytics, 2026]. Contribution metrics are described as deliberately conservative and an underestimate [same source].

| Baseline | Captured how | Compare at |
|---|---|---|
| PR cycle time | Your git host | Week 4 and 8 |
| Review turnaround | Your git host | Week 4 and 8 |
| Defect escape rate | Incident tracker | Week 8 |
| Developer sentiment | Survey | Day 0 and week 8 |

The failure mode: **Retro baseline.** You collect the 'before' numbers after the pilot has started, so they already include Claude Code effects.

The fix: Freeze baseline exports on the day before kickoff and store them with a date.

Cross-references: metrics detail is Module 10.8.

**If you remember one thing:** no baseline, no claim.

---

## 10.1.2.4 — EXIT CRITERIA

**Framing.** A pilot ends with a decision, so write the decision rule first. [Practitioner heuristic, not from the docs.] Tie each criterion to a number you can pull: adoption from the analytics dashboard, spend from the spend report, quality from your own trackers.

```text
Exit criteria (example, agree before kickoff)
1. >= 70% of pilot users active in weeks 3-4        (dashboard)
2. Spend per active user within the agreed band       (spend report)
3. No rise in defect escape rate vs baseline          (tracker)
Decision date: fixed, owner: named
```

The failure mode: **Moving goalposts.** Criteria are written after seeing results, so the pilot always 'succeeds'.

The fix: Sign the charter before kickoff; changes need a dated amendment.

Cross-references: guardrails to have in place first are Module 10.1.6 topic and Module 10.4.

**If you remember one thing:** criteria first, results second.

## THE PROVE-IT SECTION

**Deliverable.** A signed pilot charter and a decision memo that applies it.

**Close this topic. Build the artifact below from memory. Return to the text only after your first attempt is complete.**

| Step | Action | Output |
|---|---|---|
| 1 | Draft the roster across seniority and stack | `roster.md` |
| 2 | Export baselines and date-stamp them | `baseline/` |
| 3 | Write three exit criteria with data sources | `charter.md` |
| 4 | Name decision owner and date | Charter header |
| 5 | Run the pilot and capture weekly numbers | Weekly table |
| 6 | Apply the criteria and write the decision | Decision memo |

**A passing artifact looks like this:**

| Section | Content |
|---|---|
| Roster | 8 people, 3 stacks, 1 sceptic |
| Baseline | Dated exports for cycle time, review time, escapes |
| Criteria | Three numeric, each with a source |
| Decision | Date and owner named |

**A failing artifact (a realistic near-miss):**

| Element | What is wrong |
|---|---|
| Roster is the Slack channel regulars | **Volunteer-only pilot** |
| Baseline dated after kickoff | Retro baseline |

**The verdict.** The charter passes only if the baseline pre-dates kickoff and every exit criterion names its data source.

## CLOSING REFRAME

This is the craft of the pilot: **a mixed group, a dated baseline, and rules for the decision written first.** The administrator who understands this does not ask "did people like it?" — they ask "what number would change our decision?"
