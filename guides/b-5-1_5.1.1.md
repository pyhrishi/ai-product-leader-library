# MODULE 5.1.1 — THE MENU: THE COMPLETE CRAFT

---

## THE THESIS OF THIS TOPIC

**Claude Code's extensions are a small menu in which each item plugs into a different part of the agentic loop, so choosing one is a matter of matching the job to the loop stage, not of taste.**

**Prove-it, in one sentence:** given six real needs, name the one extension that fits each and say which loop stage it plugs into.

**The single most important discipline: name the job first (always know, sometimes know, connect, isolate, enforce, package), then pick the feature.**

**The counterintuitive claim you will learn to defend:** skills, not CLAUDE.md, are called the most flexible extension: a skill can be invoked by you, loaded by Claude, or run in an isolated context [Claude Code docs, Extend Claude Code, 2026].

**THE TIME BUDGET.** Reading time: ~20 minutes. Prove-it time: ~1.5 hours (90 minutes, 4.5 times the reading time).

## 5.1.1.1 — THE TEN ITEMS

**Framing.** The overview page lists the items that plug into the agentic loop: CLAUDE.md, output styles, skills, code intelligence, MCP, subagents, dynamic workflows, cross-session messaging, hooks, and plugins with marketplaces; artifacts appear in the comparison table as an eleventh row [Claude Code docs, Extend Claude Code, 2026]. Plugins are described as the packaging layer, not a separate capability.

| Feature | What it does | Use it for |
|---|---|---|
| CLAUDE.md | Persistent context loaded every conversation | Conventions, "always do X" rules |
| Output style | Sets role, tone and response format for a session | A voice or format you want in every response |
| Skill | Instructions, knowledge and workflows | Reusable content, repeatable tasks |
| Subagent | Isolated execution context returning a summary | Context isolation, parallel work |
| Dynamic workflow | A script Claude writes that runs many subagents in the background | Work that outgrows a handful of subagents |
| Cross-session messaging | Claude delivers a message from one of your sessions to another | Sessions that need each other's findings |
| Code intelligence | Language-server navigation and diagnostics | Typed languages, large codebases |
| MCP | Connects external services | External data or actions |
| Hook | Script, HTTP request, MCP tool call, prompt or subagent on an event | Automation that must run on every matching event |
| Artifact | Publishes session output as a private interactive page | Output better seen than read in a terminal |

[Claude Code docs, Extend Claude Code, 2026]

The failure mode: **Menu-by-habit.** You reach for the feature you learned first, usually CLAUDE.md or a long prompt, for every need, and a connection problem gets solved with a paragraph of instructions that cannot open a database.

The fix: Say the job in one word (know, connect, isolate, enforce, package) and look that word up in the table before writing anything.

Cross-references: the module-level treatment is Module 5.1; skills are Module 5.2, subagents Module 5.3, hooks Module 5.4, MCP Module 5.5, plugins Module 5.6.

**If you remember one thing:** every extension has one job; match the job before you build.

## 5.1.1.2 — THE LOOP STAGE EACH ONE PLUGS INTO

**Framing.** The overview page opens with the claim that extensions plug into different parts of the agentic loop, and then describes features as ranging from always-on context, through on-demand capabilities, to background automation on events [Claude Code docs, Extend Claude Code, 2026]. That gives a three-tier reading of the menu that is more useful than an alphabetical one.

| Tier | Features | Who decides it runs |
|---|---|---|
| Always-on | CLAUDE.md, output styles | Nobody; it is loaded |
| On demand | Skills, subagents, workflows, MCP tools, code intelligence | You, or Claude matching a description |
| On event | Hooks | The lifecycle event itself |

```
 gather ──► act ──► verify
   │         │        │
 CLAUDE.md  hooks    hooks (PostToolUse)
 skills     MCP      subagent (independent check)
 LSP        subagent
```
The diagram is a teaching aid built from the tier table, not a figure from the docs.

The failure mode: **Tier confusion.** You put a must-happen rule in an always-on or on-demand feature, such as CLAUDE.md, and expect event-level certainty from it.

The fix: If it must happen every time, move it to the on-event tier (a hook); keep always-on tiers for facts and style.

Cross-references: the loop itself is Module 1.2; hooks as the on-event tier are Module 5.4.

**If you remember one thing:** decide whether the thing is always on, on demand or on an event.

## 5.1.1.3 — SKILLS AS THE FLEXIBLE DEFAULT

**Framing.** The overview says skills are the most flexible extension: a markdown file of knowledge, workflows or instructions that you can invoke with a command such as `/deploy`, that Claude can load automatically when relevant, and that can run in your conversation or in an isolated context through subagents [Claude Code docs, Extend Claude Code, 2026]. It also separates reference skills (knowledge used throughout a session) from action skills (do something specific).

| Skill kind | Example | Typical invocation |
|---|---|---|
| Reference | Your API style guide | Claude loads it when relevant |
| Action | `/deploy` runs the deployment checklist | You type the name |
| Forked | A skill with `context: fork` | Runs as a subagent |

When a need does not obviously fit another row, a skill is the usual first try, because it costs little until used: descriptions load at session start and full content loads when invoked [Claude Code docs, Extend Claude Code, 2026].

The failure mode: **Skill-for-everything.** A hard guarantee, such as blocking edits to `.env`, is written as a skill instruction, and Claude interprets it rather than obeying it.

The fix: Keep skills for judgement and knowledge; put guarantees in a hook (Module 5.4).

Cross-references: writing skills is Module 5.2; the hook-versus-skill choice is sub-topic 5.1.5.

**If you remember one thing:** a skill is the default for knowledge and workflows, never for guarantees.

## 5.1.1.4 — PLUGINS PACKAGE, THEY DO NOT ADD

**Framing.** The docs describe plugins as the packaging layer: a plugin bundles skills, hooks, subagents and MCP servers into one installable unit, with plugin skills namespaced like `/my-plugin:review` so several plugins can coexist; use one when the same setup is needed across repositories or for distribution through a marketplace [Claude Code docs, Extend Claude Code, 2026].

| You have | Package as | Reason |
|---|---|---|
| One repo, one team | Files in `.claude/` committed to git | No packaging needed |
| Same setup in a second repo | Plugin | The trigger the docs give |
| Setup for people outside your org | Plugin in a marketplace | Distribution |

A plugin adds no new capability type; each component inside it is one of the menu items above.

The failure mode: **Premature packaging.** You build a plugin and marketplace for a setup that exists in one repository and has one user.

The fix: Wait for the stated trigger: a second repository needs the same setup.

Cross-references: plugins are Module 5.6.

**If you remember one thing:** a plugin is a container for menu items, not a menu item.

**Deliverable.** A one-page menu card: every extension, its job, its loading behaviour and one example from your own repository.

| 4 | Mark any whose job does not match its feature | Mismatch list |

| Feature | Job | Tier | Own example | Match? |
|---|---|---|---|---|
| CLAUDE.md | Know | Always-on | "Use pnpm" | Yes |
| Skill | Workflow | On demand | `/release` | Yes |
| Skill | Guarantee (no `.env` edits) | On demand | - | No, move to hook |

**A failing artifact (a realistic near-miss):**

| Element | What is wrong |
|---|---|
| Plugin listed as a capability on a par with skills | Plugins package; see **Premature packaging** |
| No tier column | Cannot detect **Tier confusion** |

**The verdict.** The artifact passes only if every row has a job, a tier and an own-repo example, and at least one mismatch is found and re-homed.

## CLOSING REFRAME

This is the craft of the menu: **one job per feature, three tiers, and packaging as a separate step.** The engineer who understands this does not ask "how do I make Claude do this?" — they ask "what job is this, and which tier owns it?"
