# MODULE 9.1.6 — KEEPING SPECS ALIVE: THE COMPLETE CRAFT

## THE THESIS OF THIS TOPIC

**A spec that is not updated when reality changes becomes a false standard, so update it in the same change as the code and move durable decisions into CLAUDE.md or decision records.**

**Prove-it, in one sentence:** show a diff where code and spec change together, and a decision moved from SPEC.md into a durable home.

**The single most important discipline: no code change that contradicts the spec merges without a spec edit.**

**The counterintuitive claim you will learn to defend:** most of what a spec says should die with the feature; only decisions that guide future work deserve a permanent home.

## 9.1.6.1 — UPDATE THE SPEC IN THE SAME CHANGE

**Framing.** When implementation discovers the spec was wrong, edit the spec first, then the code, so review still has a true standard. This guide treats that as judgement; the docs only establish that the spec is the file reviewers check against [Claude Code docs, Best practices, 2026].

| Discovery | Edit |
|---|---|
| Edge case not in spec | Add E-number, then test |
| Requirement impossible | Strike with a reason, note in PR |
| Scope grew | Move to Out of scope or a new spec |

```bash
git diff --stat   # SPEC.md and the code appear in the same commit
```

The failure mode: **Spec drift.** The code changed and SPEC.md still states the old behaviour, so the next review fails correct work or passes wrong work.

The fix: Make 'SPEC.md updated or no behavioural change' a line in the definition of done (Module 9.12.4).

Cross-references: definition of done is Module 9.12.4.

**If you remember one thing:** the spec changes in the same commit.

## 9.1.6.2 — WHERE DURABLE DECISIONS LIVE

**Framing.** The docs say CLAUDE.md should hold only what Claude cannot work out from the code: commands, misleading places, decisions not in the repo, anything corrected twice. Keep it short; `/init` output should be trimmed and the memory guide recommends staying under 200 lines [Claude Code docs, Best practices, 2026].

| Content | Home |
|---|---|
| This feature's requirements | SPEC.md (delete or archive after merge) |
| A team-wide decision ('use errors.ts helpers') | CLAUDE.md |
| Rule for one directory | `.claude/rules/*.md` with `paths:` |
| Why we chose X over Y | Decision record (ADR) in docs/ |
| Procedure | A skill |

The failure mode: **Spec hoarding.** Every old SPEC.md stays in the repo and in CLAUDE.md, the file balloons and relevant lines get lost.

The fix: Promote only decisions that will guide future work; archive or delete the rest at merge.

Cross-references: CLAUDE.md craft is Module 3.2; decision records are Module 9.11.1.

**If you remember one thing:** promote decisions, retire requirements.

---

## 9.1.6.3 — SPECS AND PATH-SCOPED RULES

**Framing.** A rule that matters in one part of the code belongs in `.claude/rules/` with a `paths:` filter so it loads only there [Claude Code docs, Best practices, 2026]. The docs example loads a rule for `src/api/**/*.ts`.

```markdown
---
paths:
  - "src/api/**/*.ts"
---
- Every new endpoint needs an entry in openapi.yaml, CI fails without it
```

The failure mode: **Global rule for local fact.** A rule about one directory sits in the root CLAUDE.md and loads for every task.

The fix: Move it to a path-scoped rules file.

Cross-references: rules files are Module 3.3.

**If you remember one thing:** scope rules to where they apply.

## THE PROVE-IT SECTION

**Deliverable.** A commit diff changing code and SPEC.md together, plus one decision promoted to CLAUDE.md or a rules file.

**Close this topic. Build the artifact below from memory. Return to the text only after your first attempt is complete.**

| Step | Action | Output |
|---|---|---|
| 1 | Find a spec contradicted by the build | Evidence |
| 2 | Edit spec first | Spec diff |
| 3 | Edit code | Code diff |
| 4 | Promote one decision | CLAUDE.md or ADR diff |
| 5 | Archive the spec | Move or delete |

**A passing artifact looks like this:**

| Item | Evidence |
|---|---|
| Spec edit in same commit | yes |
| Promoted decision | 1 line in rules file |

**A failing artifact (a realistic near-miss):**

| Element | What is wrong |
|---|---|
| Code only changed | **Spec drift** |
| Whole spec pasted in CLAUDE.md | **Spec hoarding** |

**The verdict.** The artifact passes only if the commit touches both SPEC.md and code and at most one durable line is promoted.

## CLOSING REFRAME

This is the craft of living specs: **same-commit edits, promote decisions, retire requirements.** The engineer who understands this does not ask "where do I keep this spec?" — they ask "which of these lines will still matter in a year?"
