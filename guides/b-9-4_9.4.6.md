## THE THESIS OF THIS TOPIC

**`/simplify` reviews changed code for reuse, simplification, efficiency and the right level of abstraction and applies the fixes, while `/code-review` is the tool for correctness bugs.**

**Prove-it, in one sentence:** run /simplify on a diff, classify each change it made and confirm tests still pass.

**The single most important discipline: cleanup passes follow green tests and never mix with behaviour changes.**

**The counterintuitive claim you will learn to defend:** a cleanup pass that is not reviewed can be a rewrite in disguise.

## 9.4.6.1 — WHAT /SIMPLIFY DOES

**Framing.** `/simplify [target]` reviews changed code for cleanup opportunities and applies fixes. Four review agents run in parallel covering reuse of existing helpers, simplification, efficiency, and whether the change is at the right level of abstraction. It does not look for correctness bugs; use `/code-review` for that. Pass a path or PR reference to review a specific target [Claude Code docs, Commands, 2026].

| Command | Looks for | Applies fixes |
|---|---|---|
| `/simplify` | Reuse, simplification, efficiency, abstraction level | Yes |
| `/code-review` | Correctness bugs (and, by model and effort, cleanup) | With `--fix` |

Order: tests green, `/simplify`, tests green, `/code-review`.

The failure mode: **Cleanup as rewrite.** The pass restructures far beyond the diff, and reviewers cannot tell what changed.

The fix: Scope with a target path, cap the diff size, and commit the cleanup separately.

Cross-references: code review is Module 9.12.3.

**If you remember one thing:** scope the pass.

---

## 9.4.6.2 — REVIEW WHAT IT CHANGED

**Framing.** Treat the cleanup like any diff: read it, run the checks and reject changes that alter behaviour. The docs warn that a reviewer asked to find problems will always find something, so fixing every finding adds layers [Claude Code docs, Best practices, 2026].

| Change type | Action |
|---|---|
| Reuses an existing helper | Accept after tests |
| Inlines an abstraction | Accept if clearer |
| New abstraction layer | Question; reject unless needed |
| Behaviour change | Revert |

The failure mode: **Over-abstraction.** The pass introduces a helper used once, and the codebase gains an indirection.

The fix: Reject abstractions with a single caller unless the spec calls for them.

Cross-references: maintainability is Module 9.13.4.

**If you remember one thing:** cleanup should reduce code.

---

## 9.4.6.3 — WHEN TO RUN IT

**Framing.** Run after a feature is green and before the PR so reviewers see clean code. Avoid running it on code you did not change unless you scope it by path.

| Moment | Run |
|---|---|
| Feature green | `/simplify` |
| Before PR | `/code-review` |
| Legacy cleanup | `/simplify path/to/module` with a scoped PR |

The failure mode: **Drive-by cleanup.** A feature PR includes unrelated cleanup, so review is noisy.

The fix: One concern per PR (Module 9.4.7).

Cross-references: churn is Module 9.4.7.

**If you remember one thing:** clean after green, in its own commit.

## CLOSING REFRAME

This is the craft of cleanup: **after green, scoped, reviewed, separate.** The engineer who understands this does not ask "can it be tidier?" — they ask "does this change make the code smaller without changing it?"
