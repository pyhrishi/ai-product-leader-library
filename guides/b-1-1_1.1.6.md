## THE THESIS OF THIS TOPIC

**Claude Code is not a replacement for tests, review, version control or judgment, and the model can be confidently wrong. Safe use is a set of layers, each covering a gap the others leave.**

**Prove-it, in one sentence:** for five realistic mishaps, name which layer catches it (tests, review, git, permissions or checkpoints) and which does not.

**The single most important discipline: never ship what you cannot verify, and never rely on one safeguard to cover another's job.**

**The counterintuitive claim you will learn to defend:** the safeguard people trust most, checkpoints, covers the least. They snapshot edits made through file tools and do not track Bash changes or remote effects [Claude Code docs, Glossary, 2026].

## 1.1.6.1 — THE TRUST-THEN-VERIFY GAP

**Framing.** The best-practices page names the first failure pattern directly: Claude produces a plausible-looking implementation that does not handle edge cases. The fix is to provide verification (tests, scripts, screenshots) and, if you cannot verify it, not to ship it [Claude Code docs, Best practices, 2026].

| Looks fine | Can still be wrong |
|---|---|
| Compiles and runs | Edge cases, concurrency, error paths |
| Tests pass | The tests were weakened or do not cover the change |
| Summary reads well | Summary and diff disagree |
| Confident tone | Confidence is not evidence |

A verification loop is how a session knows the work is done rather than plausible: a check Claude can run, such as tests, a build or a screenshot comparison. The glossary names it the prerequisite for `/goal`, unattended runs and dynamic workflows [Claude Code docs, Glossary, 2026].

The failure mode: **Trust-then-verify gap.** The diff looks right, the tests were never run, and an edge case ships.

The fix: Provide verification every time (tests, scripts, screenshots), ask Claude to show evidence, and do not ship what you cannot verify.

Cross-references: verification is Module 2.3; the security threat model is Module 11.1.

**If you remember one thing:** plausible is not verified.

## 1.1.6.2 — CHECKPOINTS ARE NOT GIT

**Framing.** A checkpoint is a restore point created at each prompt that starts a turn; Claude Code snapshots files before every edit. Press `Esc` twice or run `/rewind` to restore code, conversation or both. Checkpoints are saved with the conversation, so a resumed session can still rewind, but they are separate from git and do not track changes made through the Bash tool [Claude Code docs, Glossary, 2026]. Actions that affect remote systems such as databases, APIs and deployments cannot be checkpointed [Claude Code docs, How Claude Code works, 2026].

| Mishap | Checkpoint helps? | What does |
|---|---|---|
| Bad edit through the file tools | Yes | `/rewind` |
| `rm -rf build/` run through Bash | No | Git, backups, deny rules and sandbox |
| A migration applied to a database | No | Migration rollback, permission rules |
| A bad commit | No | Git |
| Wrong direction in conversation | Yes (conversation rewind) | `/rewind` or `/clear` |

```bash
# Prove it yourself in a scratch repo:
echo hi > scratch.txt && git add scratch.txt && git commit -m scratch
# Ask Claude: "delete scratch.txt using the shell, not the edit tool"
# Then /rewind: the file is not restored by the checkpoint. `git restore scratch.txt` does.
```

The failure mode: **Checkpoint-as-git assumption.** You rely on `Esc Esc` to undo a Bash-made change or a database write, and the checkpoint does not cover it.

The fix: Keep work in git, commit often, and use permission rules for anything that touches remote systems.

Cross-references: checkpoints are Module 2.5; sandboxing is Module 4.4; permissions are Module 4.2.

**If you remember one thing:** git protects files, permissions protect the world, checkpoints protect edits.

## 1.1.6.3 — PERMISSIONS AS THE SECOND SAFETY LAYER

**Framing.** Permission modes set what Claude may do without asking. In Manual mode it starts with read-only permissions and asks before edits and commands, running a built-in set of read-only commands such as `ls`, `cat` and `git status` without asking [Claude Code docs, Security, 2026]. It can write only to the folder where it started and its subfolders and asks before reading outside that boundary with Read, Grep and Glob [Claude Code docs, Security, 2026]. Suspicious Bash commands require manual approval even if previously allowlisted [Claude Code docs, Security, 2026].

| Mode | Behaviour | Right when |
|---|---|---|
| Manual (`default`) | Asks before edits and commands | New repos, unknown tasks |
| Accept edits | Auto-approves file edits | You review diffs afterwards |
| Plan | Explores, no source edits | Uncertain approach |
| Auto | A classifier reviews actions | Trusted tasks with a check, on eligible plans |
| `bypassPermissions` | Skips prompts | Isolated, disposable environments only |

[Claude Code docs, Glossary and Permission modes, 2026]

Which mode a new terminal session starts in comes from, in order, the `--permission-mode` flag, then `permissions.defaultMode` in a settings file, then the built-in default; setting `"auto"` in project settings does not take effect [Claude Code docs, Permission modes, 2026].

The failure mode: **Bypass-by-default.** You run with prompts disabled on your real machine because it is faster, and a single bad command touches files you did not intend.

The fix: Reserve bypass mode for disposable environments, and use rules and sandboxing for everything else.

Cross-references: permission modes are Module 4.3; sandboxing is Module 4.4; enterprise policy is in Part 11.

**If you remember one thing:** a mode is a convenience; a rule or a sandbox is a boundary.

## 1.1.6.4 — THE CONTEXT LIMIT BEHIND MOST BAD BEHAVIOUR

**Framing.** Most best practices follow from one constraint: the context window fills fast and performance degrades as it fills [Claude Code docs, Best practices, 2026]. The docs name recurring patterns and their fixes.

| Pattern | Symptom | Fix named in the docs |
|---|---|---|
| Kitchen-sink session | Unrelated tasks in one context | `/clear` between tasks |
| Correcting over and over | Same mistake corrected 3+ times | `/clear` and a better first prompt |
| Over-specified CLAUDE.md | Important rules lost in noise | Prune hard; turn reliable rules into hooks |
| Infinite exploration | Unscoped investigate fills context | Scope narrowly or use subagents |

[Claude Code docs, Best practices, 2026]

Hooks are deterministic while CLAUDE.md is advisory: if something must happen every time, use a hook [Claude Code docs, Best practices, 2026].

The failure mode: **Advisory-for-mandatory.** A rule that must hold every time lives only in CLAUDE.md, so it holds most of the time.

The fix: Convert any rule you cannot tolerate breaking into a hook or deny rule.

Cross-references: the context window is Module 3.1; hooks are Module 5.4; large codebases are Module 3.5.

**If you remember one thing:** when quality drops, suspect the context before the model.
