## 1.3.5.1 — AUTO-UPDATE AND MANUAL UPDATE

**Framing.** Native installs auto-update in the background; Homebrew and WinGet do not. Run `claude update` to apply an update immediately [Claude Code docs, Setup, 2026]. If already current, native installs report that Claude Code is up to date with the version; Homebrew, WinGet and apk installs report 'Claude is up to date!' [Claude Code docs, Installation, 2026].

| Task | Command |
|---|---|
| Show version | `claude --version` |
| Update now | `claude update` |
| Read what changed | `/release-notes` |
| Block all updates | `DISABLE_UPDATES` |

The failure mode: **Stale package-manager install.** You installed with Homebrew or WinGet, assume it self-updates, and months later a documented feature is missing.

The fix: Update on a schedule and compare `claude --version` with what the docs require.

Cross-references: install paths are Module 1.3.1; environment variables are Module 4.8.

**If you remember one thing:** check, then update, then read the notes.

## 1.3.5.2 — CHANNELS AND PINNING

**Framing.** The native installer accepts a specific version number or a release channel, latest or stable [Claude Code docs, Setup, 2026].

| Need | Choice |
|---|---|
| Newest features | `latest` |
| Fewer surprises | `stable` |
| Reproducibility | A pinned version |
| Locked fleet | Pin and set `DISABLE_UPDATES` |

The failure mode: **Silent-update regression.** An auto-update changes a behaviour your team relied on and no one can say which version it started on.

The fix: Record the version in bug reports, read `/release-notes`, and pin via stable or a version for fleets.

Cross-references: enterprise version control is in Part 11.

**If you remember one thing:** reproducibility needs a pin.

## 1.3.5.3 — VERSION-GATED FEATURES

**Framing.** Features have minimum versions, so documentation can be correct and still not apply to you. Examples from the docs: reading AGENTS.md directly needs v2.1.277 or later; `onFailure: "block"` for hooks needs v2.1.295; subagent concurrency override needs v2.1.217; spend-limit dialogs need v2.1.208; auto mode became the built-in starting mode from v2.1.283; `/powerup` arrived in v2.1.90 [Claude Code docs and community sources, 2026].

| Feature | Minimum version |
|---|---|
| `/powerup` | v2.1.90 (community sources; no official docs page found) |
| Spend-limit dialogs | v2.1.208 |
| Concurrency override | v2.1.217 |
| AGENTS.md direct read | v2.1.277 |
| Auto mode built-in start | v2.1.283 |
| Hook `onFailure: "block"` | v2.1.295 |

The failure mode: **Version-blind doc use.** You follow a docs example on a version older than the feature and conclude it is broken.

The fix: Check the minimum version in the docs and update before debugging.

Cross-references: troubleshooting is Module 1.3.7; settings are Module 4.1.

**If you remember one thing:** a feature note without a version is half a note.

## 1.3.5.4 — RELEASE NOTES AS A HABIT

**Framing.** `/release-notes` shows what changed. A team habit of reading them after each update catches renamed features and changed defaults before they cause incidents.

| Step | When |
|---|---|
| Record `claude --version` | Before and after update |
| Read `/release-notes` | After update |
| Re-test your runbook's top three commands | After update |

The failure mode: **Release-note skipping.** You never read the notes and learn a rename or default change from a failing script.

The fix: Read `/release-notes` after each update and re-test the top three runbook commands.

Cross-references: the vocabulary and renames are Module 1.5.

**If you remember one thing:** read the notes after the update, not after the incident.

## CLOSING REFRAME

This is the craft of updating: **know the version, control the cadence, read the notes.** The engineer who understands this does not ask "is it updated?" — they ask "which version is this, and what changed since the last one?"
