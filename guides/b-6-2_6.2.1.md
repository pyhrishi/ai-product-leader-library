# MODULE 6.2.1 — WHAT WORKTREES ARE AND WHY THEY MATTER: THE COMPLETE CRAFT

---

## THE THESIS OF THIS TOPIC

**A git worktree is a separate working directory with its own files and branch that shares repository history and remote, so each parallel session edits its own copy and never touches another session's files.**

**Prove-it, in one sentence:** run two sessions at once against one repository, make conflicting edits to the same file, and show both survive in separate worktrees.

**The single most important discipline: give every session that edits files its own checkout before you start it.**

**The counterintuitive claim you will learn to defend:** a worktree isolates files, not decisions: it does nothing to stop two sessions from making incompatible changes that conflict at merge time [Claude Code docs, Worktrees, 2026].

## 6.2.1.1 — WHAT A WORKTREE IS

**Framing.** The docs define it plainly: a git worktree is a separate working directory with its own files and branch, sharing the same repository history and remote as your main checkout. Running each session in its own worktree means edits in one never touch files in another, so one session can build a feature while a second fixes a bug [Claude Code docs, Worktrees, 2026].

| Property | Main checkout | A worktree |
|---|---|---|
| Files on disk | Your working directory | A separate directory |
| Branch | Whatever you have checked out | Its own branch |
| History and remote | The repository's | Shared with the main checkout |
| Untracked files like `.env` | Present | Absent unless copied (sub-topic 6.2.3) |

The failure mode: **Branch-sharing assumption.** You run two sessions in the same directory and expect separate branches, so both write the same files and one silently overwrites the other.

The fix: Start each editing session with its own worktree, so the isolation is on disk, not in your head.

Cross-references: git basics for sessions are Module 2.6; parallel options are Module 6.1.

**If you remember one thing:** a worktree is a second directory, not a second repository.

---

## 6.2.1.2 — THE COLLISION IT PREVENTS

**Framing.** Without isolation, two sessions edit the same working tree and the second write wins. The docs position worktrees as the isolation tool among the parallel approaches: they isolate file edits, subagents split work within a session, and cross-session messaging passes findings between sessions in your worktrees [Claude Code docs, Worktrees, 2026].

```text
No worktrees:   session A edits auth.ts  --\
                session B edits auth.ts  ---> one working copy: last write wins

Worktrees:      A -> .claude/worktrees/feature-a/auth.ts
                B -> .claude/worktrees/bugfix-b/auth.ts   (separate copies, merged later)
```

The failure mode: **Isolation-as-integration.** You assume separate worktrees mean the two changes will merge cleanly, and discover at merge time that they changed the same function incompatibly.

The fix: Isolate for editing, then plan the merge: tell the sessions what the other is changing, with cross-session messaging, before they diverge.

Cross-references: messaging is Module 6.6; merge discipline is Module 9.12.

**If you remember one thing:** isolation prevents overwrites, not conflicts.

---

## 6.2.1.3 — WHEN YOU DO NOT NEED ONE

**Framing.** A worktree is for sessions that edit files at the same time. Read-only work, a single session, and subagents that only search do not collide. The docs note that most sessions need only start-in-a-worktree and clean-up-on-exit [Claude Code docs, Worktrees, 2026].

| Situation | Worktree needed? | Why |
|---|---|---|
| Two sessions editing the same repo | Yes | Edits would collide |
| One session, sequential tasks | No | Nothing runs concurrently |
| Parallel read-only investigation | Usually no | No writes to collide |
| Many subagents editing files | Yes, per-subagent isolation (6.2.2) | Each needs its own copy |
| Agent teams | Not provided; partition files | The comparison page says teams are not isolated in worktrees |

The failure mode: **Worktree-everywhere reflex.** You create a worktree for every read-only question and spend time on setup and cleanup that bought nothing.

The fix: Use a worktree when two writers could touch the same files, and not otherwise.

Cross-references: teams and file ownership are sub-topic 6.4.5.

**If you remember one thing:** isolate writers, not readers.

---

## 6.2.1.4 — REQUIREMENTS AND FIT

**Framing.** Worktrees require a git repository; for other version control systems you configure hooks to replace the git logic (sub-topic 6.2.5). In the desktop app you pick the worktree option when you start a session [Claude Code docs, Worktrees, 2026].

| Surface | How you get a worktree |
|---|---|
| CLI | `claude --worktree <name>` or `-w` |
| Inside a session | Ask Claude to work in a worktree; it uses the EnterWorktree tool |
| Desktop app | Select the worktree option when you start a session |
| By hand | `git worktree add ../project-feature-a -b feature-a` |

The failure mode: **Non-git blindness.** You expect `--worktree` to work in an SVN or Perforce checkout and it does not.

The fix: Use WorktreeCreate and WorktreeRemove hooks to supply your own creation and cleanup logic.

Cross-references: the flag and settings are sub-topic 6.2.2; non-git hooks are sub-topic 6.2.5.

**If you remember one thing:** a worktree needs git or a hook that stands in for it.

| Check | Result |
|---|---|
| Two directories under `.claude/worktrees/` | Yes |

**A failing artifact (a realistic near-miss):**

| Element | What is wrong |
|---|---|
| Both edits made in the main checkout | **Branch-sharing assumption** |
| Claims 'no conflicts because worktrees' | **Isolation-as-integration** |

**The verdict.** The log passes only if the two edits coexisted on disk in separate worktrees and a real merge conflict was observed and explained.

## CLOSING REFRAME

This is the craft of isolating writers: **one directory per concurrent editor, merged on purpose.** The engineer who understands this does not ask "can these run at once?" — they ask "can their edits ever collide, and what will tell them about each other?"
