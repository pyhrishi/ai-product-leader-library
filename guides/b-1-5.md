# MODULE 1.5 — THE CLAUDE CODE VOCABULARY: THE COMPLETE CRAFT

---

## THE THESIS OF THIS MODULE

**Most confusion in Claude Code is vocabulary confusion: two features with similar names that live in different layers of the loop, so a fix aimed at the wrong one does nothing.**

**Prove-it, in one sentence:** define each of the 23 core terms in one sentence without looking, then place each on the loop diagram.

**The single most important discipline: learn terms in pairs that are easy to confuse, and learn the one fact that separates each pair.** A flat glossary teaches words; a contrast table teaches decisions.

**The counterintuitive claim you will learn to defend:** the glossary's renamed and deprecated terms matter as much as the current ones, because the internet is full of the old names. A search for "headless mode" or "slash commands" finds answers about features that have since been renamed [Claude Code docs, Glossary, 2026].

**THE TIME BUDGET.** Reading time: ~25 minutes. Prove-it time: ~2.5 hours. 2.5 hours is 150 minutes, six times the reading time.

## 1.5.1 — CORE TERMS

**Framing.** The syllabus lists 23 terms: agentic loop, context window, compaction, CLAUDE.md, auto memory, skill, subagent, hook, MCP, plugin, marketplace, mod, worktree, checkpoint, session, permission mode, sandbox, headless mode, Agent SDK, dynamic workflow, agent view, agent team, channel. Rather than alphabetical, learn them in the five clusters below, which follow the loop. Every definition is a paraphrase of the official Glossary unless flagged [Claude Code docs, Glossary, 2026].

### Cluster A — The engine

| Term | One-sentence definition | The fact that separates it from its neighbour |
|---|---|---|
| **Agentic loop** | The cycle of gather context, take action, verify results, repeat until done | A *turn* is one pass from your message to Claude finishing; the loop is what happens inside it |
| **Context window** | The working memory of a session: history, file contents, command outputs, CLAUDE.md, memory, skills and system instructions | Not the same as a session: `/clear` starts a new session with a new window |
| **Compaction** | Automatic summarisation of the conversation when the window nears its limit, clearing old tool outputs first | Project-root CLAUDE.md survives and is re-read; conversation-only instructions may not |
| **Session** | A conversation tied to the current directory with its own context window, stored under `~/.claude/projects/` | Resumable and forkable; `/clear` makes a new one |
| **Checkpoint** | A restore point created at each prompt that starts a turn, snapshotting files before edits | Separate from git, and does not track changes made through Bash |

### Cluster B — Instructions and memory

| Term | Definition | Separating fact |
|---|---|---|
| **CLAUDE.md** | A markdown file of persistent instructions you write, loaded at session start | You write it; auto memory is what Claude writes |
| **Auto memory** | Notes Claude writes for itself from your corrections, stored per git repository; the first 200 lines or 25 KB of `MEMORY.md` load each session | All worktrees of one repo share one memory directory |
| **Rules** | Modular files in `.claude/rules/` that load alongside CLAUDE.md, optionally path-scoped | Path-scoped rules load only when a matching file is read |

### Cluster C — Extensions

| Term | Definition | Separating fact |
|---|---|---|
| **Skill** | A `SKILL.md` playbook Claude loads when relevant or you invoke with `/name` | Recommended successor to custom commands; follows the Agent Skills open standard |
| **Subagent** | A specialised assistant in its own context window that returns a summary | Stays inside the session; teammates in an agent team are separate sessions |
| **Hook** | A user-defined handler that runs at a fixed lifecycle point; deterministic | CLAUDE.md is advisory; a hook always fires |
| **MCP** | Model Context Protocol, an open standard for connecting AI tools to external data and services; servers give Claude new tools | MCP server is the program; a *connector* is a server added to your claude.ai account |
| **Plugin** | A bundle of skills, hooks, subagents and MCP servers as one installable unit | Skills are namespaced `plugin-name:skill-name` |
| **Marketplace** | A catalogue through which plugins are distributed across teams | The glossary links plugin distribution through a marketplace; details in Module 5.6 [definition paraphrased from the Plugin entry] |
| **Mod** | A customisation unit covered in Module 5.7 | [Not defined on the Glossary page I fetched; confirm the definition in the Mods docs before relying on this one] |

### Cluster D — Control and safety

| Term | Definition | Separating fact |
|---|---|---|
| **Permission mode** | The baseline approval behaviour: `default` (shown as Manual), `acceptEdits`, `plan`, `auto`, `dontAsk`, `bypassPermissions` | Rules refine it; rules are evaluated deny, ask, allow, first match wins |
| **Sandbox** | OS-level filesystem and network isolation for the Bash tool | A separate layer from permission rules |
| **Worktree** | An isolated git worktree under `.claude/worktrees/` enabled with `-w` or `isolation: worktree` | Changes stay on a separate branch in a separate directory |

### Cluster E — Scale, automation and reach

| Term | Definition | Separating fact |
|---|---|---|
| **Headless mode** | Old name for non-interactive mode, run with `-p` or `--print` | **Renamed**; same flag, same behaviour. The Agent SDK is the Python and TypeScript equivalent |
| **Agent SDK** | The programmatic library for building agents on the same engine, in Python and TypeScript | CLI-only scripting is `claude -p`; the SDK is code you write |
| **Agent team** | Multiple independent sessions coordinated by a lead with a shared task list and peer messaging; experimental, off by default | Each teammate has its own context and you can talk to any of them |
| **Dynamic workflow** | A multi-step automated workflow; the glossary names the verification loop as its prerequisite | [Definition summarised from the glossary's cross-references; read Module 6.5 for detail] |
| **Agent view** | A view for monitoring and managing background and parallel sessions | [Not defined on the Glossary page I fetched; see Module 6.3] |
| **Channel** | An MCP server that pushes events into a running session so Claude can react while you are away; two-way in some cases; Telegram, Discord and iMessage are in research preview | Differs from Remote Control, which continues a local session from another device |

**Three look-alike clusters to master (the L4 content):**

| Confusion | Left | Right | One fact that separates them |
|---|---|---|---|
| Cloud vs remote | **Cloud session**: runs on cloud infrastructure and survives closing your laptop | **Remote Control**: a local session you drive from phone or browser; execution stays on your machine | Where the code runs |
| Command vs skill | **Command**: a `/name` you type; built-ins like `/clear`, or files in `.claude/commands/` | **Skill**: a `SKILL.md` playbook; the recommended way to package multi-step commands | Both create `/name`; skills add invocation control and subagent execution |
| Subagent vs agent team | **Subagent**: inside one session, reports only to parent | **Agent team**: separate sessions, shared task list, peer messaging | Who can talk to whom |

[Claude Code docs, Glossary, 2026]

**Deprecated and renamed terms** (the glossary's own table):

| Old term | Now called |
|---|---|
| Headless mode | Non-interactive mode |
| Web session; "Claude Code on the web" for any cloud session | Cloud session ("Claude Code on the web" now names only the browser surface at claude.ai/code) |
| Custom commands | Skills (`.claude/commands/` files still work) |
| Slash commands | Commands |

[Claude Code docs, Glossary, 2026]

**Three more precision traps from the glossary:**

- "Command" also names a `claude` CLI subcommand such as `claude mcp add`, and the `command` field of a stdio MCP server entry that says which executable to launch. All three are unrelated [Claude Code docs, Glossary, 2026].
- The `default` permission mode is labelled **Manual** in the CLI, the VS Code and JetBrains extensions and the desktop app; `manual` is accepted as an alias [Claude Code docs, Glossary, 2026].
- Settings layers, highest to lowest: managed policy, command-line arguments, local settings (`.claude/settings.local.json`), project settings (`.claude/settings.json`), user settings (`~/.claude/settings.json`); arrays merge across layers, scalars at a higher layer override lower ones [Claude Code docs, Glossary, 2026].

The failure mode: **Look-alike conflation.** You treat two similar terms as one, such as asking for a "subagent" when you need an agent team, or "cloud session" when you want Remote Control, and spend an hour configuring the wrong feature.

The fix: for each pair, ask the separating question (who can talk to whom? where does the code run? is it advisory or deterministic?) before choosing.

The failure mode: **Stale-term search.** You search "headless mode" or "slash commands" and follow an old tutorial whose flags or file locations have changed.

The fix: translate through the renamed-terms table first, then search the current name, and prefer the official docs over older blog posts.

The failure mode: **Glossary-as-understanding.** You can recite a definition but cannot say which layer of the loop the thing acts in, so you cannot debug it.

The fix: for every term, name the loop location (before the prompt, around a tool call, between turns, at compaction) as part of the definition.

## 1.5.2 — WHERE TO LOOK

**Framing.** A glossary is a map, not the territory. **The official Glossary page defines Claude Code terminology and links each entry to the page where the concept is covered in depth**; it also points to the platform glossary for model-level concepts (tokens, temperature, RAG) and to the Claude Help Center for Desktop terms such as desktop extension, MCPB and DXT [Claude Code docs, Glossary, 2026].

| You need | Go to | Why |
|---|---|---|
| A Claude Code term | Claude Code Glossary | Each entry links to its deep page |
| A model-level concept | Platform glossary (platform.claude.com) | Tokens, temperature, RAG, MCP protocol |
| Desktop-app terms | Claude Help Center | DXT, MCPB, desktop extension |
| The page list | `code.claude.com/docs/llms.txt` | The docs index for discovering pages |
| Live behaviour | `/help`, `/context`, `/memory`, `claude doctor` | Your version, your session |
| What changed | `/release-notes` | Renames and new terms arrive by release |

[Claude Code docs, Glossary, 2026]

**Habit for staying current.** Terms move. The glossary's own "Deprecated and renamed terms" table exists because the product renames features. Re-read it after major updates, and add new terms to your own glossary with the date and version.

**Your own glossary.** For a team, keep a one-page file in the repo (a docs file, or a section of CLAUDE.md pointing to it) listing the five or six terms your workflow depends on, with the separating fact for each, so new teammates stop confusing them.

The failure mode: **Source-of-truth drift.** The team's internal glossary is three months old, still says "slash commands" and "headless mode", and new teammates learn names the product no longer uses.

The fix: date each entry, review it after each release using `/release-notes`, and link every entry to the official page rather than copying its text.

The failure mode: **Wrong-glossary lookup.** You search the Claude Code glossary for a model-level term such as temperature, or a Desktop term such as MCPB, and conclude it does not exist.

The fix: use the glossary's own pointers: the platform glossary for model concepts and the Help Center for Desktop terms.

Cross-references: the quick-reference part is Part 14; the library and drills are Part 17.

**If you remember one thing:** the glossary tells you the name, the linked page tells you the behaviour, and `/release-notes` tells you when either changed.

:::details Answers — do not read until you have written yours down.

1. The cycle of gather context, take action, verify results, repeat until done. A turn is one complete response, from your message to Claude finishing, with any number of tool calls inside it; the loop describes what happens inside a turn.
2. **Look-alike conflation.** Cloud sessions run on cloud infrastructure; to continue a local session from another device use Remote Control.
3. The first 200 lines or 25 KB, whichever applies first.
4. **Stale-term search.** The current term is non-interactive mode; the flag is the same.
5. Deny, then ask, then allow; first match wins.
6. CLAUDE.md is advisory; a hook is deterministic.
7. **Glossary-as-understanding.** Attach the location: compaction acts when the window nears its limit and summarises conversation, so a conversation-only rule can be lost, while project-root CLAUDE.md is re-read from disk.
8. Highest: managed policy; lowest: user settings (`~/.claude/settings.json`). Arrays merge; scalars at a higher layer override lower ones.
9. **Wrong-glossary lookup.** Use the platform glossary for model-level concepts.
10. Restores code, conversation or both to an earlier point. Checkpoints do not track changes made through the Bash tool.
11. **Source-of-truth drift.** Date entries, review after each release with `/release-notes`, and link to official pages.
12. UserPromptSubmit hook first (once per prompt), then within each tool call: the permission mode and rules check (after any PreToolUse hook), execution, PostToolUse hook; compaction happens when context nears its limit, between or within long turns; the Stop hook fires last when Claude finishes responding.

## CLOSING REFRAME

This is the craft of the vocabulary: **names are handles on layers of one loop, and the useful skill is knowing, for any term, where it acts and what separates it from its look-alike.** The engineer who understands this does not ask "what does this word mean?" — they ask "which layer is this, and is that the layer my problem lives in?"
