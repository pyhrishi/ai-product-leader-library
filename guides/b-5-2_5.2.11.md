## THE THESIS OF THIS TOPIC

**A skill reaches other people by being committed to the repo, packaged in a plugin, or deployed through managed settings, and each route has its own audience and update path.**

**Prove-it, in one sentence:** share one skill through the repo and confirm a clean checkout runs it.

**The single most important discipline: share through version control first; package into a plugin only when a second repository needs it.**

**The counterintuitive claim you will learn to defend:** personal skills are scoped to you: `~/.claude/skills/` serves 'all your projects' but lives on your machine, not in the repository [Claude Code docs, Skills, 2026].

## 5.2.11.1 — THREE ROUTES

**Framing.** The skills page lists three scopes: project skills by committing `.claude/skills/` to version control, plugins by creating a `skills/` directory in a plugin, and managed deployment organisation-wide through managed settings [Claude Code docs, Skills, 2026].

| Route | Audience | Update path |
|---|---|---|
| Commit `.claude/skills/` | Everyone who clones the repo | Pull request |
| Plugin `skills/` directory | Anyone who installs the plugin | New plugin version |
| Managed settings | Whole organisation | Admin deployment |

The failure mode: **Works-on-my-machine skill.** A skill lives in your home folder; teammates never see it.

The fix: Commit it under the project's `.claude/skills/`.

Cross-references: plugins are Module 5.6; managed settings are Module 4.1.

**If you remember one thing:** pick the narrowest route that reaches the audience.

## 5.2.11.2 — CLONE AND SYNC BEHAVIOUR

**Framing.** Project skills are committed with the repository, so they arrive with a clone; personal skills live under your home directory and serve only your own projects. Skills synced from your claude.ai account download into a separate `synced` subfolder of `~/.claude/skills/`, and Claude Code never runs injected shell commands in them; project skills committed to a repo also load when that repo is used in a Claude Tag channel [Claude Code docs, Skills, 2026]. How cloud sessions treat each location was not verified for this guide.

| Where the skill is | Who gets it |
|---|---|
| Repo `.claude/skills/` | Everyone who clones the repo |
| `~/.claude/skills/` | You, across your projects |
| claude.ai-synced skills | You, in `~/.claude/skills/synced`, without shell injection |

The failure mode: **Secrets-in-skill.** A shared skill embeds a token in a script or injected command, and it is committed with the repo.

The fix: Read secrets from the environment and never commit them in skill files.

Cross-references: security of project config is sub-topic 5.2.12.

**If you remember one thing:** if it is committed, everyone with access can read it.

---

## 5.2.11.3 — NAMING FOR SHARED USE

**Framing.** Plugin skills are namespaced so they cannot clash; project skills can be shadowed by a teammate's personal skill of the same name because personal overrides project [Claude Code docs, Skills, 2026]. Names for shared skills should therefore be distinctive.

| Choice | Effect |
|---|---|
| Generic name `review` in project | A personal `review` shadows it |
| Distinct name `acme-review` | Hard to shadow by accident |
| Plugin skill | `/acme:review`, never clashes |

The failure mode: **Shadowed share.** You share a project skill named `deploy` and teammates with a personal `deploy` run theirs instead.

The fix: Use distinctive names or ship via plugin.

Cross-references: priority rules are sub-topic 5.2.2.

**If you remember one thing:** shared names must survive personal overrides.

## CLOSING REFRAME

This is the craft of sharing: **commit it, name it, test it fresh.** The engineer who understands this does not ask "is it saved?" — they ask "does a stranger's clone run it?"
