## THE THESIS OF THIS TOPIC

**Skills are filesystem artifacts you scope with the skills option and dispatch by name, and plugins are local directories you load by path, which together let you package reusable behaviour without code.**

**Prove-it, in one sentence:** create a skill, scope it with the skills option, dispatch it with /name, package it in a plugin, and verify both through the init message.

**The single most important discipline: verify every skill and plugin from the init message, never from the file tree.**

**The counterintuitive claim you will learn to defend:** restricting the skills list does not restrict dispatch by name: sending /<name> runs a user-invocable skill even if skills omits it [Agent SDK docs, Extend agents with skills, 2026].

## 8.2.5.1 — SKILLS: DISCOVERY AND SCOPING

**Framing.** Skills are SKILL.md files under .claude/skills/<name>/, discovered through settingSources; the SDK has no programmatic API for registering them. Discovered skills are enabled by default, and the skills option takes 'all', a list of names, or [] [Agent SDK docs, Extend agents with skills, 2026].

| skills value | Effect |
|---|---|
| omitted | Discovered user and project skills enabled; Skill tool available |
| "all" | Every discovered skill invocable |
| ["pdf", "docx"] | Only these; unlisted are invisible to the model and rejected by the Skill tool |
| [] | None invocable |

[Agent SDK docs, Extend agents with skills, 2026]. Setting skills adds the Skill tool to allowedTools; with an explicit tools list, include 'Skill'. Names must be exact: wildcards and padded names make query() reject the list (TypeScript 0.3.221 or later, Python 0.2.129 or later). Plugin skills use plugin:skill.

The failure mode: **Hidden-file illusion.** You restrict skills to a list and assume the other skills are unreachable, yet their files stay readable through Read and Bash.

The fix: Treat the list as scoping what the model sees; protect sensitive skills with permissions or by not placing them on the filesystem.

Cross-references: allowed tools and permissions are Module 8.6.1; skills in Claude Code are Module 1.2.

**If you remember one thing:** the skills list scopes invocation, not file access.

## 8.2.5.2 — COMMANDS AND DISPATCH BY NAME

**Framing.** A command is anything you run by sending /<name> in a prompt: built-in commands such as /compact, bundled skills such as /code-review, your skills, and older .claude/commands/ files. The init message's slash_commands field lists the available ones [Agent SDK docs, Extend agents with skills, 2026].

```python
async for m in query(prompt="/security-check", options=ClaudeAgentOptions(max_turns=10)):
    ...
```
| Case | Result |
|---|---|
| /name matches a command | Runs, even if skills omits it |
| /name matches nothing | Sent to Claude as an ordinary message with a note it did not run; costs a model turn (since v2.1.274) |
| /theme (unavailable built-in) | Returns '/theme isn't available in this environment.' with no model turn |
| /compact with no history | success result, no compact_boundary; reason in result text |
| /clear in one-shot query | No practical effect |

[Agent SDK docs, Extend agents with skills, 2026]. A command can hit max_turns like any prompt. A user-invocable: false skill does not appear in skills or slash_commands.

The failure mode: **Typo burns a turn.** You dispatch /secuirty-check, no command matches, and the SDK silently spends a model turn answering a plain message.

The fix: Check the name against slash_commands from the init message before dispatching.

Cross-references: context and compaction are Module 8.2.1.

**If you remember one thing:** check slash_commands before you dispatch.

## 8.2.5.3 — PLUGINS: LOAD BY PATH AND VERIFY

**Framing.** plugins takes a list of {type: 'local', path}; local is the only accepted type. Relative paths resolve against cwd; the path must be the plugin root, the parent of skills/, agents/, hooks/, commands/ or .claude-plugin/. Marketplace plugins must be downloaded first [Agent SDK docs, Plugins in the SDK, 2026].

| Plugin component | Location in plugin |
|---|---|
| Skills | skills/<name>/SKILL.md (invoked as /plugin-name:skill-name) |
| Commands | commands/*.md (flat files; use skills/ for new plugins) |
| Agents | agents/*.md |
| Hooks | hooks/hooks.json |
| MCP servers | .mcp.json |
| Manifest | .claude-plugin/plugin.json (optional) |

[Agent SDK docs, Plugins in the SDK, 2026]. The SDK does not expand ~ in paths. A nonexistent path is skipped and the session continues, so check the plugins list in init, and plugin_errors for load failures. TypeScript reloadPlugins() applies changes; addPlugins needs TypeScript SDK 0.3.301 or later; Python sends /reload-plugins as a prompt.

The failure mode: **Skipped-plugin success.** A plugin path with ~ or a typo is skipped, the run succeeds, and nobody notices the plugin never loaded.

The fix: Assert on init plugins and plugin_errors in CI and fail the job if a plugin is absent.

Cross-references: plugins in the CLI are Module 1.2; deployment of plugin files is Module 8.7.2.

**If you remember one thing:** a plugin that did not load looks exactly like a plugin that did.

## 8.2.5.4 — PRE-APPROVING TOOLS AND TROUBLESHOOTING

**Framing.** Skills run with the session's tools. For project and personal skills Claude Code applies the allowed-tools frontmatter in SDK sessions, and you can also pre-approve via allowedTools. Pre-approval does not restrict other tools [Agent SDK docs, Extend agents with skills, 2026].

| Symptom | Check | Fix |
|---|---|---|
| Skills not found | settingSources excludes user and project | Include them, or load via plugins |
| Skills not found | cwd outside the repo containing .claude/skills | Point cwd at or below it |
| Skill not used | Name missing from skills list: 'Skill <name> is not in this session's skills allowlist' | Add it, or dispatch /name |
| Skill not used | Vague description | Make description specific |
| Plugin not loading | Wrong root, invalid plugin.json, unreadable, missing dir | Check plugin_errors in init |

[Agent SDK docs, Extend agents with skills and Plugins in the SDK, 2026].

The failure mode: **Empty-sources skills.** You set settingSources to [] for isolation and skills: 'all', and no skill ever loads.

The fix: Load skills through a plugin path when you need both isolation and skills.

Cross-references: isolation is Module 8.2.4 and Module 8.7.3.

**If you remember one thing:** skills need a source; isolation needs a plugin path.

## THE PROVE-IT SECTION

**Deliverable.** A plugin directory with one skill, a script that loads it, and the init-message output proving it loaded and was dispatched as /plugin:skill.

**Close this topic. Build the artifact below from memory. Return to the text only after your first attempt is complete.**

| Step | Action | Output |
|---|---|---|
| 1 | Create .claude/skills/security-check/SKILL.md with name and description | A skill file |
| 2 | Run with skills 'all' and read skills and slash_commands in init | An init dump |
| 3 | Dispatch /security-check and record the result | A transcript |
| 4 | Move the skill into a plugin and load by absolute path | A plugin dir |
| 5 | Dispatch /my-plugin:security-check | A transcript |
| 6 | Break the path on purpose and record plugin_errors | An error observation |

**A passing artifact looks like this:**

| Check | Evidence |
|---|---|
| Skill discovered | init skills includes security-check |
| Dispatched | /security-check returns success |
| Plugin loaded | plugins lists my-plugin; skills has my-plugin:security-check |
| Failure path | bad path gives absence plus plugin_errors |

**A failing artifact (a realistic near-miss):**

| Element | What is wrong |
|---|---|
| Loads plugin with ~/ path | **Skipped-plugin success** |
| Uses [] sources and skills all | **Empty-sources skills** |

**The verdict.** The artifact passes only if the init message proves load, dispatch is demonstrated, and a deliberate failure was observed.
