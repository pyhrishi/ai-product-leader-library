# MODULE 5.1.5 — HOOK VS SKILL: THE COMPLETE CRAFT

---

## THE THESIS OF THIS TOPIC

**A hook is run by Claude Code at an event whether or not Claude cooperates; a skill is read by Claude and interpreted, so guardrails belong in hooks and judgement belongs in skills.**

**Prove-it, in one sentence:** turn a 'never edit .env' skill instruction into a hook that blocks, and show the skill version failing once.

**The single most important discipline: if the rule must hold every time, it is a hook; if it needs reasoning, it is a skill.**

**The counterintuitive claim you will learn to defend:** an instruction in CLAUDE.md or a skill is 'a request, not a guarantee'; a PreToolUse hook that blocks the edit is enforcement [Claude Code docs, Extend Claude Code, 2026].

## 5.1.5.1 — THE FIVE DIFFERENCES

**Framing.** Claude Code runs a hook at a lifecycle event; it loads a skill into context for Claude to apply [Claude Code docs, Extend Claude Code, 2026].

| Aspect | Hook | Skill |
|---|---|---|
| Runs | Shell command, HTTP request, MCP tool call, LLM prompt or subagent | Instructions Claude reads and follows |
| Triggered by | Lifecycle events such as `PostToolUse`, `SessionStart` | You typing `/<name>`, or Claude matching the description |
| Determinism | Fires without Claude deciding | Claude interprets; outcome can vary |
| Context cost | Zero unless the hook returns output | Description loads each session; full content when used |
| Best for | Linting after edits, blocking unsafe commands, logging, notifications | Reasoning workflows, reference, multi-step tasks |

The failure mode: **Advisory guardrail.** A safety rule lives only as text in a skill, Claude weighs it against the task, and one run proceeds anyway.

The fix: Move the rule to a PreToolUse hook that blocks the call.

Cross-references: hooks in depth are Module 5.4; hooks as a loop-level control are Module 1.2 (sub-topic 1.2.6).

**If you remember one thing:** hooks fire; skills are read.

## 5.1.5.2 — GUARDRAILS ARE HOOKS

**Framing.** The docs say to put guardrails in hooks: if a rule must hold every time, make it a hook rather than a prompt instruction [Claude Code docs, Extend Claude Code, 2026]. The skills page repeats this in troubleshooting: when Claude skips a rule that must hold every time, move it to a hook, optionally defined in the skill's own `hooks` frontmatter so it applies from invocation until the session ends [Claude Code docs, Skills, 2026].

```bash
#!/usr/bin/env bash
# PreToolUse hook: block edits to .env files
path=$(jq -r '.tool_input.file_path // empty')
case "$path" in
  *.env|*/.env.*) echo "Blocked: .env files are protected." >&2; exit 2 ;;
esac
exit 0
```
Exit code 2 is what blocks on events that can block; other nonzero codes are non-blocking errors [Claude Code docs, Hooks, 2026; see Module 5.4].

The failure mode: **Exit-code slip.** Your guardrail hook exits 1, the tool call proceeds, and you assume the rule is enforced.

The fix: Exit 2 (or print a JSON block decision) and test by violating the rule once.

Cross-references: exit-code semantics are sub-topic 5.4.7.

**If you remember one thing:** a guardrail is only real once you have watched it block.

## 5.1.5.3 — REASONING STAYS IN SKILLS

**Framing.** Hooks run without Claude thinking, so they suit format-on-save, rejecting `rm -rf /`, and notifying when a session ends. Skills suit a `/release` checklist, an API style guide or a debugging playbook, where Claude decides how to apply the steps [Claude Code docs, Extend Claude Code, 2026].

| Job | Right tool |
|---|---|
| Run ESLint after every edit | Hook |
| Decide how to resolve the lint results | Skill (`/fix-lint`) |
| Reject destructive shell commands | Hook |
| Walk a release, adapting to what is found | Skill |

Hook output lands in context: a PostToolUse linter hook feeds results back as text Claude reads, and a skill tells Claude how to resolve them [Claude Code docs, Extend Claude Code, 2026].

The failure mode: **Script-in-prose.** You describe a deterministic command sequence in a skill and let Claude run it by hand each time, with occasional skipped steps.

The fix: Move the fixed part into a hook or script and leave only the judgement in the skill.

Cross-references: script-bearing skills are sub-topic 5.2.7.

**If you remember one thing:** hooks do the same thing every time; skills do the thinking.

## CLOSING REFRAME
