# MODULE 9.3.7 — PRODUCTION SAFETY: THE COMPLETE CRAFT

---

## THE THESIS OF THIS TOPIC

**Never give an unattended session write access to production: use read-only tooling, put never-rules in deny rules and hooks, and require human approval for changes.**

**Prove-it, in one sentence:** configure a session so a production write is blocked by a rule, not by a prompt, and show the block.

**The single most important discipline: anything that must never happen belongs in a deny rule, a hook or managed settings, not in the prompt.**

**The counterintuitive claim you will learn to defend:** auto mode is a judgement, not a wall; the docs say 'never' rules belong in deny rules or hooks.

## 9.3.7.1 — LAYERS OF CONTROL

**Framing.** The docs separate non-deterministic instructions (prompt, CLAUDE.md, skills, auto mode's classifier) from deterministic ones (hooks, deny rules, sandbox, managed settings); for rules that cannot have exceptions use the second kind [Claude Code docs, Best practices, 2026].

| Layer | Kind | Use |
|---|---|---|
| Prompt, CLAUDE.md | Non-deterministic | Guidance |
| Auto mode classifier | Non-deterministic | Blocks risky actions such as production deploys and force pushes by default |
| Deny rule | Deterministic | `Read(./.env)`, `Bash(kubectl delete *)` (pattern is an example) |
| PreToolUse hook | Deterministic | Exit 2 blocks |
| Sandbox | Deterministic OS-level | Confines shell commands |
| Managed settings | Deterministic, org-wide | Policy no personal file can override |

Deny rules hold in every permission mode including auto and `bypassPermissions` [Claude Code docs, Best practices, 2026].

The failure mode: **Prompt-only guard.** The only protection against touching production is a sentence in CLAUDE.md or the prompt, and context compaction loses it.

The fix: Move it to a deny rule or a PreToolUse hook and test that it blocks.

Cross-references: permissions are Module 4.2; sandboxing is Module 4.4.

**If you remember one thing:** never-rules are configuration.

## 9.3.7.2 — CREDENTIALS AND MODES

**Framing.** `bypassPermissions` approves everything your deny and ask rules do not cover and only makes sense in a disposable container. After three blocks in a row or twenty in total, auto mode pauses and goes back to asking [Claude Code docs, Best practices, 2026].

| Session type | Credentials |
|---|---|
| Interactive investigation | Read-only observability tokens |
| Unattended `claude -p` | `--permission-mode dontAsk` or `auto` with `--permission-prompts none`; no prod write tokens |
| Disposable container | May use bypassPermissions; still no prod secrets |
| Change to production | Human runs it, or approves each step |

The failure mode: **Ambient credential.** Your shell has a production admin profile exported, and Claude inherits it.

The fix: Run investigations in an environment with only scoped, read-only credentials.

Cross-references: headless is Module 6.8; cloud environments are Module 4.5.

**If you remember one thing:** credentials define the maximum damage.

## 9.3.7.3 — HUMAN APPROVAL FOR CHANGES

**Framing.** Changes to production should pass a human gate. Keep `ask` rules for risky commands so the permission prompt is the gate, and keep the final merge or deploy with a person [Claude Code docs, Best practices, 2026].

```json
{
  "permissions": {
    "ask":  ["Bash(git push *)"],
    "deny": ["Read(./.env)", "Read(./secrets/**)"]
  }
}
```

| Gate | Owner |
|---|---|
| Diff review | Human |
| Deploy approval | Human or protected pipeline |
| Rollback | Human, using a manual skill (Module 9.3.6) |

The failure mode: **Approval fatigue.** After ten routine prompts you approve a dangerous one without reading it.

The fix: Allowlist the safe read-only commands (`/fewer-permission-prompts`) so prompts that remain are meaningful.

Cross-references: norms are Module 9.12.

**If you remember one thing:** keep prompts rare and real.
