## 3.2.9.1 — WHEN TO CHANGE IT

**Framing.** Add when Claude repeats a mistake, when code review catches something it should have known, or when you retype the same correction [Claude Code docs, Memory, 2026]. The same triggers tell you when to update what you have: a repeated mistake or recurring review comment is a CLAUDE.md edit [Claude Code docs, Extend Claude Code, 2026].

| Signal | Action |
|---|---|
| Mistake twice | Add a line |
| Review comment recurs | Add or sharpen a line |
| Line never mattered | Remove it |
| Rule must always hold | Move to a hook |

The failure mode: **Chat-fix-only.** You correct Claude in chat each time instead of editing the file, so every session repeats the mistake.

The fix: Turn each repeated correction into a CLAUDE.md edit the same day.

Cross-references: adding to memory is Module 3.3.

**If you remember one thing:** repeat equals edit.

## 3.2.9.2 — VERSION CONTROL AND REVIEW

**Framing.** Commit the project file so teammates inherit it, and review CLAUDE.md edits in pull requests like any documentation change so conventions track the code [Claude Code docs, Large codebases, 2026]. Keep personal preferences in `CLAUDE.local.md` and add it to `.gitignore` [Claude Code docs, Best practices, 2026]. Block-level HTML comments are stripped before injection, so maintainer notes can live in the file without costing context [Claude Code docs, Memory, 2026].

```markdown
<!-- maintainer: keep under 200 lines; run /doctor before each release -->
# Conventions
- Prefix commit subjects with the package name
```

| Artifact | Git |
|---|---|
| `CLAUDE.md` | Commit |
| `CLAUDE.local.md` | Gitignore |
| `.claude/rules/*.md` | Commit |

The failure mode: **Comment-in-code-block.** You put a maintainer note in a code block expecting it to be stripped, but comments inside code blocks are kept and cost context.

The fix: Use a block-level HTML comment outside any code block.

Cross-references: rules directory is Module 3.3.

**If you remember one thing:** only block-level comments are stripped.

## 3.2.9.3 — TESTING AND REVISITING

**Framing.** Test changes by watching whether behaviour shifts. Revisit instructions after major model releases, since workarounds for an older limitation can become overhead, and consider a Stop hook that receives the session transcript path and proposes CLAUDE.md updates while the gap is fresh [Claude Code docs, Large codebases, 2026].

| Step | Evidence |
|---|---|
| Pick a task that exercises the line | Task text |
| Run before the change | Result |
| Change one line | Diff |
| Run after in a fresh session | Result |

The failure mode: **Untested-edit.** You merge a CLAUDE.md change after reading it, never watching whether behaviour changed.

The fix: Attach a before and after run of one relevant task to the pull request.

Cross-references: evals are Module 10.1.

**If you remember one thing:** no evidence, no merge.

## THE PROVE-IT SECTION

**Deliverable.** A pull request template for CLAUDE.md changes and one completed change with its behaviour test.

**Close this topic. Build the artifact below from memory. Return to the text only after your first attempt is complete.**

| Step | Action | Output |
|---|---|---|
| 1 | Pick a recurring correction | Trigger |
| 2 | Write one line to address it | Diff |
| 3 | Run a task before the change | Before |
| 4 | Run after, in a fresh session | After |
| 5 | Open a PR with both runs attached | PR text |
| 6 | Add a block-level maintainer comment | Comment |

**A passing artifact looks like this:**

| Run | Before | After |
|---|---|---|
| Task exercising the line | Mistake repeated | Mistake gone |

**A failing artifact (a realistic near-miss):**

| Element | What is wrong |
|---|---|
| PR with no run evidence | **Untested-edit** |
| Note placed in a code block | **Comment-in-code-block** |

**The verdict.** The artifact passes only if both runs are attached and the change touched one line.

## CLOSING REFRAME

This is the craft of upkeep: **hypothesis, diff, test, merge.** The engineer who understands this does not ask "is the file good?" — they ask "what did this change do to behaviour?"
