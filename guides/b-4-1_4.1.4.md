## 4.1.4.1 — WHICH PAGE ANSWERS WHICH QUESTION

**Framing.** The docs split settings knowledge four ways. The settings page opens with a tip pointing to All settings for any single key [Claude Code docs, Settings files and precedence, 2026].

| Question | Page |
|---|---|
| Which file? Who wins? Why ignored? | Settings files and precedence |
| Type, default, scope, per-session overrides of one key | All settings (settings reference) |
| What do a real developer, team and organization file look like? | Example settings files |
| How do I deliver policy to every machine? | Deploy managed settings |
| What does allow/ask/deny syntax look like? | Configure permissions |

The reference lists the scope labels User, Project, Local, Managed, Any file and Global config (`~/.claude.json`) [Claude Code docs, All settings, 2026].

The failure mode: **Page roulette.** You read the permissions page to learn why a `model` key is ignored, and the answer is on a different page.

The fix: Route by question type using the table, then read only that section.

Cross-references: managed delivery is sub-topic 4.1.6; permissions syntax is Module 4.2.

**If you remember one thing:** route by question, not by keyword.

## 4.1.4.2 — READING A KEY ENTRY

**Framing.** Each entry in All settings gives the file you set it in, the type, the default and an example, plus per-session overrides and which one wins [Claude Code docs, Settings files and precedence, 2026].

| Field | Example: `effortLevel` |
|---|---|
| Type | `"low"`, `"medium"`, `"high"`, `"xhigh"` |
| Default | unset |
| Override | `--effort` for one session; `CLAUDE_CODE_EFFORT_LEVEL` overrides both |
| Note | In user settings applies to Opus 5 and earlier; in project/local/managed/`--settings` applies to every model |

Other examples: `availableModels` default unset (all allowed); `fallbackModel` keeps at most three distinct allowed models; `alwaysThinkingEnabled` false turns thinking off [Claude Code docs, All settings, 2026].

The failure mode: **Default guessing.** You assume a key's default instead of reading it, such as expecting thinking off or effort low.

The fix: Open the key's entry and read Default before changing it.

Cross-references: model keys are Module 4.6.

**If you remember one thing:** defaults live in the entry, not in memory.

## 4.1.4.3 — THE EXAMPLE FILES AND THE INDEX

**Framing.** The example page shows three commented files: a personal file, a team's shared settings and an organization's managed file [Claude Code docs, Settings files and precedence, 2026]. The all-settings index tells you per key whether it applies from the shared file.

| Scope column says | Meaning |
|---|---|
| `User, local, or managed` | Never applies from the shared project file (a few can be switched off there) |
| `Managed` | Only a managed source honors it |
| `Global config` | Only `~/.claude.json` |
| `Any file` | All four files |

The published JSON schema can lag the newest CLI, so a validation warning on a recently documented key does not mean your config is invalid.

The failure mode: **Schema trust.** You delete a valid new key because the editor's schema flags it as unknown.

The fix: Check the key on the settings reference before removing it; run claude doctor for real rejection.

Cross-references: diagnostics are sub-topic 4.1.5.

**If you remember one thing:** the schema lags; the reference leads.
