## THE THESIS OF THIS TOPIC

**The context window holds far more than your messages: instructions, every file read, tool output, Claude's own replies and text you never see in the terminal, and everything in it is re-sent on every request.**

**Prove-it, in one sentence:** list the contents of a fresh session before you type anything, then predict and measure what one file read adds.

**The single most important discipline: before blaming a long session, inventory what is in it by source: startup load, reads, outputs, additions by Claude Code itself.**

**The counterintuitive claim you will learn to defend:** the biggest context items are often ones you never typed and never see, such as skill descriptions, MCP tool names and system reminders [Claude Code docs, Context window, 2026].

## 3.1.1.1 — THE STARTUP LOAD

**Framing.** Before you type anything, CLAUDE.md, auto memory, MCP tool names and skill descriptions are already in context; AGENTS.md files can load in place of CLAUDE.md, and an output style or `--append-system-prompt` text adds more [Claude Code docs, Context window, 2026]. Auto memory contributes the first 200 lines or 25KB of `MEMORY.md`, whichever comes first; CLAUDE.md loads in full [Claude Code docs, Memory, 2026].

| Loader | What enters | Scope of the limit |
|---|---|---|
| CLAUDE.md files | Full content, all levels | No cap; docs target under 200 lines per file |
| Auto memory | `MEMORY.md` index only | First 200 lines or 25KB |
| MCP servers | Tool names and server instructions | Schemas deferred until needed |
| Skills | Names and descriptions | Full body only on use |
| Output style, `--append-system-prompt` | Style or appended text | Every request |

The interactive explainer uses *representative* token counts, not measured ones, so treat its numbers as illustrative and read your own with `/context` [Claude Code docs, Context window, 2026].

The failure mode: **Startup-blindness.** You assume a fresh session is empty, then wonder why 10 percent of the window is gone before the first prompt, because instructions, skill descriptions and tool names loaded silently.

The fix: Run `/context` at the very start of a session and record the baseline before any task.

Cross-references: per-feature costs are in sub-topic 3.1.4 of Module 3.1; CLAUDE.md is Module 3.2; auto memory is Module 3.3.

**If you remember one thing:** the window starts partly full, by design.

## 3.1.1.2 — WHAT EACH TURN ADDS

**Framing.** As Claude works, each file read adds to context, path-scoped rules load alongside matching files, and a PostToolUse hook that returns output adds more [Claude Code docs, Context window, 2026]. Every request re-sends the whole conversation, so a session that collected three unrelated tasks re-reads all three on every turn of the fourth [Claude Code docs, Best practices, 2026].

| Source | When it enters | Stays? |
|---|---|---|
| File read | When Claude reads it | Until compaction or `/clear` |
| Path-scoped rule | When a matching file is read, written or edited | In history, so compaction can summarise it away |
| Command output | When a Bash call returns | Same |
| Hook output | Only if the hook returns it | Same |
| Subagent work | Only its summary returns | Raw reads stay out |

The failure mode: **Output-flood.** One command prints thousands of lines, such as a full test log or `git log`, and the noise stays in context for the rest of the session.

The fix: Ask for bounded output (`tail`, `--stat`, a filter) or route noisy work through a subagent so only a summary returns.

Cross-references: bounding output is a prompting skill covered in Module 2.2; subagents are Module 5.3.

**If you remember one thing:** reads and outputs are the growth term; bound them.

## 3.1.1.3 — CONTEXT CLAUDE CODE ADDS ON ITS OWN

**Framing.** Some context is added without you writing it: your CLAUDE.md files, the active output style's instructions, a note when a file Claude read earlier changes on disk, and commit and pull request attribution lines [Claude Code docs, How Claude Code works, 2026]. If Claude follows a rule you never wrote, such as a `Co-Authored-By` trailer, it may have come from a system reminder.

```text
Surprise rule seen in behaviour?
  1. Is it in a CLAUDE.md or rules file?  -> /memory lists loaded files
  2. Is it an output-style instruction?   -> /output-style shows the active style
  3. Is it attribution or git guidance?   -> settings: attribution, includeGitInstructions
  4. Otherwise: a system reminder; search the transcript for it
```

To change attribution lines set `attribution`; to remove built-in commit and pull request instructions set `includeGitInstructions` to `false` [Claude Code docs, How Claude Code works, 2026].

The failure mode: **Phantom-rule hunt.** You search your CLAUDE.md for the origin of a behaviour that Claude Code injected itself, and edit the wrong file for an hour.

The fix: Walk the four-step origin check above before editing any instruction file.

Cross-references: output styles are Module 3.6; attribution settings are Module 4.1.

**If you remember one thing:** not every instruction in context is yours.

## 3.1.1.4 — COUNTING AND PRICING THE WINDOW

**Framing.** Models differ in window size: Fable 5.1, Fable 5, Sonnet 5 and later, Haiku 5.5, and Opus 4.7 and later run with a 1M-token window by default, while Opus 4.6 and Sonnet 4.6 reach 1M only through a `[1m]` variant [Claude Code docs, Model configuration, 2026]. A larger window does not make unneeded context free: you still pay for it on every request, at a discounted rate while the cache is warm and full price once it expires [Claude Code docs, Best practices, 2026].

| Window fact | Value | Source |
|---|---|---|
| Default window, Sonnet 5 and later | 1M tokens | Model configuration |
| Opus 4.6 / Sonnet 4.6 without `[1m]` | 200K boundary | Model configuration |
| Opt out of 1M | `CLAUDE_CODE_DISABLE_1M_CONTEXT=1` | Model configuration |
| Memory index loaded | 200 lines or 25KB | Memory |

The failure mode: **Big-window complacency.** You treat a 1M window as permission to keep every task in one session, and the cost and noise of old history grows each turn.

The fix: Use `/clear` between unrelated tasks; it costs nothing and stops the next task paying for the last one's history.

Cross-references: cost and cache effects are Module 3.4; cost controls are Module 6.1.

**If you remember one thing:** size is capacity, not a licence to fill it.

## CLOSING REFRAME

This is the craft of the window: **know what is in it, by source, before you decide what to do about it.** The engineer who understands this does not ask "why did it forget?" — they ask "what was in the window, and what did it displace?"
