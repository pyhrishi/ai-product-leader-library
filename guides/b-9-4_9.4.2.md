# MODULE 9.4.2 — SMALL STEPS WITH VERIFICATION BETWEEN THEM: THE COMPLETE CRAFT

---

## THE THESIS OF THIS TOPIC

**Refactoring succeeds as a chain of small changes each followed by a check, so a failure localises to the last step and rewinding costs one step, not a day.**

**Prove-it, in one sentence:** perform a refactor in at least five steps with a recorded green check after each.

**The single most important discipline: never take a second step on a red first step.**

**The counterintuitive claim you will learn to defend:** the speed of a refactor is the speed of its slowest recovery, so smaller steps are faster overall.

**THE TIME BUDGET.** Reading time: ~13 minutes. Prove-it time: ~1.5 hours (90 minutes, 6.9 times the reading time).

## 9.4.2.1 — THE STEP CONTRACT

**Framing.** The docs advise doing refactoring in small, testable increments and verifying with tests after each [Claude Code docs, Common workflows, 2026]. Claude Code adds `/rewind` (or double `Esc`) to roll code, conversation or both back to an earlier prompt [Claude Code docs, Best practices, 2026].

| Step | Check | On red |
|---|---|---|
| Extract function | Pinned tests | `/rewind` to previous prompt |
| Rename | Typecheck plus tests | Revert |
| Move file | Imports resolve, tests | Revert |
| Remove duplicate | Tests | Revert |
| Simplify | Tests, `/simplify` | Revert |

Checkpoints cover files edited with Claude's own file tools; a file touched only by a Bash command is not restored, so commit often [Claude Code docs, Best practices, 2026].

The failure mode: **Step pile-up.** Five changes land before the first check, and a red result cannot be localised.

The fix: One concern per step, a check after each, and a commit on green.

Cross-references: checkpoints are Module 2.5; characterisation is Module 9.4.1.

**If you remember one thing:** check after every step.

## 9.4.2.2 — COMMIT RHYTHM

**Framing.** A commit per green step makes bisect and revert trivial and keeps diffs reviewable. Ask Claude to commit only after the check passes and to show its output.

```text
Do step 1 only: extract the validation block into validate().
Run the pinned tests and show output. If green, commit with message "refactor: extract validate()".
Stop and wait.
```

| Practice | Benefit |
|---|---|
| One commit per step | Small revert unit |
| Message names the step | Review by commit |
| Stop after each | Human checkpoint |

The failure mode: **Mega-commit.** A single commit contains all steps, so nothing can be reverted selectively.

The fix: Commit per green step; squash later only if the team wants.

Cross-references: pull request norms are Module 9.12.2.

**If you remember one thing:** commit per verified step.

## 9.4.2.3 — STOPPING RULES

**Framing.** Define when a step is too big: the check fails twice, or the diff exceeds your review limit. The docs advise after more than two failed corrections to `/clear` and write a better prompt [Claude Code docs, Best practices, 2026].

| Signal | Action |
|---|---|
| Two failed corrections | `/clear`, new prompt with lessons |
| Diff over your size limit | Split the step |
| Check slow | Narrow to one file in the inner loop (Module 9.2.6) |

The failure mode: **Correction spiral.** You keep correcting a failed step inside one cluttered context.

The fix: After two failed corrections, `/rewind` or `/clear` and restate the step smaller.

Cross-references: the loop is Module 1.2.

**If you remember one thing:** shrink the step when it fails.

## CLOSING REFRAME

This is the craft of small steps: **one concern, one check, one commit.** The engineer who understands this does not ask "can I do it all at once?" — they ask "what is the smallest step I can verify?"
