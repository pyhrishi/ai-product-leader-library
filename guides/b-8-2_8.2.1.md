## THE THESIS OF THIS TOPIC

**One query() call is a sequence of turns; each turn yields messages, runs tools, and grows a context window that the SDK compacts when it nears its limit, and every limit, hook and result subtype attaches to that sequence.**

**Prove-it, in one sentence:** given a transcript of SDK messages, label each turn, name the message type of every item, and predict which result subtype ends the run.

**The single most important discipline: read the message stream as the ground truth of the loop before changing any option.**

## 8.2.1.1 — THE CYCLE AND ITS MESSAGES

**Framing.** Every session follows five steps: receive the prompt (a SystemMessage with subtype init), evaluate and respond (AssistantMessage), execute tools, repeat, and return the result (a final AssistantMessage then a ResultMessage). A turn is one round trip: Claude's output with tool calls, SDK execution, and results fed back without yielding control to your code [Agent SDK docs, How the agent loop works, 2026].

| Message type | Emitted when | Note |
|---|---|---|
| SystemMessage | Session lifecycle: `init`, `compact_boundary`, `informational`, `worker_shutting_down` | Subtype distinguishes them |
| AssistantMessage | After each Claude response, including the final text-only one | Text and tool-call blocks |
| UserMessage | After each tool execution, and for inputs you stream mid-loop | Carries tool results |
| StreamEvent | Only when partial messages are enabled | Raw API streaming events |
| ResultMessage | Marks the end | Final text, usage, cost, session id |

[Agent SDK docs, How the agent loop works, 2026]. Worked example from the docs: 'Fix the failing tests in auth.ts' took four turns, three with tool calls and one final text-only response [same page]. A few system events, such as prompt_suggestion, can arrive after the ResultMessage, so iterate to completion instead of breaking on the result.

The failure mode: **Early-break read.** You break out of the stream on the ResultMessage and miss trailing system events and cleanup, or you never drain the iterator and leak the subprocess.

The fix: Iterate the stream to completion and treat the ResultMessage as the end of the loop, not the end of the stream.

Cross-references: streaming output is Module 8.4.2; the Claude Code loop it mirrors is Module 1.2.

**If you remember one thing:** a turn is a tool round trip, and the ResultMessage ends the loop.

## 8.2.1.2 — TOOL EXECUTION: CONCURRENCY AND PERMISSION

**Framing.** Tool calls in a turn run concurrently or sequentially depending on the tool: read-only tools such as Read, Glob, Grep and MCP tools marked read-only can run concurrently, while Edit, Write and Bash run sequentially. Custom tools default to sequential unless readOnlyHint is set [Agent SDK docs, How the agent loop works, 2026].

| Option | Effect | Detail |
|---|---|---|
| `allowed_tools` / `allowedTools` | Auto-approves listed tools | Unlisted tools remain available but need permission |
| `disallowed_tools` / `disallowedTools` | Blocks listed tools | Regardless of other settings |
| `permission_mode` / `permissionMode` | Oversight level | default, acceptEdits, plan, dontAsk, auto, bypassPermissions |

[Agent SDK docs, How the agent loop works, 2026]. A denied call returns a rejection message as the tool result, and Claude typically tries another approach or reports it cannot proceed. bypassPermissions cannot run as root on Unix and, in TypeScript, also requires allowDangerouslySkipPermissions: true [same page].

The failure mode: **Allowlist-as-sandbox.** You list three tools in allowed_tools and assume nothing else can run, but unlisted tools stay available and fall through to the permission mode.

The fix: Use disallowed tools or dontAsk mode when you need a hard deny, and keep allowed tools for auto-approval only.

Cross-references: permissions in depth are Module 8.6.1; built-in tools are Module 8.3.1.

**If you remember one thing:** allowed means pre-approved, not exclusive.

## 8.2.1.3 — LIMITS, EFFORT AND THE RESULT SUBTYPE

**Framing.** Two caps bound a loop: max_turns (tool-use round trips only) and max_budget_usd. Both default to no limit, and hitting one returns a ResultMessage with error_max_turns or error_max_budget_usd [Agent SDK docs, How the agent loop works, 2026]. The budget cap includes subagent spend and, from Claude Code v2.1.217, spawning another subagent past the cap fails with 'Budget limit reached' [same page].

| Subtype | Meaning | `result` present |
|---|---|---|
| success | Finished normally | Yes |
| error_max_turns | Hit turn cap | No |
| error_max_budget_usd | Hit budget cap | No |
| error_during_execution | API failure or cancelled request | No |
| error_max_structured_output_retries | No valid structured output within retry limit | No |

[Agent SDK docs, How the agent loop works, 2026]. A single-shot query() yields the error result and then raises; wrap the loop in try/except. In configuration, max_turns 0 means no limit, while max_budget_usd 0 is rejected by the CLI at startup [Agent SDK docs, Configure your agent, 2026]. The effort option takes low, medium, high, xhigh and max; if unset the SDK defers to the model default.

The failure mode: **Zero-budget trap.** You pass max_budget_usd=0 expecting 'no spend allowed' and the session never starts, while max_turns=0 silently means unlimited.

The fix: Leave options unset to mean no cap, and use a small positive number for a tight budget.

Cross-references: cost tracking is Module 8.6.3; failure handling is Module 8.7.5.

**If you remember one thing:** every cap has a subtype, and zero does not mean the same thing for both caps.

## 8.2.1.4 — THE CONTEXT WINDOW AND COMPACTION

**Framing.** The context window accumulates across turns: system prompt, tool definitions, conversation history, tool inputs and outputs. Stable content such as system prompt, tool definitions and CLAUDE.md is prompt cached. When the window nears its limit, the SDK compacts: it summarizes older history and emits a SystemMessage with subtype compact_boundary [Agent SDK docs, How the agent loop works, 2026].

| Source | When it loads | Impact |
|---|---|---|
| System prompt | Every request | Small fixed cost |
| CLAUDE.md | Session start, via settingSources | Full content every request (cached) |
| Tool definitions | Every request; MCP schemas deferred by default | Built-in schemas always load |
| Conversation history | Accumulates | Grows each turn |
| Skill descriptions | Session start | Short; full content on invoke |

[Agent SDK docs, How the agent loop works, 2026]. Compaction can drop early instructions, so persistent rules belong in CLAUDE.md, which is re-injected on every request. Customize with a summary-instructions section in CLAUDE.md, a PreCompact hook (trigger is manual or auto), or send /compact as a prompt. Each subagent starts fresh, and only its final response returns to the parent.

The failure mode: **Prompt-borne rules.** You put a hard rule only in the first prompt, a long run compacts, and the rule is summarized away.

The fix: Move persistent rules into CLAUDE.md or the system prompt and add a PreCompact hook to archive the transcript.

Cross-references: system prompts are Module 8.2.3; subagents are Module 8.3.5; hooks are Module 8.6.2.

**If you remember one thing:** rules that must survive compaction live outside the conversation.
