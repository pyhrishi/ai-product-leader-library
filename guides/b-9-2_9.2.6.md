# MODULE 9.2.6 — FLAKY TESTS AND SLOW SUITES: THE COMPLETE CRAFT

## THE THESIS OF THIS TOPIC

**Flaky and slow tests are diagnosed by isolating and reproducing them first, and managed by running single tests during development, so Claude fixes the cause instead of adding retries.**

**Prove-it, in one sentence:** isolate one flaky test, reproduce the flake, fix the cause and show repeated passes.

**The single most important discipline: reproduce the flake before changing anything.**

**The counterintuitive claim you will learn to defend:** retrying a flaky test hides a real race condition, and retries are what an agent will add if you ask it to 'make it pass'.

## 9.2.6.1 — ISOLATE AND REPRODUCE

**Framing.** The docs' bug advice is to tell Claude the command that reproduces the issue and to say whether the error is intermittent or consistent [Claude Code docs, Common workflows, 2026]. For flaky tests, raising effort helps: the docs list 'a flaky test' among cases where getting it right depends on cases that are quick to overlook, and suggest `/effort high` or `xhigh` [Claude Code docs, Best practices, 2026].

| Step | Command or prompt |
|---|---|
| Run alone | `pnpm vitest run path/to/flaky.test.ts` (sample command from the docs) |
| Repeat | Loop it 20 times in a shell (the 20 is an example) |
| Randomise order | Use your runner's shuffle option (runner-specific, not verified) |
| Raise effort | `/effort high` |

```text
This test fails about 1 in 10 runs. Run it 30 times alone, record failures, then 30 times
with the whole file, and tell me which condition produces the flake before you change code.
```

The failure mode: **Retry patch.** Claude adds a retry or a sleep and the flake becomes rarer, not gone.

The fix: Prohibit retries and sleeps in the prompt; require a root cause statement and a failing reproduction.

Cross-references: root-cause discipline is Module 9.3.5; reasoning effort is Module 4.6.

**If you remember one thing:** reproduce, then fix the cause.

## 9.2.6.2 — COMMON CAUSES AND FIXES

**Framing.** Most flakes come from shared state, time, ordering, concurrency or the network. This table is general practice, not from the Claude Code docs.

| Cause | Symptom | Fix |
|---|---|---|
| Shared state | Passes alone, fails in suite | Isolate fixtures; reset per test |
| Real clock | Fails near boundaries | Inject a fake clock |
| Async race | Fails under load | Await the condition, not a delay |
| Test order | Fails when shuffled | Remove inter-test dependencies |
| Network | Fails in CI | Fake the boundary |

The failure mode: **Sleep-for-sync.** A fixed sleep waits for an async result and fails on slow machines.

The fix: Wait on the event or condition with a bounded timeout instead.

Cross-references: test quality is Module 9.2.3.

**If you remember one thing:** match the fix to the cause.

## 9.2.6.3 — SLOW SUITES: RUN THE NARROWEST CHECK

**Framing.** During development run single tests and keep the full suite for the gate. The docs' CLAUDE.md sample lists how to run one test file, and `/usage` shows where time and tokens went [Claude Code docs, Best practices, 2026].

| Loop | What runs |
|---|---|
| Inner (seconds) | One test file |
| Middle (per step) | Changed module's tests |
| Outer (gate) | Full suite in Stop hook or CI |

Ask Claude to profile the suite (slowest tests) and propose fixes, then verify the total time before and after.

The failure mode: **Full-suite inner loop.** Every edit runs the entire suite, so a 10-minute run is paid dozens of times.

The fix: Put the single-test command in CLAUDE.md and the full suite in the gate only.

Cross-references: CI is Module 9.9.2.

**If you remember one thing:** the inner loop should take seconds.

| Check | Evidence |

**The verdict.** The artifact passes only if the flake was reproduced before the fix and the fix diff contains no retry or sleep.

## CLOSING REFRAME

This is the craft of flaky and slow tests: **reproduce, root-cause, narrow the loop.** The engineer who understands this does not ask "how do I make it pass?" — they ask "under what condition does it fail?"
