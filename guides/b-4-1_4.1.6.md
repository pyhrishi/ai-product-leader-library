## THE THESIS OF THIS TOPIC

**Managed-only keys let an organization restrict where customization may come from, but each key is a lock on a surface, not a general kill switch, and delivery rules decide whether it even applies.**

**Prove-it, in one sentence:** given a policy goal, choose the managed keys, deliver them, and state what a developer can still do.

## 4.1.6.1 — MANAGED-ONLY KEYS ARE LOCKS

**Framing.** Claude Code reads a set of keys only from a managed source; in user or project files they have no effect. Most are locks: the governed value (permission rules, `sandbox.network.allowedDomains`) is an ordinary key any level can set, and the lock tells Claude Code to honor only the managed value [Claude Code docs, Deploy managed settings, 2026].

| Key | What it locks |
|---|---|
| `strictPluginOnlyCustomization` | Skills, agents, hooks, MCP from user and project sources; `true` locks all four, an array names which (`.agents`, `.hooks`, `.mcp`, `.skills`) |
| `strictKnownMarketplaces` / `blockedMarketplaces` | Which marketplace sources users may add |
| `allowManagedHooksOnly` | Which hooks run |
| `allowManagedPermissionRulesOnly` | Permission rules only from managed |
| `allowManagedMcpServersOnly` | Only managed `allowedMcpServers` respected; `deniedMcpServers` still merges |
| `disableSideloadFlags` | Rejects `--plugin-dir`, `--plugin-url`, `--agents`, `--mcp-config` (v2.1.193+) |
| `disableCommandPluginSources` | Blocks `command` plugin sources (v2.1.229+) |

The failure mode: **Lock-less policy.** You deploy `permissions.deny` but not the lock, so users still add their own allow rules beside it.

The fix: Add `allowManagedPermissionRulesOnly` when only managed rules should count; remember deny always wins anyway.

Cross-references: permission rules are Module 4.2; plugins are covered in the plugin modules.

**If you remember one thing:** a lock governs one surface.

## 4.1.6.2 — DELIVERY AND COMBINING MANAGED SOURCES

**Framing.** A managed settings file, MDM profile or claude.ai console applies one policy to everyone it reaches. When several deliver to one machine, the default `first-wins` uses the highest-ranked source with at least one policy key and ignores the rest [Claude Code docs, Deploy managed settings, 2026].

| Rank | Source | Read |
|---|---|---|
| 1 | Server-managed (claude.ai console or gateway) | Fetched at startup, polled hourly |
| 2 | MDM/OS policy (macOS plist, HKLM) | Read at startup, checked every 30 minutes |
| 3 | `managed-settings.json` + `managed-settings.d/*.json` | Reloaded on file change |
| 4 | HKCU registry | Only when no admin document above it |

File paths: `/Library/Application Support/ClaudeCode/` (macOS), `/etc/claude-code/` (Linux, WSL), `C:\Program Files\ClaudeCode\` (Windows). Drop-ins merge alphabetically; later single values win, lists union.

The failure mode: **Shadowed source.** You change the managed file but the console already delivers a policy, so first-wins ignores the file with no warning.

The fix: Run /status to see which source is used and skipped; set `managedSourcesBehavior: merge` (v2.1.242+) if you want all composed.

Cross-references: precedence is sub-topic 4.1.2.

**If you remember one thing:** ranking decides which source speaks.

## 4.1.6.3 — WHAT A DEVELOPER CAN STILL CHANGE

**Framing.** Managed settings bind Claude Code only and not the developer's other tools; some items sit outside the lock [Claude Code docs, Deploy managed settings, 2026].

| Still possible | Why |
|---|---|
| Pick a model with `--model` / `ANTHROPIC_MODEL` | Managed `model` is a default; use `availableModels`/`deniedModels` |
| Edit the managed file as local admin | MDM can redeploy on a schedule |
| Edit server-managed cache | Lasts until next successful fetch |
| Call the API from another tool | Settings bind Claude Code only |
| Cloud sessions | Device files do not reach them; only server-managed does |

`forceRemoteSettingsRefresh` blocks CLI startup until remote settings are freshly fetched and exits if fetch fails (fail-closed). `requiredMinimumVersion` blocks an outdated binary but does not end a running session.

The failure mode: **Lock overconfidence.** You report the model as locked because you set a managed `model`, then a developer runs `--model` and uses another.

The fix: Deploy `availableModels` (and `deniedModels`, v2.1.283+) for a real lock.

Cross-references: models are Module 4.6; cloud is Module 4.5.

**If you remember one thing:** a default is not a lock.
