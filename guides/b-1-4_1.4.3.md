## THE THESIS OF THIS TOPIC

**Speed and depth are purchasable meters; open them on purpose and close them after.**

**Prove-it, in one sentence:** run one mechanical task at two effort levels and show no quality difference with a usage difference.

**The single most important discipline: set a moderate default and raise it deliberately.**

**The counterintuitive claim you will learn to defend:** more thinking is not always better thinking; on mechanical work it is pure cost.

## 1.4.3.1 — THE LEVERS

**Framing.** Effort controls adaptive reasoning: higher effort means more thinking tokens and deeper reasoning, lower is faster and cheaper; it is supported on Fable models, Opus 4.6 and later, and Sonnet 4.6 and later [Claude Code docs, Glossary, 2026].

| Lever | Speed | Cost | Use for |
|---|---|---|---|
| Lower effort | Faster | Cheaper | Renames, formatting |
| Default effort | Balanced | Balanced | Most feature work |
| Higher effort | Slower | More thinking tokens | Architecture, hard bugs, security review |
| Fast mode | Faster output | Usage credits on individual plans | Interactive latency pain |
| Smaller model | Faster | Cheaper | Search subagents |

The exact fast-mode multiplier is not reliably established here; check the Costs page.

The failure mode: **Effort-as-default.** You leave effort at maximum for everything and the plan bar empties on routine edits.

The fix: Set a moderate default, raise it for hard steps, lower it for batch mechanical work.

Cross-references: models, effort and speed are Module 4.6; model layer is Module 1.2.8.

**If you remember one thing:** effort is a meter, not a mood.

## 1.4.3.2 — FAST MODE

**Framing.** Fast mode is billed through usage credits on individual plans, so it shows up in your credit total rather than the plan bar [Claude Code docs, Costs, 2026].

| Habit | Why |
|---|---|
| Turn on per task | Latency matters now |
| Turn off after | Credits keep draining otherwise |
| Check month-to-date credit spend weekly | Catch drift |

The failure mode: **Fast-mode forgetting.** You enable fast mode for an afternoon and discover the credit spend a month later.

The fix: Treat fast mode as a per-task switch and review credit spend weekly.

Cross-references: credits are Module 1.4.2.

**If you remember one thing:** open it, use it, close it.

## 1.4.3.3 — THINKING TOKENS COUNT

**Framing.** Thinking tokens count against limits. A session on maximum effort pays for deep reasoning on steps that did not need it, and on a subscription that spends your window. Extended thinking can be capped on models with a fixed budget through `MAX_THINKING_TOKENS` [Claude Code docs, Glossary, 2026].

| Symptom | Likely cause |
|---|---|
| Plan bar drains on small edits | High effort default |
| Slow answers on trivial tasks | High effort default |
| Shallow answers on hard tasks | Effort too low |

The failure mode: **Shallow-default regret.** You drop effort to save usage and then accept a shallow answer on a genuinely hard step.

The fix: Raise effort for planning and review steps and keep it low for mechanical ones.

Cross-references: planning is Module 2.1.

**If you remember one thing:** cut thinking where it adds nothing; keep it where it earns.

## 1.4.3.4 — PER-STEP SETTINGS

**Framing.** A pragmatic pattern is a stronger model and higher effort for planning and review, default for implementation, and a small model for search subagents.

| Step | Setting |
|---|---|
| Plan | Strong, high |
| Implement | Default |
| Search subagent | Small |
| Review | Strong, high |

[Judgement-based pattern; measure with `/usage`.]

The failure mode: **Single-setting habit.** One model and effort for the whole task overspends on easy steps or underpowers hard ones.

The fix: Switch per step with `/model` and set subagent models in frontmatter.

Cross-references: subagents are Module 1.2.5.

**If you remember one thing:** settings follow the step.
