## THE THESIS OF THIS TOPIC

**Each extension has a recognisable trigger, so a setup should grow from repeated friction rather than be designed up front.**

**Prove-it, in one sentence:** show three real repeated frictions from your own sessions, each mapped to the extension its trigger names.

**The single most important discipline: do not add a feature until its trigger has fired; when it has, add it the same day.**

**The counterintuitive claim you will learn to defend:** the same triggers tell you when to update what you already have: a repeated mistake or recurring review comment is a CLAUDE.md edit, not a one-off correction [Claude Code docs, Extend Claude Code, 2026].

## 5.1.2.1 — THE NINE-ROW TRIGGER TABLE

**Framing.** The overview says you do not need to configure everything up front: each feature has a recognisable trigger and most teams add them in roughly the order below [Claude Code docs, Extend Claude Code, 2026].

| Trigger | Add |
|---|---|
| Claude gets a convention or command wrong twice | CLAUDE.md |
| You keep asking Claude to be shorter, explain more, or answer in the same format | Output style |
| You keep typing the same prompt to start a task | User-invocable skill |
| You paste the same playbook into chat for the third time | Skill |
| You keep copying data from a browser tab Claude cannot see | MCP server |
| Claude reads many files to find where a symbol is defined or used | Code intelligence plugin |
| A side task floods your conversation with output you will not reference again | Subagent |
| You want something to happen every time without asking | Hook |
| A second repository needs the same setup | Plugin |

[Claude Code docs, Extend Claude Code, 2026]

The failure mode: **Speculative setup.** You install ten servers, five skills and three hooks in week one because they look useful, and none has a trigger behind it, so you pay context for nothing.

The fix: Add a feature only when its row in the trigger table has fired at least once in your own work.

Cross-references: the menu is sub-topic 5.1.1; context cost of unused features is sub-topic 5.1.8 and Module 3.1.

**If you remember one thing:** the trigger comes first, the feature second.

## 5.1.2.2 — COUNTING: TWICE, THIRD TIME

**Framing.** Two rows carry numbers: a convention wrong twice, and a playbook pasted for the third time. Numbers matter because they stop you building on a single event, and stop you tolerating a tenth repeat.

| Event count | What the docs imply |
|---|---|
| 1 | Correct it in chat |
| 2 (convention or command wrong) | Add to CLAUDE.md |
| 3 (playbook pasted) | Capture as a skill |
| Every time, no exceptions | Hook |

```text
# friction log entry
2026-11-24  Claude ran npm instead of pnpm   (2nd time)  -> CLAUDE.md: "Use pnpm, not npm."
2026-11-24  pasted release checklist         (3rd time)  -> /release skill
```

The failure mode: **Third-paste tolerance.** You paste the same playbook into chat a fifth and sixth time because writing the skill feels like a detour.

The fix: At the third paste, stop and write the skill; the detour is shorter than every later paste.

Cross-references: writing the skill is Module 5.2.

**If you remember one thing:** count repeats; two means rule, three means skill.

## 5.1.2.3 — TRIGGERS ALSO SAY WHEN TO UPDATE

**Framing.** The docs state that the same triggers tell you when to update what you already have: a repeated mistake or a recurring review comment is a CLAUDE.md edit, and a workflow you keep tweaking by hand is a skill that needs another revision [Claude Code docs, Extend Claude Code, 2026].

| Signal | Edit |
|---|---|
| Same code-review comment on three pull requests | CLAUDE.md or a rule |
| You hand-edit a skill's output the same way each run | Revise the skill |
| A hook blocks something you now want | Revise the hook |

The failure mode: **Chat-only correction.** You fix the same mistake in conversation every session and never write the correction down, so it recurs forever.

The fix: Convert every repeated correction into a file edit the same day.

Cross-references: memory files and rules are sub-topic 5.1.4 and Module 3.2.

**If you remember one thing:** a repeated correction belongs in a file.

## THE PROVE-IT SECTION

**Deliverable.** A friction log of one week with each entry mapped to a trigger row and a done/not-done mark.

**Close this topic. Build the artifact below from memory. Return to the text only after your first attempt is complete.**

| Step | Action | Output |
|---|---|---|
| 1 | Keep a friction log for one working week | `friction.md` |
| 2 | Map each entry to a trigger row | Mapping column |
| 3 | Count repeats per entry | Counts |
| 4 | Apply the feature for any entry at its threshold | Edits or new files |
| 5 | Re-run the same task once to see if friction dropped | Before/after note |
| 6 | List features you have with no trigger behind them | Candidate removals |

**A passing artifact looks like this:**

| Date | Friction | Count | Trigger row | Action |
|---|---|---|---|---|
| 24 Nov | Used npm not pnpm | 2 | Convention wrong twice | CLAUDE.md line added |
| 24 Nov | Release checklist pasted | 3 | Playbook third time | `/release` skill |

**A failing artifact (a realistic near-miss):**

| Element | What is wrong |
|---|---|
| Entries without counts | Cannot tell **Third-paste tolerance** from first occurrence |
| Actions are 'add MCP server' with no friction behind them | **Speculative setup** |

**The verdict.** The artifact passes only if each action is tied to a counted friction and at least one existing feature without a trigger is flagged.
