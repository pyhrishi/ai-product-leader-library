## 3.2.4.1 — WHAT BELONGS

**Framing.** The categories are commands Claude cannot guess, style rules that differ from defaults, test runners, repository etiquette, architectural decisions, environment quirks and non-obvious gotchas [Claude Code docs, Best practices; Memory, 2026]. Keep it to facts Claude should hold every session.

| Category | Example line |
|---|---|
| Commands | Typecheck with `npm run typecheck`, not `tsc` |
| Deviation | Use the error helpers in `src/lib/errors.ts`, never throw raw strings |
| Etiquette | Prefix commit subjects with the package name |
| Gotcha | Integration tests need `DATABASE_URL`, see `.env.example` |
| Architecture | API handlers live in `src/api/handlers/` |

The failure mode: **Obvious-line padding.** You include lines Claude would infer, such as 'use meaningful names', which cost context on every request and dilute the lines that matter.

The fix: Delete any line Claude could learn from the code or already does by default.

Cross-references: what to exclude is sub-topic 3.2.5 of Module 3.2.

**If you remember one thing:** include the unguessable.

## 3.2.4.2 — SPECIFICITY AND CHECKABILITY

**Framing.** The docs give three pairs: 'Use 2-space indentation' instead of 'Format code properly'; 'Run `npm test` before committing' instead of 'Test your changes'; 'API handlers live in `src/api/handlers/`' instead of 'Keep files organized' [Claude Code docs, Memory, 2026]. A command line lets Claude check its own work as it goes; enforcement of a passing typecheck is a job for a Stop hook, and 'Always typecheck before you finish' in the file works most of the time, not every time [Claude Code docs, Best practices, 2026].

```text
Vague:    Keep the code clean.
Checked:  Run `npm run lint` after edits; fix all errors before reporting done.

Vague:    Write good tests.
Checked:  New handlers need a test in src/__tests__/routes/ mirroring the file path.
```

The failure mode: **Vague-virtue.** You write aspirations such as 'follow best practices', which nothing can check and Claude cannot act on.

The fix: Rewrite each as a command, path or measurable condition, or delete it.

Cross-references: verification is Module 2.3.

**If you remember one thing:** if it cannot be checked, it is not a rule.

## 3.2.4.3 — CONSISTENCY AND OWNERSHIP

**Framing.** Contradictory rules may be resolved arbitrarily, so review files periodically [Claude Code docs, Memory, 2026]. Use markdown headers and bullets for structure. Anything multi-step or area-specific belongs in a skill or path-scoped rule rather than the always-loaded file.

| Smell | Fix |
|---|---|
| Two lines disagree | Keep one; delete the other at its source |
| Section about one directory | Move to nested CLAUDE.md or path-scoped rule |
| Ten-step procedure | Make it a skill |

The failure mode: **Contradiction-drift.** Rules from different authors and months disagree, and Claude resolves the clash arbitrarily.

The fix: Review the file at a set cadence and run the prompt audit to flag contradictions.

Cross-references: rule files are Module 3.3; the prompt audit is sub-topic 3.2.12 of Module 3.2.

**If you remember one thing:** one fact, one place.
