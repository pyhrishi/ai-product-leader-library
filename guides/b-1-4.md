# MODULE 1.4 — PLANS, LIMITS AND BILLING BASICS: THE COMPLETE CRAFT

---

## THE THESIS OF THIS MODULE

**Cost and limits in Claude Code are a function of tokens, and tokens are a function of context, so cost control is context control with a billing label on it.**

**Prove-it, in one sentence:** run the same small task two ways, measure the difference with `/usage` and `/context`, and explain it by naming the habit that caused it.

**The single most important discipline: measure before you optimise.** `/usage` and `/context` tell you what is being spent and why; guesses about cost are usually wrong in the direction of the thing you can see.

**The counterintuitive claim you will learn to defend:** the cheapest session is rarely the one on the cheapest model. A weak model that needs four correction rounds in a bloated context can cost more than a stronger model that finishes in one clean pass.

**THE TIME BUDGET.** Reading time: ~20 minutes. Prove-it time: ~2 hours. 2 hours is 120 minutes, six times the reading time.

| Depth | What you can do after this module |
|---|---|
| L3 | Read `/usage`, name what counts against limits, and apply five cost habits |
| L4 | Choose billing path and spend limits for a team and defend the choice |
| L5 | Forecast and govern organisation-wide Claude Code spend |

**Honesty note.** Plan prices, window lengths and per-token rates change often and vary by region and date. This guide gives the mechanism and the commands, and sends you to `claude.com/pricing` and the Claude Console for current figures rather than quoting prices that would go stale.

## 1.4.1 — SUBSCRIPTION USAGE

**Framing.** On a subscription, **Claude Code usage is included in the plan and limited by rolling windows**, not billed per token [Claude Code docs, Costs, 2026]. Two limit horizons appear in Anthropic's help material: a five-hour session limit and a weekly limit [Claude Help Center, 2026]. What matters operationally is what counts against them and how to see it.

| Item | Detail |
|---|---|
| Included | Claude Code on Pro and Max (and Team, Enterprise) plans |
| Limit horizons | A session window of about five hours, and a weekly limit [Claude Help Center, 2026; one third-party page also says limits reset every five hours] |
| Higher tiers | Max comes in 5x and 20x variants, offering more capacity than Pro [Claude Help Center, 2026] |
| Shared pool | Claude Code and the Claude apps draw on the same plan limits [Claude Help Center, 2026; confirm against your plan page] |
| Subagents | Subagent requests count toward the same limits as the main conversation [Claude Code docs, Subagents, 2026] |

**`/usage` is the instrument.** The Session block shows API token usage and is meant for API users. For Max and Pro subscribers the session cost figure is not relevant to billing; instead you see plan usage bars, activity stats and a **breakdown of what counts against your plan limits** [Claude Code docs, Costs, 2026]. For authoritative billing the docs point you to the Usage page in the Claude Console [Claude Code docs, Costs, 2026].

```text
/usage          # plan bars, activity, and the breakdown of what is counting
/context        # where this session's tokens are going right now
```

**What drives subscription consumption.** Anything that makes the model read or write more tokens: long sessions with big contexts, many parallel subagents, high effort, large file reads, and verbose tool output. The window you hit is a symptom; the context is the cause.

**When you hit the wall,** Anthropic's help material lists the options by plan: upgrade (Pro to Max 5x, Max 5x to Max 20x), enable usage credits to continue past the limit, switch to a Console account with API credits, or wait for the reset [Claude Help Center, 2026]. The Max plan's monthly API credits cannot be used in Claude Code or the Claude apps [Claude Help Center, 2026].

The failure mode: **Limit-surprise.** You start a large multi-agent task near the end of a window or late in the week, and the run stalls mid-way with half the work done.

The fix: check `/usage` before launching heavy work, split large tasks into resumable chunks with a checkpoint commit between them, and prefer starting big runs when a window has just reset.

The failure mode: **Blind-burn session.** A long-lived session accumulates context and background agents, every turn re-reads it, and the plan bar drains faster than the work justifies.

The fix: `/clear` between unrelated tasks, `/compact` with a focus before long new tasks, and read `/usage` once per hour of heavy work.

Cross-references: context and compaction are Modules 3.1 and 1.2; session management is Module 2.4.

**If you remember one thing:** `/usage` shows what counts, `/context` shows why, and long contexts are the usual reason.

## 1.4.2 — API AND PROVIDER BILLING

**Framing.** **Claude Code charges by API token consumption** when you are on API or provider billing; subscription plan pricing is separate and lives at `claude.com/pricing` [Claude Code docs, Costs, 2026]. Three billing structures exist and each has different guardrails.

| Path | You pay | Guardrails |
|---|---|---|
| Claude Console (API) | Per token | Workspaces with spend limits; cost and usage reports in the Console |
| Cloud provider (Bedrock, Google Cloud, Foundry, Claude Platform on AWS) | Per token on your cloud bill | Provider quotas, budgets and alerts |
| Subscription plus usage credits | Plan, then pay-as-you-go overflow | A monthly spend limit you set |

[Claude Code docs, Costs, 2026]

**Spend limits.** For API organisations, spend is managed through **workspaces**, where you can set workspace spend limits on total Claude Code spend; admins can view cost and usage reports in the Console [Claude Code docs, Costs, 2026]. On individual Pro and Max plans there is no organisation to manage, so you track your own usage-credit spend, including fast mode [Claude Code docs, Costs, 2026].

**Usage credits on a subscription.** Credits let you continue after plan limits by switching to pay-as-you-go [Claude Help Center, 2026]. You can set a monthly spend limit on them with `/usage-credits`; if you hit it while credits remain, Claude Code prompts you to raise or remove it so you can continue without leaving the CLI, and changing the limit requires billing access on the account [Claude Code docs, Costs, 2026]. The related dialogs require Claude Code v2.1.208 or later [Claude Code docs, Costs, 2026]. Credits already used are not refunded, except where local law requires it or in cases of fraud [Claude Help Center, 2026].

**Pitfall:** a third-party page lists `/extra-usage` and `/cost` as commands [shanraisshan mirror, 2026]. Command names change across versions; use `/help` in your own install and the Costs page to confirm what exists for you.

**How to estimate.** Cost per task is roughly (input tokens plus output tokens) times the model's per-token price, with context re-reads dominating long sessions. The docs advise estimating a team's spend by starting with a small pilot group and using the tracking tools to build a baseline before wider rollout [Claude Code docs, Costs, 2026].

The failure mode: **Uncapped key.** An API key with no workspace spend limit is used in a loop or a CI job, and the first signal is the invoice.

The fix: create a dedicated workspace per use case, set a spend limit before issuing the key, and alert on the Usage page.

The failure mode: **Credits-on-autopilot.** You enable usage credits to get past a limit and forget, so every later limit hit converts quietly to spend.

The fix: set a monthly credit limit with `/usage-credits` on the day you enable credits, and review month-to-date spend.

Cross-references: sign-in paths are Module 1.3; enterprise cost governance is in Part 11, starting at Module 11.1.

**If you remember one thing:** every billing path needs a ceiling set before the first run, not after the first surprise.

## 1.4.3 — FAST MODE AND EFFORT

**Framing.** Speed and depth are purchasable. **Effort level controls adaptive reasoning: higher effort means more thinking tokens and deeper reasoning; lower effort is faster and cheaper**, and it is supported on Fable models, Opus 4.6 and later, and Sonnet 4.6 and later [Claude Code docs, Glossary, 2026]. Extended thinking is the visible reasoning the model performs before responding, adjustable with effort, or capped with `MAX_THINKING_TOKENS` on models with a fixed thinking budget [Claude Code docs, Glossary, 2026].

| Lever | Effect on speed | Effect on cost | Use it for |
|---|---|---|---|
| Lower effort | Faster | Cheaper | Mechanical edits, renames, formatting |
| Default effort | Balanced | Balanced | Most feature work |
| Higher effort | Slower | More thinking tokens | Architecture, hard debugging, security review |
| Fast mode | Faster output | Billed through usage credits on individual plans [Claude Code docs, Costs, 2026] | Interactive sessions where latency hurts |
| Smaller model | Faster | Cheaper | Subagents doing search, simple transformations |

[Claude Code docs, Glossary and Costs, 2026; the exact pricing multiplier for fast mode is not reliably established here, treat as order-of-magnitude and check the Costs page]

```text
/model                          # switch model
claude --model <name>           # per-session model
# In a subagent file:  model: haiku   # cheap search worker
```

**Why this interacts with limits.** Thinking tokens count. A session left on maximum effort pays for deep reasoning on steps that did not need it, and on a subscription that spends your window.

The failure mode: **Effort-as-default.** You leave effort at maximum for everything because it feels safer, and the plan bar empties on routine edits.

The fix: set a moderate default, raise it deliberately for hard steps, and lower it for batch mechanical work.

The failure mode: **Fast-mode forgetting.** You turn on fast mode for an afternoon, never turn it off, and discover the extra spend in the usage-credit total.

The fix: treat fast mode as a per-task switch and check month-to-date credit spend weekly.

Cross-references: models, effort and speed in depth are Module 4.6; the model layer in the loop is Module 1.2.

**If you remember one thing:** effort and speed are meters you open on purpose, not settings you leave on.

## 1.4.4 — FEATURE AVAILABILITY BY PLAN AND PROVIDER

**Framing.** A feature in the docs is not necessarily a feature on your account. **Some features, for example auto mode, cloud sessions and Code Review, differ by plan or backend; the docs maintain a feature-availability page for this** [syllabus Module 1.4.4].

| Example | What the docs say | Implication |
|---|---|---|
| Auto mode | Built-in starting mode on Pro, Max and Team for interactive terminal and VS Code sessions; from v2.1.283 a built-in starting mode more broadly [Claude Code docs, 2026] | Your session may start in a different mode than a colleague's |
| Computer use, Dispatch | Desktop, on Pro and Max [Claude Code docs, 2026] | A Team member may not have it |
| Third-party providers | CLI and the IDE extensions support them; Bedrock or Foundry users use the CLI or an IDE extension [Claude Code docs, 2026] | Some surfaces are unavailable on that route |
| Artifacts sharing | Public link on Pro and Max; organisation sharing on Team and Enterprise, public links once an Owner enables them [Claude Code docs, Glossary, 2026] | Sharing policy differs by plan |
| Agent teams | Experimental, disabled by default [Claude Code docs, Glossary, 2026] | Opt in, do not assume |

The full availability table is not reproduced here because it changes release to release [feature-availability page not fetched this session; check it before standardising a workflow].

**A working method.** Before you write a team runbook, list the features it uses, then for each one check three things: plan, provider and version. Record the version with `claude --version`.

The failure mode: **Doc-as-entitlement.** You read a feature in the docs, build a workflow around it, and a teammate on a different plan or provider cannot run it.

The fix: check the feature-availability page against each plan, provider and version on the team, and put the check in the runbook.

Cross-references: surface and provider trade-offs are Module 7.1; enterprise provider setup is in Part 11.

**If you remember one thing:** a documented feature is not an entitled feature until you have checked plan, provider and version.

## 1.4.5 — COST CONTROL HABITS

**Framing.** The syllabus gives five habits; the mechanism behind all of them is the same: **fewer tokens carried per turn, and fewer turns wasted.**

| Habit | Why it works | Command or practice |
|---|---|---|
| Clear between tasks | Stops re-reading an irrelevant history on every turn | `/clear` |
| Scope searches | Limits what lands in context | "Search `src/payments/` for X", not "search the repo" |
| Subagents for exploration | Keeps large reads out of the main window | Delegate broad searches, accept the summary |
| Right model for the step | Avoids paying for depth on mechanical work | `/model`, subagent `model:` field |
| Watch `/context` | Makes bloat visible before it hurts | Check at task boundaries |

[syllabus Module 1.4.5; mechanisms from Claude Code docs, Best practices, Context window and Costs, 2026]

**Compaction is a cost lever too.** `/compact focus on the auth bug fix` produces a summary biased toward what you still need, instead of an automatic summary that guesses [Claude Code docs, Context window, 2026]. MCP servers add cost through tool definitions, but full schemas are deferred by tool search, so idle servers cost little [Claude Code docs, Glossary, 2026]. Preprocessing hooks can trim noisy tool output before it reaches the model, and the Costs page covers this pattern [Claude Code docs, Costs, 2026].

**The best-practices guidance on corrections** is also a cost rule: after more than two failed corrections on the same issue, `/clear` and rewrite the prompt with what you learned, because a context cluttered with failed attempts degrades results [Claude Code docs, Best practices, 2026].

A habit table, ranked by typical effect (judgement, not measured data; treat as order-of-magnitude intuition): clearing between unrelated tasks and scoping searches usually matter most; model choice matters most on subagent-heavy work; effort matters most on reasoning-heavy work.

The failure mode: **Kitchen-sink session.** One session carries a feature, a bug fix and a docs edit, so every turn re-reads all three.

The fix: one task per session, `/clear` or a new session between tasks, and `/compact` with a focus when a long task must continue.

The failure mode: **Unscoped exploration.** "Investigate why this is slow" with no boundary makes Claude read dozens of files and fill the window.

The fix: name the directory, the symptom and the stopping condition, or delegate the exploration to a subagent and keep the summary.

The failure mode: **Optimising blind.** You apply every tip without measuring, so you cannot say which one helped or whether any did.

The fix: read `/usage` and `/context` before and after one change at a time, and keep a two-line log of what moved.

Cross-references: the context window is Module 3.1; large codebases are Module 3.5; subagents are Module 5.3; prompting is Module 2.2.

**If you remember one thing:** one task per session, scoped searches, and a measurement before and after.

## THE PROVE-IT SECTION

**Deliverable.** A one-page cost experiment: the same task run twice, with measurements, and a conclusion that names the habit responsible for the difference.

**Close this module. Build the artifact below from memory. Return to the text only after your first attempt is complete.**

| Step | Action | Output |
|---|---|---|
| 1 | Pick a task you can repeat: "add input validation to function X and run its tests" | One-line task |
| 2 | Run A in a long, cluttered session (do not clear; include two unrelated tasks first); record `/context` and `/usage` before and after | Numbers A |
| 3 | Reset the repo to the same state | Clean tree |
| 4 | Run B in a fresh session with a scoped prompt that names the directory and the test command | Numbers B |
| 5 | Compare turns taken, tool calls, files read, context at the end, and plan usage change | A three-row table |
| 6 | Name the habit(s) responsible and the failure mode(s) that A exhibited | Two sentences |
| 7 | Write the runbook line you will adopt, and one billing guardrail you set (a spend limit, credit limit or plan-check habit) | Two lines |

**A passing artifact looks like this** (numbers illustrative; yours will differ):

| Metric | Run A (cluttered) | Run B (fresh, scoped) |
|---|---|---|
| Files read | 14 | 4 |
| Context at end (from `/context`) | high, near compaction | low |
| Correction rounds | 3 | 0 |
| Plan usage consumed | noticeably higher | lower |
| Failure modes shown | **Kitchen-sink session**, **Unscoped exploration** | None |

The conclusion states the habit ("scope the prompt; one task per session"), the measurement source (`/context`, `/usage`) and the guardrail ("monthly credit limit set to the figure I chose").

**A failing artifact (a realistic near-miss):**

| Element | What is wrong |
|---|---|
| "Run B felt faster" with no numbers | **Optimising blind** |
| The two runs used different tasks | The comparison proves nothing |
| No guardrail set | **Uncapped key** or **Credits-on-autopilot** remains possible |

**The verdict.** The artifact passes only if both runs address the same task from the same repo state, and every claim in the conclusion points to a number you read from `/usage` or `/context`.

## CLOSING REFRAME

This is the craft of plans, limits and billing: **cost is tokens, tokens are context, and every billing path needs a ceiling and a measurement.** The engineer who understands this does not ask "which model is cheapest?" — they ask "what is this session carrying, what ceiling have I set, and which number proves my change helped?"
