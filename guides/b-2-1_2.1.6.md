# MODULE 2.1.6 — THE SPEC INTERVIEW PATTERN: THE COMPLETE CRAFT

---

## THE THESIS OF THIS TOPIC

**When you do not yet know what you want, you can have Claude interview you with structured questions and write the answers into a spec file, which turns a vague idea into a definition of done that a fresh session can execute.**

**Prove-it, in one sentence:** run an interview for a real feature, get a SPEC.md, and show three decisions the interview forced that you had not made.

**The single most important discipline: let the interview end in a file, and read the file before you build from it.**

**The counterintuitive claim you will learn to defend:** the interview works because it asks you things the code cannot answer; a spec that only restates the code is a sign the interview asked the wrong questions [Claude Code docs, Best practices, 2026].

**THE TIME BUDGET.** Reading time: ~19 minutes. Prove-it time: ~2.5 hours (150 minutes, 7.9 times the reading time).

| L3 | Run the interview prompt and produce a spec file |

## 2.1.6.1 — THE PROMPT AND WHAT COMES BACK

**Framing.** Best practices gives the pattern verbatim: ask Claude to interview you until it could write the spec and write it to a file. Claude responds with multiple-choice questions on the parts you have not pinned down, such as per-user versus per-key limits, behaviour over the limit and what is out of scope, and keeps asking until the answers add up to a spec [Claude Code docs, Best practices, 2026].

```text
I want to add rate limiting to the public API but haven't thought it through yet. Interview me until you could write the spec, then write it to SPEC.md.
```
The prompt library has a variant naming the coverage areas: implementation, UX, edge cases and tradeoffs [Claude Code docs, Prompt library, 2026].

| Component | Detail |
|---|---|
| Question format | Multiple choice, per the docs |
| Stop condition | Claude could write the spec |
| Output | A file such as `SPEC.md` |

The failure mode: **Interview-to-nowhere.** The interview ends with answers in chat and no file, so the decisions vanish at the next compaction or session.

The fix: State the output file in the prompt and confirm it exists before you close the session.

Cross-references: context survival is Module 3.1; spec-driven development is Module 9.1.

**If you remember one thing:** the interview must end in a file.

## 2.1.6.2 — WHY THE QUESTION TOOL MAKES IT BETTER

**Framing.** The pattern relies on Claude's question tool, which presents choices rather than open prose. The interactive-mode page notes that when you type your own answer in the `Other` row of such a question, pressing `Esc` twice cancels it [Claude Code docs, Interactive mode, 2026]. The tools reference documents its behaviour under an AskUserQuestion entry that I linked to but did not read [Claude Code docs, Best practices, 2026; page not fetched].

| Question style | Strength | Weakness |
|---|---|---|
| Multiple choice | Fast, forces a decision | Options may omit your case; use `Other` |
| Open prose | Captures nuance | Easy to leave tradeoffs unstated |

Answer the tradeoff questions slowly. The cheapest place to change your mind is the interview.

The failure mode: **Option-capture.** You pick from the offered options even when none fits, and the spec encodes a compromise nobody wanted.

The fix: Use the `Other` row and write your own answer whenever the options miss the case.

Cross-references: prompting is Module 2.2; the tool name list is Module 1.2.

**If you remember one thing:** answer in your own words when the options are wrong.

## 2.1.6.3 — WHAT A GOOD SPEC CONTAINS

**Framing.** Best practices says the written spec is also the file you point the reviewer at later, and shows a review prompt that checks every requirement is implemented and the listed edge cases have tests, reporting correctness gaps only [Claude Code docs, Best practices, 2026]. A spec that cannot be checked that way is too vague.

| Section | Test of quality |
|---|---|
| Behaviour | A reviewer could write a test from each line |
| Edge cases | Each has an expected result |
| Out of scope | Names at least two tempting extras |
| Check command | The exact command that proves done |
| Open questions | Marked, not hidden |

The failure mode: **Untestable-spec.** The spec says things like handle errors gracefully, so neither the build nor the review has anything concrete to check.

The fix: Rewrite each line so a test or a command could fail it.

Cross-references: review against a spec is guide 2.3.6; specification craft is Module 9.1.

**If you remember one thing:** a spec line you cannot test is a wish.

## 2.1.6.4 — INTERVIEW VERSUS PLAN MODE

**Framing.** Plan mode proposes an implementation of a decided task; the interview decides the task. The prompt library separates them: `plan how to refactor ... don't edit anything yet` is planning, while the interview prompt writes SPEC.md [Claude Code docs, Prompt library, 2026].

| Question you cannot answer | Tool |
|---|---|
| What should it do? | Interview |
| How should it be built? | Plan mode |
| Did we build it? | Review against the spec |

The failure mode: **Phase-swap.** You use plan mode to decide product behaviour, and the plan quietly invents requirements that you then approve as implementation detail.

The fix: Decide behaviour in the interview and let the plan only decide the build.

Cross-references: planning is guide 2.1.2; product framing for non-engineers is Module 13.3.

**If you remember one thing:** interview decides what; plan decides how.

## THE PROVE-IT SECTION

**Deliverable.** A SPEC.md from a real interview, annotated with the three decisions the interview forced.

**Close this topic. Build the artifact below from memory. Return to the text only after your first attempt is complete.**

| Step | Action | Output |
|---|---|---|
| 1 | Pick a feature you have not thought through | One-line feature |
| 2 | Run the interview prompt naming the output file | Transcript |
| 3 | Answer using `Other` at least once | Marked answers |
| 4 | Read the SPEC.md and rewrite two untestable lines | Edits |
| 5 | List three decisions the interview forced | Three lines |
| 6 | Write the review prompt that uses the spec | Prompt text |

**A passing artifact looks like this:**

| Spec element | Present |
|---|---|
| 429 response with Retry-After header | Yes, testable |
| Out of scope: per-endpoint tiers, admin override | Yes |
| Check: `pnpm vitest run rate-limit` | Yes |
| Open question: shared limits across keys | Marked |

**A failing artifact (a realistic near-miss):**

| Element | What is wrong |
|---|---|
| Spec says handle limits gracefully | **Untestable-spec** |
| No file on disk | **Interview-to-nowhere** |

**The verdict.** The artifact passes only if SPEC.md exists, every behaviour line could fail a test, and three interview-forced decisions are named.

## CLOSING REFRAME

This is the craft of the interview: **questions only you can answer, ending in a file a reviewer can test against.** The engineer who understands this does not ask "how do I describe the feature?" — they ask "what has Claude not yet made me decide?"
