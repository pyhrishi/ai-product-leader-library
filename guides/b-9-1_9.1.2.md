# MODULE 9.1.2 — WHAT MAKES A SPEC EXECUTABLE: THE COMPLETE CRAFT

---

## THE THESIS OF THIS TOPIC

**A spec is executable when Claude can build from it and a reviewer can check the diff against it, which needs files and interfaces named, exclusions stated, edge cases listed and an end-to-end verification step at the end.**

**Prove-it, in one sentence:** take a vague one-paragraph spec and rewrite it so each of the four properties is present and checkable.

**The single most important discipline: every spec ends with a command or action whose output proves the feature works.**

**The counterintuitive claim you will learn to defend:** an out-of-scope list is a requirement: it is the only part of the spec that stops silent scope creep.

**THE TIME BUDGET.** Reading time: ~18 minutes. Prove-it time: ~2 hours (120 minutes, 6.7 times the reading time).

## 9.1.2.1 — THE FOUR PROPERTIES

**Framing.** The docs' own spec example asks Claude to capture what is out of scope and the edge cases, and the review prompt checks that every requirement is implemented and the listed edge cases have tests [Claude Code docs, Best practices, 2026]. Together with the docs' advice to name files and give a pass-or-fail check, those give four properties.

| Property | What to write | Check that it is present |
|---|---|---|
| Names files and interfaces | `src/api/limiter.ts`, `check(key): Result` | A grep for each path succeeds |
| States out of scope | "No per-tenant limits; no UI" | Section titled Out of scope exists |
| Lists edge cases | "Bucket resets at window edge; clock skew" | Each case has a numbered line |
| Ends with verification | "Run `pnpm test limiter` and a curl loop; expect 429 on the 101st request" | A runnable command with expected output |

The failure mode: **Unfalsifiable requirement.** A line such as 'should be fast and robust' cannot be checked, so the reviewer cannot report it as a gap.

The fix: Rewrite it as a measurable statement with a command that shows the result.

Cross-references: interview prompts are Module 9.1.3; verification is Module 9.2.

**If you remember one thing:** each property is a thing a reviewer can point at.

## 9.1.2.2 — A SKELETON YOU CAN REUSE

**Framing.** The skeleton below is this guide's own template, not an official format. It puts the checkable parts where a reviewer prompt can reference them by number.

```markdown
# SPEC: rate limiting for the public API
## Goal
One paragraph, user-visible behaviour.
## Files and interfaces
1. src/api/limiter.ts exports check(key): {allowed, retryAfterMs}
2. src/api/middleware.ts calls check before handlers
## Out of scope
- UI, per-tenant plans
## Edge cases
E1 Burst at window boundary  E2 Missing API key  E3 Clock skew
## Verification
V1 pnpm vitest run src/api/limiter.test.ts
V2 curl loop: request 101 returns 429 with Retry-After
```

The failure mode: **Numberless spec.** Requirements are prose with no ids, so the review cannot say which one is missing.

The fix: Number files, edge cases and verification steps so the review prompt can cite them.

Cross-references: plan files are Module 9.1.4; reviewers are Module 9.1.5.

**If you remember one thing:** numbers make gaps reportable.

## 9.1.2.3 — END-TO-END VERIFICATION AS THE LAST SECTION

**Framing.** The docs advise giving Claude something that comes back pass or fail, and asking for evidence: the command it ran and its output, or a screenshot [Claude Code docs, Best practices, 2026].

| Verification type | Example line in the spec |
|---|---|
| Test file | `pnpm vitest run path/to/file.test.ts` passes |
| Build exit code | `pnpm tsc --noEmit` exits 0 |
| Script against fixture | `diff out.json fixtures/expected.json` is empty |
| Running app | `/verify` run shows the feature working (Module 9.2.5) |

The failure mode: **Mocked finish line.** The verification step runs only unit tests with mocks, so the spec passes while the real flow is broken.

The fix: Add at least one step that drives the real entry point and records its output.

Cross-references: running the real app is Module 9.2.5.

**If you remember one thing:** the last line of a spec is the proof.

## THE PROVE-IT SECTION

**Deliverable.** A rewritten spec with all four properties plus a one-line check per property.

**Close this topic. Build the artifact below from memory. Return to the text only after your first attempt is complete.**

| Step | Action | Output |
|---|---|---|
| 1 | Take a vague paragraph spec | Original |
| 2 | Name files and interfaces | Section 1 |
| 3 | Add out-of-scope | Section 2 |
| 4 | Add 3 numbered edge cases | Section 3 |
| 5 | Add two verification commands with expected output | Section 4 |
| 6 | Run a reviewer prompt that cites ids | Gap list with ids |

**A passing artifact looks like this:**

| Property | Evidence |
|---|---|
| Files | 2 paths, both exist |
| Out of scope | 2 bullets |
| Edge cases | E1 to E3 |
| Verification | V1 command and expected output |

**A failing artifact (a realistic near-miss):**

| Element | What is wrong |
|---|---|
| "Handle errors well" | **Unfalsifiable requirement** |
| Only unit tests with mocks | **Mocked finish line** |

**The verdict.** The artifact passes only if a stranger could run V1 and V2 unaided and a reviewer prompt can name a missing item by id.

## CLOSING REFRAME

This is the craft of the executable spec: **named things, stated limits, numbered cases, and a proof step.** The engineer who understands this does not ask "is the spec long enough?" — they ask "could a reviewer fail this build against it?"
