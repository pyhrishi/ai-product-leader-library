## THE THESIS OF THIS TOPIC

**Claude Code has five ways to work on several tasks at once, and they differ in who coordinates, where the work runs and whether workers can talk, so the choice is a decision about coordination and not about speed.**

**Prove-it, in one sentence:** given six task descriptions, assign each to one of the five approaches or a supporting tool and defend the choice in one sentence using the docs' three questions.

**The single most important discipline: ask who coordinates, whether workers must talk, and whether they touch the same files, before you name a tool.**

**The counterintuitive claim you will learn to defend:** worktrees, cross-session messaging and /batch are not ways to run agents; they support the five approaches, and treating them as peers is how people pick the wrong one [Claude Code docs, Run agents in parallel, 2026].

## 6.1.1.1 — THE FIVE APPROACHES

**Framing.** The docs list five ways to work on several tasks at once: subagents, agent view, agent teams, dynamic workflows and projects. They differ in how involved you stay and in whether the work runs on your machine or in the cloud [Claude Code docs, Run agents in parallel, 2026].

| Approach | What it gives you | Status noted in the docs |
|---|---|---|
| Subagents | Delegated workers inside one session, own context, return a summary | Stable |
| Agent view (`claude agents`) | One screen to dispatch and monitor background sessions | Research preview |
| Agent teams | Coordinated sessions with a shared task list and a lead | Experimental, disabled by default |
| Dynamic workflows | A script that runs many subagents and cross-checks results | Described as available on all paid plans |
| Projects | One conversation where Claude starts parallel cloud sessions called threads | Public beta on Pro and Max |

Status is quoted from the comparison page and the workflows page; re-check it, because three of the five carry preview or experimental labels [Claude Code docs, Run agents in parallel, 2026; Claude Code docs, Dynamic workflows, 2026].

The failure mode: **Five-equals illusion.** You treat the five approaches as interchangeable speed-ups and pick the one you read about last, so a task that needed a shared task list runs as isolated subagents, or a one-line side question gets a whole session.

The fix: Pick by coordination first: write who coordinates, whether workers talk and whether files overlap, then read the table row that matches.

Cross-references: the module overview is Module 6.1; subagents are Module 5.3.

**If you remember one thing:** five approaches, five different answers to who holds the plan.

## 6.1.1.2 — THE THREE SUPPORTING TOOLS

**Framing.** Three more tools support parallel work without being a way to run agents: worktrees, cross-session messaging and `/batch`. Worktrees give each session a separate git checkout, messaging lets sessions pass findings, and `/batch` is a skill that splits one change into 5 to 30 worktree-isolated subagents [Claude Code docs, Run agents in parallel, 2026].

| Tool | What it does | What it is not |
|---|---|---|
| Worktrees | Separate git checkout per session | Not a way to start agents |
| Cross-session messaging | Claude lists and messages your other sessions | Not shared state or shared history |
| /batch | 5 to 30 worktree-isolated subagents for one large change | Not a separate coordination style; a packaged use of subagents and worktrees |

The docs add three look-alikes that solve a different problem: a background bash command (one shell command, no agent), a forked subagent (inherits your full conversation; start with `/subtask`) and a routine (a scheduled cloud session, not parallel on your machine) [Claude Code docs, Run agents in parallel, 2026].

The failure mode: **Tool-as-agent confusion.** You search for the worktree option in agent view or expect `/batch` to be a sixth coordination style, then wait for coordination that is not there.

The fix: Remember that worktrees isolate files, messaging passes notes and `/batch` is a packaged fan-out; none of them decides what runs next.

Cross-references: worktrees are Module 6.2; messaging is Module 6.6; /batch is Module 6.5.

**If you remember one thing:** supporting tools change safety and communication, not who coordinates.

## 6.1.1.3 — THE THREE QUESTIONS

**Framing.** The docs reduce the choice to three questions: who coordinates the work, do the workers need to talk to each other, and do the tasks touch the same files [Claude Code docs, Run agents in parallel, 2026].

| Question | If the answer is | Reach for |
|---|---|---|
| Who coordinates? | Claude, inside one conversation | Subagents |
|  | You hand off and check back | Agent view |
|  | Claude plans, assigns and supervises | Agent teams |
|  | A script holds the plan | Dynamic workflows |
| Must workers talk? | Between sessions you run | Cross-session messaging |
|  | Teammates in a team | Direct messages, plus a shared task list if they have the Task tools |
| Same files? | Sessions or subagents | A worktree each |
|  | Agent teams | No worktree isolation; partition files so each teammate owns different ones |

The failure mode: **Shared-file collision.** You run two agent-team teammates on the same module because the lead split the work by topic, and their edits overwrite each other.

The fix: Partition by file ownership before spawning, or move the work to sessions that each have a worktree.

Cross-references: agent teams are Module 6.4; the coordination spectrum is sub-topic 6.1.2.

**If you remember one thing:** ask the three questions in order and the tool usually names itself.

## 6.1.1.4 — WHERE TO CHECK ON RUNNING WORK

**Framing.** Each approach has its own place to look. For background sessions it is `claude agents`; for subagents in the current session it is the @-mention typeahead; for anything running in the background of this session it is `/tasks`; for dynamic workflows it is `/workflows` [Claude Code docs, Run agents in parallel, 2026].

```text
claude agents     # agent view: every background session, its state, who needs you
/tasks            # background work in this session, incl. finished subagents
/workflows        # running and completed workflow runs, phase, agents finished
```

The docs warn that `/agents` is separate from `claude agents`: the slash command points to subagent file locations, the shell command opens agent view [Claude Code docs, Run agents in parallel, 2026].

The failure mode: **Wrong-dashboard check.** You type `/agents` expecting the agent view screen and conclude background sessions are not running.

The fix: Use `claude agents` from the shell for sessions and `/tasks` inside a session for its own background work.

Cross-references: agent view is Module 6.3; workflow runs are Module 6.5.

**If you remember one thing:** know which command shows which kind of work before you launch it.
