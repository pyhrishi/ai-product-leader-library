# MODULE 9.2.3 — TEST QUALITY: THE COMPLETE CRAFT

## THE THESIS OF THIS TOPIC

**A test suite is only as good as its ability to fail when the code is wrong, so avoid over-mocking, test behaviour not structure, cover the edge cases you listed, and prove the tests fail when you break the code.**

**Prove-it, in one sentence:** break the code on purpose in three ways and show the suite catches each.

**The single most important discipline: no test is trusted until it has failed against a deliberately broken implementation.**

**The counterintuitive claim you will learn to defend:** a high pass rate says nothing about test quality; only failures on broken code do (general practice, not from the Claude Code docs).

## 9.2.3.1 — BEHAVIOUR OVER MOCKS

**Framing.** The docs advise being specific about what behaviour you want to verify when asking for tests; Claude examines existing test files to match style, frameworks and assertion patterns [Claude Code docs, Common workflows, 2026]. Over-mocking is a general-practice hazard: a test that mocks the unit under test asserts the mock.

| Smell | What it tests | Better |
|---|---|---|
| Mock returns the expected value | The mock | Real collaborator or a fake with logic |
| Asserts call counts only | Wiring | Assert outputs and effects |
| Snapshot of everything | Today's output | Targeted assertions |
| Tests private helpers | Structure | Test through the public interface |

The failure mode: **Mock-the-subject.** The test replaces the code under test or its decisive collaborator with a mock, so it passes whatever the code does.

The fix: Allow mocks only at process boundaries (network, clock), and require one real-path assertion per test.

Cross-references: integration tests are Module 9.2.4.

**If you remember one thing:** assert behaviour a user would notice.

## 9.2.3.2 — COVER THE LISTED EDGE CASES

**Framing.** The docs' review prompt checks that listed edge cases have tests [Claude Code docs, Best practices, 2026]. So map each edge-case id in the spec to at least one test name.

| Edge id | Test name |
|---|---|
| E1 window boundary | `allows_request_after_window_resets` |
| E2 missing key | `rejects_missing_key_with_401` |
| E3 clock skew | `tolerates_5s_skew` (the 5 s is an example value) |

Ask Claude to identify edge cases you missed: error conditions, boundary values and unexpected inputs [Claude Code docs, Common workflows, 2026].

The failure mode: **Orphan edge case.** A spec edge case has no test, so a regression passes unnoticed.

The fix: Keep a table of edge ids to test names and have the spec review fail on any empty cell.

Cross-references: spec edge cases are Module 9.1.2.

**If you remember one thing:** every listed case has a named test.

## 9.2.3.3 — MUTATION BY HAND: DO TESTS FAIL WHEN CODE BREAKS?

**Framing.** Break the implementation deliberately and confirm the suite goes red. Automated mutation tools exist but this guide did not verify any specific tool, so use manual breaks.

| Break | Expected |
|---|---|
| Flip a comparison (`>` to `>=`) | At least one boundary test fails |
| Return a constant | Behaviour tests fail |
| Delete a branch | Its edge test fails |
| Skip the call to a dependency | An integration test fails |

```text
Introduce each of these four bugs one at a time on a scratch branch, run the suite after
each, and report which tests failed. Revert after each.
```

The failure mode: **Green-on-broken.** The suite stays green after you break the code, and nobody notices because it was never tried.

The fix: Run the four breaks above on a scratch branch and fix every uncaught one before merging.

Cross-references: adversarial review in fresh context is Module 9.13.3.

**If you remember one thing:** tests earn trust by failing.
