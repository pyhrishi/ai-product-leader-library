## 10.1.3.1 — WHAT A CHAMPION DOES

**Framing.** The module brief describes a champion kit as a playbook for engineers who advocate internally. I could not retrieve a page of that name in the Claude Code docs index, so the kit contents below are what the docs support rather than a retrieved template. The docs recommend investing in documentation so Claude Code understands your codebase, deploying CLAUDE.md at organisation level and repository level, and having one central team configure MCP servers and check a `.mcp.json` into the codebase [Claude Code docs, Enterprise deployment overview, 2026].

| Responsibility | Docs-supported artefact |
|---|---|
| Keep repo context current | Repository `CLAUDE.md` |
| Share integrations | Checked-in `.mcp.json` |
| Show safe first tasks | Codebase Q&A, small bug fixes, plan first |
| Give a one-click install | An internal install path |

The failure mode: **Advocate without artefacts.** Champions give talks but leave no checked-in configuration, so each team rediscovers the same prompts.

The fix: Make every champion output a committed file, not a slide.

Cross-references: configuration scope is Module 3.2; managed policy is Module 10.4.

**If you remember one thing:** a champion's output is a committed file.

## 10.1.3.2 — SELECTING AND FUNDING CHAMPIONS

**Framing.** The docs say a one-click install path is key to growing adoption in a custom environment [Claude Code docs, Enterprise deployment overview, 2026]. [Practitioner heuristic: pick one champion per team, give a named weekly time budget, and rotate yearly.]

```text
Champion charter
Role:        one per team, volunteer + manager-approved
Time:        2 h/week protected (example; set your own)
Outputs:     repo CLAUDE.md, .mcp.json, 1 demo per month
Escalation:  admin channel for policy questions
```

The failure mode: **Unfunded champion.** Champions are named but given no time, so the role decays within a month.

The fix: Write the hours into the charter and have the manager sign it.

Cross-references: metrics for champions are Module 10.8.

**If you remember one thing:** name the hours or the role is decoration.

## 10.1.3.3 — THE CHAMPION KIT CONTENTS

**Framing.** The module brief lists a playbook; the closest retrievable guidance is the docs' own onboarding resources: the Quickstart, Common workflows, and the Anthropic Academy courses Claude 101 and Claude Code in Action [Claude Code docs, Set up Claude Code for your organization, 2026]. [Whether a separate champion kit exists is not verified here.]

| Kit item | Source |
|---|---|
| First-session walkthrough | Quickstart |
| Everyday patterns | Common workflows |
| Self-paced courses | Claude 101; Claude Code in Action |
| Login fixes | `/logout` then `/login`; `claude update` |

The failure mode: **Kit drift.** Each champion writes their own kit, so teams get contradictory advice on permissions and models.

The fix: Keep one canonical kit in a repository and have champions fork only the team-specific page.

Cross-references: training formats are Module 10.1.5 topic.

**If you remember one thing:** one kit, many champions.

## 10.1.3.4 — MEASURING CHAMPIONS

**Framing.** The analytics leaderboard shows the top 10 users by contribution volume, and the docs suggest using it to find people with high adoption who can share techniques and help onboard others [Claude Code docs, Track team usage with analytics, 2026]. Treat it as a way to find champions, not to rank people.

| Signal | Where | Caveat |
|---|---|---|
| Top contributors | Analytics leaderboard (top 10) | Volume, not quality |
| Team adoption | Adoption chart | Team-level only |

The failure mode: **Leaderboard worship.** You pick champions by raw contribution volume and publish the ranking, which rewards volume over teaching.

The fix: Use the leaderboard to find candidates, then choose by teaching ability.

Cross-references: pitfalls with vanity metrics are Module 10.8.

**If you remember one thing:** find champions with data, choose them with judgement.
