## THE THESIS OF THIS TOPIC

**/doctor with the prompt-audit option audits your instruction files for outdated, broken and contradictory lines, and its findings are proposals for you to judge.**

**Prove-it, in one sentence:** run the audit on a real instruction set and adjudicate every finding as accept, reject or defer.

**The single most important discipline: an audit proposes; you decide, and you retest after accepting.**

**The counterintuitive claim you will learn to defend:** the audit flags instructions written for older models, so a rule that once worked may now be the overhead [Claude Code docs, Best practices, 2026].

**THE TIME BUDGET.** Reading time: ~12 minutes. Prove-it time: ~1 hours (60 minutes, 5.0 times the reading time).

## 3.2.12.1 — WHAT THE AUDIT DOES

**Framing.** `/doctor prompt-audit` flags instructions that were written for older models, point at files that no longer exist, or contradict each other; plain `/doctor` suggests cuts for anything Claude can already work out from the code, and the How Claude Code works page describes `/doctor` as a setup checkup that diagnoses installation and configuration issues and can fix them [Claude Code docs, Best practices; How Claude Code works, 2026]. The Memory page links an 'audit your instruction files' section; its content was not retrieved here.

| Finding type | Typical action |
|---|---|
| Written for older models | Test removal; likely delete |
| Points at a missing file | Fix path or delete |
| Contradicts another line | Keep one, delete the other |
| Derivable from code (plain /doctor) | Cut |

The failure mode: **Auto-accept.** You accept every finding without review and delete a gotcha that looked derivable but was not.

The fix: Judge each finding against a real task before accepting.

Cross-references: pruning is sub-topic 3.2.6 of Module 3.2.

**If you remember one thing:** proposals need a judge.

---

## 3.2.12.2 — ADJUDICATING FINDINGS

**Framing.** Treat the audit as a reviewer: for each finding choose accept, reject or defer, give a reason, and test the accepted ones by watching whether behaviour shifts [Claude Code docs, Memory, 2026].

| Finding | Decision | Reason | Retest |
|---|---|---|---|
| Old-model workaround | Accept | Newer model no longer needs it | Task A same |
| Missing path | Accept | File moved | n/a |
| Contradiction | Accept | Keep newer | Task B same |
| 'Derivable' gotcha | Reject | Not in code | n/a |

The failure mode: **Unlogged-decision.** You accept and reject findings without recording why, so the next audit re-litigates them.

The fix: Log each decision and reason in the pull request.

Cross-references: review loop is sub-topic 3.2.9 of Module 3.2.

**If you remember one thing:** log the reason.

---

## 3.2.12.3 — CADENCE AND LIMITS

**Framing.** Run the audit after major model releases and before sharing a file with a team, in line with the guidance to revisit instructions after major releases [Claude Code docs, Large codebases, 2026]. The audit cannot judge whether a rule is right for your project, only whether it looks outdated, broken or conflicting.

| Trigger | Run |
|---|---|
| New major model | Audit |
| Before onboarding a team | Audit |
| After large merges moving files | Audit for missing paths |

The failure mode: **Audit-as-proof.** You treat a clean audit as proof the file is good, though it checks only staleness and conflicts.

The fix: Pair the audit with a behaviour test on real tasks.

Cross-references: evals are Module 10.1.

**If you remember one thing:** clean means not obviously broken.

## THE PROVE-IT SECTION

**Deliverable.** A findings log with a decision and rationale for each, plus a post-change behaviour check.

**Close this topic. Build the artifact below from memory. Return to the text only after your first attempt is complete.**

| Step | Action | Output |
|---|---|---|
| 1 | Run `/doctor prompt-audit` | Raw findings |
| 2 | Adjudicate each finding | Decision table |
| 3 | Apply the accepted ones | Diff |
| 4 | Retest two tasks | Results |
| 5 | Record the reasons | Log |
| 6 | Schedule the next audit | Date |

**A passing artifact looks like this:**

| Finding | Decision | Reason |
|---|---|---|
| Old workaround | Accept | Test shows no change |
| Gotcha flagged derivable | Reject | Not derivable |

**A failing artifact (a realistic near-miss):**

| Element | What is wrong |
|---|---|
| Audit output pasted with no decisions | **Auto-accept** risk |
| No retest | Changes unproven |

**The verdict.** The artifact passes only if every finding has a decision and a reason and accepted changes were retested.
