# MODULE 1.1.5 — DELEGATE, DO NOT DICTATE: THE COMPLETE CRAFT

## THE THESIS OF THIS TOPIC

**You get the best result by stating the outcome, the constraints and the check, and letting Claude choose the steps. Dictating the steps caps the result at the quality of your plan.**

**Prove-it, in one sentence:** rewrite three step-by-step prompts as outcome, constraint and check prompts, and run one of each to compare the results.

**The single most important discipline: every prompt carries an outcome, the constraints that matter, and a check Claude can run.**

**The counterintuitive claim you will learn to defend:** more detail is not always better. Specificity belongs in the outcome and the check; spelling out the steps removes exactly the adaptation that makes an agent worth using [Claude Code docs, How Claude Code works, 2026].

## 1.1.5.1 — WHAT DELEGATING LOOKS LIKE

**Framing.** The docs recommend treating Claude Code like a capable colleague: give context and direction, then trust it to work out the details. Their example states the symptom and the location (checkout fails for users with expired cards, the code is in `src/payments/`) and asks Claude to investigate and fix it, without naming files or commands [Claude Code docs, How Claude Code works, 2026].

```text
# DICTATED (caps the result at your plan)
Open src/payments/charge.ts, find validateCard, add a check on the expiry month,
then open the test file and add a test for expired cards...

# DELEGATED (outcome + constraint + check)
Checkout fails for users with expired cards. Relevant code is in src/payments/.
Write a failing test that reproduces it, fix it, and run the payments tests.
Do not add dependencies.
```

| Part | What it carries | If missing |
|---|---|---|
| Outcome | What "done" means | Claude optimises for something else |
| Location | Where to look | Exploration spreads across the repo |
| Constraint | What not to do | Surprises in the diff |
| Check | How Claude knows it worked | It stops when the work looks done |

The failure mode: **Dictating the steps.** You write the exact edits you want, Claude follows them literally, and the result is only as good as your plan, which was the thing you wanted to delegate.

The fix: State the outcome, the location and the constraints, add a check, and let Claude choose the route.

Cross-references: prompting craft is Module 2.2; the explore, plan, implement, commit loop is Module 2.1.

**If you remember one thing:** the prompt is an outcome, a boundary and a check, not a recipe.

## 1.1.5.2 — SPECIFIC WHERE IT COUNTS

**Framing.** Delegation is not vagueness. The best-practices guidance asks for specificity in the places that matter: scope the task, point to sources, reference existing patterns, describe the symptom and what fixed looks like [Claude Code docs, Best practices, 2026].

| Vague | Specific, still delegating |
|---|---|
| "Fix the login bug" | "Users report login fails after session timeout. Look at `src/auth/`, especially token refresh. Write a failing test, then fix it." |
| "Add tests for foo.py" | "Write tests for foo.py covering the edge case where the user is logged out. Avoid mocks." |
| "Add a calendar widget" | "Look at how existing widgets are implemented on the home page, follow that pattern, and add a calendar widget without new libraries." |

[Prompt shapes follow the Best practices page's specificity table; the wording here is paraphrased.]

The failure mode: **Delegating without a check.** You say 'fix the login bug' with no failing test, no command and no definition of fixed, and Claude stops when the work merely looks done.

The fix: Attach a check Claude can run, such as a reproduction test, a build exit code or a screenshot comparison.

Cross-references: verification is Module 2.3; sessions are Module 2.4.

**If you remember one thing:** be specific about outcome and check, silent about steps.

## 1.1.5.3 — WHEN TO BE DIRECTIVE: PLAN FIRST

**Framing.** Delegation has a limit. When the approach is uncertain, the change spans several files or you do not know the code, ask Claude to plan before editing. The docs' rule of thumb: if you could describe the diff in one sentence, skip the plan [Claude Code docs, Best practices, 2026].

```
 Could you describe the diff in one sentence?
 ├─ yes ──► delegate directly (outcome + check)
 └─ no  ──► Explore (read-only) ► Plan (review it) ► Implement ► Commit
```

Plan mode is a permission mode where Claude researches and proposes changes without editing your source files; enter with `/plan` or `Shift+Tab` [Claude Code docs, Glossary, 2026]. For tasks too large to describe in a sentence, an interview prompt that asks Claude to question you and write a spec first is the docs' suggested route [Claude Code docs, Best practices, 2026].

The failure mode: **Plan-skipping.** You delegate a multi-file change with an unclear approach directly, and the diff touches the wrong abstraction.

The fix: Use plan mode first for multi-file or unfamiliar work, review the plan, then switch to implementation.

Cross-references: plan mode is Module 4.3; the explore, plan, implement loop is Module 2.1.

**If you remember one thing:** a one-sentence diff is delegated; anything bigger is planned first.

## 1.1.5.4 — REVIEWING DELEGATED WORK

**Framing.** Delegation moves your effort from typing to reviewing. A delegated task is not finished when Claude says so; it is finished when you have read evidence.

| Review step | What you read |
|---|---|
| The check | The test or build output in the transcript |
| The diff | `git diff` for scope, unrelated edits and removed code |
| The constraint | Whether any forbidden dependency or pattern appears |
| The summary | Whether Claude's description matches the diff |

If more than two corrections on the same issue fail, the docs advise `/clear` and a rewritten prompt that includes what you learned, because the context is cluttered with failed attempts [Claude Code docs, Best practices, 2026].

The failure mode: **Summary-trust.** You accept Claude's description of what it did without opening the diff or the test output.

The fix: Read the diff and the check output before accepting, and ask for the command and its result if either is missing.

Cross-references: checkpoints and undo are Module 2.5; code review workflows are Module 2.6.

**If you remember one thing:** review evidence, not the summary.

| Metric | Dictated | Delegated |
|---|---|---|
| Diff correct | Yes, but missed a related call site | Yes, found the related call site |
| Tool calls | 9 | 14 |
| Check passed | Only the one you named | Full suite |

Numbers are illustrative; the template contains outcome, location, constraint and check fields.

**A failing artifact (a realistic near-miss):**

| Element | What is wrong |
|---|---|
| Delegated prompt has no check line | **Delegating without a check** |
| The 'delegated' prompt lists file paths and line edits | **Dictating the steps** in disguise |
| No comparison, only 'felt better' | Nothing demonstrated |

**The verdict.** The artifact passes only if both runs started from the same state, each delegated prompt contains all four parts, and the comparison cites diffs and test output.

## CLOSING REFRAME

This is the craft of delegation: **an outcome, a boundary and a check, with the route left to the agent.** The engineer who understands this does not ask "what exact steps should I tell it?" — they ask "what does done look like, what must not change, and how will Claude prove it?"
