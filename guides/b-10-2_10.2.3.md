## THE THESIS OF THIS TOPIC

**The Bedrock and Vertex wizards configure one developer's user settings; fleets need the manual route, and Foundry has no wizard at all.**

**Prove-it, in one sentence:** run a wizard on a test account, find what it wrote, and translate that block into a managed-settings fragment.

**The single most important discipline: treat wizard output as a template for fleet configuration, never as the fleet configuration.**

## 10.2.3.1 — WHAT THE WIZARDS ARE

**Framing.** Run `claude`, choose 3rd-party platform at the login prompt, then Amazon Bedrock or Google Vertex AI (the label the prompt still uses for Agent Platform). If already signed in, `/setup-bedrock` opens the Bedrock wizard and `/setup-vertex` the Vertex one; until `CLAUDE_CODE_USE_BEDROCK=1` is set, Claude Code hides `/setup-bedrock` from the command menu, so type it in full [Claude Code docs, Claude Code on Amazon Bedrock, 2026] [Claude Code docs, Claude Code on Google Cloud's Agent Platform, 2026].

| Wizard | Opens via | Chooses |
|---|---|---|
| Bedrock | `/setup-bedrock` or login prompt | AWS profile, Bedrock API key, access key, or environment credentials; region; model pins |
| Vertex | `/setup-vertex` or login prompt | ADC from gcloud, service account key, or environment; project; region; model pins |
| Foundry | none | Environment variables only |

The failure mode: **Hidden command panic.** You search the command menu for `/setup-bedrock`, do not see it, and conclude the version is too old.

The fix: Type the command in full; it appears in the menu only once the switch variable is set.

Cross-references: the provider routes are Module 10.2.2.

**If you remember one thing:** the command exists even when the menu hides it.

## 10.2.3.2 — WHAT THE WIZARD WRITES

**Framing.** The wizard saves its result to the `env` block of your user settings file, so you do not export variables yourself. It writes `~/.claude/settings.json`, or `$CLAUDE_CONFIG_DIR/settings.json` when `CLAUDE_CONFIG_DIR` is set; re-run it any time to change credentials, region or pins [Claude Code docs, Claude Code on Amazon Bedrock, 2026].

```json
// ~/.claude/settings.json (wizard output shape)
{
  "env": {
    "CLAUDE_CODE_USE_BEDROCK": "1",
    "AWS_REGION": "us-east-1",
    "ANTHROPIC_DEFAULT_SONNET_MODEL": "us.anthropic.claude-sonnet-4-6"
  }
}
```

The failure mode: **Wizard-as-policy.** You tell developers to run the wizard and consider the fleet configured, but each can change it and drift appears within weeks.

The fix: Copy the produced `env` keys into managed settings and treat the wizard as a bootstrap.

Cross-references: managed delivery is Module 10.4.

**If you remember one thing:** wizards configure; managed settings enforce.

## 10.2.3.3 — VERIFICATION INSIDE THE WIZARD

**Framing.** For Bedrock, the wizard verifies which Claude models your account can invoke and lets you pin them, and applies a 60 second limit to each AWS call it makes while verifying credentials; a check that exceeds it fails with a `Timed out after 60s waiting for AWS` message [Claude Code docs, Claude Code on Amazon Bedrock, 2026]. Behind a TLS-inspecting proxy whose root certificate is only in the OS store, versions before v2.1.261 could show models as `unreachable` while inference worked.

| Symptom | Likely cause | Fix |
|---|---|---|
| Models show `unreachable` | Old version behind TLS-inspecting proxy | Update to v2.1.261 or later |
| `Timed out after 60s waiting for AWS` | Credential helper stalled | Fix chain or raise `CLAUDE_CODE_AWS_CHAIN_RESOLVE_TIMEOUT_MS` |

The failure mode: **Unreachable-model misread.** The wizard marks models unreachable and you conclude the account lacks access, when only the certificate trust was wrong.

The fix: Check the version and the CA configuration before requesting access.

Cross-references: network and certificates are Module 10.5.

**If you remember one thing:** read the wizard's failure as a network symptom first.

## 10.2.3.4 — FROM WIZARD TO FLEET

**Framing.** For CI or a scripted rollout the Bedrock and Vertex pages give a manual setup; the docs say to pin model versions before rolling out to a team [Claude Code docs, Claude Code on Amazon Bedrock, 2026]. [Practitioner approach: run the wizard on one machine, diff `settings.json`, and promote the keys to your managed source.]

| Step | Output |
|---|---|
| Run wizard on a test machine | `env` block |
| Remove personal keys (profiles, secrets) | Clean block |
| Promote to managed settings | Fleet fragment |
| Verify with `/status` | Evidence |

The failure mode: **Personal values promoted.** You copy a personal AWS profile name or token into the fleet fragment.

The fix: Strip user-specific values and keep only provider, region and model pins.

Cross-references: managed settings are Module 10.4.

**If you remember one thing:** promote the shape, not the secrets.

| Key | Kept | Reason |
|---|---|---|
| CLAUDE_CODE_USE_BEDROCK | Yes | Provider |
| AWS_PROFILE | No | Personal |

| Element | What is wrong |
|---|---|
| Fragment includes AWS_PROFILE=alice | **Personal values promoted** |
| No managed delivery | Wizard-as-policy |

**The verdict.** The artifact passes only if the fleet fragment contains no personal values and a clean user's `/status` shows the provider.
