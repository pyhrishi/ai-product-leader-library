# MODULE 9.3.1 — REPRODUCE FIRST: THE COMPLETE CRAFT

---

## THE THESIS OF THIS TOPIC

**A bug fix without a failing reproduction is a guess; a failing test or script before any fix gives Claude a pass-or-fail check and gives you proof the fix addressed the reported problem.**

**Prove-it, in one sentence:** turn a bug report into a failing test or script, show it fails, then show the fix turns it green.

**The single most important discipline: no fix is attempted until the reproduction fails on demand.**

**The counterintuitive claim you will learn to defend:** the reproduction is worth more than the fix, because it keeps protecting you after the incident ends.

## 9.3.1.1 — FROM REPORT TO REPRODUCTION

**Framing.** The docs' contrast is between 'fix the login bug' and a prompt that names the symptom, the code location and asks Claude to write a failing test that reproduces it, then fix it [Claude Code docs, Best practices, 2026]. Tell Claude the command to reproduce and whether the error is intermittent or consistent [Claude Code docs, Common workflows, 2026].

| Report element | Becomes |
|---|---|
| "Login fails after the session times out" | Test name: `refreshes_token_after_session_timeout` |
| Where | `src/auth/` token refresh |
| Frequency | Consistent or intermittent (say which) |
| Done | The test passes and the neighbouring suite stays green |

```text
users report login fails after the session times out. look at token refresh in src/auth/,
write a failing test that reproduces it, then fix it
```

The failure mode: **Fix-first guess.** Claude edits code from the description alone, the symptom changes and nobody knows whether the cause was found.

The fix: Require a failing reproduction and its output before the first edit.

Cross-references: prompting craft is Module 2.2; TDD is Module 9.2.1.

**If you remember one thing:** red before any green.

## 9.3.1.2 — WHEN A TEST IS THE WRONG REPRODUCTION

**Framing.** Some bugs need a script, a curl sequence or a data fixture rather than a unit test. The reproduction is whatever returns pass or fail reliably; the docs list scripts that diff output against a fixture as valid checks [Claude Code docs, Best practices, 2026].

| Bug type | Reproduction form |
|---|---|
| Logic error | Unit test |
| Wrong HTTP result | curl script with expected status |
| Data-dependent | Fixture file plus test |
| UI | Screenshot compared with expected |
| Intermittent | Loop script with failure count |

The failure mode: **Unreproducible fix.** You cannot reproduce, so Claude 'fixes' a plausible cause and the report stays open.

The fix: Mark the bug as not reproduced, gather more evidence (Module 9.3.2) and add logging instead of changing logic.

Cross-references: evidence is Module 9.3.2.

**If you remember one thing:** no reproduction, no fix claim.

---

## 9.3.1.3 — KEEP THE REPRODUCTION

**Framing.** After the fix, the test stays in the suite as a regression guard. The docs advise asking for evidence of the passing check [Claude Code docs, Best practices, 2026].

| After the fix | Do |
|---|---|
| Test name | Describes the behaviour, not the ticket number alone |
| Commit | Test and fix together, message cites the report |
| Evidence | Failing output before, passing output after |

The failure mode: **Throwaway reproduction.** The scratch script is deleted after the fix and the bug returns in a month.

The fix: Convert it into a permanent test before closing the ticket.

Cross-references: root cause is Module 9.3.5.

**If you remember one thing:** a reproduction becomes a regression test.

## CLOSING REFRAME

This is the craft of reproduction: **make it fail on demand, then fix, then keep the test.** The engineer who understands this does not ask "what is the fix?" — they ask "what proves the bug exists, and will prove it is gone?"
