# MODULE 2.1.4 — COMMIT: MESSAGES, PULL REQUESTS AND THE GH CLI: THE COMPLETE CRAFT

## THE THESIS OF THIS TOPIC

**Committing is the point where a session becomes team history, so the discipline is a reviewed diff, a message that explains why, and a pull request linked back to the session that produced it.**

**Prove-it, in one sentence:** produce a commit and a pull request from a session, then find the session again from the PR number.

**The single most important discipline: read the diff before asking for the commit, and read the PR text before submitting.**

**The counterintuitive claim you will learn to defend:** a commit message written by Claude describes the diff it saw, not your intent, so intent is the part you must supply [Claude Code docs, Common workflows, 2026].

**THE TIME BUDGET.** Reading time: ~19 minutes. Prove-it time: ~2 hours (120 minutes, 6.3 times the reading time).

## 2.1.4.1 — ASKING FOR THE COMMIT

**Framing.** The prompt library includes `commit these changes with a message that summarizes what I did` and `review my uncommitted changes and flag anything that looks risky before I commit` [Claude Code docs, Prompt library, 2026]. The second prompt is the one that matters first: review precedes commit.

| Step | Prompt or command |
|---|---|
| Inspect | `/diff` (Module 2.6 covers review in depth) |
| Risk pass | `review my uncommitted changes and flag anything that looks risky before I commit` |
| Commit | `commit these changes with a message that summarizes what I did` |
| Conflicts | `resolve the merge conflicts in this branch and explain what you kept from each side` |

All four prompts are from the prompt library [Claude Code docs, Prompt library, 2026].

The failure mode: **Commit-blind.** You ask for the commit without reading the diff, and a stray debug edit or a touched generated file lands in history.

The fix: Run the risk-pass prompt and read `/diff` first, then commit.

Cross-references: review tools are guide 2.6.8; keeping to scope is Module 2.2.

**If you remember one thing:** review before you commit, not after.

## 2.1.4.2 — PULL REQUESTS WITH GH

**Framing.** You can create a pull request by asking directly (`create a pr for my changes`) or by stepping through summarize, create, then enhance the description; the docs advise reviewing the generated PR and asking Claude to highlight risks [Claude Code docs, Common workflows, 2026]. For CLIs it has not seen, Claude can read `--help`, and with `gh` installed and signed in it opens PRs and reads review comments without explanation [Claude Code docs, Best practices, 2026].

```text
summarize the changes I've made to the authentication module
create a pr
enhance the PR description with more context about the security improvements
```
| Tool | Role |
|---|---|
| `gh` | GitHub PRs and review comments |
| `glab` | GitLab merge requests |
| MCP server | Systems without a CLI (Module 5.5) |

The failure mode: **Summary-as-intent.** The PR description restates the diff and omits why the change exists, so reviewers re-derive the reason and the linked issue never gets closed.

The fix: Add the motivation, linked issue and risks yourself before submitting, and ask Claude to tighten rather than invent them.

Cross-references: PR workflows are guide 2.6.5; MCP is Module 5.5.

**If you remember one thing:** you supply the why; Claude supplies the what.

## 2.1.4.3 — LINKING A SESSION TO ITS PR

**Framing.** Claude Code links the session to the PR when Claude creates it with `gh pr create` or `glab mr create`, and when Claude works on an existing PR. Find it later with `claude --from-pr 1234`, which opens the picker filtered to that PR, or paste the PR URL into the `/resume` picker search [Claude Code docs, Common workflows, 2026; Manage sessions, 2026].

| Need | Command |
|---|---|
| Sessions for PR 1234 | `claude --from-pr 1234` |
| Search by URL | Paste the PR URL in the `/resume` picker |
| Most recent session here | `claude --continue` |

A session resumed through the picker keeps its transcript, so a reviewer comment a week later can be answered with the original reasoning [Claude Code docs, Manage sessions, 2026].

The failure mode: **Orphan-session.** You open a PR from a manual `git push` and web form, so the session is not linked and the reasoning behind the change is hard to recover.

The fix: Let Claude create the PR with `gh pr create`, or name the session after the branch so `/resume <name>` finds it.

Cross-references: naming sessions is guide 2.4.2; resume is guide 2.4.1.

**If you remember one thing:** create the PR from the session so the link exists.

## 2.1.4.4 — KEEPING THE SAFETY RAILS ON

**Framing.** Pushes are an irreversible-by-others action, so keep ask rules and branch protection in place. Best practices lists `Bash(git push *)` as an ask rule in its example and says a person approves the merge in unattended runs [Claude Code docs, Best practices, 2026].

```json
{ "permissions": { "ask": ["Bash(git push *)"] } }
```
| Control | Layer |
|---|---|
| `ask` on `git push` | Harness, deterministic |
| Branch protection | The host, outside Claude |
| Reviewer approval | A person |

Auto mode blocks force pushes over other people's work by default, but deny rules and hooks apply before the classifier [Claude Code docs, Best practices, 2026].

The failure mode: **Push-without-pause.** A broad allow rule lets Claude push to the shared branch without a prompt, and an unreviewed commit reaches teammates.

The fix: Keep `git push` on an ask rule and protect the default branch on the host.

Cross-references: permissions are Module 4.2; safe autonomy is Module 11.7.

**If you remember one thing:** the merge approval stays with a person.

## THE PROVE-IT SECTION

**Deliverable.** One commit, one PR and a transcript showing `claude --from-pr` finding the session.

**Close this topic. Build the artifact below from memory. Return to the text only after your first attempt is complete.**

| Step | Action | Output |
|---|---|---|
| 1 | Finish a small change and read `/diff` | Diff notes |
| 2 | Run the risk-pass prompt | Findings list |
| 3 | Commit with the library prompt; edit the message to add the why | Commit text |
| 4 | Create the PR from the session; add motivation and linked issue | PR text |
| 5 | Exit and run `claude --from-pr <n>` | Resume log |
| 6 | Show your push rule and branch protection | Config snippet |

**A passing artifact looks like this:**

| Item | Evidence |
|---|---|
| Risk pass run | 1 stray log line removed |
| Commit message | States the why and issue number |
| PR linked | `claude --from-pr 87` lists the session |
| Push rule | `ask` on `git push *` |

**A failing artifact (a realistic near-miss):**

| Element | What is wrong |
|---|---|
| PR created from web form | **Orphan-session** |
| Description equals commit list | **Summary-as-intent** |

**The verdict.** The artifact passes only if `claude --from-pr` returns the session and the PR text contains a reason you wrote.

## CLOSING REFRAME

This is the craft of committing: **a read diff, a why you wrote, and a PR the session is linked to.** The engineer who understands this does not ask "can Claude push this?" — they ask "did I read it, and can I find the session when a reviewer asks?"
