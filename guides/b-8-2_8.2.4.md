## 8.2.4.1 — WHAT EACH SOURCE LOADS

**Framing.** Omitting settingSources is equivalent to ['user', 'project', 'local'], and query() then reads the same filesystem settings as the CLI. Passing [] disables user, project and local settings. cwd determines where project inputs are found [Agent SDK docs, Use Claude Code features in the SDK, 2026].

| Source | Loads | Location |
|---|---|---|
| project | settings.json and hooks; CLAUDE.md and rules; skills, commands, subagents | <cwd>/.claude/ for settings and hooks; cwd and every parent for CLAUDE.md and rules; cwd and parents up to repo root for skills, commands, agents |
| user | user settings.json, CLAUDE.md, rules, skills, commands, subagents | ~/.claude/ |
| local | CLAUDE.local.md, .claude/settings.local.json | <cwd>/.claude/; CLAUDE.local.md in cwd and parents |

[Agent SDK docs, Use Claude Code features in the SDK, 2026]. Project settings.json loads from <cwd>/.claude/ with no parent fallback. Child-directory CLAUDE.md files load on demand.

The failure mode: **Wrong-cwd silence.** The agent runs from a different directory than the repo root and silently loads none of your project settings or hooks.

The fix: Set cwd explicitly and verify the init message lists the skills and hooks you expect.

Cross-references: skills are Module 8.2.5; the CLI's equivalent is Module 1.2.

**If you remember one thing:** the sources are a union; cwd picks the project.

## 8.2.4.2 — WHAT SETTINGSOURCES DOES NOT CONTROL

**Framing.** Five inputs are read regardless of settingSources: managed policy settings, the global ~/.claude.json, auto memory at ~/.claude/projects/<project>/memory/, claude.ai MCP connectors (when authenticated with claude.ai login), and sandbox credentials deny and mask entries [Agent SDK docs, Use Claude Code features in the SDK, 2026].

| Input | How to disable |
|---|---|
| Managed policy settings | Remove the managed file/plist/registry policy; server-managed settings are controlled by an org Owner |
| ~/.claude.json | Relocate with CLAUDE_CONFIG_DIR in env |
| Auto memory | `autoMemoryEnabled: false` or CLAUDE_CODE_DISABLE_AUTO_MEMORY=1 |
| claude.ai connectors | strictMcpConfig: true, disableClaudeAiConnectors: true, or ENABLE_CLAUDEAI_MCP_SERVERS=false; mcpServers: {} does not suppress them |
| sandbox credentials entries | Remove from ~/.claude/settings.json |

[Agent SDK docs, Use Claude Code features in the SDK, 2026]. The docs' multi-tenant recipe: each tenant in its own filesystem, settingSources [] and CLAUDE_CODE_DISABLE_AUTO_MEMORY=1 in env.

The failure mode: **Empty-list isolation.** You pass settingSources: [] and believe the agent is isolated, but it still loads auto memory from the host and any claude.ai connectors.

The fix: Also disable auto memory, set strictMcpConfig, and give each tenant a separate filesystem.

Cross-references: multi-tenant isolation is Module 8.7.3; secure deployment is Module 8.7.4.

**If you remember one thing:** empty settingSources narrows loading; it does not isolate.

## 8.2.4.3 — PROJECT INSTRUCTIONS: LEVELS AND CONFLICTS

**Framing.** CLAUDE.md levels are additive: project, project rules, parent directories, local and user. There is no hard precedence rule, so conflicting instructions are resolved by how Claude interprets them; the docs advise non-conflicting rules or explicit precedence [Agent SDK docs, Use Claude Code features in the SDK, 2026].

| Level | Location | Loaded when |
|---|---|---|
| Project | <cwd>/CLAUDE.md or .claude/CLAUDE.md | project source |
| Project rules | .claude/rules/*.md in cwd and parents | project source |
| Parent dirs | CLAUDE.md above cwd | project source, at start |
| Child dirs | CLAUDE.md in subdirectories | project source, on demand |
| Local | CLAUDE.local.md | local source |
| User | ~/.claude/CLAUDE.md and rules | user source |

[Agent SDK docs, Use Claude Code features in the SDK, 2026]. State precedence in the specific file, for example 'These project instructions override any conflicting user-level defaults'.

The failure mode: **Layered contradiction.** A user-level CLAUDE.md says one thing and the project file says another, and the agent obeys a different one on different runs.

The fix: Remove the conflict or state precedence explicitly in the more specific file.

Cross-references: memory in Claude Code is Module 1.2; compaction and CLAUDE.md are in Module 8.2.1.

**If you remember one thing:** levels add up; they do not override.

## 8.2.4.4 — HOOKS AND CHOOSING THE RIGHT FEATURE

**Framing.** Two hook types run side by side: filesystem hooks in settings.json (command, http, mcp_tool, prompt, agent), and programmatic callbacks passed to query(). Both fire inside subagents; callback input carries agent_id and agent_type [Agent SDK docs, Use Claude Code features in the SDK, 2026].

| Goal | Use | SDK surface |
|---|---|---|
| Conventions the agent always follows | CLAUDE.md | settingSources project |
| Reference material loaded when relevant | Skills | settingSources + skills |
| Isolated subtask in a fresh context | Subagents | agents + allowedTools Agent |
| Deterministic logic on tool calls | Hooks | hooks callbacks or settings.json |
| Structured access to an external service | MCP | mcpServers |

[Agent SDK docs, Use Claude Code features in the SDK, 2026]. For PreToolUse, return {} for no decision; to block, return hookSpecificOutput with permissionDecision 'deny' and a reason that is sent to Claude. Python supports fewer hook events than TypeScript. Agent teams are a CLI feature not configured through SDK options [same page].

The failure mode: **Hook-for-everything.** You encode a convention as a hook that blocks and retries when a line in CLAUDE.md would have done.

The fix: Use CLAUDE.md for guidance and hooks for rules that must be enforced deterministically.

Cross-references: hooks as callbacks are Module 8.6.2; subagents are Module 8.3.5; MCP is Module 8.3.3.

**If you remember one thing:** guidance goes in files, enforcement goes in hooks.
