# MODULE 5.2.4 — WRITING A GOOD DESCRIPTION: THE COMPLETE CRAFT

---

## THE THESIS OF THIS TOPIC

**The description is the trigger: Claude sees only that text until the skill loads, so vague or overlapping descriptions cause missed or wrong loads.**

**Prove-it, in one sentence:** write a description, measure its hit rate on should-trigger and should-not-trigger prompts, and improve it.

**The single most important discipline: start the description with the key use case and phrase it as 'use when'.**

**The counterintuitive claim you will learn to defend:** a long, thorough description can be worse than a short one: the combined description and when_to_use is truncated at 1,536 characters, and with many skills descriptions are dropped to fit the listing budget [Claude Code docs, Skills, 2026].

**THE TIME BUDGET.** Reading time: ~20 minutes. Prove-it time: ~2.5 hours (150 minutes, 7.5 times the reading time).

## 5.2.4.1 — WHAT CLAUDE SEES

**Framing.** Claude only sees the description until the skill loads, so it decides on that text. The listing always includes every skill name, but with many skills Claude Code drops some descriptions to fit a budget that scales at 1% of the model's context window, dropping the least-invoked first [Claude Code docs, Skills, 2026].

| Limit | Value |
|---|---|
| Combined `description` + `when_to_use` per entry | 1,536 characters |
| Listing budget | 1% of the model's context window (`skillListingBudgetFraction`) |
| Per-entry cap setting | `skillListingMaxDescChars` |
| Fallback if description omitted | First non-empty line of the body |

[Claude Code docs, Skills, 2026]

The failure mode: **Buried key use case.** The trigger phrase sits at the end of a 1,400-character description, and after truncation or budget trimming the use case Claude needed is gone.

The fix: Put the key use case first and keep the combined text short.

Cross-references: context cost is sub-topic 5.1.8.

**If you remember one thing:** the description is all Claude has when deciding.

## 5.2.4.2 — SHAPE OF A GOOD DESCRIPTION

**Framing.** The docs' guidance: put the key use case first, include trigger phrases and example requests (in `description` or `when_to_use`), and use the 'when' form; the example reads 'Use when the user asks what changed, wants a commit message, or asks to review their diff' [Claude Code docs, Skills, 2026].

| Weak | Better |
|---|---|
| "Helps with git" | "Summarizes uncommitted changes and flags anything risky. Use when the user asks what changed, wants a commit message, or asks to review their diff." |
| "Database stuff" | "Query patterns and schema notes for the orders database. Use when writing or debugging SQL against orders." |

The failure mode: **Overlap collision.** Two skills both say 'use for code review', and Claude loads the wrong one or neither.

The fix: Give each a distinct trigger and say what it is not for.

Cross-references: invocation by name is sub-topic 5.2.6.

**If you remember one thing:** distinct triggers beat broad coverage.

---

## 5.2.4.3 — TESTING TRIGGERS

**Framing.** Troubleshooting steps: check the description includes keywords users would naturally say, verify the skill appears when you ask what skills are available, rephrase the request to match, and invoke directly with `/skill-name` [Claude Code docs, Skills, 2026]. For plugin skills, an eval with a `tool_used: Skill` grader run with `claude plugin eval` can measure trigger rate; the skill-creator also tunes descriptions with should-trigger and should-not-trigger prompts [Claude Code docs, Skills, 2026].

```text
should trigger:     "what did I change?"   "write a commit message"   "review my diff"
should NOT trigger: "explain git rebase"   "what is a diff in math"
hit rate = triggered-as-expected / total
```

The failure mode: **One-prompt testing.** You test with the one phrase you wrote the skill for and conclude it triggers, then it misses real users' phrasing.

The fix: Test at least five should-trigger and five should-not-trigger prompts.

Cross-references: plugin evals are sub-topic 5.6.7.

**If you remember one thing:** measure the hit rate, not a single success.

## THE PROVE-IT SECTION

**Deliverable.** Three before/after descriptions with a 10-prompt trigger test and hit rates.

**Close this topic. Build the artifact below from memory. Return to the text only after your first attempt is complete.**

| Step | Action | Output |
|---|---|---|
| 1 | Pick one skill with poor triggering | Skill name |
| 2 | Write 5 should-trigger and 5 should-not prompts | Prompt set |
| 3 | Run each and record loads | Baseline hit rate |
| 4 | Rewrite: key use case first, 'use when' form | New description |
| 5 | Rerun the set | New hit rate |
| 6 | Check for overlap with other skills | Overlap note |

**A passing artifact looks like this:**

| Version | Should-trigger hits | Should-not hits |
|---|---|---|
| Before | 2/5 | 1/5 false |
| After | 5/5 | 0/5 false |

**A failing artifact (a realistic near-miss):**

| Element | What is wrong |
|---|---|
| Only should-trigger prompts | False positives unmeasured |
| Description over 1,536 characters | Will be cut |

**The verdict.** The artifact passes only if both prompt sets were run before and after the rewrite.
