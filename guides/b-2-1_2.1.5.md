# MODULE 2.1.5 — WHEN TO SKIP PLANNING: THE COMPLETE CRAFT

---

## THE THESIS OF THIS TOPIC

**Planning is a tool with a cost, and the decision to skip it should come from how well you can specify the change and how cheaply you can undo it, not from habit in either direction.**

**Prove-it, in one sentence:** classify ten changes as plan or skip with a stated reason each, then run two of them the opposite way and compare cost.

**The single most important discipline: decide plan or skip from specifiability and reversibility, and write the reason down.**

**The counterintuitive claim you will learn to defend:** the current Best practices page says your first plain prompt in a fresh session already does the right thing in most cases, so heavy ceremony is the exception, not the default [Claude Code docs, Best practices, 2026].

**THE TIME BUDGET.** Reading time: ~17 minutes. Prove-it time: ~2 hours (120 minutes, 7.1 times the reading time).

## 2.1.5.1 — THE ONE-SENTENCE RULE AND WHAT THE DOCS SAY

**Framing.** This module's item says that if you can describe the diff in one sentence you should ask for it directly. I did not find that sentence on the current Best practices page; what the page says is that in most cases the first plain prompt in a fresh session already does the right thing without setup [Claude Code docs, Best practices, 2026]. Treat the one-sentence test as a useful heuristic, not a quotation.

| Source | Claim | Status |
|---|---|---|
| Best practices | First plain prompt usually right | Verified on the page |
| Common workflows | Plan mode is for changes you want to review before they touch disk | Verified [Claude Code docs, Common workflows, 2026] |
| One-sentence diff test | Skip planning if you can state the diff in a sentence | Heuristic from this module, not found verbatim |

The failure mode: **Source-laundering.** You cite the one-sentence rule to a team as an official instruction, and the docs do not say it, so the rule loses credibility the first time someone checks.

The fix: Label it a heuristic and cite the verified statements instead.

Cross-references: the extra-careful sourcing habit is Module 16.1.

**If you remember one thing:** label heuristics as heuristics.

## 2.1.5.2 — SPECIFIABILITY AND REVERSIBILITY

**Framing.** Common workflows describes plan mode as the choice for changes you want to review before they touch disk [Claude Code docs, Common workflows, 2026]. Two questions decide it: can you state what done looks like, and can you undo the change cheaply? Checkpoints make undoing cheap for file edits, though not for shell side effects [Claude Code docs, Checkpointing, 2026].

| Specifiable | Reversible | Decision |
|---|---|---|
| Yes | Yes | Skip planning; ask directly |
| Yes | No (migration, deploy config) | Plan, approve manually |
| No | Yes | Explore, then interview (guide 2.1.6) |
| No | No | Explore, interview, plan, stage |

The failure mode: **Reversibility-assumption.** You skip planning because edits are undoable, but the change runs a shell command or migration that rewind does not restore.

The fix: Treat any change with shell side effects as not reversible and plan it.

Cross-references: limits of rewind are guide 2.5.3; git as the net is guide 2.5.5.

**If you remember one thing:** undo covers file edits, not side effects.

## 2.1.5.3 — PLAN FATIGUE AND THE COST OF CEREMONY

**Framing.** Every plan round costs tokens and your attention. The docs warn about over-correction in a different place, `What you can stop doing`, which lists advice that current models made unnecessary, such as telling Claude to keep going or to be thorough [Claude Code docs, Best practices, 2026]. Apply the same scepticism to rituals you add.

| Ritual | Keep if |
|---|---|
| Plan every change | Never as a blanket rule |
| Interview before every feature | The feature has unstated tradeoffs |
| Fresh session per task | Context is unrelated (guide 2.1.7) |
| A `/goal` for every small fix | The end state is verifiable and long-running |

The failure mode: **Ritual-planning.** You plan every change, including typo fixes, because planning feels safe, and the loop slows without catching more mistakes.

The fix: Reserve plans for uncertain or multi-file or irreversible changes and measure whether plans caught anything.

Cross-references: goals are Module 6.7; session hygiene is Module 2.4.

**If you remember one thing:** ceremony should earn its place.

## 2.1.5.4 — SKIPPING SAFELY: THE MINIMUM VIABLE DIRECT PROMPT

**Framing.** Skipping the plan does not mean skipping the check. A direct prompt should still name the file, the symptom or behaviour, and what done looks like; that is the table Best practices gives for specific prompts [Claude Code docs, Best practices, 2026].

```text
users report login fails after the session times out. look at token refresh in src/auth/, write a failing test that reproduces it, then fix it
```
That example, from the docs, names the symptom, the location and a check in one sentence [Claude Code docs, Best practices, 2026].

The failure mode: **Direct-and-blind.** You skip planning and the prompt too, so Claude spends turns rediscovering which file you meant and may edit the wrong one.

The fix: Even a direct prompt names the file or directory and the check.

Cross-references: prompt detail is Module 2.2; verification is Module 2.3.

**If you remember one thing:** skip the plan, never the check.
