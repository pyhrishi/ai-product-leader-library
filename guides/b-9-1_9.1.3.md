## 9.1.3.1 — THE PROMPT SHAPE

**Framing.** The docs' interview prompt is short: describe the goal, say you have not thought it through, and ask for questions until Claude could write the spec to a named file. Claude replies with multiple-choice questions [Claude Code docs, Best practices, 2026]. The tool behind this is `AskUserQuestion`, which asks multiple-choice questions to gather requirements or clarify ambiguity and does not prompt for permission [Claude Code docs, Tools reference, 2026].

```text
Interview me about this feature using the AskUserQuestion tool. Cover implementation,
UI and UX, edge cases, concerns and trade-offs. Skip questions whose answer is obvious
from the repo. Keep going until you could write SPEC.md, then write it.
```

| Area | Example question Claude might ask |
|---|---|
| Implementation | Per-user or per-key counters? |
| UI and UX | What does a blocked user see? |
| Edge cases | What happens at the window boundary? |
| Concerns | Does a shared cache add a failure point? |
| Trade-offs | Accuracy versus cost of the counter |

The failure mode: **Obvious-question flood.** Claude asks which test framework you use, which the repo already shows, and you answer ten trivial questions before the real ones.

The fix: Add 'skip questions whose answer is obvious from the repo' and name the areas you do care about.

Cross-references: the tool list is Module 1.2; plan-mode alternative is Module 2.1.

**If you remember one thing:** ask for the unknowns, not for the knowns.

## 9.1.3.2 — CONTROLLING DEPTH AND EXIT

**Framing.** An interview needs an exit condition or it keeps asking. 'Until you could write the spec' is that condition in the docs' example [Claude Code docs, Best practices, 2026]. Questions stay open until you answer them by default [Claude Code docs, Tools reference, 2026].

| Control | Prompt wording |
|---|---|
| Exit | "...until you could write the spec" |
| Output | "...then write it to SPEC.md" |
| Breadth | "cover implementation, UI and UX, edge cases, concerns, trade-offs" |
| Pace | "ask three questions at a time" (this guide's suggestion, not a docs setting) |
| Veto | "if I answer 'your call', choose and note it as an assumption" |

The failure mode: **Endless interview.** No exit condition is given and Claude keeps asking, so the session ends with no file.

The fix: State the output file and the 'until you could write it' condition in the first prompt.

Cross-references: spec skeleton is Module 9.1.2.

**If you remember one thing:** name the file the interview must produce.

## 9.1.3.3 — ASSUMPTION LOGGING

**Framing.** 'Your call' answers hide decisions. Having Claude record them as numbered assumptions in the spec makes them reviewable in step three of the workflow (Module 9.1.1).

| Answer you give | Claude should write |
|---|---|
| A choice | Decision D3: per-key limits |
| "Your call" | Assumption A2: sliding window chosen; revisit if cost matters |
| "Not sure" | Open question Q1 with an owner |

The failure mode: **Silent decision.** You answer 'your call' and the choice never appears in the spec, so nobody reviews it.

The fix: Require an Assumptions section with numbered entries for every delegated answer.

Cross-references: keeping specs alive is Module 9.1.6.

**If you remember one thing:** delegated decisions still get written down.
