## 3.2.2.1 — THE FOUR LOCATIONS

**Framing.** Listed in load order, broadest to most specific [Claude Code docs, Memory, 2026].

| Scope | Location | Shared with |
|---|---|---|
| Managed policy | macOS `/Library/Application Support/ClaudeCode/CLAUDE.md`; Linux/WSL `/etc/claude-code/CLAUDE.md`; Windows `C:\Program Files\ClaudeCode\CLAUDE.md` | All users in org |
| User | `~/.claude/CLAUDE.md` | You, all projects |
| Project | `./CLAUDE.md` or `./.claude/CLAUDE.md` | Team via source control |
| Local | `./CLAUDE.local.md` (add to `.gitignore`) | You, current project |

The failure mode: **Wrong-level edit.** You put a personal preference into the shared project file, and the whole team inherits it.

The fix: Put personal preferences in `CLAUDE.local.md` or the user file and keep the project file for team facts.

Cross-references: managed rollout is Module 9.1.

**If you remember one thing:** choose the level by audience.

## 3.2.2.2 — HOW LOADING WORKS

**Framing.** Claude walks up the directory tree from the working directory, loading every CLAUDE.md and CLAUDE.local.md it finds, so running in `foo/bar/` loads `foo/bar/CLAUDE.md`, `foo/CLAUDE.md` and local files alongside them [Claude Code docs, Memory, 2026]. Content is ordered from filesystem root down to the working directory, with `CLAUDE.local.md` after `CLAUDE.md` in the same directory. Subdirectory files are not loaded at launch; they load when Claude reads files in that subdirectory. Block-level HTML comments are stripped before injection, while comments inside code blocks are kept.

```text
cwd = /work/mono/packages/api
launch order:  /work/mono/CLAUDE.md -> /work/mono/packages/api/CLAUDE.md -> CLAUDE.local.md
on demand:     /work/mono/packages/api/src/db/CLAUDE.md  (when a file there is read)
not loaded:    /work/mono/packages/web/CLAUDE.md          (until a file there is read)
```

The failure mode: **Launch-directory blindness.** You start Claude in a different directory than you assumed, so a file you expect never loaded or an unrelated one did.

The fix: Check `/memory` or `/context` for the loaded list and start Claude in the directory the task belongs to.

Cross-references: monorepo layering is Module 3.5.

**If you remember one thing:** the launch directory decides.

## 3.2.2.3 — ADDITIVE, WITH MANAGED AND EXCLUDED FILES

**Framing.** Files are concatenated, not overridden, so contradictory rules may be resolved arbitrarily and files should be reviewed periodically [Claude Code docs, Memory, 2026]. The managed file cannot be excluded by individual settings, and `claudeMdExcludes` skips ancestor files by glob (arrays merge across settings layers; managed policy files cannot be excluded). Additional directories added with `--add-dir` do not load CLAUDE.md unless `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1` is set.

| Mechanism | Effect |
|---|---|
| `claudeMdExcludes` | Skip matching ancestor files; not managed ones |
| `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1` | Load CLAUDE.md, `.claude/rules/*.md` and local files from `--add-dir` directories |
| Managed CLAUDE.md | Cannot be excluded |

The failure mode: **Override-expectation.** You write a project rule to cancel a user-level rule, but both load and Claude reconciles them unpredictably.

The fix: Remove or reword the conflicting rule at its source; do not expect precedence to cancel it.

Cross-references: settings layering is Module 4.1.

**If you remember one thing:** additive means conflicts persist.
