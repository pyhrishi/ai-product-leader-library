# MODULE 2.1.2 — PLAN: WRITE IT, EDIT IT, APPROVE IT: THE COMPLETE CRAFT

---

## THE THESIS OF THIS TOPIC

**A plan is a reviewable artifact that sits between exploration and edits, and the approval prompt, the editor shortcut and the context choice are the three controls that decide whether it earns its cost.**

**Prove-it, in one sentence:** get a plan from plan mode, edit it in your own editor with Ctrl+G, approve it with a deliberate option, and show what changed in the session mode.

**The single most important discipline: never approve a plan you have not read and edited at least once.**

**The counterintuitive claim you will learn to defend:** approving a plan changes the permission mode of the whole session, so the choice you click is a security decision as well as a workflow one [Claude Code docs, Permission modes, 2026].

**THE TIME BUDGET.** Reading time: ~20 minutes. Prove-it time: ~2 hours (120 minutes, 6.0 times the reading time).

## 2.1.2.1 — WHAT A PLAN IS AND WHERE IT LIVES

**Framing.** In plan mode Claude researches and then presents a plan and asks how to proceed; source edits stay blocked until you approve [Claude Code docs, Permission modes, 2026]. The permission-modes page does not give a dedicated plan-file location, it only notes under protected paths that the session's plan files live in `~/.claude/plans/` or in the `plansDirectory` you set [Claude Code docs, Permission modes, 2026].

| Fact | Detail |
|---|---|
| Entering | `Shift+Tab`, `/plan [description]`, or `--permission-mode plan` |
| Leaving without approving | `Shift+Tab` again |
| Plan file directory | `~/.claude/plans/` or `plansDirectory` [from a protected-paths note, not a dedicated section] |
| Default mode setting | `"permissions": {"defaultMode": "plan"}` in `.claude/settings.json` |

`/plan fix the auth bug` enters plan mode and starts on that task in one step [Claude Code docs, Commands, 2026].

The failure mode: **Plan-in-chat-only.** You treat the plan as a chat message and never open the file, so a plan that should have been saved and reviewed is lost at the next compaction.

The fix: Open the plan with `Ctrl+G` or find it under the plans directory and keep the final version in the repo when it will guide a later session.

Cross-references: context survival is Module 3.1; repo-level instructions are Module 3.2.

**If you remember one thing:** the plan is a file, so treat it like one.

## 2.1.2.2 — EDITING THE PLAN YOURSELF

**Framing.** Press `Ctrl+G` to open the proposed plan in your default text editor and edit it directly before Claude proceeds [Claude Code docs, Permission modes, 2026]. The interactive-mode page lists the same key as opening the prompt in your editor, with `Ctrl+X Ctrl+E` as the readline-native binding [Claude Code docs, Interactive mode, 2026].

Edits worth making, in order of value:

| Edit | Why |
|---|---|
| Delete steps outside scope | Removes the quiet scope creep |
| Reorder so tests come first | Gives the implement phase a check |
| Add the verification command | Closes the loop (Module 2.3) |
| Add a `Do not touch:` list | Turns a convention into a boundary |

The failure mode: **Rubber-stamp-plan.** You press approve on a plan whose steps you skimmed, and Claude executes a step you would have deleted.

The fix: Make at least one edit, even a deletion, so approval is evidence that you read the plan.

Cross-references: verification is Module 2.3; prompting scope is Module 2.2.

**If you remember one thing:** if you changed nothing, you probably did not read it.

## 2.1.2.3 — THE APPROVAL PROMPT IS A MODE SWITCH

**Framing.** When the plan is ready Claude asks how to proceed, and approving exits plan mode and switches the session to the mode the option describes [Claude Code docs, Permission modes, 2026].

| Option as worded in the docs | Resulting mode |
|---|---|
| Yes, and use auto mode | Auto mode |
| Yes, auto-accept edits (shown when auto is unavailable) | Accept edits |
| Yes, and switch to BYPASS PERMISSIONS ... (shown if the session started with bypass enabled) | Bypass permissions |
| Yes, manually approve edits | Edits prompt one by one |
| No, keep planning | Stay in plan mode |

With `showClearContextOnPlanAccept` enabled the list gains a first option that approves and clears planning context. Accepting also titles the session from the plan unless you already named it [Claude Code docs, Permission modes, 2026].

The failure mode: **Approve-as-default.** You click the first option every time, and the session quietly moves into a mode with fewer prompts than the work deserves.

The fix: Read the option text, pick the mode on purpose, and choose manual approval for plans that touch migrations or deploy config.

Cross-references: modes are Module 4.3; the mode baseline is Module 1.2.

**If you remember one thing:** the approve button chooses your permission mode.

## 2.1.2.4 — REPLANNING AND WHEN PLANNING IS OVERHEAD

**Framing.** To plan again, cycle back with `Shift+Tab` or prefix the next prompt with `/plan` [Claude Code docs, Permission modes, 2026]. A plan helps most when the path is uncertain or crosses files; for a change you can state in one diff it is overhead (guide 2.1.5).

```text
/plan the migration touches three services; propose steps, name the tests that prove each step, and list what you will NOT change
```
| Signal | Action |
|---|---|
| Plan keeps growing | Split it; approve step one only |
| Plan contradicts what you learned | `No, keep planning` and say why |
| Plan was approved but implementation drifts | Esc, rewind, re-plan from the checkpoint (Module 2.5) |

The failure mode: **Plan-sprawl.** The plan grows to dozens of steps nobody can review, so approval becomes a formality and the implement phase runs unattended.

The fix: Split the plan into stages with a check at each boundary and approve only the next stage.

Cross-references: checkpoints are Module 2.5; unattended runs are Module 6.7.

**If you remember one thing:** a plan you cannot review is not a plan.

## THE PROVE-IT SECTION

**Deliverable.** A plan edited by you, the approval option you chose, and a one-line statement of the resulting permission mode.

**Close this topic. Build the artifact below from memory. Return to the text only after your first attempt is complete.**

| Step | Action | Output |
|---|---|---|
| 1 | Enter plan mode and request a plan for a real change | Plan v1 |
| 2 | Open it with `Ctrl+G`; delete one step, add the check command, add a do-not-touch list | Plan v2 |
| 3 | Diff v1 and v2 | Edit list |
| 4 | Pick an approval option on purpose; note the mode shown after | Mode line |
| 5 | Find the plan file on disk | Path |
| 6 | State what you would choose for a migration and why | Two sentences |

**A passing artifact looks like this:**

| Item | Evidence |
|---|---|
| Plan edited | v1 to v2 diff shows 3 edits |
| Check command in plan | `pnpm tsc --noEmit` listed per stage |
| Approval option | Manual edits; status bar confirms |

**A failing artifact (a realistic near-miss):**

| Element | What is wrong |
|---|---|
| Plan v1 equals v2 | **Rubber-stamp-plan** |
| Mode after approval not recorded | **Approve-as-default** |

**The verdict.** The artifact passes only if the plan changed between v1 and v2 and the resulting permission mode is named from the status bar.

## CLOSING REFRAME

This is the craft of planning: **an artifact you edit, an approval that sets your mode, and stages you can review.** The engineer who understands this does not ask "is the plan good?" — they ask "what did I change in it, and what mode did I just grant?"
