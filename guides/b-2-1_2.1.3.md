## THE THESIS OF THIS TOPIC

**Implementation is the phase where Claude edits files, and it goes well when the plan, a test and a check command are all in front of it, and badly when the only definition of done is that it looks finished.**

**Prove-it, in one sentence:** implement one planned change test-first, show the failing test, the passing run, and the diff that links them.

**The single most important discipline: start implementation from a check Claude can run.**

**The counterintuitive claim you will learn to defend:** Claude stops when the work looks done, so a plan without a runnable check produces confident, unverified output [Claude Code docs, Best practices, 2026].

## 2.1.3.1 — LEAVING PLAN MODE DELIBERATELY

**Framing.** Approving a plan exits plan mode and switches the session to the mode of the option you chose, after which Claude starts editing [Claude Code docs, Permission modes, 2026]. `Shift+Tab` cycles modes and the status bar shows which is active [Claude Code docs, Permission modes, 2026].

| Status bar text | Mode |
|---|---|
| `⏸ manual mode on` | `default` (Manual) |
| `⏵⏵ accept edits on` | `acceptEdits` |
| `⏸ plan mode on` | `plan` |
| `⏵⏵ auto mode on` | `auto` |
| `⏵⏵ bypass permissions on` | `bypassPermissions` |

The built-in default is `auto` for interactive terminal and VS Code sessions from v2.1.283; `claude -p` and the Agent SDK default to Manual [Claude Code docs, Permission modes, 2026].

The failure mode: **Mode-blind-edit.** You begin implementation without looking at the status bar and discover the session is in a more permissive mode than the task deserved.

The fix: Read the status bar after every approval and switch with `Shift+Tab` before the first edit.

Cross-references: the baseline is Module 1.2; mode choice is Module 4.3.

**If you remember one thing:** check the mode before the first edit.

## 2.1.3.2 — TEST FIRST OR CHECK AFTER

**Framing.** The prompt library carries both orders: `write tests for {feature} first, then implement it until they pass` and `write tests for {path}, run them, and fix any failures` [Claude Code docs, Prompt library, 2026]. Best practices lists the checks Claude can read: a test file, a build exit code, a linter, a script diffing against a fixture, a browser screenshot [Claude Code docs, Best practices, 2026].

| Order | Use when | Risk |
|---|---|---|
| Test first | Behaviour is specifiable now | Tests mirror a wrong spec |
| Check after | Existing behaviour must not change (refactor) | Tests rewritten to pass |
| Screenshot compare | UI work | Compares pixels, not behaviour |

```text
write tests for the rate limiter first, then implement it until they pass. do not edit the tests once they are committed to the plan.
```

The failure mode: **Test-bending.** Claude edits the failing test to match its code instead of fixing the code, and the suite goes green on a wrong implementation.

The fix: Tell Claude the tests are fixed once planned, review test diffs separately, and run `git diff` on test files before accepting.

Cross-references: test-driven work is Module 9.2; verification is Module 2.3.

**If you remember one thing:** a green suite means nothing if the tests moved.

## 2.1.3.3 — STAGES AND THE DIFF YOU CAN READ

**Framing.** Implement in stages that match the plan, because every stage boundary is a place to run the check, look at the diff and, if needed, rewind. The `/diff` command shows the working tree including the edits Claude made so far [Claude Code docs, Commands, 2026].

```text
Stage 1: add the failing test.   Check: the test fails for the right reason.
Stage 2: implement.               Check: `pnpm vitest run path/to/file.test.ts` passes.
Stage 3: typecheck and lint.      Check: `pnpm tsc --noEmit` exits 0.
```
| Boundary action | Command |
|---|---|
| Read the changes | `/diff` |
| Undo a bad stage | `/rewind` (Module 2.5) |
| Record progress | A small commit (guide 2.1.4) |

The failure mode: **Big-bang-diff.** You let the whole plan run before looking, and a wrong early decision is buried under a large diff that is hard to review or rewind.

The fix: Run each stage to its check, read `/diff`, and only then continue.

Cross-references: checkpoints are Module 2.5; reviews are guide 2.6.8.

**If you remember one thing:** small stages keep every decision reviewable.

## 2.1.3.4 — WHAT CLAUDE CANNOT SEE WHILE IT IMPLEMENTS

**Framing.** Best practices says to write down only what Claude cannot find by reading the repo: the exact test, typecheck and lint commands, misleading code, decisions not in the repo and anything you corrected twice [Claude Code docs, Best practices, 2026].

```markdown
# Commands
- Run one test file: pnpm vitest run path/to/file.test.ts
- Typecheck: pnpm tsc --noEmit
```
That file is the docs' own short example of a CLAUDE.md that passes the test [Claude Code docs, Best practices, 2026]. If a rule must hold every time, it belongs in a hook rather than a prompt (Module 5.4).

The failure mode: **Hidden-command.** The check command lives in your head, so Claude guesses a test invocation, fails or skips it, and reports success.

The fix: Put the one-test and typecheck commands in CLAUDE.md and name them in the plan.

Cross-references: CLAUDE.md is Module 3.2; hooks are Module 5.4.

**If you remember one thing:** the check command is the most valuable line you can write down.

## THE PROVE-IT SECTION

**Deliverable.** A staged implementation with a failing-then-passing test and a per-stage check log.

**Close this topic. Build the artifact below from memory. Return to the text only after your first attempt is complete.**

| Step | Action | Output |
|---|---|---|
| 1 | Approve a plan with manual edits and record the mode | Mode line |
| 2 | Add a failing test; run it; show it fails for the right reason | Failing log |
| 3 | Implement stage two; run the single-test command | Passing log |
| 4 | Run typecheck and lint | Exit codes |
| 5 | Run `git diff` on the test files to prove they did not move | Empty test diff |
| 6 | Read `/diff` and write one sentence per stage | Stage notes |

**A passing artifact looks like this:**

| Stage | Check | Result |
|---|---|---|
| 1 failing test | `vitest run file.test.ts` | Fails: expected 429, got 200 |
| 2 implement | same command | Passes |
| 3 typecheck | `tsc --noEmit` | Exit 0 |
| Test files in diff | `git diff -- '*.test.ts'` | Unchanged since stage 1 |

**A failing artifact (a realistic near-miss):**

| Element | What is wrong |
|---|---|
| Tests edited during stage 2 | **Test-bending** |
| One 600-line diff | **Big-bang-diff** |

**The verdict.** The artifact passes only if the test failed first, passed later without the test file changing, and each stage has a recorded check.
