# MODULE 2.1.7 — FRESH SESSION FOR EXECUTION: THE COMPLETE CRAFT

## THE THESIS OF THIS TOPIC

**After a spec or plan exists as a file, the best execution starts from a clean context that holds the spec and the code and nothing else, because the written document carries the decisions and the old conversation carries only noise.**

**Prove-it, in one sentence:** execute a spec in a fresh session and show that the first prompt plus the file was enough, with context contents checked by /context.

**The single most important discipline: move decisions into files, then clear.**

**The counterintuitive claim you will learn to defend:** clearing is not free of consequence in either direction: it saves tokens and focus, but a cold cache means the first turn is full price [Claude Code docs, Best practices, 2026].

**THE TIME BUDGET.** Reading time: ~18 minutes. Prove-it time: ~2 hours (120 minutes, 6.7 times the reading time).

## 2.1.7.1 — WHY A CLEAN CONTEXT WINS

**Framing.** Best practices says that after the spec exists you should start a fresh session so the build begins with a clean context and a written definition of done [Claude Code docs, Best practices, 2026]. It also says `/clear` between unrelated tasks costs nothing and keeps the next task from paying for the previous one's history, because every request sends the whole conversation [Claude Code docs, Best practices, 2026].

| Keep going | Clear |
|---|---|
| Same task, context is the asset | Spec or plan is written |
| Mid-debug with evidence in context | Corrected the same thing twice |
| Short follow-up | Unrelated next task |

The page also notes that most current models have a 1M-token window with automatic compaction, so running out is rare, but `/clear` between tasks is still worth doing for focus and cost [Claude Code docs, Best practices, 2026].

The failure mode: **Marathon-session.** One session accumulates three unrelated tasks, and each later turn re-reads all of them at cost while old details compete with the current task.

The fix: Clear between unrelated tasks and name the old session so you can return.

Cross-references: context mechanics are Module 3.1; cost is Module 3.4.

**If you remember one thing:** one task, one context.

## 2.1.7.2 — THE MECHANICS OF CLEARING SAFELY

**Framing.** `/clear [name]` starts a new conversation with empty context; pass a name to label the previous conversation in the `/resume` picker. The previous session is saved and can be resumed, and within the same process the rewind menu shows a previous-session entry [Claude Code docs, Commands and Checkpointing, 2026].

```text
/clear oauth-migration     # new session; old one labelled oauth-migration
/resume oauth-migration    # come back later
```
| Behaviour | Detail |
|---|---|
| Aliases | `/reset`, `/new` |
| Name kept | A name from `--name` or `/rename` survives; an AI-generated title does not |
| Active goal | `/clear` also removes it [Claude Code docs, Goal, 2026] |

The failure mode: **Unnamed-clear.** You clear without naming the old session and cannot tell it apart in the picker a day later.

The fix: Pass a name to `/clear` or `/rename` before clearing.

Cross-references: naming is guide 2.4.2; resume is guide 2.4.1.

**If you remember one thing:** name what you leave.

## 2.1.7.3 — THE HANDOFF FILE

**Framing.** A fresh session knows only what loads at startup (CLAUDE.md, memory) and what you tell it. The handoff is therefore a file: the spec from guide 2.1.6, or a plan, plus the check command. Best practices says only to write down what Claude cannot find by reading the repo [Claude Code docs, Best practices, 2026].

```text
Read SPEC.md and implement it in stages. Run `pnpm vitest run rate-limit` after each stage. Stop and ask if the spec and the code disagree.
```
| Handoff content | Why |
|---|---|
| Spec path | Definition of done |
| Check command | Closes the loop |
| Stop rule | Prevents silent divergence |
| Branch name | Ties work to history |

The failure mode: **Lossy-handoff.** The handoff is a chat summary that omits a decision, and the fresh session rebuilds the feature with the omitted choice reversed.

The fix: Put decisions in the file, not the summary, and point the first prompt at the file.

Cross-references: CLAUDE.md is Module 3.2; spec-driven work is Module 9.1.

**If you remember one thing:** the file carries the decisions.

## 2.1.7.4 — COMPACT, REWIND OR CLEAR

**Framing.** Three tools reduce context differently. `/compact [instructions]` replaces history with a summary, the rewind menu can summarize from or up to a chosen message without changing files, and `/clear` starts over [Claude Code docs, Manage sessions and Checkpointing, 2026].

| Tool | Effect | Use when |
|---|---|---|
| `/compact keep the API changes and the test commands` | Summarizes the whole conversation | Same task, noisy history |
| Rewind: Summarize from here | Compresses from a point forward | A verbose debug midstream |
| `/clear` | New context | Task done or spec written |

Compaction is itself a large request on a long session, more so once the cache expires [Claude Code docs, Best practices, 2026].

The failure mode: **Compact-reflex.** You compact whenever the session feels heavy, paying for a big summarizing request, when the task is done and a clear would cost nothing.

The fix: Clear when the task ended, compact only when the same task must continue.

Cross-references: compaction survival is Module 3.1; checkpoints are Module 2.5.

**If you remember one thing:** finished tasks get cleared, not compacted.

## THE PROVE-IT SECTION

**Deliverable.** A handoff file, a fresh-session first prompt, and a `/context` snapshot proving the context held only what you intended.

**Close this topic. Build the artifact below from memory. Return to the text only after your first attempt is complete.**

| Step | Action | Output |
|---|---|---|
| 1 | Finish a SPEC.md from the interview and commit it | Spec in repo |
| 2 | Name and clear the old session | Picker entry |
| 3 | Start fresh with the handoff prompt | First prompt |
| 4 | Run `/context` before the first edit | Snapshot |
| 5 | Implement one stage; confirm the check | Log |
| 6 | Resume the old session by name once, to prove it | Resume log |

**A passing artifact looks like this:**

| Item | Evidence |
|---|---|
| Old session | Named `rate-limit-spec`; `/resume rate-limit-spec` works |
| Fresh context | `/context` shows CLAUDE.md, tools and no old conversation |
| Handoff | First prompt names SPEC.md and the check |

**A failing artifact (a realistic near-miss):**

| Element | What is wrong |
|---|---|
| Handoff pasted as chat summary | **Lossy-handoff** |
| Old session never named | **Unnamed-clear** |

**The verdict.** The artifact passes only if `/context` shows no leftover conversation and the build followed the file rather than memory of the old chat.
