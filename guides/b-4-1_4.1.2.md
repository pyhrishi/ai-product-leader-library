## THE THESIS OF THIS TOPIC

**When one key is set in several places, the highest level wins, lists merge instead of overriding, and managed settings sit above everything a user can touch.**

**Prove-it, in one sentence:** given a key set in four places, predict the winning value, and given two lists, predict the merged result.

**The single most important discipline: before debugging a setting that does not apply, name every level that sets that key.**

**The counterintuitive claim you will learn to defend:** a key at a lower level does not 'lose' when you add a list entry above it; for list keys such as permissions.allow the files combine, so a user allow rule survives next to a project one [Claude Code docs, Settings files and precedence, 2026].

## 4.1.2.1 — THE FIVE LEVELS

**Framing.** Claude Code uses the value from the highest level that sets the key [Claude Code docs, Settings files and precedence, 2026].

| Rank | Level | Note |
|---|---|---|
| 1 | Managed | Beats user, project, local and `--settings` |
| 2 | Command line (`--settings`) | One session; below managed |
| 3 | Project local | Your personal project overrides |
| 4 | Shared project | Team's committed file |
| 5 | User | Your global defaults |

Environment variables are not a level: `ANTHROPIC_MODEL` beats the `model` key from any file, while `ANTHROPIC_DEFAULT_MODEL` applies only when no file sets `model`. Decided per pair [Claude Code docs, Settings files and precedence, 2026].

The failure mode: **Env-var blind spot.** You change `model` in a settings file and nothing changes because `ANTHROPIC_MODEL` is exported in your shell.

The fix: Check the key's pair on the env-vars reference; unset the variable or use `--model`.

Cross-references: scopes are Module 4.1.1; model precedence is Module 4.6.

**If you remember one thing:** levels decide files; env vars decide per pair.

## 4.1.2.2 — LISTS MERGE, ARRAYS OF MODEL LISTS DO NOT

**Framing.** Setting the same list key, such as `permissions.allow`, in more than one file combines the lists so each file can add entries without removing another's. Four model-related keys follow their own rules [Claude Code docs, Settings files and precedence, 2026].

| Key | Merge behaviour |
|---|---|
| `permissions.allow/ask/deny` | Union across files |
| `fallbackModel` | Whole value from highest file that sets it |
| `modelPicker` | Whole value from managed, `--settings` or user; ignored in project/local |
| `availableModels` | Managed list applied as-is; user/project/local entries ignored |
| `sandbox.filesystem` arrays | Merged across scopes |
Within the managed tier by default, `first-wins`: the highest-ranked source with a policy key is used and the rest ignored; `managedSourcesBehavior: merge` (v2.1.242+) combines them [Claude Code docs, Deploy managed settings, 2026].

The failure mode: **Replace assumption.** You expect your project allow list to replace the user list, then are surprised an old user allow rule still fires.

The fix: Treat list keys as unions; to remove an entry, delete it from the file that holds it.

Cross-references: permission rules combine with deny first in Module 4.2; managed tier is 4.1.6.

**If you remember one thing:** lists add up; scalars override.

## 4.1.2.3 — EXCEPTIONS: STRICTER LOWER VALUES THAT STILL COUNT

**Framing.** For a few security keys Claude Code honors a restrictive value from a scope that otherwise could not override managed settings [Claude Code docs, Settings files and precedence, 2026].

| Key | Honored from lower scope |
|---|---|
| `disableClaudeAiConnectors` | `true` from any scope |
| `permissions.blockReadsOutsideWorkingDirectories` | `true` from any scope (v2.1.257+) |
| `isolatePeerMachines` | `true` from any scope |
| `maxEffortLevel` | Lower cap from any scope (v2.1.267+); lowest applies |
| `remoteControlAtStartup` | `false` from project or local file |

Also `permissions.defaultMode` values `auto` and `bypassPermissions` do not take effect from project or local settings; use user or managed, or `--permission-mode`.

The failure mode: **Project mode trap.** You commit `defaultMode: auto` or `bypassPermissions` in the project file and every session starts in Manual.

The fix: Set those values in user or managed settings, or pass `--permission-mode` for one session.

Cross-references: permission modes are Module 4.3.

**If you remember one thing:** the exceptions only ever make things stricter.
