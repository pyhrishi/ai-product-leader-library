## THE THESIS OF THIS TOPIC

**The fastest route from quickstart to a real agent is to run the nearest official example, then change one thing at a time against a check you wrote first.**

**Prove-it, in one sentence:** run one official example locally, record what it needs, change exactly one option, and write down what changed and how you measured it.

**The single most important discipline: treat an example as a hypothesis about your use case, not as production code.**

**The counterintuitive claim you will learn to defend:** demos are for local development, not for deployment: the docs call the demo repository 'demos for local development', so copy their shape, not their security posture [Agent SDK docs, Examples, 2026].

## 8.1.4.3 — RUNNING AN EXAMPLE AS AN EXPERIMENT

**Framing.** Treat the example as a hypothesis. Run it unchanged, record the result, change one option, and compare. The result message gives you cost, usage, number of turns and a session id for each run [Agent SDK docs, How the agent loop works, 2026].

```text
Run A: unchanged         turns=?  cost=?  subtype=?
Run B: effort="low"      turns=?  cost=?  subtype=?
Run C: max_turns=5       turns=?  cost=?  subtype=?
```

| Variable you can change | Option | Effect named in docs |
|---|---|---|
| Reasoning depth | effort (low to max) | Fewer tokens per turn at low [Agent loop] |
| Loop length | max_turns | Stops tool-use round trips; error_max_turns [Agent loop] |
| Spend | max_budget_usd | error_max_budget_usd [Agent loop] |
| Tools | allowed_tools | Auto-approves listed tools [Agent loop] |

Sources: [Agent SDK docs, How the agent loop works, 2026]. Costs are estimates: the headless page calls them client-side estimates that can differ from the bill [Claude Code docs, Run Claude Code programmatically, 2026].

The failure mode: **Multi-change run.** You change effort, tools and prompt together, the result improves, and you cannot say which change caused it.

The fix: Change one variable per run and keep the runs in a table.

Cross-references: options are Module 8.2.2; cost tracking is Module 8.6.3; evals are Module 8.6.5.

**If you remember one thing:** one change per run, recorded.

## 8.1.4.4 — FROM DEMO TO PROTOTYPE: THE GAP LIST

**Framing.** A demo skips what production needs. The gap list is the work between the two. Items come from the docs: permissions, limits, isolation and hosting are separate pages because they are separate jobs.

| Gap | Question to ask | Module |
|---|---|---|
| Permissions | What can it run unattended? | 8.6.1 |
| Limits | What stops a runaway loop? | 8.6.3 |
| Isolation | What does it read from the host? | 8.7.3 |
| Secrets | Where do keys live? | 8.7.4 |
| Check | What proves a run was right? | 8.6.5 |
| Failure | What happens on crash? | 8.7.5 |

The mapping of gaps to modules is this curriculum's own structure, not a docs list.

The failure mode: **Demo-to-prod copy.** You deploy a demo with broad permissions and no budget because it worked on your laptop.

The fix: Fill the gap list before the first deployment and treat any unanswered row as a blocker.

Cross-references: security is Module 8.7; evals are Module 8.6.

**If you remember one thing:** the gap list is the plan.

## THE PROVE-IT SECTION

**Deliverable.** A lab notebook: example chosen, setup steps, one-change experiment, and a list of production gaps found.

**Close this topic. Build the artifact below from memory. Return to the text only after your first attempt is complete.**

| Step | Action | Output |
|---|---|---|
| 1 | Pick one example by product shape and write why | A choice note |
| 2 | Run it unchanged three times and record turns, cost and subtype | A 3-row table |
| 3 | Change exactly one option and run three more times | A second table |
| 4 | Write what the change did, with numbers | A paragraph |
| 5 | Fill the six-row gap list for the example | A gap list |
| 6 | Decide: adopt, adapt or discard | A decision line |

**A passing artifact looks like this:**

| Run | Change | Turns | Cost | Subtype |
|---|---|---|---|---|
| A1-A3 | none | recorded | recorded | success |
| B1-B3 | effort low | recorded | recorded | success |

Gap list: six rows, two marked blocker. Decision: adapt.

**A failing artifact (a realistic near-miss):**

| Element | What is wrong |
|---|---|
| One run, no numbers | No comparison possible |
| Three options changed at once | **Multi-change run** |
| Gap list absent | **Demo-to-prod copy** |

**The verdict.** The notebook passes only if each run has numbers, exactly one variable differs between tables, and the gap list is complete.
