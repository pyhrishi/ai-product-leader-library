# MODULE 1.1 — WHAT CLAUDE CODE IS: THE COMPLETE CRAFT

---

## THE THESIS OF THIS MODULE

**Claude Code is not a smarter autocomplete or a chatbot with a shell; it is a harness that lets a model act on your project, observe the result and keep going, which moves the human from typing code to specifying outcomes and checking evidence.**

**Prove-it, in one sentence:** explain to a colleague, in two minutes and without notes, how Claude Code differs from a chatbot and from autocomplete, and show it with one real task.

**The single most important discipline: give Claude an outcome and a check it can run, then let it choose the steps.**

**The counterintuitive claim you will learn to defend:** the biggest gain does not come from the model writing code faster. It comes from the loop closing without you. Anthropic's own guidance says a check Claude can run is the difference between a session you watch and one you walk away from [Anthropic, Best practices, 2026].

**THE TIME BUDGET.** Reading time: ~25 minutes. Prove-it time: ~2 hours. The ratio is the point: 2 hours is 120 minutes, almost five times the reading time. If you finish the prove-it while the page is still warm, you have read a summary, not a module.

| Depth | What you can do after this module |
|---|---|
| L3 | Explain what Claude Code is, name the tools and surfaces, recognise the failure |
| L4 | Choose the surface and permission posture for a task and defend it |
| L5 | Set the team's operating model for delegating to agents |

This module is written at L3, with the L4 judgment calls marked, because the syllabus target is L3. Definitions are kept short; the work is in the failure modes.

## 1.1.1 — DEFINITION

**Framing.** Before you can judge a tool you need the one-sentence definition that survives contact with a sceptical engineer. The official one is: **Claude Code is an agentic coding tool that reads your codebase, edits files, runs commands and integrates with your development tools**, available in the terminal, IDE, desktop app and browser [Anthropic, Claude Code docs, 2026]. Three verbs carry the weight: reads, edits, runs. A tool that only reads is a search engine; one that reads and edits is an editor plugin; one that also runs commands and observes the output is an agent.

The docs add a framing that matters: Claude Code is **the agentic harness around the model**. The model reasons; the harness provides tools, manages the context the model sees, and supplies the execution environment [Anthropic, How Claude Code works, 2026].

```
                  ┌────────────────────────────────────────┐
   your prompt ──►│  HARNESS (Claude Code)                 │
                  │  ┌──────────┐   ┌───────────────────┐  │
                  │  │  MODEL   │◄─►│  TOOLS            │  │──► your files
                  │  │ (reasons)│   │ read / edit /     │  │──► your shell
                  │  └──────────┘   │ search / run /web │  │──► git, MCP, web
                  │       ▲         └───────────────────┘  │
                  │       │ context: files, outputs,       │
                  │       └─ CLAUDE.md, memory, skills     │
                  └────────────────────────────────────────┘
```

**What the harness gives the model.** Five categories of built-in tools, each a different kind of agency [Anthropic, How Claude Code works, 2026]:

| Category | What Claude can do | Failure mode if you ignore it |
|---|---|---|
| File operations | Read, edit, create, rename | Treating edits as irreversible and over-planning |
| Search | Find files by pattern, search content by regex | Pasting files by hand that Claude could find itself |
| Execution | Run shell commands, tests, servers, git | Never giving it a command that verifies |
| Web | Search, fetch documentation, look up errors | Assuming it only knows what is in the repo |
| Code intelligence | Type errors, definitions, references, via plugins | Expecting symbol-aware navigation with no plugin installed |

Two things make this more than a wrapper. First, the scope: **it sees your project, your terminal and your git state, not just the current file**, which is why "fix the authentication bug" can become a search, several reads, coordinated edits, a test run and a commit [Anthropic, How Claude Code works, 2026]. Second, it is not limited to code: the docs say it can help with anything you can do from the command line, including docs, builds and research [Anthropic, How Claude Code works, 2026].

The failure mode: **Chatbot-in-a-terminal framing.** You treat Claude Code as a chat window that happens to sit in a terminal, so you paste context by hand and ask it to "show me the code", and you never use the loop.

The fix: describe the outcome and the check, point it at the repository, and let it search, edit and run on its own.

Cross-references: the vocabulary behind these terms is Module 1.5; the loop itself is Module 1.2.

**If you remember one thing:** Claude Code is a harness that gives a model tools and context so it can act on your project.

## 1.1.2 — CHATBOT VS AGENT

**Framing.** The distinction is operational, not marketing. **A chatbot answers and waits; an agent plans, acts, observes the result and loops until done or blocked.** The docs describe the loop as three blended phases: gather context, take action, verify results, repeating until the task is complete, with you able to interrupt at any point [Anthropic, How Claude Code works, 2026].

```
 AUTOCOMPLETE         CHATBOT                       AGENT
 ───────────         ───────                       ─────
 sees: cursor        sees: what you paste          sees: your project via tools
 does: next tokens   does: one answer, then waits  does: act ► observe ► decide ► act
 you: accept/reject  you: copy, paste, run, report you: set outcome, check evidence
```

| Mode | Who runs the code | Who closes the loop | Failure mode |
|---|---|---|---|
| Autocomplete | You | You, line by line | Plausible code that never meets the rest of the system |
| Chatbot | You, by copy and paste | You, by reading and relaying results | You become the messenger between the model and the machine |
| Agent | The agent, through tools | The agent, if it has a check | Confident work with no check, which you only discover later |

An example makes the difference concrete. For "fix the failing tests", the docs show the agent chaining six moves: run the suite, read the error output, search for the relevant files, read them, edit, run the tests again [Anthropic, How Claude Code works, 2026]. A chatbot can do the thinking in steps two to five but cannot do steps one and six, so you do them.

**The loop adapts.** A question about the codebase may need only context gathering; a bug fix cycles through all three phases repeatedly; a refactor may involve heavy verification [Anthropic, How Claude Code works, 2026]. You are part of the loop: press `Esc` to stop immediately, or type a correction and press `Enter` to steer without stopping [Anthropic, How Claude Code works, 2026].

The failure mode: **Human-as-messenger loop.** You copy an error into the tool, copy its suggestion into the editor, run it, copy the new error back. The model is an agent in capability and a chatbot in practice, and you are the slowest component.

The fix: give Claude the command that reproduces the problem and the check that proves it fixed, so the loop runs without you relaying anything.

Cross-references: the loop in depth is Module 1.2; the explore, plan, implement, commit pattern is Module 2.1; verification is Module 2.3.

**If you remember one thing:** a chatbot ends its turn with an answer, an agent ends it with evidence.

## 1.1.3 — WHERE IT RUNS

**Framing.** The same engine runs in many places, and **where it runs decides what it can touch and what happens when you close the laptop**. The docs separate two things that people blur: the execution environment (where code runs) and the interface (how you interact). The loop is identical in all of them [Anthropic, How Claude Code works, 2026].

**Three execution environments** [Anthropic, How Claude Code works, 2026]:

| Environment | Where code runs | Use case | Failure mode |
|---|---|---|---|
| Local | Your machine | Default; full access to your files and tools | Long task dies with the laptop sleeping |
| Cloud | Anthropic-managed VMs, or self-hosted environments your organisation operates | Offload tasks, work on repos you do not have locally | Task needs a local tool or secret the VM does not have |
| Remote Control | Your machine, controlled from a browser | Use the web UI while execution and files stay local | Machine goes offline and the session stalls |

**Surfaces.** The docs list the terminal CLI, VS Code, JetBrains, the desktop app, the web and mobile, plus integrations such as Chrome, Slack, GitHub Actions, GitLab CI/CD and Code Review [Anthropic, Platforms and integrations, 2026]:

| Surface | Best for | Trade-off |
|---|---|---|
| CLI | Terminal workflows, scripting, remote servers | Full feature set; scripting and the Agent SDK are CLI-only |
| Desktop | Visual review, parallel sessions, managed setup | Gives up some CLI-only features |
| VS Code / JetBrains | Working inside the editor | Gives up some CLI-only features; JetBrains runs the CLI in its terminal |
| Web | Long tasks that need little steering, or work that continues offline | Cloud; less suited to heavy back-and-forth |
| Mobile | Starting and monitoring tasks away from the computer | A thin client into cloud sessions or Remote Control |

**Working when you are away** is a decision table of its own, with distinct triggers: Dispatch (message a task from the mobile app to Desktop), Remote Control (drive a running session from `claude.ai/code` or the mobile app), Channels (push events from chat apps into a session), Slack (mention `@Claude`), self-hosted environments, and scheduled tasks [Anthropic, Platforms and integrations, 2026].

```
 Where should this task run?
 ├─ needs my local files, tools or secrets? ──yes──► Local (CLI / Desktop / IDE)
 │                                            no
 │                                            ▼
 ├─ long-running, needs little steering? ──yes──► Cloud (web), then check back
 │                                            no
 │                                            ▼
 ├─ I want to steer from another device? ──yes──► Remote Control
 └─ it should happen on a schedule or an event? ──► Scheduled task, Channels, or CI
```

**If you are unsure where to start**, the docs say to install the CLI and run it in a project directory; if you would rather avoid a terminal, Desktop offers the same engine with a graphical interface [Anthropic, Platforms and integrations, 2026].

The failure mode: **Wrong-surface choice.** You start a two-hour migration in a local terminal and close the laptop, or you run a task that needs constant steering in a cloud session you cannot see.

The fix: use the decision tree above, and match the surface to how much steering the task needs and whether it must outlive your machine.

Cross-references: choosing a surface in depth is Module 7.1; cloud sessions are Module 7.4; mobile and remote control are Module 7.5; the desktop app is Module 7.2.

**If you remember one thing:** the surface decides where the code runs and whether the task survives you walking away.

## 1.1.4 — SAME ENGINE, MANY SURFACES

**Framing.** If the engine is the same, your investment should carry across surfaces. It mostly does: **each surface connects to the same underlying engine, so your repository's CLAUDE.md files, settings and MCP servers work across all of them** [Anthropic, Overview, 2026]. The docs add that configuration, project memory and MCP servers are shared across the local surfaces [Anthropic, Platforms and integrations, 2026]. What does not carry over is availability: some features exist on only some surfaces.

| Shared across local surfaces | Differs by surface | Failure mode |
|---|---|---|
| CLAUDE.md, settings, MCP servers | Scripting and the Agent SDK: CLI only | Building a pipeline on a surface that lacks it |
| Project memory | Third-party providers: work in CLI and the IDE extensions; Desktop has its own provider support | Assuming your provider works everywhere |
| Skills, hooks | Computer use (CLI on macOS and Desktop) and Dispatch (Desktop): Pro and Max | Assuming a plan feature exists on your plan |
| The agentic loop | Diff viewer and app preview: Desktop | Expecting visual review in the terminal |

The surface mix is also a plan and provider question. The docs state that for Amazon Bedrock or Microsoft Foundry you use the CLI or an IDE extension, or Claude Desktop on third-party providers, rather than the standard Desktop app [Anthropic, Platforms and integrations, 2026]. Feature availability across providers has its own documentation page, and the syllabus points you to it; this module does not reproduce its table because it changes often.

**A practical rule.** Put what must be consistent in files the engine reads (CLAUDE.md, settings, hooks), not in your habits at one surface. If a rule lives in a file in the repo, every surface obeys it.

The failure mode: **Assumed parity.** You write the team runbook around a command or feature you saw in the terminal, and a teammate on a different surface or plan cannot do it.

The fix: before standardising on a feature, check the feature-availability page for each surface and provider your team uses, and keep the check in the runbook.

Cross-references: the full surface comparison is Module 7.1; settings precedence is Module 4.1; the extension layer is Part 5, starting at Module 5.1.

**If you remember one thing:** put shared rules in files the engine reads, and verify a feature exists on every surface before you depend on it.

## 1.1.5 — DELEGATE, DO NOT DICTATE

**Framing.** The working relationship the docs recommend is delegation to a capable colleague: **give context and direction, then trust Claude to figure out the details** [Anthropic, How Claude Code works, 2026]. The doc's own example states the outcome and location, not the steps: the checkout flow is broken for users with expired cards, the code is in `src/payments/`, investigate and fix it. You do not specify which files to read or which commands to run.

This is not a licence for vagueness. The same docs insist on specificity where it matters: scope the task, point to sources, reference existing patterns, describe the symptom and what "fixed" looks like [Anthropic, Best practices, 2026].

| Delegate (Claude chooses) | Specify (you decide) | Failure mode |
|---|---|---|
| Which files to read | The outcome | Dictating the steps |
| Which commands to run | The constraints (no new libraries, avoid mocks) | Constraints discovered after the diff |
| The order of work | The check that proves it is done | Delegating without a check |

```text
# Dictating the steps (weak)
Open src/payments/charge.ts, find the function validateCard, add a check on the
expiry month, then open the test file and add a test...

# Delegating with outcome, constraints and a check (strong)
The checkout flow fails for users with expired cards. Relevant code is in
src/payments/. Write a failing test that reproduces it, fix it, and run the
payments test suite. Do not add dependencies.
```

**Why delegation works better.** Claude chains dozens of actions and course-corrects from what each step reveals [Anthropic, How Claude Code works, 2026]. A script of steps written in advance cannot adapt to what the code actually contains. **Your leverage is in the outcome and the check, not the keystrokes.**

**Where to be more directive.** Planning pays off when you are uncertain about the approach, the change touches several files, or you do not know the code. The docs' rule of thumb: if you could describe the diff in one sentence, skip the plan [Anthropic, Best practices, 2026].

The failure mode: **Dictating the steps.** You write the exact edits you want, Claude follows them literally, and the result is only as good as your plan, which was the thing you wanted to delegate.

The fix: state the outcome, the location and the constraints, and add a check, then let Claude choose the route.

The failure mode: **Delegating without a check.** You say "fix the login bug" with no failing test, no command and no definition of fixed, and Claude stops when the work merely looks done.

The fix: attach a check Claude can run, such as a reproduction test, a build exit code or a screenshot comparison.

Cross-references: prompting craft is Module 2.2; the explore, plan, implement, commit loop is Module 2.1; verification design is Module 2.3.

**If you remember one thing:** specify the outcome, the constraints and the check, and leave the steps to Claude.

## 1.1.6 — WHAT IT IS NOT

**Framing.** A tool this capable invites over-trust. **Claude Code is not a replacement for tests, code review, version control or judgment, and the model can be confidently wrong.** Anthropic's own framing is the "trust-then-verify gap": Claude produces a plausible-looking implementation that does not handle edge cases, and the fix is always to provide verification such as tests, scripts or screenshots; if you cannot verify it, do not ship it [Anthropic, Best practices, 2026].

| It is not a replacement for | Why | What still does the job |
|---|---|---|
| Tests | It stops when work "looks done" unless a check exists | Your test suite, run by Claude and by CI |
| Code review | A plausible diff can hide a wrong assumption | A human reviewer, plus an independent subagent review |
| Version control | Checkpoints cover only edits made through its file tools; Bash changes and external processes are not captured | git |
| Your judgment | The model can be wrong with high confidence | You, reading evidence |

**Two limits to know exactly.** Checkpoints are separate from git, remain available when you resume a conversation, and cover only file changes; actions that affect remote systems such as databases, APIs and deployments cannot be checkpointed and are governed by your permission mode and rules [Anthropic, How Claude Code works, 2026]. The docs say plainly that checkpoints are not a replacement for git [Anthropic, Best practices, 2026].

**Permissions are the other safety layer.** The docs list four modes, cycled with `Shift+Tab`: Auto, Manual, Accept edits and Plan. In Manual, Claude asks before file edits and shell commands; in Plan, it explores and proposes without editing source files [Anthropic, How Claude Code works, 2026]. Which mode a session starts in depends on version and plan; the docs state that from v2.1.283 auto mode is the built-in starting mode for interactive terminal and VS Code sessions, and that on earlier versions it applies only on Pro, Max and Team plans [Anthropic, How Claude Code works, 2026]. Treat that as a moving fact and check your version.

**The context window is the real constraint.** Most best practices follow from one fact: the context window fills fast and performance degrades as it fills [Anthropic, Best practices, 2026]. A single debugging session or codebase exploration can consume tens of thousands of tokens [Anthropic, Best practices, 2026; exact figure not reliably established, treat as order-of-magnitude].

| Pattern | Symptom | Fix named in the docs |
|---|---|---|
| Kitchen sink session | One task, then an unrelated one, then back; context full of irrelevant material | `/clear` between unrelated tasks |
| Correcting over and over | Same mistake corrected more than twice | `/clear` and write a better initial prompt |
| Over-specified CLAUDE.md | Important rules lost in noise | Prune hard; convert reliable rules to hooks |
| Infinite exploration | Unscoped "investigate" fills context | Scope narrowly or use subagents |

[Anthropic, Best practices, 2026]

The failure mode: **Trust-then-verify gap.** The diff looks right, the tests were never run, and an edge case ships.

The fix: provide verification every time (tests, scripts, screenshots), ask Claude to show evidence, and do not ship what you cannot verify.

The failure mode: **Checkpoint-as-git assumption.** You rely on `Esc Esc` to undo a Bash-made change or a database write, and the checkpoint does not cover it.

The fix: keep work in git, commit often, and use permission rules for anything that touches remote systems.

Cross-references: checkpoints and undo are Module 2.5; permissions and modes are Modules 4.2 and 4.3; the context window is Module 3.1; the threat model of a coding agent is Module 11.1.

**If you remember one thing:** treat every diff as plausible until a check you can read proves it right.

**Deliverable.** A two-minute spoken explanation of how Claude Code differs from a chatbot and from autocomplete, backed by one real task you ran both ways, with a one-page evidence sheet.

| Step | Action | Output |

| Run | Handoffs by hand | Tool calls by Claude | Check passed | Evidence |

**The verdict.** If you cannot point to the specific transcript line where Claude ran the check and read the result, you have not shown the difference between an agent and a chatbot.
