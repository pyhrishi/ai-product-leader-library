## 3.1.3.1 — WHAT THE DOCUMENTATION ACTUALLY CLAIMS

**Framing.** Claude compacts automatically, but instructions from early in the conversation can get lost; put persistent rules in CLAUDE.md and run `/context` to see what is using space [Claude Code docs, How Claude Code works, 2026]. When context fills, older tool outputs are cleared first, then the conversation is summarised: requests and key code snippets are preserved, detailed early instructions may be lost [Claude Code docs, How Claude Code works, 2026]. Nothing on the pages read explains the model-internal cause.

| Documented effect | Source | Documented remedy |
|---|---|---|
| Early instructions can get lost | How Claude Code works | Rules in CLAUDE.md |
| Old conversation crowds out files you need | Context window | `/clear` between tasks |
| Longer CLAUDE.md reduces adherence | Memory | Keep under 200 lines |
| Repeated corrections add failed attempts | Best practices | `/clear` after two failed corrections |

The failure mode: **Mechanism-invention.** You explain degradation with a confident internal mechanism the docs never state, then design around a guess.

The fix: State only the documented effects, label anything else as inference, and test the remedy empirically.

Cross-references: instruction placement is Module 3.2; compaction detail is sub-topic 3.1.7 in Module 3.1.

**If you remember one thing:** document the effect; do not invent the cause.

## 3.1.3.2 — WHY LONG DEBUGGING SESSIONS GET WORSE

**Framing.** A debugging session accumulates failed attempts, error output and abandoned hypotheses, all of which are re-sent each turn. The docs' advice is concrete: after more than two failed corrections on the same issue, `/clear` and write a better first prompt, because a third correction mostly adds to a conversation that already contains two failed attempts to keep re-reading [Claude Code docs, Best practices, 2026].

```text
Turn 1  hypothesis A  -> wrong, 200 lines of output stay
Turn 5  hypothesis B  -> wrong, 300 more lines stay
Turn 9  hypothesis C  -> context now mostly dead ends
Better: /clear, then one prompt that states A and B as ruled out
```

The failure mode: **Dead-end hoarding.** You keep every failed attempt in context and keep asking for the next idea, so the session is mostly material that no longer applies.

The fix: After two failed corrections, `/clear` and restate what you learned in one new prompt.

Cross-references: session management is Module 2.4; verification loops are Module 2.3.

**If you remember one thing:** reset with what you learned; do not append.

## 3.1.3.3 — PLACEMENT DEFEATS LOSS

**Framing.** What survives compaction depends on how it was loaded: project-root CLAUDE.md and unscoped rules are re-injected from disk, while conversation-only instructions are lost [Claude Code docs, Memory, 2026]. A rule that cannot have exceptions belongs in a hook or deny rule, because an instruction in conversation may be lost when the conversation compacts [Claude Code docs, Best practices, 2026].

| Instruction lives in | After compaction | Right for |
|---|---|---|
| Conversation only | May be lost | Throwaway steering |
| Project-root CLAUDE.md | Re-injected from disk | Standing conventions |
| Path-scoped rule or nested CLAUDE.md | Reloads on demand when a trigger file is read | Area-specific rules |
| Hook or deny rule | Always enforced | Rules with no exceptions |

The failure mode: **Chat-only rule.** You state a critical constraint once in conversation, work for an hour and watch it be violated after compaction.

The fix: Write it into CLAUDE.md, or into a hook or deny rule if it admits no exceptions.

Cross-references: hooks are Module 5.4; permissions are Module 4.2.

**If you remember one thing:** durable rules go in files.

## 3.1.3.4 — DISAGREEMENT: IS CONTEXT STILL THE MAIN CONSTRAINT?

**Framing.** Older guidance said to manage context aggressively because it was the main constraint. Current Best practices lists that under advice you can stop following, since most current models have a 1M-token window and compaction happens on its own, yet keeps `/clear` between tasks because a focused context gets better answers and costs less [Claude Code docs, Best practices, 2026]. The Context window page still advises `/clear` because old conversation crowds out the files you need next [Claude Code docs, Context window, 2026].

| Position | Claim | Practical reading |
|---|---|---|
| Old advice | Context is the main constraint | Superseded for running out |
| Current Best practices | Running out is rare; focus and cost still matter | Clear between tasks |
| Context window page | Old conversation crowds out needed files | Same action |

The failure mode: **Stale-advice anchoring.** You follow a 2025-era rule, such as compacting at 50 percent, without checking whether it still applies to your model and window.

The fix: Check the current Best practices and your model's window before adopting any context rule of thumb.

Cross-references: the auto-compact window is sub-topic 3.1.6 in Module 3.1.

**If you remember one thing:** the reason changed from capacity to focus and cost.
