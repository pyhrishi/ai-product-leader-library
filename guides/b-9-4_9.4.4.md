## THE THESIS OF THIS TOPIC

**`/batch` decomposes a large change into independent units run in isolated worktrees, and a shell loop over `claude -p` does the same for a list of files you control.**

**Prove-it, in one sentence:** migrate a set of files in parallel through /batch or a loop and show per-unit checks and a merged result.

**The single most important discipline: approve the decomposition before any unit runs.**

**The counterintuitive claim you will learn to defend:** parallelism helps only when units are truly independent; a shared file turns it into merge conflicts.

## 9.4.4.1 — /BATCH

**Framing.** `/batch <instruction>` is a bundled skill that researches the codebase, decomposes the work into 5 to 30 independent units, and presents a plan. Once approved, it spawns one background subagent per unit in an isolated worktree; each implements its unit, runs tests and publishes its change. It requires a git repository or a `WorktreeCreate` hook, and outside a git repository needs v2.1.281 or later [Claude Code docs, Commands, 2026].

| Property | Value |
|---|---|
| Example | `/batch migrate src/ from JavaScript to TypeScript` |
| Units | 5 to 30 |
| Isolation | One worktree per unit |
| Gate | You approve the plan first |
| Each unit | Implements, runs tests, publishes |

The failure mode: **Coupled units.** The plan splits work that touches a shared module, so units conflict when they publish.

The fix: Review the plan for shared files and move them into a prior serial step.

Cross-references: worktrees are Module 6.2; dynamic workflows are Module 6.5.

**If you remember one thing:** approve the split.

## 9.4.4.2 — LOOP CLAUDE -P OVER A LIST

**Framing.** When you already have the file list, script it. `claude -p` runs non-interactively; `--allowedTools` pre-approves tools; `--max-turns` and `--max-budget-usd` bound a run, and `--bare` skips auto-discovery for reproducible CI runs [Claude Code docs, Headless, 2026; Claude Code docs, Best practices, 2026].

```bash
while read f; do
  claude -p "Migrate $f from callbacks to async/await. Keep behaviour. Run its tests." \
    --allowedTools "Read,Edit,Bash(pnpm vitest run *)" --max-turns 20 \
    >> migrate.log
done < files.txt
```

| Option | Purpose |
|---|---|
| `--allowedTools` | Pre-approve tools |
| `--output-format json` | Parse results including `total_cost_usd` |
| `--permission-mode acceptEdits` | Baseline for edits |
| `--max-budget-usd` | Cap spend with `-p` |

The failure mode: **Unbounded fan-out.** The loop has no turn or budget cap and one stuck file burns the budget.

The fix: Set `--max-turns` or `--max-budget-usd` and log per-file exit codes.

Cross-references: headless is Module 6.8.

**If you remember one thing:** bound each unit.

## 9.4.4.3 — COLLECTING AND VERIFYING RESULTS

**Framing.** Per-unit checks do not prove the whole. After merging, run the full suite and the app. Subagent worktrees with changes persist until the sweep can remove them; remove manually with `git worktree remove` [Claude Code docs, Worktrees, 2026].

| Phase | Check |
|---|---|
| Per unit | Unit tests in the worktree |
| After each merge | Full suite |
| End | `/verify` on the app |
| Cleanup | `git worktree list`, remove leftovers |

The failure mode: **Green parts, red whole.** Each unit passed alone but the merged result fails an integration test.

The fix: Merge sequentially and run the full suite after each merge.

Cross-references: verification is Module 9.2.5.

**If you remember one thing:** verify the sum, not only the parts.

## CLOSING REFRAME

This is the craft of parallel migration: **independent units, bounded runs, verified sum.** The engineer who understands this does not ask "how fast can it fan out?" — they ask "are these units really independent?"
