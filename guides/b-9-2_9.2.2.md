# MODULE 9.2.2 — SEPARATE WRITERS: THE COMPLETE CRAFT

---

## THE THESIS OF THIS TOPIC

**When one session writes the tests and another writes the code, the tests cannot be shaped around the implementation, because the second session meets them as fixed requirements.**

**Prove-it, in one sentence:** run two sessions with disjoint roles and show the second never edited the first's tests.

**The single most important discipline: the session that writes the code does not get to change the tests.**

**The counterintuitive claim you will learn to defend:** the model that wrote the code is the worst reviewer of tests written to fit it, because it carries the reasoning that produced both.

**THE TIME BUDGET.** Reading time: ~15 minutes. Prove-it time: ~2 hours (120 minutes, 8.0 times the reading time).

## 9.2.2.1 — WHY SEPARATE

**Framing.** The docs note that a reviewer which has not seen how the code was written is a reason to use a subagent, and that `/code-review` runs in a fresh subagent that never saw your conversation and so is not swayed by the reasoning that produced the code [Claude Code docs, Best practices, 2026]. The same logic applies to tests.

| Setup | Risk |
|---|---|
| One session writes both | Tests mirror the implementation's assumptions |
| Two sessions, tests first | The second session meets tests as given |
| Subagent with read-only tools | Reviewer cannot edit (`tools: Read, Grep, Glob`) [Claude Code docs, Best practices, 2026] |

The failure mode: **Mirror test.** Tests assert what the code does, including its bugs, because the same context wrote both.

The fix: Write tests from the spec in a session that has not seen the implementation.

Cross-references: specs are Module 9.1; separate-context review is Module 9.13.3.

**If you remember one thing:** separate context breaks the mirror.

## 9.2.2.2 — MECHANICS OF TWO SESSIONS

**Framing.** Use a fresh session for each role, committing the tests between them. `claude --worktree <name>` gives each session its own checkout and branch if you want them parallel [Claude Code docs, Worktrees, 2026].

```bash
# Session A: tests from the spec only
claude --worktree tests-a   # prompt: write tests for SPEC.md, do not look at src/
# Session B: implementation against committed tests
claude --worktree impl-b    # prompt: make tests/ pass; do not edit tests/
```

| Guard | How |
|---|---|
| B cannot edit tests | A PreToolUse hook that exits 2 for `tests/` paths (Module 5.4) |
| A cannot see src | Instruction only; not enforced (judgement) |

The failure mode: **Unenforced separation.** The rule 'do not edit tests' lives only in the prompt, and the implementer edits an assertion under pressure.

The fix: Enforce it with a PreToolUse hook that exits 2 for test paths, since only hooks and deny rules are deterministic [Claude Code docs, Best practices, 2026].

Cross-references: hooks are Module 5.4; worktrees are Module 6.2.

**If you remember one thing:** enforce what must hold.

---

## 9.2.2.3 — WHAT TO HAND ACROSS THE BOUNDARY

**Framing.** The only things that cross are the spec, the committed tests and the command that runs them. Anything else leaks the implementation's assumptions.

| Crosses | Does not cross |
|---|---|
| SPEC.md | Chat history |
| Committed tests | Drafts and rejected ideas |
| The run command | Implementation notes |

The failure mode: **Leaky handoff.** You paste the implementation plan into the test session, so the tests inherit its blind spots.

The fix: Hand over the spec and only the spec.

Cross-references: context sessions are Module 2.4.

**If you remember one thing:** narrow the interface between sessions.

## CLOSING REFRAME

This is the craft of separate writers: **tests as a given, enforced boundary, narrow handoff.** The engineer who understands this does not ask "did Claude write tests?" — they ask "could these tests have disagreed with the code?"
