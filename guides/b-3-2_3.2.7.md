## THE THESIS OF THIS TOPIC

**Emphasis markers are a last resort for one stubborn line, and the first question is why the line is being skipped: the file is too long, or the rule belongs in a hook.**

**Prove-it, in one sentence:** take a skipped line, diagnose it as length, wording or enforcement, and fix it without adding capitals.

**The single most important discipline: diagnose before you shout; emphasis is a symptom treatment.**

## 3.2.7.1 — WHAT THE DOCUMENTATION SAYS

**Framing.** If Claude keeps ignoring a line that is in CLAUDE.md, adding IMPORTANT probably will not fix it: either the file has grown long enough that the line gets lost, or the line is a rule that cannot have exceptions and belongs in a hook [Claude Code docs, Best practices, 2026]. If you keep adding emphasis to a line and Claude still misses it, that is a sign it belongs in a hook; the reverse also holds, so preferences encoded as hooks should be deleted. The Memory page does not cover emphasis markers.

| Symptom | Likely cause | Fix |
|---|---|---|
| Line skipped in a long file | Length | Prune or split the file |
| Rule that must never break is skipped | Needs enforcement | Hook or deny rule |
| Line vague | Wording | Make it specific and checkable |

The failure mode: **Shout-first.** You add capitals and IMPORTANT to a skipped line without checking file length or whether it needs a hook.

The fix: Diagnose first: length, wording, enforcement; emphasise only after the others are ruled out.

Cross-references: hooks are Module 5.4.

**If you remember one thing:** diagnose before you emphasise.

---

## 3.2.7.2 — WHY EMPHASIS BACKFIRES

**Framing.** Best practices lists adding IMPORTANT or ALL CAPS among old advice you can stop following: older models sometimes needed emphasis, current ones follow a plainly worded line, and piling on emphasis mostly makes Claude over-apply the rule [Claude Code docs, Best practices, 2026]. The course syllabus allows sparing emphasis on one line that keeps being skipped.

| Source | Position on emphasis |
|---|---|
| Best practices, 'what you can stop doing' | Stop; plain wording works; it causes over-application |
| Course syllabus for this topic | Use sparingly on one skipped line |
| Memory page | Not covered |

The failure mode: **Over-application.** An emphasised rule such as 'ALWAYS run the linter' makes Claude run it when it is irrelevant, such as for a docs-only change.

The fix: State the condition in plain words (for example, after editing source files) and drop the capitals.

Cross-references: wording is a prompting skill from Module 2.2.

**If you remember one thing:** emphasis widens a rule's reach.

---

## 3.2.7.3 — A TEST PROTOCOL FOR A SKIPPED LINE

**Framing.** Test changes by watching whether behaviour shifts: rerun the failing task before and after each change, one change at a time, in a fresh session so earlier context does not mask the effect [Claude Code docs, Best practices, 2026].

```text
Skipped line: 'Run the linter after edits'
 Run 1: baseline                      -> skipped
 Run 2: prune 60 other lines          -> followed?   (length hypothesis)
 Run 3: rewrite as a command          -> followed?   (wording hypothesis)
 Run 4: Stop hook runs linter         -> always      (enforcement)
```

The failure mode: **Multi-change testing.** You change length, wording and emphasis at once and cannot say which fixed the problem.

The fix: Change one variable per run and record the result.

Cross-references: evals are Module 10.1.

**If you remember one thing:** one variable per run.
