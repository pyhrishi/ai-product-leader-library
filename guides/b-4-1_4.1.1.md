# MODULE 4.1.1 — SCOPES: THE COMPLETE CRAFT

---

## THE THESIS OF THIS TOPIC

**A setting's scope is the file you save it in, and the file decides who it affects: only you, everyone in one folder, you in one project, or a whole organization.**

**Prove-it, in one sentence:** given any ten settings, place each in the correct file and say who it reaches, including what a teammate and a cloud session would see.

**The single most important discipline: choose the scope before you write the key, not after it fails to apply.**

**The counterintuitive claim you will learn to defend:** installing Claude Code creates no settings file at all; files appear only when you or an admin put them there, and the local file is written by Claude Code itself when you answer 'Yes, and don't ask again' [Claude Code docs, Settings files and precedence, 2026].

## 4.1.1.1 — THE FOUR FILES AND THEIR AUDIENCES

**Framing.** Claude Code reads JSON settings from four places and an organization can add managed delivery on top. The scope of a file is the set of people and projects a setting saved in it applies to [Claude Code docs, Settings files and precedence, 2026].

| Scope | File | Who it affects |
|---|---|---|
| User | `~/.claude/settings.json` | You, in every project on this machine |
| Shared project | `.claude/settings.json` | Everyone working in that folder; commit it |
| Project local | `.claude/settings.local.json` | You, in this one project only |
| Managed | `managed-settings.json` and other managed sources | Everyone the organization deploys it to |

On Windows `~/.claude` means `%USERPROFILE%\.claude`; `CLAUDE_CONFIG_DIR` moves the home-directory files. A fifth file, `~/.claude.json`, is written by Claude Code for itself: account details, MCP server configuration, trust decisions and the global config keys `/config` writes [Claude Code docs, Settings files and precedence, 2026].

The failure mode: **Wrong-file save.** You put a personal preference in the committed project file, so every teammate inherits it, or a team rule in your user file, so nobody else gets it.

The fix: Ask who must be affected before choosing the file. Personal and everywhere: user. Team: shared project. Personal for one repo: local.

Cross-references: the precedence order itself is Module 4.1 sub-topic 4.1.2; managed delivery is Module 4.2.

**If you remember one thing:** the file is the audience.

## 4.1.1.2 — LOCAL SETTINGS: WRITTEN BY CLAUDE CODE, KEPT OUT OF GIT

**Framing.** Claude Code writes `.claude/settings.local.json` the first time you give a standing approval such as 'Yes, and don't ask again' for a Bash command. It then adds `**/.claude/settings.local.json` to your global git excludes, so the file stays out of commits [Claude Code docs, Settings files and precedence, 2026].

| Situation | Where the file lives |
|---|---|
| Start in a subdirectory of a git repo | The repository root (v2.1.211 and later) |
| Worktree | The main checkout's root |
| Outside a repo, repo root is home, Windows, or root/.git/.claude not owned by you | Stays with `.claude/settings.json` |
| You created the file by hand | You must add it to `.gitignore` yourself |

An untracked local file's allow rules apply without the trust step; if git tracks the file, trust applies to it too [Claude Code docs, Permissions, 2026].

The failure mode: **Hand-made local file.** You create `settings.local.json` yourself and commit it by accident because Claude Code has not yet written to it and so has not excluded it.

The fix: Add the file to `.gitignore` yourself, or let Claude Code create it through a first approval.

Cross-references: trust gating of allow rules is Module 4.2 (workspace trust); the rule format is Module 4.2.

**If you remember one thing:** the local file is yours, but only Claude Code's own write keeps it out of git.

## 4.1.1.3 — WHAT SCOPE DOES NOT REACH: TEAMMATES, CLONES AND CLOUD

**Framing.** A scope reaches only the machines that have the file. A committed `.claude/settings.json` reaches teammates and a single-repository cloud session only if you commit it; user and local files are never read in cloud sessions [Claude Code docs, Settings files and precedence, 2026].

| Surface | Reads |
|---|---|
| Your machine (CLI, VS Code, JetBrains, desktop) | All four scopes |
| Teammate clone | Only what is committed |
| Cloud session, one repo | Committed `.claude/settings.json`; not user or local |
| Cloud, several repos (Anthropic-hosted) | Only `enabledPlugins` and `extraKnownMarketplaces` from each repo |
| Cloud threads in a project | None of the repo's permission rules, hooks or env |

Only server-managed settings reach a cloud session from the managed tier [Claude Code docs, Settings files and precedence, 2026].

The failure mode: **Cloud blind spot.** You test a hook or permission in your user settings and assume a cloud session has it, but user and local files are not read there.

The fix: Commit the key to the project file for single-repo cloud sessions, or set an environment variable on the cloud environment.

Cross-references: cloud environments are Module 4.5.

**If you remember one thing:** scope ends where the file stops being present.

## THE PROVE-IT SECTION

**Deliverable.** A scope map: ten real settings, each placed in a file with the audience it reaches and the one thing that could stop it applying.

**Close this topic. Build the artifact below from memory. Return to the text only after your first attempt is complete.**

| Step | Action | Output |
|---|---|---|
| 1 | List ten settings you use or want (theme, model, deny rules, hooks, env vars) | A raw list |
| 2 | Assign each to user, project, local or managed | A scope column |
| 3 | Name who each reaches: you, teammates, cloud | An audience column |
| 4 | Create a local file by approving one Bash command and check git status | Observation |
| 5 | Mark the one condition that could stop each applying (trust, cloud, higher level) | A blocker column |
| 6 | Run /status and match each loaded source to your map | A verified map |

**A passing artifact looks like this:**

| Setting | Scope | Reaches | Could stop it |
|---|---|---|---|
| `theme` | User | Me, all projects | Managed override |
| `permissions.deny` for `.env` | Shared project | Whole team once committed | Nothing (deny applies immediately) |
| My `model` for this repo | Local | Me, this repo | Managed or `--settings` |

**A failing artifact (a realistic near-miss):**

| Element | What is wrong |
|---|---|
| Team deny rules placed in user file | **Wrong-file save**: teammates never get them |
| Cloud session assumed to see user hooks | **Cloud blind spot** |

**The verdict.** Passes only if every setting has a scope, an audience that includes teammates and cloud, and a named blocker, and the map was checked with /status.

## CLOSING REFRAME

This is the craft of scope: **one key, one file, one audience.** The engineer who understands this never says 'it works on my machine' about a setting; they say which file it is in and who that file reaches.
